# 编辑器、IDE、项目导航与源码定位

打开一个项目以后，左侧出现很多目录，中间显示源码，底部可能同时有终端、构建输出和“问题”列表。初学者最容易把“能看见文件”等同于“已经正确打开项目”，把搜索到的第一个同名文本当成定义，把 `target/` 或 `generated/` 中的副本当成应该修改的源码，还可能在文件没有保存、运行配置指向另一个目录时反复重跑旧结果。编辑器没有随机失灵，它只是在依据当前打开范围、项目模型、语言服务和运行配置工作。

本章建立一套跨 VS Code 与 IntelliJ IDEA 都能迁移的导航模型。界面名称、默认快捷键和主题会变，稳定核心却相同：先确认项目根与搜索范围，再区分磁盘文件、规范源码、测试、依赖和生成物；随后按“文件—文本—符号—定义—引用—诊断位置”的证据阶梯定位；最后核对保存状态、字符编码和运行配置。你会用两个 IDE 的通用概念完成同一任务，而不是背一张只能在某台电脑上使用的快捷键表。

本章不会进入断点、调用栈、线程、条件断点或框架热更新。那些内容需要先掌握具体语言的运行时与调试模型。这里也不会宣称 IDE 的红线就是真正编译结果：实时分析、编译器、构建工具和运行进程是不同观察者。我们只训练“找到正确对象、说清证据来源、避免改错文件”的基础能力。

## 学完后你必须能做什么

完成正文与实验后，你应当能够：

1. 区分磁盘目录、编辑器窗口、workspace/project、模块和项目根，不把它们混成“项目”；
2. 根据根标记、构建描述文件与源码布局证明自己打开了正确范围；
3. 从项目树辨认业务源码、测试、资源、配置、依赖视图、缓存和生成目录；
4. 说明文件名搜索、全文搜索和符号搜索分别查询什么索引，知道结果为空不等于对象不存在；
5. 从一次调用跳到定义，再查找引用，并能返回原位置，形成可复述的导航路径；
6. 发现同名定义时，优先判断来源根、包或模块，不直接修改第一个搜索结果；
7. 识别 `target/`、`build/`、`dist/`、代码生成目录中的派生文件，并追溯到生成输入或规范源码；
8. 区分编辑器即时诊断、语言服务问题、编译日志、测试失败和运行输出；
9. 从诊断的文件、行列和消息定位第一处可信位置，而不是从最后一行泛化结论；
10. 核对文件是否已保存、编码是否正确、换行是否变化，并解释为什么运行结果可能仍是旧版本；
11. 读懂基础运行配置中的入口、工作目录、参数、环境、运行时和任务，不依赖“运行当前文件”的猜测；
12. 在 FactoryCare 样例中完成一次错误根目录与生成物误编辑的诊断、修复和复跑；
13. 审查 AI 生成的导航建议，拒绝批量替换、未知扩展安装和直接修改生成物等高风险动作；
14. 在无 AI 条件下，用 120 秒解释从“问题面板”到“规范源码”的完整证据链。

会打开文件不代表掌握本章。掌握要求是：面对陌生项目，你可以先预测应该去哪里找，再用项目根、路径、符号和构建证据证明选择；即使 IDE 索引暂时失效，也能退回文件系统与构建日志继续定位。

## 零基础补救：编辑器、IDE、项目与工作区

### 编辑器负责文本，IDE 组织开发上下文

文本编辑器最基本的职责是读取、显示、修改和保存文件。现代编辑器还可以通过扩展提供语法高亮、语言服务、任务、版本控制和运行入口。IDE 通常把这些能力与项目模型、构建系统、运行时、测试和分析器更紧密地集成。VS Code 常被称为代码编辑器，但安装语言扩展后也能承担很多 IDE 工作；IntelliJ IDEA 是以项目模型和 Java 生态集成为核心的 IDE。

不要把产品标签当成能力保证。“使用 IDE”不代表项目已经正确导入，“使用编辑器”也不代表只能编辑纯文本。诊断时应问：当前窗口打开了什么范围？哪个语言服务正在工作？构建工具识别了哪个模块？运行入口和工作目录是什么？这些问题比争论名称更有用。

### 一个窗口不一定等于一个项目根

假设磁盘结构如下：

```text
Study/
└── Computer/
    ├── curriculum/
    ├── book/
    ├── examples/
    └── pom.xml
```

如果只打开 `book/`，编辑器仍能显示 Markdown，却看不到同级 `examples/`，相对链接和全局搜索范围也会不同。如果打开 `Study/`，搜索可能把其他课程一起包含进来，出现大量同名文件。窗口可以打开单个文件、单个文件夹或多个根；项目根必须由当前任务和项目标记共同确定，而不是“树最上面那一行”天然决定。

在 IntelliJ IDEA 中，project 是源码、测试、库、SDK、构建说明和个人设置的顶层容器；其中还可能有多个 module。VS Code 的 workspace 可以是一个文件夹，也可以用工作区文件组合多个根。两者术语不完全相同，但都说明：可见范围与项目语义需要明确配置。

### 用根标记建立证据

常见根标记包括 `.git/`、`pom.xml`、`build.gradle`、`package.json`、`pyproject.toml`、`pubspec.yaml`、工作区描述文件和项目自己的说明。任何一个标记都不是跨项目万能答案：多模块仓库里可能有很多 `pom.xml`，单仓库也可能包含多个应用。正确做法是结合任务说明、相对路径和构建入口。

一个最小根目录核对表是：

| 问题 | 可信证据 | 常见误判 |
| --- | --- | --- |
| 当前打开范围是什么 | 窗口标题、项目树顶层、工作区配置 | 当前编辑文件所在目录就是根 |
| 构建从哪里启动 | 构建描述文件、wrapper、项目说明 | 哪里有源码就从哪里运行 |
| 源码根在哪里 | 项目模型与约定布局 | 所有 `.java` 都是规范源码 |
| 搜索包含哪些目录 | workspace 范围、include/exclude 设置 | 全文搜索等于整块磁盘搜索 |
| 运行工作目录是什么 | 运行配置或命令的 `pwd` | 一定是源码文件所在目录 |

项目根的判断必须可复现。说“IDE 自己识别了”只是现象；至少记录根路径、标记文件、入口与模块名称，别人才能重现。

## 项目树不是磁盘的完整真相

### 视图会过滤、分组和重命名

项目树是一种视图。它可能隐藏点文件、忽略目录、把包路径折叠成一行、把依赖显示成逻辑节点，或者只展示项目模型认为属于源码的文件。IntelliJ IDEA 的 Project 视图强调目录结构，Packages 视图强调包；VS Code Explorer 更接近打开范围内的文件树，但也会应用排除和嵌套规则。

因此，树里看不到文件有多种原因：文件确实不存在、打开根错误、视图过滤、被排除、尚未刷新、大小写不同、文件位于未打开根、生成步骤尚未发生。不要立刻创建同名文件。先用项目树设置和受控终端命令交叉核对路径，避免制造第二份副本。

反过来，树里看见文件也不证明它参与构建。它可能只是普通文本、被排除目录中的文件、生成缓存或另一模块的同名文件。参与构建要由源码根、构建描述和实际编译证据确认。

### 认识常见目录角色

不同技术栈名称会变，但职责可以归纳：

| 角色 | 常见路径 | 是否通常手工修改 | 主要证据 |
| --- | --- | --- | --- |
| 生产源码 | `src/main/`、`src/`、`lib/` | 是 | 项目模型、构建输入 |
| 测试源码 | `src/test/`、`test/` | 是 | 测试任务与测试报告 |
| 静态资源 | `resources/`、`public/`、`assets/` | 视合同 | 构建复制规则 |
| 项目配置 | 根目录构建文件、受控配置 | 谨慎 | 文档与版本控制 |
| 生成源码 | `generated/`、`target/generated-sources/` | 通常否 | 生成任务与输入模板 |
| 编译产物 | `target/classes/`、`build/`、`dist/` | 否 | 每轮构建重新产生 |
| 依赖与缓存 | External Libraries、`.m2`、包缓存 | 否 | 依赖解析器管理 |
| IDE 私有状态 | `.idea/`、`.vscode/` 中个人项 | 按团队约定 | 团队协作政策 |

“通常”不是绝对规则。有些仓库会提交生成代码，有些团队会共享部分运行配置。你必须读项目合同。但无论是否提交，派生文件都应追溯到生成源；直接改派生文件而不改生成源，下一次生成会覆盖修改。

### 同名文件为何危险

示例工程同时有：

```text
src/main/java/com/factorycare/navigation/DeviceStatusFormatter.java
target/generated-sources/com/factorycare/navigation/DeviceStatusFormatter.java
```

全文搜索两个文件都可能命中。规范源码位于 `src/main/java`，`target` 中副本用于演示生成物边界。若在生成副本里修复返回值，当前编辑器可能暂时显示正确，清理构建后修改却消失。导航前先看完整路径和源码根颜色，不要只看标签页短文件名。

## 五种“寻找”不是同一件事

### 文件搜索：已知或猜测文件名

文件搜索回答“当前范围内哪些路径的名称匹配”。它适合日志明确给出文件名、你知道后缀或大致目录时。搜索 `WorkOrderLabel` 可能得到源码、测试、生成物和文档。接下来仍要依据完整路径分类。

文件名结果为空时，检查拼写、大小写、打开范围和排除规则。不要把名称搜索当成内容搜索：类名与文件名在某些语言中常一致，但配置键、函数和字符串不一定如此。

### 当前文件查找：已知文字且范围很小

当前文件查找适合定位本文件中的字段、状态或重复调用。它查询已打开文本，不理解名称究竟是声明、引用、注释还是字符串。搜索结果快，但语义弱。

### 全文搜索：查询工作区中的文本

全文搜索回答“被搜索范围中的哪些文件含有这段文字”。它可以找到注释、文档、生成物、字符串和源码，是语言服务失效时的重要退路。结果是否完整取决于 include/exclude、忽略文件设置、符号链接和工作区根。

若搜索 `formatStatus` 得到十处，不能把十处都称为引用：其中可能有方法定义、测试名称、README 示例和旧构建产物。全文搜索提供候选集合，仍要分类。

### 符号搜索：查询语言模型中的名称

符号通常指类、函数、方法、字段等语言结构。符号搜索依赖语言服务或 IDE 索引，因此比纯文本更懂代码，但也更依赖正确的项目模型、语言扩展、SDK 和索引状态。未导入 Maven 项目、Java SDK 未配置或文件被当作纯文本时，符号结果可能为空或不完整。

符号搜索失败时不要重装全部 IDE。先确认文件类型、项目根、语言服务状态、构建描述与最小编译结果。全文搜索可作为退路，但要明确它不提供同等语义保证。

### 定义与引用：从关系而非名称移动

“转到定义”从使用位置寻找负责声明或实现该符号的位置。“查找引用”从定义寻找被语言模型识别的使用位置。二者适合回答“谁定义规则”和“修改会影响谁”。

一次可靠导航链应记录：

```text
诊断文件: WorkOrderSummary.java:18
使用符号: WorkOrderLabel.formatStatus
定义路径: src/main/java/.../WorkOrderLabel.java:7
引用范围: production=1, test=2, generated=0
返回方式: navigation history -> 原诊断位置
```

接口、多态、动态语言、反射和生成代码会让“定义”与“实际运行实现”更复杂。本章只要求识别静态导航提供的候选关系，不把它夸大为运行时调用证明。后续 Java 面向对象和调试章节会继续深化。

## 导航历史：走得过去，也要回得来

真实定位不是单向跳转。你会从诊断跳到使用处，从使用处跳到定义，再查看测试引用，然后需要返回原错误。标签页很多不等于保留了推理路径；随手关闭、重新搜索可能丢失上下文。

VS Code 和 IntelliJ IDEA 都提供导航历史与返回/前进动作，具体按键随系统与键位方案变化。学习时记住动作名称而不是死背按键：Go Back、Go Forward、Recent Files、Go to Definition、Find Usages。若快捷键冲突，从命令面板或菜单执行，并查看当前键位映射。

建议每轮只回答一个问题：

1. 我现在在哪个文件和完整路径？
2. 我为何来到这里？
3. 下一跳要验证什么关系？
4. 这一跳给了新证据还是只给候选？
5. 如何返回起点？

这能防止在陌生代码中“跳了很多次，却忘了最初在查什么”。

## 问题面板不是最终裁判

### 诊断来自不同生产者

编辑器中的红线或 Problems 面板可能来自语法分析器、语言服务器、linter、类型检查器、项目级检查或构建集成。终端里的编译错误来自编译器或构建插件；测试面板来自测试运行器；运行控制台来自进程。它们观察的时间、范围和配置可能不同。

例如，未保存文件在内存编辑器中已经缺少分号，Problems 立即报错；终端构建读取磁盘旧版本仍然成功。反过来，IDE 索引尚未完成时可能显示“找不到符号”，命令行 Maven 使用正确配置却能编译。不能从一个面板的颜色推翻另一个工具的真实日志，也不能只因命令成功就忽略编辑器打开了错误模块。

### 从第一处可信位置开始

诊断常包含文件、行、列、严重级别、规则 ID 和消息。优先核对：

1. 完整路径是否属于当前项目根；
2. 文件是规范源码、测试还是生成物；
3. 行列附近的源码是否与磁盘已保存内容一致；
4. 消息由哪个分析器产生，使用哪个项目/SDK 配置；
5. 更早的诊断是否导致后续级联错误。

“问题有 37 个”不是根因。一个 package 声明错误可能使后面大量符号无法解析。先修第一处可信、因果上游的错误，再重新收集诊断，不要对所有红线同时修改。

### Problems 与构建日志怎样互证

可以建立三栏记录：

| 观察 | 位置/生产者 | 可证明什么 |
| --- | --- | --- |
| Problems 指向源码第 12 行 | Java language service | 当前项目模型认为这里有问题 |
| `mvn test` 在 compile 阶段失败 | Maven compiler + javac | 磁盘上的构建输入无法编译 |
| 测试报告断言失败 | Surefire + JUnit | 编译成功但行为不满足预言 |

三者都重要，却不能互相替代。只有了解生产者，才能解释为什么它们暂时不一致。

## 保存、编码与“为什么运行的还是旧代码”

### 编辑器缓冲区与磁盘文件

你在标签页中输入的内容先存在编辑器缓冲区。显式保存或自动保存触发后，磁盘文件才更新。VS Code 会用未保存标记提示脏文件；IDEA 通常自动保存，但保存时机与外部构建、文件同步仍需理解。不要凭产品习惯假设，直接观察文件状态和构建输入。

运行结果像旧代码时，依次核对：

1. 修改的是不是规范源码；
2. 修改是否保存到磁盘；
3. 运行配置是否构建当前模块；
4. 是否从另一输出目录启动旧类或旧 bundle；
5. 工作目录和 classpath 是否指向另一项目副本；
6. 构建是否因更早错误而没有产生新产物。

不要把“Clean Everything”当第一反应。清缓存会删除证据并耗费时间，只有在证明输出陈旧或索引失配后才有针对性地清理。

### 编码和换行同样属于文件身份

编辑器状态栏通常显示编码与换行风格。错误地以另一编码重新打开或保存，中文可能变乱码；批量改变 LF/CRLF 会制造与业务无关的巨大 diff。修改前记录原编码与换行，保存后用版本差异确认只改变了预期内容。

“看起来正常”不是字节证据。前章已经介绍 UTF-8 和路径；这里把它应用到编辑行为：编码选项决定如何解释和写回字节，字体只决定如何绘制字符，两者不能混淆。

## 运行配置：不是“点击绿色三角”这么简单

### 六个基础输入

一个可复现的运行配置至少要回答：

1. **入口**：运行哪个主类、脚本、测试或任务；
2. **工作目录**：相对路径从哪里解析；
3. **程序参数**：业务程序收到什么参数；
4. **运行时参数**：JVM、Node、Python 等运行时收到什么选项；
5. **环境**：允许传入哪些非秘密环境变量；
6. **运行时/模块**：使用哪个 JDK、解释器、模块与 classpath。

有些配置还会先执行构建任务。点击相同按钮但项目、模块或配置不同，结果就不同。顶部显示的配置名称是线索，不是全部证据；打开配置查看具体字段，并与命令行构建对照。

### “运行当前文件”的边界

对单文件脚本，运行当前文件可能合适；对 Maven、多模块 Java、前端构建或 Flutter 项目，单文件通常不是完整运行单元。它可能缺少依赖、资源、编译参数或测试框架。应该选择项目任务或已定义配置，而不是为了得到绿色输出绕过真实构建。

本章只理解配置输入，不进入断点。若运行失败，先核对入口、保存、工作目录、参数、环境和运行时，再进入语言特定调试。

## 正例、边界与预期失败

### 正例：从测试失败找到生产定义

固定样例中，测试文件调用 `DeviceStatusFormatter.format`。正确流程是：

1. 由问题或任务记录完整测试路径；
2. 在使用处确认符号名称与参数；
3. 转到 `src/main/java` 中定义；
4. 查找引用，区分生产、测试与文档候选；
5. 修改规范源码并保存；
6. 用固定验证器重跑精确预言。

这里每一步都缩小不确定性。直接全文替换 `format` 既扩大范围，也可能改到生成物和文档。

### 边界：两个模块都有同名类

若 `device-api` 和 `device-worker` 都有 `WorkOrderMapper`，符号搜索会返回多个候选。先从当前使用处的包、import、模块依赖和源码根判断，不以“列表第一项”决定。若 IDE 仍不确定，查看编译 classpath 与实际错误路径。

### 预期失败：打开错误根

只打开 `workspace/src/` 时，源码文件仍可编辑，但根标记、测试、构建文件和生成目录都在范围外。文件搜索似乎成功，符号引用却不完整，运行配置也可能退化成单文件。这个失败不是“IDE 太笨”，而是输入给错。修复是重新打开任务规定的项目根，然后确认索引与构建模型，不是在 `src/` 内复制缺失文件。

### 预期失败：编辑生成物

在 `target/generated-sources` 中修改同名文件，短期文本搜索会显示新值。执行清理或生成任务后修改消失。第一处可信证据是完整路径包含生成输出边界，修复应定位生成输入或 `src/main` 规范源码；若生成器本身错误，才修改生成模板或生成器并重新产生。

## 安全边界：项目也可能是不可信输入

打开项目不仅是读取文本。编辑器扩展、构建导入、任务、运行配置和终端命令可能执行代码。来源不明的仓库应先只读检查说明、构建文件、任务与脚本，不盲目接受“信任并运行”。VS Code 的 Workspace Trust 与扩展安全机制、IDE 的安全模式都在提醒同一原则：信任决定哪些能力可以执行，不是弹窗障碍。

还要遵守以下边界：

- 不把真实 Token、密码、私钥粘进搜索框、运行配置、截图或 AI 对话；
- 不让“搜索环境变量”变成输出整个环境，因为环境可能含凭据；
- 不安装来源不明的扩展来解决一个普通导航问题；
- 不运行项目内未知脚本，只因为名称叫 `verify` 或 AI 说“安全”；
- 全局替换前先预览范围，排除生成物、依赖、证据和私有答案；
- 修改前查看版本差异，保存后再次核对编码与路径。

如果发现秘密已经进入文件，停止传播并按凭据提供方流程立即撤销或轮换；删除本地文字不能恢复已经泄露的秘密。具体 Git 处置在下一章讲解。

## FactoryCare 场景：问题面板指向了“正确的错误文件”吗

FactoryCare 的工单页面显示状态标签错误。AI 建议搜索 `formatStatus` 并修改第一个结果。搜索得到：

```text
frontend/src/formatStatus.ts
backend/src/main/java/.../WorkOrderLabel.java
backend/target/generated-sources/.../WorkOrderLabel.java
book/examples/formatStatus.md
```

任务说明错误来自 Java 后端测试，问题面板路径也指向 `backend/src/test/java`。因此应先从测试使用处跳到后端生产定义，而不是修改前端同名函数或生成副本。查找引用显示生产入口一个、测试两个；修改后运行后端固定测试。若 UI 仍错误，再建立新的前后端契约问题，不在本轮混改两端。

假设你误开了 `backend/src/main/java` 作为根，IDE 没有识别 `pom.xml`，定义跳转只依靠文本猜测。正确修复顺序是：

1. 保存当前修改并记录完整路径；
2. 关闭错误根，打开含 `pom.xml` 的 `backend/`；
3. 确认 JDK 与 Maven 项目模型加载；
4. 从原测试错误重新跳转，而不是依赖旧标签页；
5. 确认目标在规范源码根；
6. 构建并核对测试数量、失败数与退出状态。

这套流程不依赖 VS Code 或 IDEA 的按钮位置，换 IDE 后仍成立。

## 预测—构建—诊断—变更训练

### 预测

在运行任何验证器前，阅读样例树并写下：项目根、生产定义路径、测试引用路径、生成副本路径、文件名搜索命中数、全文搜索候选数、符号引用应排除的对象。再预测只打开 `src/` 会缺失哪些证据。

### 构建

打开配套样例的根目录，依次完成文件搜索、全文搜索、定义跳转、引用查找和返回起点。记录每一步的动作名称、起点、终点、完整路径和结论。快捷键只作为个人备注，不能成为唯一操作说明。

### 注入故障并诊断

实验故意包含同名生成物和未完成的 `navigation-evidence.txt`。首次运行实验验证器应非零失败，提示证据字段尚未填写。这是预期失败，不应通过删除断言或把退出状态强制改成零“修复”。完成导航后填写精确字段，再复跑到通过。

另一个故障是把打开根从 `workspace/` 改成 `workspace/src/`。预测文件搜索、符号搜索和运行配置的差异，截取最小文字证据，不保存包含用户名的全屏截图。

### 需求变更

若规范源码中的方法从 `label` 政名为 `formatStatus`，列出定义、生产引用、测试引用、文档示例和生成物中哪些需要变、哪些应由生成任务自动变。先用引用关系估计影响，再做最小修改；不要全仓盲替换 `label` 这个普通词。

## 无 AI 独立训练

关闭 AI 辅助，限时 50 分钟完成：

1. 用根标记证明实验项目根；
2. 在不展开整棵树的情况下找到生产定义；
3. 从测试调用跳到定义并列出引用；
4. 解释为什么生成副本不能直接修；
5. 从固定 Problems 记录定位首个可信路径；
6. 填完导航证据并让验证器通过；
7. 修改一个符号需求并说明验证范围；
8. 用 120 秒复述完整模型。

允许查看本章速查表和 IDE 官方帮助，不允许查看私有解析。验证器通过只能证明固定证据文件满足预言，不证明你真的使用了语义导航；你还必须现场演示一次跳转与返回，并解释每一步的证据强度。

## 复述题与间隔复习

### 当天复述

不用看正文，回答：

1. 项目树为何不等于磁盘完整真相？
2. 文件搜索、全文搜索和符号搜索分别依赖什么？
3. 定义与引用能证明什么，不能证明什么？
4. Problems、编译日志与测试失败为何不能互换？
5. 生成物误编辑的第一处可信证据是什么？
6. 运行结果仍旧时按什么顺序核查？

### 第 2 天检索

不打开 IDE，画出“窗口—workspace/project—module—source root—file—symbol”的层级。再给出一个错误根导致符号索引不完整的反例。

### 第 7 天迁移

在另一种技术栈中辨认源码、测试、资源、生成物和依赖。例如从 Java Maven 迁移到 Vue/Vite 时，把 `src/main` 对应到 `src`，把 `target` 对应到 `dist` 或构建缓存，同时指出哪些只是类比而非完全相同。

### 第 21 天故障回放

故意打开实验的错误子目录，收集文件搜索与语义导航差异；恢复正确根后复跑。若你只记得快捷键却说不出搜索范围、索引和路径，本章需要补练。

## 速查表

| 目标 | 首选动作 | 必查边界 | 失败时退路 |
| --- | --- | --- | --- |
| 已知文件名 | 文件搜索 | 根、大小写、排除 | 项目树与受控 `find`/`rg --files` |
| 已知文本 | 全文搜索 | include/exclude、生成物 | 限定路径的文本搜索 |
| 已知类/方法 | 符号搜索 | 语言服务、项目模型 | 全文候选后人工分类 |
| 从调用找声明 | 转到定义 | 多模块、多实现 | import、包、构建依赖 |
| 估计修改影响 | 查找引用 | 动态调用、反射 | 文本搜索与测试 |
| 从错误定位 | Problems/构建日志 | 生产者、完整路径、保存 | 命令行构建的首个错误 |

## 常见误区与纠正

| 误区 | 为什么错 | 可复用规则 |
| --- | --- | --- |
| 树顶层一定是仓库根 | 窗口可打开任意子目录或多根 | 用任务和根标记证明 |
| 搜到第一项就修改 | 同名对象可能来自测试、生成物、文档 | 先看完整路径与角色 |
| 红线就是编译失败 | 实时分析器与构建器不同 | 记录生产者并交叉验证 |
| 保存只是 UI 小事 | 构建常读磁盘而非缓冲区 | 运行前确认保存状态 |
| 清缓存能修任何问题 | 会删除证据且不修输入错误 | 先证明缓存失配 |
| 定义跳转等于运行调用 | 静态候选不等于运行轨迹 | 后续用测试/调试证明 |
| 生成文件也能先改着用 | 下一次生成会覆盖 | 修改规范输入或生成器 |
| 快捷键背得多就会导航 | 键位会变且不解释模型 | 记动作、输入和证据 |

## 术语表

- **编辑器缓冲区**：尚未或已经保存的当前内存文本状态。
- **workspace / 工作区**：编辑器组织一个或多个打开根及其设置的范围。
- **project / 项目**：IDE 用于组织源码、测试、依赖、SDK 和构建的顶层开发上下文。
- **module / 模块**：项目内具有相对独立源码、依赖或构建边界的单元。
- **project root / 项目根**：当前任务所认可的顶层路径，通常由构建和仓库标记共同证明。
- **source root / 源码根**：项目模型认定参与特定编译角色的目录。
- **generated source / 生成源码**：由工具从其他输入派生的源码，通常不直接手工修改。
- **file search / 文件搜索**：按路径或文件名称查找候选。
- **text search / 全文搜索**：按字面内容在选定范围查找候选。
- **symbol / 符号**：语言模型识别的类、函数、字段等命名结构。
- **definition / 定义**：声明或实现符号规则的位置。
- **reference / 引用**：语言模型识别的符号使用位置。
- **language service / 语言服务**：为编辑器提供解析、补全、诊断和语义导航的进程或组件。
- **index / 索引**：为加速文件或符号查询而建立的数据结构；可能尚未完成或已经过期。
- **Problems / 问题面板**：汇总某些分析器诊断的界面，不是所有构建结果的总裁判。
- **run configuration / 运行配置**：入口、工作目录、参数、环境、运行时和前置任务的可复现组合。
- **working directory / 工作目录**：进程解析相对路径的起点，不一定等于源码目录。
- **dirty / 未保存**：编辑器缓冲区与磁盘版本存在差异的状态。

## 本章小结

编辑器导航的核心不是“点得快”，而是维护一条可解释的定位链：先证明项目根和搜索范围，区分规范源码、测试、生成物与依赖；再选择文件、文本或符号查询，从使用跳到定义并检查引用；遇到 Problems 时识别诊断生产者和完整路径；运行前核对保存、编码、入口、工作目录、环境和运行时。IDE 提供候选和自动化，最终结论仍要由路径、项目模型、构建日志和固定预言共同支持。

请继续完成配套示例、实验和练习。保留第一次错误预测与验证器的预期失败，修复后再复跑；不要修改 `target/` 中的演示副本，也不要用真实项目、真实用户名或凭据作为学习输入。
