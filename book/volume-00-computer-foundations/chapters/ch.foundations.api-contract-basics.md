# API 资源、错误、版本、分页、缓存与幂等语义

- [《HTTP 报文、方法、状态码、Header、Body 与 curl》](ch.foundations.http-curl.md)：独立完成资源与错误、交付语义前，必须先具备「HTTP 报文、方法、状态码、Header、Body 与 curl」已经验证的知识与失败边界
<!-- END GENERATED LEARNING PREREQUISITES -->

HTTP 告诉我们如何表达请求与响应，但一个可长期使用的 API 还需要更具体的承诺：什么叫“设备”，成功时返回哪些字段，失败时客户端如何稳定分类，数据很多时怎样继续翻页，旧客户端遇到新字段会怎样，缓存怎样确认旧副本仍可用，创建请求因超时重试时如何避免生成两张工单。

这些承诺合起来就是 API 契约。契约不是一张漂亮的接口截图，也不等于某个控制器方法。它是客户端和服务提供方都能观察、验证并据此行动的规则。本章用 JSON 与 HTTP 作为具体记号，但重点是协议无关的语义；不实现 Spring 路由、鉴权、数据库事务或分布式锁。

## 本章要解决的问题

完成本章后，你应当能够：

1. 区分资源、资源标识与某次资源表示；
2. 写出成功表示中字段名称、类型、必填性、空值、单位与枚举边界；
3. 为未知内部异常设计稳定、可行动且不泄露实现的外部错误；
4. 从真实消费者依赖判断兼容与破坏，不只看版本号是否改变；
5. 手算 offset/page 在并发插入下为何产生重复或遗漏；
6. 设计具有稳定排序和唯一 tie-breaker 的游标分页边界；
7. 解释 ETag 是表示验证器，匹配后的 304 为什么没有新 Body；
8. 区分 HTTP 方法的幂等语义、业务操作幂等和本地示例的幂等键约定；
9. 说明幂等键还需请求指纹、并发原子性、保留周期和冲突行为；
10. 用固定输入重放字段改名、页码漂移、内部错误泄露和重复创建四类缺陷；
11. 为 FactoryCare 写出契约变更的影响、迁移、回滚与非目标。

达标不是“能画 API 表格”，而是旧客户端、重试、缓存命中、空页和未知异常都能得到事先写明且可证伪的结果。

## 前置：HTTP 只是承载，契约才给结果含义

请先掌握 [HTTP 报文、方法、状态码、Header、Body 与 curl](./ch.foundations.http-curl.md)。本章会使用 method、status、Header、Body、`Content-Type` 等概念，但不重复讲传输失败。若根本没有收到 HTTP 响应，应回到网络与 curl 证据；只有收到响应后，才判断 API 契约。

同一个业务契约也可以通过消息、函数或本地模型表达。配套实验故意不用 HTTP 服务器，以便把“规则是否清楚”和“框架是否启动”分开。

## 什么是 API 契约

API 契约至少回答以下问题：

- **输入**：允许什么方法/动作、目标、字段、类型、单位和约束；
- **输出**：成功与失败分别返回什么状态、字段和内容类型；
- **不变量**：哪些关系跨调用、重试和版本必须保持；
- **顺序与集合**：列表如何排序、翻页、结束和处理并发变化；
- **时间**：缓存多久可复用，验证器何时改变，幂等记录保留多久；
- **兼容**：旧消费者遇到新提供方时哪些行为仍成立；
- **安全边界**：哪些信息可以公开，哪些只进受控内部日志；
- **失败恢复**：超时后能否重试，重复请求产生什么结果。

“示例里碰巧如此”不是契约。契约需要明确哪些是必须稳定的规则，哪些是可选扩展，哪些不在保证范围。

## 资源、标识与表示

### 资源不是数据库行

资源是 API 选择标识和操作的领域概念，例如设备 `DEV-001`。数据库行是内部存储形式，可能包含租户键、软删除标记、审计列、内部备注、密钥或实现关联。直接序列化数据库对象会把存储演进和外部消费者绑死，还可能泄露敏感字段。

API 应主动定义表示。例如：

```json
{
  "id": "DEV-001",
  "displayName": "一号循环泵",
  "status": "ACTIVE"
}
```

这里 JSON 对象是某个版本下的一次表示，不是设备本体。设备可以有 JSON、HTML 或事件等多种表示；同一表示还可能因权限、语言或版本不同而变化。

### 稳定标识与可变属性

`id` 用于长期引用，通常不应因设备改名或移动而变化。`displayName` 是可变属性。若把可变名称当主键，改名会让缓存、链接、工单关联和客户端收藏失效。

“稳定”不等于永远公开内部自增整数。标识策略还要考虑可猜测性、租户边界和迁移。本章只要求客户端能把同一资源在多次响应中可靠识别。

### 字段契约不只是一串名字

每个字段至少需要说明：

- 名称和含义；
- JSON 类型或其他表示类型；
- 必填、可选、可为 null 还是缺失；
- 数字单位与范围；
- 时间格式与时区；
- 枚举允许值及未知值策略；
- 是否可写、只读或由服务器生成；
- 权限不足时是省略、遮蔽还是整个请求失败；
- 版本演进规则。

例如 `temperature: 42` 不知道是摄氏、华氏还是传感器原始值；`updatedAt` 不说明时区也会让排序和审计歧义。契约必须消除会导致不同实现的关键歧义。

### 缺失、null、空字符串与空数组不同

- 字段缺失：当前表示未提供该字段，原因由契约说明；
- `null`：字段存在，但值为空/未知/不适用，具体语义需定义；
- `""`：存在一个长度为零的字符串；
- `[]`：存在一个已知为空的集合。

把它们互换会破坏客户端。列表查询在没有项目时通常返回稳定的空数组，而不是把 `items` 整个删除或改成 null；这样消费者无需为同一个概念猜四种形状。

### 表示的排序也是契约

JSON 对象成员的视觉顺序不应成为业务判断，但数组顺序可以有业务意义。设备列表若承诺按 `createdAt DESC, id DESC` 排序，客户端和分页游标都会依赖它。只说“按时间排序”还不够：时间相同时需要唯一 tie-breaker，否则同一数据可能跨请求换位。

## 成功响应：状态与表示共同组成合同

成功不等于所有接口都返回 200。创建可能返回 201 与新资源位置；删除或更新可能选择 204；缓存验证匹配可返回 304，它不是 2xx，却是条件请求的正常结果。每个操作要明确：

- 成功状态；
- 是否有 Body；
- 响应媒体类型；
- 新资源标识或位置；
- 是否返回完整资源、摘要还是异步任务；
- 客户端下一步可以做什么。

不要在 200 Body 中藏 `{"success":false}` 却让通用 HTTP 软件以为成功，也不要对 204/304 强制解析 JSON。

## 错误契约：客户端需要稳定分类，攻击者不该得到内部地图

### 状态码与问题详情分工

HTTP status 给通用软件一个粗类别，Problem 类型和字段给 API 客户端更细的机器可读信息。例如：

```json
{
  "type": "https://factorycare.example/problems/device-not-found",
  "title": "Device was not found",
  "status": 404,
  "detail": "No visible device matches the supplied identifier.",
  "instance": "/problems/INC-20260716-001",
  "code": "device-not-found"
}
```

客户端应主要按稳定的 status、type/code 和契约字段行动，不能解析人类文字来决定分支。`detail` 可以帮助人理解，但文案、语言和标点可能变化。

### 未知内部错误仍要有稳定外形

生产错误可能来自空指针、SQL、磁盘、第三方超时或配置。把异常类名、查询、表名、文件路径、堆栈和凭据原样返回会泄露实现，也让客户端依赖偶然细节。

外部 500 应映射到稳定 Problem，给出不泄露实现的通用说明和 opaque 关联标识。完整异常进入访问受控的内部日志；两侧通过关联标识连接。关联标识本身不能包含账号、数据库键或可用于越权读取详情的秘密。

### Problem 不是调试堆栈容器

RFC 9457 明确区分 HTTP 接口问题详情与底层实现调试信息。公共错误需要可行动，但不需要告诉未知客户端内部类、SQL 或节点路径。对合法用户是否展示更多字段，还要经过权限和隐私设计，本章不实现鉴权。

### status 字段与 HTTP status 必须一致

若 Problem Body 写 `status: 404`，实际状态行却是 500，代理、客户端和日志会得出不同结论。外层 HTTP status 是通用软件的依据，Body 中 status 只是表示内的辅助信息；提供方必须保证一致。

### 错误格式也要兼容演进

新增可选扩展字段通常比重命名 `type`、`code` 安全。客户端应忽略未知扩展，但不能因此假设枚举值可随意扩大：有些客户端对枚举做穷举分支。兼容性仍需真实消费者预言。

## 兼容版本：看旧消费者是否仍成立

### 版本号不自动创造兼容

把路径从 `/v1` 改成 `/v2` 只标记边界，不会自动迁移客户端；不改路径也不代表变化兼容。兼容判断必须从旧消费者依赖出发：旧请求能否被新提供方接受，旧客户端能否正确解释新响应，安全和业务含义是否保持。

### 常见变化矩阵

| 变化 | 常见风险 | 默认判断 |
| --- | --- | --- |
| 新增可选字段 | 严格拒绝未知字段的客户端可能失败 | 往往可兼容，但必须验证 |
| 删除旧字段 | 旧客户端读取失败 | 破坏性 |
| 字段改名 | 等同删除旧名并新增新名 | 破坏性 |
| 类型从整数改字符串 | 解析、排序、比较改变 | 破坏性 |
| 必填改可选 | 客户端可能遇到缺失 | 对响应消费者可能破坏 |
| null 语义改变 | 分支与展示错误 | 可能破坏 |
| 新增枚举值 | 穷举客户端可能崩溃或误判 | 需兼容策略 |
| 放宽请求接受范围 | 旧客户端通常仍可发送 | 常较安全，仍查安全边界 |
| 收紧校验 | 原来成功的旧请求失败 | 破坏性 |
| 改默认排序 | 分页、UI、缓存变化 | 破坏性 |

“新增字段永远安全”也不正确。若客户端反序列化器配置为拒绝未知字段，仍会失败。理想长期契约应要求消费者容忍未知可选字段，同时提供方不能利用这一点悄悄改变旧字段含义。

### 加法演进示例

v1：

```json
{"id":"DEV-001","displayName":"一号循环泵","status":"ACTIVE"}
```

v1.1：

```json
{"id":"DEV-001","displayName":"一号循环泵","status":"ACTIVE","location":"A-01"}
```

若旧客户端忽略未知字段，旧字段名称、类型和值语义未变，这是加法兼容候选。若把 `displayName` 改成 `name`，旧客户端看到字段消失，属于破坏性改名。

### 迁移与回滚要先写

破坏性变化应给出：受影响消费者、过渡期、双写/双读或转换方案、观测指标、停止旧版本条件和回滚。回滚 API 代码不一定能撤销已经写入的新数据，因此“回滚”需区分读取合同、写入路径和数据迁移。

本章不规定统一的 URL、Header 或媒体类型版本方案。选择哪种方式是架构决策；无论选择什么，都必须用消费者契约验证，而不是依赖命名。

## 分页：把一个变化中的有序集合分段交付

### 为什么不能一次返回全部

集合可能很大，一次返回会增加内存、延迟、带宽和客户端处理成本。分页把结果分成有限片段，但也引入顺序、边界和数据变化问题。契约至少说明：

- 固定且确定的排序；
- 页大小默认值、最大值与非法值；
- 第一页如何请求；
- 下一页令牌如何返回；
- 空集合、最后一页和页后空页形状；
- 数据插入、删除或权限变化时的一致性边界；
- 令牌无效、过期或与查询不匹配时怎样报错；
- 总数是精确、估算、快照还是不提供。

### offset/page 的漂移

初始倒序为：

```text
D, C, B, A
```

第一页 limit=2 得 `D,C`。此时顶部插入 `E`，新顺序为：

```text
E, D, C, B, A
```

客户端再取 offset=2，得到 `C,B`，于是 C 重复。若期间删除数据，也可能遗漏。offset 适合某些稳定或低变化场景，但不能把它宣传成并发变化下的快照保证。

### 游标/键集分页

若排序为 `createdAt DESC, id DESC`，第一页末项 C 的排序键可以成为边界。下一页表达“取严格排在 C 之后的项”，即使顶部插入 E，仍得到 `B,A`。

游标应被客户端当作 opaque token：原样保存、原样传回，不解析、不修改、不拼接。opaque 不等于秘密。Base64 只能改变表示，不能防篡改；生产令牌可能需要签名、过期、查询绑定、租户绑定和权限复核。

### tie-breaker 不可缺

若只按秒级 `createdAt` 排序，两条设备可能时间相同。没有唯一第二键，边界项可能换位、重复或遗漏。通常加入稳定唯一 ID 作为 tie-breaker，并保证比较方向与编码一致。

### 空页与末页

建议稳定形状：

```json
{"items":[],"nextCursor":null}
```

空数组表示本页已知没有项目，null 游标表示没有下一页。不要在空页把 `items` 删除，也不要返回与上一页相同游标导致客户端死循环。

### 游标不是任意数据库位置

游标是外部契约令牌，不应暴露表名、原始 SQL、未授权 ID 或秘密。服务端解码失败时返回稳定的 `invalid-cursor` Problem，而不是堆栈。权限改变后，旧游标是否继续有效也要明确。

## 缓存验证器：确认旧副本是否仍代表当前表示

### 缓存与验证不是同一件事

缓存保存先前响应；验证器帮助判断该副本是否仍可复用。ETag 是服务器给表示的 opaque 标记。客户端应保存并原样回传，不能从 ETag 反推业务版本或自行计算“应该是什么”。

首次响应：

```http
HTTP/1.1 200 OK
ETag: "abc123"
Content-Type: application/json

{"id":"DEV-001","displayName":"一号循环泵","status":"ACTIVE"}
```

再次验证：

```http
GET /devices/DEV-001 HTTP/1.1
If-None-Match: "abc123"
```

若当前选择的表示仍匹配，服务器可以返回 304 与相关字段，不发送新的表示 Body。客户端使用自己的缓存副本。304 不是“资源为空”，也不是“找不到”。

### ETag 对应表示，不只是数据库行

同一资源可能因媒体类型、压缩、语言、权限或版本得到不同表示。验证器必须与所验证的表示选择一致。若只对数据库更新时间生成一个全局 ETag，却忽略权限裁剪，可能错误复用含敏感字段的副本。

### 强、弱验证器的边界

HTTP 区分强弱验证器，适用比较不同。本章实验只使用固定强式外观的标签证明 200→304 流程，不教授范围请求等高级语义。不能只看引号就断言真实实现满足强验证器要求；生成策略必须符合规范。

### 缓存安全

共享缓存若键中没有包含租户、身份或影响表示的请求字段，可能把甲用户的响应给乙用户。敏感响应是否允许存储、使用 `private`/`no-store` 等指令、`Vary` 与授权请求行为都需要专门设计。本章只建立验证器模型，不宣称生产缓存策略完成。

## 幂等语义：重试同一逻辑操作，不产生额外效果

### 为什么创建最容易重复

客户端发送创建工单，服务端已经写入，但响应在途中丢失。客户端只知道“没有收到响应”，不知道写入是否发生。若直接再发一次，服务端可能创建第二张工单。

这不是简单的网络错误，而是不确定交付下的业务语义问题。安全重试需要双方约定如何识别“同一逻辑操作”。

### HTTP 方法幂等与业务幂等

HTTP 规范为某些方法定义幂等语义，但应用仍必须按方法合同实现。POST 不天然幂等；它可以通过业务设计获得某个操作的幂等行为。反过来，把 PUT 写在请求上也不能拯救一个每次都会追加记录的错误实现。

本章示例使用名为 `Idempotency-Key` 的本地契约字段表达逻辑操作标识。这个字段名在此是示例 API 约定，不宣称所有 API 都必须采用同名标准。

### 同键同请求

第一次：

```text
key=demo-operation-001
payload={deviceId: DEV-001, summary: 轴承温度过高}
→ 创建 FC-2001
```

响应丢失后重试同样 key 与 payload，应返回同一逻辑结果，资源数仍为一。可以标记 `replayed=true` 帮助观察，但客户端不能因此获得其他用户的结果。

### 同键不同请求

若同一个 key 后来配了不同 summary，服务端不应悄悄返回旧结果，也不应创建新记录。稳定做法是保存规范化请求指纹并返回明确冲突，例如 409 Problem。这样能暴露客户端错误地复用键。

### 并发原子性

“先查键是否存在，再插入”若没有原子约束，两条并发请求可能同时查不到并各自插入。生产实现需要数据库唯一约束、事务或等价原子机制，让业务写入与幂等记录保持一致。本章纯内存顺序模型没有验证并发和崩溃恢复，必须明确标为未验证。

### 保留周期与作用域

幂等记录不能无限增长。契约要说明键在何种调用方/租户/操作作用域内唯一、保留多久、过期后重试怎样处理。过短会让迟到重试重复，过长会增加存储和隐私风险。

幂等键本身不应携带密码、人员信息或完整业务内容。日志可以记录安全摘要或受控关联值。

### 幂等不等于“响应字节永远相同”

同一逻辑操作的额外业务效果应不增加；响应可能包含不同的观测时间、`replayed` 标志或追踪信息。契约要明确哪些字段稳定，不能用模糊“结果一样”掩盖差异。

## 六类语义如何组合

以创建设备工单为例：

| 关注点 | 契约问题 | 示例预言 |
| --- | --- | --- |
| 资源 | 新工单怎样标识与表示 | `id` 稳定，内部列不公开 |
| 错误 | 未知异常怎样公开 | 稳定 Problem，不泄露堆栈 |
| 版本 | 新增 location 如何迁移 | 保留旧字段，旧消费者继续解析 |
| 分页 | 工单列表怎样继续 | 稳定排序，游标边界无重复 |
| 缓存 | 设备详情副本是否仍有效 | ETag 命中返回 304、无新 Body |
| 幂等 | 创建响应丢失后怎样重试 | 同键同 payload 保持一个 ID |

它们相互影响。版本改变表示可能改变 ETag；权限改变可能使游标和缓存失效；错误格式本身也要版本兼容；幂等重放需要返回与原操作相容的表示。契约不能只在六份互不相干的文档里各写一半。

## 可运行示例

进入示例目录：

```bash
cd examples/encyclopedia/ch.foundations.api-contract-basics
ruby verify.rb
```

验证器只用内存与固定虚构数据，证明：

1. v1 旧字段在加法 v1.1 中保持，字段改名被判破坏；
2. 未知内部错误映射为稳定 Problem，内部文字没有泄露；
3. 顶部插入 E 后 offset 第二页重复 C，而游标得到 `D,C` 后 `B,A`；
4. after-A 返回空数组/空游标，非法游标返回稳定问题；
5. 首次 200 的 ETag 在再次匹配时得到 304 与 nil Body；
6. 无保护重试创建两个 ID；有键重放保持一个 ID；同键不同 payload 得 409。

预期摘要：

```text
resource/version: v1 stable; additive v1.1 accepted; field rename rejected
error: unknown internal exception mapped to stable, non-leaking Problem
pagination: offset duplicate C exposed; cursor pages D,C then B,A; final page empty
cache: 200 with ETag -> matching validator gives 304 with no body
idempotency: unsafe retry duplicated; stable key replayed one FC identity; changed payload got 409
api-contract-basics verification: PASS
```

exit 0 证明固定预言通过，不证明数据库并发、真实客户端或代理缓存。

## 常见错误与调试

### 直接返回 ORM/数据库对象

症状是内部列随数据库迁移出现在 API，字段重命名同时破坏存储与客户端。修复方向是显式表示投影和独立契约测试，不是给每个内部字段临时加隐藏注解后继续直出。

### 所有结果都返回 200

客户端、代理和观测无法使用 HTTP 通用语义，错误只能解析 Body 文案。应让 status 与结果类别一致，再用稳定 Problem 表达细节。

### 错误 Body 返回堆栈

这会泄露实现并让外部格式随代码结构漂移。第一证据是公开响应包含类名、路径、SQL 或秘密。修复为内部完整日志 + 外部稳定 Problem + 安全关联标识。

### 新增字段就宣称兼容

严格反序列化客户端可能拒绝未知字段，枚举扩大也可能破坏穷举。列出真实消费者、固定旧请求/响应 fixture，再验证。兼容是证据结论，不是改动类型标签。

### page=2 出现重复项

先冻结第一次排序、期间插入/删除和第二次 offset，手算重复。不要靠“再刷新一次”消失。若选择游标，必须同时修正稳定排序和唯一 tie-breaker。

### 游标只是把 offset Base64

客户端虽然看不懂，但数据漂移语义未改变。opaque 只描述接口边界，不能替代键集或快照机制，也不提供安全。

### 304 仍返回完整 Body

这混淆了“没有修改”的条件响应语义，浪费传输，并让客户端处理不一致。验证器命中时应检查状态、ETag 和无新表示 Body。

### 前端自己防重复

按钮禁用只能减少误点，无法覆盖网络重试、多个客户端和并发请求。幂等必须由拥有写入权威的一侧执行，并在存储层保证原子性。

### 同键不同 payload 仍返回旧结果

这会把调用方错误悄悄隐藏。保存请求指纹并明确冲突，让客户端生成每个逻辑操作的新键。

## FactoryCare 契约示例

### 设备列表

- 资源标识：`id`；
- 表示：`id`、`displayName`、公开 `status`，可选新增 `location`；
- 排序：`createdAt DESC, id DESC`；
- 第一页：没有 after；
- 下一页：原样回传 `nextCursor`；
- 末页：`items=[]` 或最后一批项目，`nextCursor=null`；
- 无效游标：400 `invalid-cursor` Problem；
- 非目标：不承诺列表是跨所有页面的数据库快照，除非另有快照契约。

### 设备详情缓存

- 200 返回表示与 ETag；
- `If-None-Match` 匹配返回 304，无新 Body；
- 权限、版本与表示选择参与验证策略；
- 敏感表示不默认共享缓存。

### 创建工单

- 每个逻辑创建生成稳定幂等键；
- 同键同 payload 返回同一工单 ID；
- 同键不同 payload 返回 409 Problem；
- 未知内部异常返回稳定 500 Problem；
- 生产实现必须原子保存业务写入和幂等结果；
- 本章不定义认证、租户、事务和事件发布。

## 速查表

| 概念 | 核心不变量 | 典型反例 | 最小证据 |
| --- | --- | --- | --- |
| 资源表示 | 外部字段显式稳定 | 直接序列化数据库行 | 固定表示 fixture |
| Problem | 外形稳定、不泄露内部 | 返回堆栈/SQL | status/type/code/公开字段 |
| 兼容版本 | 旧消费者依赖仍成立 | 改名却称新增 | 旧消费者回放 |
| 分页 | 稳定排序、无意外重复 | offset 遇顶部插入 | 两页项目与游标 |
| 缓存验证 | ETag 对应所选表示 | 304 带新 Body | 200→304 对照 |
| 幂等写入 | 同一逻辑操作不增效果 | 超时重试建两条 | 键、指纹、资源计数 |

### 六句复述

1. 资源不是数据库行，表示也不是资源本体；
2. 外部错误稳定，内部细节留在受控日志；
3. 兼容看旧消费者，不看版本号自我声明；
4. 分页先定义稳定全序，再定义令牌；
5. ETag 是 opaque 表示验证器，304 复用旧副本；
6. 幂等键要绑定请求指纹并原子执行。
