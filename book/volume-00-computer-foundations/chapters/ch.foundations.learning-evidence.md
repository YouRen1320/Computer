# 学习证据、掌握标准与间隔复习

<!-- BEGIN GENERATED LEARNING PREREQUISITES -->
## 学习前检查

本章无编程先修。零基础读者可以直接从本章开始，并按正文中的预测、操作、验证和复述步骤建立第一份学习证据。
<!-- END GENERATED LEARNING PREREQUISITES -->

这一章不教某一种编程语言，却决定你以后学 Java、SQL、Vue、Flutter、Python 和 AI 时，是在真实进步，还是在积累“我好像会了”的感觉。

学习编程最危险的误会，不是暂时写错语法，而是把一件容易观察的事情当成能力：视频播放完了、文章划到底了、项目目录出现了、AI 说“已经实现”、终端最后显示绿色、今天坐了三小时。这些事情可能发生在学习过程中，却都不能单独回答一个更重要的问题：**当提示消失、需求略微变化、程序故意出错时，你还能解释、修改、验证并恢复吗？**

本章建立一套贯穿全书的证据语言。以后每章都会出现“预测—构建—故障—复跑—复述”。这不是为了增加作业，而是为了让“会”变成可以被观察、被反驳、被修正的主张。你不需要一开始就完美；你只需要诚实地区分“我做过”“我看懂了”“我在这个条件下验证过”和“我还没有独立做到”。

## 本章要解决的问题

学完以后，你应当能够：

1. 把“我会某个知识点”改写成范围明确、可以失败的学习主张；
2. 为主张选择匹配的证据，而不是用文件存在、阅读时长或 AI 自述代替；
3. 区分解释、独立构建、故障诊断三种互补能力；
4. 在执行前写出预测，在执行后比较预期与实际；
5. 把失败记录成“输入—操作—现象—定位—修复—复跑”，而不是只截最后一行；
6. 用主动检索、间隔复习和复述检查记忆能否在提示消失后被取回；
7. 明确写下未验证边界，避免把一次成功夸大为任何环境、任何需求都成立；
8. 为 FactoryCare 后续每一项功能建立可追溯的学习证据。

本章不会给“聪明程度”打分，也不会要求每天机械打卡。证据用于决定下一步练什么，不用于制造焦虑或伪造进度。

## 如果你完全没有学习方法基础

先记住三个普通词：

- **主张**：你声称已经能做什么；
- **证据**：别人或未来的你可以重新观察到什么；
- **边界**：这份证据在哪些条件下成立，哪些条件还没有验证。

例如，“我今天学了 Java 两小时”是时间记录，不是能力主张。“我能在没有示例代码时写出一个读取姓名并输出问候的 Java 程序；用固定输入 `小李` 运行后得到预期文本；把变量类型改错时能从第一条编译错误定位并恢复”才是较完整的主张。它可能失败，因此也有学习价值。

你不需要先懂测试框架、Git 或终端。开始时可以用纸、文本文件或表格记录。以后学到命令、测试和版本控制，再把证据自动化。工具会升级，主张—证据—边界的关系不会过时。

## 直觉模型：法庭、体检与飞行记录

可以用三个类比理解学习证据。

第一，主张像法庭中的陈述。“我会”只是陈述；可重放的输入、操作和结果才是证据。证据不必证明一个人永远不会错，只要它能支持一个范围明确的结论，并允许反例推翻结论。

第二，证据像体检。一次正常读数不等于一生健康；它只说明在某日、某条件、某种测量方法下得到一个结果。范围写得越清楚，结论越可靠。未测项目标“未验证”，比假装正常更专业。

第三，调试记录像飞行记录器。事故后最有价值的不是“飞机最后停了”，而是故障前后的输入、状态和事件顺序。编程日志也是这样：最后的 `BUILD FAILURE` 只是结论；第一条具体错误、对应文件位置、输入和阶段更接近原因。

把三者合起来，就是本书的最小证据循环：

```text
明确主张 → 写下预测 → 在固定条件下操作 → 保存实际现象
     ↑                                      ↓
下一次检索 ← 记录边界与下一步 ← 修复并按原预言复跑 ← 比较差异
```

## 精确定义：什么叫可证伪

“可证伪”不是说主张一定是错的，而是说我们能描述什么现象会让它不成立。

主张“我已经看懂循环”很难反驳，因为“看懂”没有外部标准。可以把它改写为：

> 在不看现成答案的情况下，我能根据整数列表写出 `for` 循环统计大于等于 4 的元素；能预测空列表结果为 0；能解释循环变量每轮取值；把比较符号误改为 `>` 后，能用包含 4 的输入发现并修复错误。

这条主张包含：任务、独立程度、固定输入、预期、边界案例和故障案例。输入 `[5, 2, 4]` 若得到 1，主张在本次尝试中失败；这不是坏事，而是精确暴露了 `>=` 与 `>` 的差异。

一个实用主张通常回答六个问题：

| 问题 | 示例 |
| --- | --- |
| 做什么 | 统计高优先级工单 |
| 在什么输入下 | `[5, 2, 4]` 与空列表 |
| 期望什么 | 分别为 2 与 0 |
| 独立到什么程度 | 只看语言速查表，不看完整答案 |
| 如何观察 | 运行结果或自动断言 |
| 什么会推翻它 | 结果不同、无法解释边界、故障后不能恢复 |

范围不能无限扩大。“我在 macOS、JDK 25 上验证了这段代码”不等于 Windows、JDK 21、不同字符集和生产数据上都成立。工程师可信度的一部分，就是愿意说“这一项尚未验证”。

## 证据强度：不同问题需要不同证据

证据没有脱离主张的绝对等级。同一份结果，对一个窄主张可能足够，对一个宽主张可能完全不够。

### 过程痕迹

阅读记录、观看时长、提交次数、笔记页数属于过程痕迹。它们可以帮助管理时间，不能单独证明掌握。坐三小时可能一直卡在环境问题；五分钟也可能完成一次高质量复习。

### 产物存在

源码、报告、截图、项目目录属于产物。产物比“我看过”更具体，但文件可能是复制的、AI 生成的、旧版本遗留的，甚至不能运行。产物需要配合来源、操作和结果。

### 可重复观察

固定输入、明确命令或操作、精确预期、实际输出、退出状态、时间与环境构成可重复观察。另一个人按照记录重做，应能得到同类结果。对纯概念题，也可以用固定问题、限时复述和评分要点形成观察。

### 需求变更

在原功能上改一个条件，比照抄原题更能暴露理解。例如工单“紧急”的阈值从 4 改为 3：你应先更新预期，再定位规则所在，完成最小修改并复跑边界案例。若只能让 AI 重写整个文件，原有结构仍未被你掌控。

### 故障诊断与恢复

故意注入一个受控错误，预测失败阶段，读第一条可信证据，只改变一个条件，最后按原预言复跑。这能证明你不仅见过成功路径，也知道系统在哪里拒绝错误。

### 延迟后的独立检索

今天在提示旁完成，不代表一周后还能取回。隔一段时间，在更少提示下重新解释、构建或诊断，是对长期可用性的证据。

## 掌握不是一个开关，而是三条轴

本书把每章的核心成果固定为 `explain`、`build`、`diagnose`，因为三者容易被混淆。

### Explain：能解释责任与边界

解释不是背定义。你要能用普通语言回答：它解决什么问题、不解决什么问题、输入和输出是什么、一个失败反例是什么、与已知概念有什么区别。

例如解释 `mounted` 时，只说“它是布尔值”不够。更可靠的解释是：“Flutter State 的 `mounted` 表示该 State 当前是否仍关联在组件树中；异步结果回来后先检查它，可避免页面销毁后调用 `setState`，但它不会自动取消网络请求，也不会防止函数被重复调用。”这段话同时给出责任与两个边界。

### Build：能从约束独立构建

构建要求把需求转为可工作的产物。不是必须一字不查，而是不能把完整答案逐行复制。可以看语法速查、官方 API 和错误信息；但你要能说明关键结构、修改一个要求，并用预言验收。

AI 可以生成初稿，但“AI 输出完成”不等于你的 build 证据。你至少要指出规则在哪里、输入从哪里进入、失败如何表现，亲自完成一次局部修改和验证。

### Diagnose：能在失败中缩小范围

诊断不是看到红字就重写。你要区分失败阶段，找到第一处具体证据，提出能被验证的原因假设，一次只改一个关键条件，并用同一个正常预言确认恢复。

三条轴互相支持却不能替代。有人讲得很好但写不出来；有人能模仿成功但出错就重建项目；有人会修特定错误却无法解释原理。真正的掌握标准要明确本章需要哪三类证据。

## 预测：在运行之前把大脑放进循环

预测是学习证据中成本最低、收益最高的动作之一。若先看结果，大脑很容易产生“我本来就知道”的错觉；先写下预测，差异才会显现。

预测不要求必然正确。一个合格预测应尽量具体：

- 哪个阶段会运行；
- 会生成或修改什么；
- 标准输出和标准错误大致出现什么；
- 退出状态是成功还是失败；
- 哪条证据最先支持判断。

例如执行错误 SQL 前，不要只写“会报错”，而要写：“解析阶段失败，不会返回结果行；错误位置靠近拼错的 `SELECT`；修正关键字后，同一筛选条件应返回固定三列。”预测错了，就比较错误发生在哪个假设。

预测还能阻止盲目粘贴危险命令。若你说不清一个命令会读取哪里、写入哪里、是否覆盖文件，就还不应该执行它。

## 从现象到证据链

一次完整记录至少包含以下字段：

| 字段 | 要回答的问题 |
| --- | --- |
| claim | 这次要证明的窄主张是什么 |
| context | 日期、工具版本、目录或题目条件是什么 |
| input | 使用了哪些固定输入 |
| prediction | 执行前预期的结果和失败阶段是什么 |
| action | 实际运行的命令或编辑器操作是什么 |
| observation | 实际输出、错误、退出状态或手工观察是什么 |
| comparison | 预期与实际哪里相同、哪里不同 |
| diagnosis | 首个可信证据和原因假设是什么 |
| repair | 只修改了哪个条件 |
| rerun | 是否按原预言重新验证成功 |
| boundary | 哪些平台、输入或能力未验证 |
| next_review | 何时用更少提示重新检索 |

“可信证据”不是日志中看起来最吓人的一行，而是与失败阶段最接近、能约束原因范围的观察。例如 Maven 最后写 `BUILD FAILURE`，它只说明生命周期失败；上方 `expected: <5997> but was: <2002>` 才说明断言比较的期望与实际；若更早已经是编译错误，则根本不会出现测试数量。

## 边界案例、失败案例和反例

只验证常见输入，会留下大片盲区。初学时先掌握三类案例：

- **正常案例**：典型输入，证明主流程可工作；
- **边界案例**：零、空、最小值、刚好等于阈值、中文、重复项等；
- **失败案例**：非法输入、缺失文件、错误类型、错误状态等，证明系统会以预期方式拒绝或报告。

以“数量乘单价”为例，`1999 × 3 = 5997` 是正常案例，数量 0 得到 0 是边界案例，负数量该被拒绝还是允许则需要需求合同。没有合同就不能把个人猜测写成正确答案。

反例用于挑战过宽主张。若有人说“`BUILD SUCCESS` 说明功能正确”，一个能编译但返回 `unitPrice + quantity` 的程序就是反例：构建可以成功，业务测试会失败。反例让概念边界变得具体。

## 常见虚假自信及其修复

### “我看懂了，所以我会”

阅读时上下文、标题和示例都在提示答案。修复办法：合上材料，用 120 秒复述；随后从空白输入完成一个小构建。

### “代码在目录里，所以任务完成”

文件可能无法编译，也可能功能错误。修复办法：记录固定输入、运行方式、精确预期、实际输出和失败路径。

### “AI 说测试通过，所以通过”

模型可能没有执行，可能看错目录，也可能只运行部分测试。修复办法：由本地工具产生可重放输出；确认测试数量、失败数、跳过数和执行范围。

### “绿色就是全部正确”

绿色只覆盖已执行预言。两个测试全绿，不能证明所有输入，也不能证明部署、权限或安全。修复办法：写明覆盖与未覆盖边界，并增加最有风险的案例。

### “我记得答案，所以我掌握了”

记住某道题不等于迁移。修复办法：更换变量名、数据和一个需求条件，要求解释为什么改这里而不是别处。

### “失败说明我不适合编程”

失败只是预测与观察不一致。修复办法：把人格判断改为可操作描述，例如“我还不能区分 compile 与 test 阶段”，然后设计一个只改变阶段的对照实验。

### “记录越多，证据越强”

大量无关日志会隐藏关键线索，也可能泄露密钥。修复办法：保留足以重放和定位的最小集合，敏感值脱敏，明确首证据与结论。

## 主动检索：不要只重复输入

重新阅读属于再输入；主动检索要求在答案不可见时，从记忆中产生解释或操作。检索会让人感觉更费力，恰恰因为它暴露了记忆缺口。

可用形式包括：

- 看术语写定义，再与原文比较；
- 只看需求写伪代码或项目树；
- 只看故障日志判断阶段与下一步；
- 根据固定输入手算结果，再运行；
- 给另一个初学者做 120 秒复述；
- 打乱步骤，让自己恢复正确顺序；
- 一周后完成同类但不同数据的题。

检索不是闭眼背整章。重点是能取回“责任、边界、预言、关键步骤和诊断策略”。具体 API 名可查官方文档，但不能把“不知道该查什么”伪装成工具能力。

## 间隔复习：在将要忘记时重新取回

连续重复十遍，短期看似流畅，长期未必可靠。把复习分散到不同日期，每次减少提示并稍微改变情境，更能检验知识是否可用。

本书默认提供 `1/3/7/21` 天节奏，它是起点，不是医学处方：

- **当天或第 1 天**：复述模型，完成一个最小成功案例；
- **第 3 天**：不看正文重做边界或失败案例；
- **第 7 天**：完成一个需求变更，解释修改位置；
- **第 21 天**：把概念用到 FactoryCare 或另一语言情境中。

若第 3 天完全无法取回，不必惩罚自己。把下次间隔缩短，重新做最小证据循环。若连续多次轻松通过，可以延长。复习日期要服务于风险：安全、事务、并发、数据迁移等高风险知识应更频繁检索。

## Teach-back：把理解压缩成可检查语言

复述不是朗读笔记。听众假设是“聪明但没学过本章的人”。推荐结构：

1. 一句话说它解决什么问题；
2. 说出两个关键概念及其关系；
3. 给一个正常例子；
4. 给一个会失败的反例；
5. 说明如何观察和修复；
6. 说出一个尚未覆盖的边界。

录音或计时能帮助控制冗长，但不要求表演。若复述中频繁出现“反正”“大概”“AI 会处理”，就在这些位置补充可观察条件。

同伴复述时，提问者不要只问“懂了吗”，而要问：“什么现象会推翻你的结论？”“如果需求改一个条件，你先改预期还是先改代码？”“这份证据不能证明什么？”

## AI 时代如何使用证据，而不是拒绝 AI

AI 可以提高产出速度，但必须把生成与掌握分开记录。

可以让 AI：解释错误信息、提出测试案例、生成重复骨架、比较两种方案、审查潜在遗漏。你仍需要：明确合同、检查生成文件、运行验证、解释关键边界、完成局部变更、诊断受控故障。

一个可靠流程是：

```text
我先写需求与预言
→ AI 生成或建议
→ 我逐文件定位规则与数据来源
→ 本地运行固定案例
→ 我故意改坏一个条件并读日志
→ 我亲自修复或指导 AI 做最小修改
→ 关闭 AI 完成一次相邻任务
```

若 AI 生成了十个文件，你无法指出入口、核心规则和测试预言，就把状态写为“产物已生成，理解未验证”，而不是“已掌握”。这不是贬低产物，而是保护下一步决策。

安全上，不要把 Token、密码、真实客户数据、私钥和完整生产配置作为学习证据发送给外部模型。日志只保留必要片段并脱敏；删除密钥文件不代表 Git 历史中的密钥已经撤回，泄露后应立即轮换。

## FactoryCare：把证据落到真实项目

FactoryCare 是贯穿课程的工业设备运维与智能工单平台。每个增量都应形成三列，而不只是功能截图：

| 能力 | FactoryCare 示例证据 |
| --- | --- |
| explain | 解释工单状态为何不能任意跳转，列出责任与边界 |
| build | 根据状态合同实现一个受控转换，并用固定输入验证 |
| diagnose | 注入非法转换，观察拒绝位置，修复后复跑原预言 |

例如学习 SQL 聚合时，主张可以是：“能统计每位维修人员已关闭工单数，排除空处理人，并筛出数量至少 2 的人员。”证据应包含表结构假设、固定样例行、查询、手算结果与数据库实际结果。若只保存 SQL 文本，没有样例数据和结果，它仍是未验证产物。

学习 Vue 时，主张可以是：“切换状态筛选时只展示最后一次请求结果。”除了页面截图，还要有快速切换案例、请求时序、过期响应不能覆盖新状态的证据。学习 Flutter 时，要区分 `mounted` 防止销毁后更新 UI 与真正取消网络请求；一句“不会内存泄漏”过于宽泛。

项目证据还要支持需求变更。例如产品把紧急阈值、SLA 或权限范围改变，先更新合同和预言，再改实现。若每次只能整页重生，说明局部控制能力仍需训练。

## 实验：建立第一份学习账本

公开实验位于 [`labs/encyclopedia/ch.foundations.learning-evidence`](../../../labs/encyclopedia/ch.foundations.learning-evidence/README.md)。选择一个你即将学习的小概念，例如“测试断言的 expected 与 actual”“SQL 的 WHERE 与 HAVING”或“Flutter mounted 的边界”。

实验分六步：

1. 写一条范围明确、可能失败的 claim；
2. 写 explain、build、diagnose 三类验收；
3. 为每类验收写固定输入、预测和观察方式；
4. 完成一次正常案例和一个边界案例；
5. 注入一个受控故障，记录首证据、修复与复跑；
6. 安排 1/3/7 天检索，并明确减少什么提示。

配套示例提供一份合格账本和一个 Ruby 标准库校验器。校验器只能检查字段是否齐全、状态是否合法，不能判断你的解释是否真正准确；人工复述和实际运行仍不可省略。

## 五类练习

练习位于 [`exercises/encyclopedia/ch.foundations.learning-evidence`](../../../exercises/encyclopedia/ch.foundations.learning-evidence/README.md)，按本书统一结构完成。

### 预测练习

给出“看完 4 小时视频”“存在一个源码文件”“固定输入的两个断言通过”“一周后独立完成需求变更”四条记录。先预测它们分别能支持什么、不能支持什么，再看解释。

### 构建练习

为“能解释绝对路径与相对路径”建立账本。不能把主张写成“我学会路径”；必须包含固定起点、目标文件、两个路径表示和一个错误起点反例。

### 故障练习

修复一份把 `artifact_exists: true` 当成 `mastered: true` 的账本。只修改状态不够，还要补上可重放输入、操作、预言和结果。

### 需求变更练习

原验收只要求正常输入。现在增加“空输入”和“恰好等于阈值”。先改证据合同，再改测试或手工检查表，解释为什么顺序不能颠倒。

### 无 AI 练习

关闭 AI，限时 30 分钟，从空白模板写一条主张、三类证据、一个失败恢复记录和 1/3/7 天计划。最后用 120 秒解释“文件存在为什么不等于掌握”。

私有解析位于 `solutions-private/encyclopedia/ch.foundations.learning-evidence/`。完成自己的记录前不要打开；看过解析后的复写不能记作本轮无 AI 证据。

## 调试自己的学习流程

学习停滞时，不要立即重做整套课程。按下面顺序定位：

1. **主张是否太大**：把“学会 Java”缩为一个可在 30 分钟验证的行为；
2. **预言是否缺失**：没有预期，就无法区分成功与偶然输出；
3. **输入是否固定**：每次换数据会让差异难以解释；
4. **执行范围是否明确**：确认运行的是哪个文件、哪些测试、哪个环境；
5. **首证据是否具体**：不要只看最终失败摘要；
6. **是否同时改了太多条件**：一次只改变最可能原因；
7. **是否完成复跑**：修复后必须按原正常预言再验证；
8. **是否只是提示依赖**：隔一段时间、减少提示重新检索。

如果连续三次都卡在相同基础点，安排窄范围补救，而不是用更多 AI 输出覆盖缺口。比如只练“读 expected/actual”五个例子，再回到原实验。

## 证据的安全、隐私与伦理边界

学习证据不是越完整越好。它不应包含真实用户隐私、公司源码、生产数据库、访问 Token、身份证号、内部 URL 或未授权录音。使用虚构 FactoryCare 数据，秘密值写成 `<REDACTED>`，但保留足够上下文让错误可理解。

不要伪造学习小时、测试数量、面试经历或工作年限。可复现证据的价值来自可信；一旦用生成日志冒充执行结果，后续计划也会被错误数据误导。

团队评审时，区分“作者自检”“自动检查”“独立复核”。三者可以互补，不应相互冒充。自动校验通过只说明规则覆盖部分；作者说“我觉得清楚”不是零基础读者试读；独立复核也不能证明所有平台。

## 120 秒复述模板

合上正文，按顺序回答：

1. 主张、证据和边界分别是什么；
2. 为什么阅读时长和文件存在不能单独证明掌握；
3. explain、build、diagnose 为什么不能互相替代；
4. 预测如何减少“看完答案觉得本来就会”的错觉；
5. 一次故障记录至少包含哪些环节；
6. 间隔复习和重复阅读有什么不同；
7. AI 生成代码后，你必须补哪几类证据；
8. 举一个 FactoryCare 的可证伪主张和未验证边界。

能在 120 秒内讲清，不代表永久掌握；它只是 explain 轴的一次证据。还要完成构建与诊断。

## 间隔复习计划

- **第 1 天**：不看正文，把“我学会了 SQL”改写为一条可证伪主张；
- **第 3 天**：从四条记录中识别过程痕迹、产物、可重放证据与延迟检索；
- **第 7 天**：给一份 AI 生成代码补充输入、预言、边界与故障案例；
- **第 21 天**：从最近的 FactoryCare 功能挑一项，检查 explain/build/diagnose 是否都有真实证据。

每次复习只记录事实：用了什么提示、是否完成、具体缺口是什么。不要补造小时或把“计划执行”写成“已执行”。

## 速查表

| 想证明的主张 | 最小合适证据 | 不能单独替代的东西 |
| --- | --- | --- |
| 能解释概念 | 限时复述、责任、边界、反例 | 划线笔记、原文朗读 |
| 能独立构建 | 固定需求、产物、运行结果、局部变更 | 文件存在、AI 自述 |
| 能诊断 | 故障注入、首证据、单一修复、复跑 | 只截最后一行、重建项目 |
| 能长期取回 | 延迟后减少提示的相邻任务 | 当天连续重复 |
| 功能正确 | 与需求匹配的预言及覆盖范围 | 编译成功、任意绿色 |

最小记录句式：

```text
我主张 ______。
在条件 ______、固定输入 ______ 下，我预测 ______。
实际观察 ______，首个可信证据在 ______。
我只修改 ______，按原预言复跑结果 ______。
这份证据尚不能证明 ______；下一次检索日期是 ______。
```

## 术语表

- **学习主张**：对自己在明确范围内能够解释、构建或诊断什么的陈述。
- **可证伪**：能够描述哪些可观察结果会使主张在本次条件下不成立。
- **预言/Oracle**：用于判断实际结果是否满足期望的明确标准。
- **过程痕迹**：时长、阅读、观看等发生过学习活动的记录。
- **可重放证据**：保留输入、操作、环境和结果，可由未来的自己或他人复现。
- **边界**：证据适用和尚未覆盖的条件。
- **主动检索**：在答案不可见时从记忆产生解释或操作。
- **间隔复习**：把检索分散到不同日期，并逐步减少提示。
- **Teach-back**：面向不了解该主题的人，用自己的话解释责任、关系、反例和边界。
- **需求变更**：改变一个合同条件，用于检验学习者能否定位并做局部调整。

## 来源与复核日期

本章稳定核心是“主张必须由匹配证据支持、主动检索优于只重复输入、复习应跨时间重新取回”。具体 `1/3/7/21` 日是本课程的可调整教学节奏，不是对所有人的固定医学结论。

- 复核日期：2026-07-16。
- Dunlosky 等，[Improving Students’ Learning With Effective Learning Techniques](https://doi.org/10.1177/1529100612453266)：综述检索练习、分散练习等学习技术的效用与边界。
- Roediger 与 Karpicke，[Test-Enhanced Learning](https://doi.org/10.1111/j.1467-9280.2006.01693.x)：支持延迟测试中主动检索相较重复学习的优势。
- The Learning Scientists，[Retrieval Practice](https://www.learningscientists.org/retrieval-practice)：提供面向学习者的检索练习说明和实践建议。
- The Learning Scientists，[Spaced Practice](https://www.learningscientists.org/spaced-practice)：支持把练习分散到不同时间，而不是一次集中完成。
- Bjork Learning and Forgetting Lab，[Making Things Hard on Yourself, But in a Good Way](https://bjorklab.psych.ucla.edu/wp-content/uploads/sites/13/2016/07/EBjork_RBjork_2011.pdf)：支持“合意困难”与长期保持的讨论。

上述研究支持一般学习原则，不直接证明某个具体编程实验已经掌握。每一章仍须用该知识点自己的输入、预言、运行、故障与延迟检索证据验收。
