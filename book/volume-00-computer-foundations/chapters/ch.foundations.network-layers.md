# IP、DNS、端口、TCP 与 TLS 分层

当浏览器显示“无法访问”、终端显示“连接失败”、前端只抛出一个 `NetworkError` 时，最没有帮助的结论是“网络坏了”。“网络”并不是一个开关，而是一条由多个阶段组成的链：输入的名称要先得到地址，地址与端口组成连接目标，TCP 要建立传输通道，TLS 还要协商加密参数并核验对端身份。任何一步失败，后面的步骤通常都没有执行。

本章建立从名称解析到加密传输的诊断模型。我们会看到 IP、DNS、端口、TCP 与 TLS 各自回答什么问题，如何留下可重放证据，以及为什么不能用某一层的成功替另一层背书。本章故意停在 TLS：握手成功以后应用发送什么请求、状态码表示什么，属于下一章 HTTP 语义。

## 本章要解决的问题

完成本章后，你应当能够：

1. 区分主机名、IP 地址与端口，不把它们当成同一种“网址”；
2. 解释 DNS 解析得到的是地址信息，不保证目标服务健康；
3. 说明监听地址与监听端口共同决定服务能从哪里被连接；
4. 解释 TCP 连接提供有序可靠的字节流，但不理解业务消息；
5. 从证据上区分名称解析失败、连接拒绝、等待超时与 TLS 校验失败；
6. 说明 TLS 提供的机密性、完整性和身份校验边界，不把“有加密”误写成“业务安全”；
7. 在底层失败时把上层标为“未执行”，而不是猜测为成功或失败；
8. 在本机回环地址上重放正常链、错误名称、关闭端口、证书名不匹配与有界等待超时；
9. 为 FactoryCare 故障记录写出目标、阶段、证据、结论边界与下一项安全动作。

真正的达标证据不是背出缩写，而是面对一段失败输出时指出“第一处失败发生在哪一层、哪些层已经有证据、哪些层还不能评价”。

## 前置补救：先会保留命令证据

本章假设你已经认识命令的 stdout、stderr 与退出码。若还不熟悉，请先复习 [stdin、stdout、stderr、管道与退出码](./ch.foundations.cli-streams-exit-codes.md)。网络诊断中，三者经常承担不同职责：正常结果可能在 stdout，失败原因可能在 stderr，自动化脚本则靠退出码判断命令是否完成。

记录一条网络命令时，至少保留：

- 执行时间与所在环境；
- 脱敏后的目标名称、IP 与端口；
- 命令及关键参数，特别是超时预算；
- stdout、stderr 与退出码；
- 第一处失败层和后续未执行层；
- 修复时唯一改变的条件；
- 修复后同一命令的复跑结果。

不要只截一张红色错误图。截图可能漏掉命令、目标和退出码，也无法自动重放。

## 一张总地图：五个问题，不是五个同义词

先把一次加密连接拆成顺序问题：

```text
输入名称
  │
  ├─ DNS/名称解析：这个名称现在对应哪些 IP？
  ▼
目标 IP
  │
  ├─ 端口选择：要连接该主机上的哪个传输端点？
  ▼
IP + TCP 端口
  │
  ├─ TCP：双方能否建立有序可靠的字节流？
  ▼
TCP 已连接
  │
  ├─ TLS：能否协商加密并验证对端是预期名称？
  ▼
受保护的字节通道
  │
  └─ 应用协议：后续章节再判断
```

这张图有两个重要规则。

第一，前一层成功只是后一层开始的条件，不是后一层成功的证明。解析出 IP 不代表端口开放；TCP 建连不代表证书正确；TLS 握手成功也不代表用户有权限或业务数据正确。

第二，前一层失败后，后一层应写“未执行”。若主机名无法解析，程序连目标 IP 都没有，便不能从这次运行得出“443 端口关闭”；若 TCP 被拒绝，TLS 没有通道，便不能声称证书过期。

## IP 地址：网络层的目标标识

### IP 回答什么

IP 地址用于在 IP 网络中标识接口或通信目标，并参与路由选择。你可以先把它理解成“把数据包送往哪里”的地址。IPv4 常写成四段十进制，例如 `192.0.2.10`；IPv6 使用更长的十六进制表示，例如 `2001:db8::10`。这两个例子来自为文档保留的地址范围，不应把它们当成可实际访问的生产服务。

主机名不是 IP。`api.factorycare.example` 是便于人和配置表达的名称；名称解析可能返回一个、多个或暂时没有地址。同一名称可以随时间返回不同 IP；同一 IP 也可以承载多个名称。诊断记录必须写清“输入名称”和“本次实际选择的地址”，不能把二者混成一栏。

### 回环地址

`127.0.0.1` 是常见 IPv4 回环地址，`::1` 是 IPv6 回环地址。发往回环地址的通信留在本机，适合安全、可重复的基础实验。本章资产只绑定 `127.0.0.1`，不会扫描局域网或公网。

“本机可访问”不能推出“其他机器可访问”。一个服务只监听回环地址时，本机客户端可能成功，另一台机器却无法通过该监听进入。这不是矛盾，而是监听范围不同。

### `0.0.0.0` 不是普通远端目标

服务端配置中的 `0.0.0.0` 常表示在所有本地 IPv4 接口上监听。它表达绑定范围，不是建议客户端连接的业务地址。客户端仍应使用明确的回环、局域网或正式服务地址。把 `0.0.0.0` 从日志复制成客户端 URL，是初学者常见的边界混淆。

IPv6 中也有表示未指定地址的形式，但本章不展开跨平台双栈绑定细节。看到监听输出时，先问它表示“所有本地接口”“仅回环”还是“某个具体接口”。

### 一个主机可以有多个地址

笔记本可能同时有回环、Wi-Fi、以太网、VPN 与容器网络地址。DNS 也可能同时返回 IPv4 的 A 记录与 IPv6 的 AAAA 记录。客户端最终使用哪个地址，受解析结果、系统地址选择、路由与失败回退策略影响。

因此“DNS 输出里有一个正确 IP”仍不够。若客户端实际优先选择另一个不可达地址，观察会不同。高质量记录应保存地址列表和本次连接的实际对端，而不是只挑一个符合预期的值。

### IP 成功不能证明什么

知道或能到达一个 IP，不证明：

- 目标 TCP 端口正在监听；
- 防火墙允许该端口的 TCP 流量；
- 连接的进程就是预期服务；
- TLS 证书为输入名称签发；
- 应用已经启动完成；
- 当前用户有业务权限。

这份“不能证明清单”是分层诊断的核心。每得到一条成功证据，都要同时写出它的边界。

## DNS：从名称取得地址信息

### DNS 不是互联网电话簿的静态副本

把 DNS 类比电话簿有助于入门，但真实机制更接近分层、分布式的命名数据库。应用通常把名称与查询类型交给本地解析器；解析器可能使用缓存，也可能向配置的名称服务器查询并继续追踪委派。最终结果可能包含 A、AAAA 等资源记录，也可能是“名称不存在”、暂时失败或等待超时。

DNS 的职责是提供名称相关信息。它不打开端口，不启动进程，不完成 TLS，也不理解工单业务。即便解析结果完全正确，后续仍可能失败。

### 名称、记录与本次解析

需要区分三个对象：

1. **输入名称**：客户端配置中写的名称；
2. **DNS/本地解析结果**：本次得到的一个或多个地址；
3. **实际连接地址**：客户端从结果中选择并尝试的地址。

名称可能通过别名间接指向另一个名称，缓存还会让不同时间或不同机器看到不同结果。诊断时不要只说“DNS 正常”，而要写“在某时某环境，把某名称按某地址族解析为哪些地址”。

### 安全的本机观察

本章用 Ruby 标准库观察 `localhost`，避免依赖公网：

```bash
ruby -rsocket -e 'p Addrinfo.getaddrinfo("localhost", nil, :INET, :STREAM).map(&:ip_address).uniq'
```

预期至少得到本机 IPv4 回环地址。实际数组顺序由环境决定，不应把顺序硬编码成协议真理。

错误名称示例使用含空格的非法主机名，解析器会立即拒绝，无需向公网发查询：

```bash
ruby -rsocket -e 'Addrinfo.getaddrinfo("bad host name", nil, :INET, :STREAM)'
```

这条命令应产生 `SocketError` 一类失败并返回非零退出状态。它证明输入无法完成名称解析；它没有测试任何远端端口。

### 名称解析失败的不同原因

“解析失败”仍需细分：

- 名称本身格式非法；
- 权威数据表明名称不存在；
- 本地解析器配置错误；
- 到名称服务器的查询超时；
- 缓存中保留旧结果；
- 搜索域把短名称扩展成非预期名称；
- A 与 AAAA 的结果或使用路径不同。

错误文本与退出状态能帮助细分，但不要把某个操作系统的一句英文当成跨平台唯一预言。实验断言失败阶段和错误类型，而不强求所有系统打印完全相同的句子。

### 缓存为何让“我这里可以”不够

DNS 记录有缓存语义。开发机、服务器、容器与企业代理可能使用不同解析路径，也可能保留不同时间点的结果。一个人解析成功不能证明所有环境当前都相同。

排查变更时应记录：查询发生在哪里、何时发生、得到了什么，以及客户端实际连了什么。不要在没有授权和回滚计划时批量清空系统缓存；清缓存会改变观察条件，可能掩盖原问题，也可能影响其他应用。

## 端口与监听：同一主机上的传输端点

### 端口回答什么

IP 把通信送到主机或接口，端口帮助传输层把通信交给具体端点。TCP 端口号范围为 0 到 65535；日常服务通常使用约定或配置中的端口。端口本身不是进程 ID，也不是程序文件。进程创建套接字并绑定地址与端口后，才形成监听关系。

目标必须至少写成 `IP:port`，还要注明传输协议。例如 `127.0.0.1:45678/TCP` 与同号 UDP 端口不是同一个传输端点。只写“45678 开着”缺少地址与协议。

### 监听地址改变可达范围

比较两种绑定：

- `127.0.0.1:45678`：通常仅本机 IPv4 回环客户端可连接；
- `0.0.0.0:45678`：通常表示所有本地 IPv4 接口都接受该端口连接，仍受防火墙、路由和系统策略限制。

将监听从回环扩大到所有接口会扩大暴露面，不是普通“修一下网络”。学习实验没有远端访问需求，因此坚持回环绑定。

### 端口 0 与临时端口

服务绑定端口 0 时，通常是在请求操作系统选择一个当前可用的临时端口。本章自动验证器使用这种方式，避免与机器上固定服务冲突。程序随后从套接字读取实际端口并传给客户端。

端口 0 是绑定请求中的特殊用法；客户端不应把“连接远端端口 0”当作正常业务目标。

### 监听证据与进程证据

在 macOS 上，经过授权可以用只读命令观察本机 TCP 监听：

```bash
lsof -nP -iTCP:45678 -sTCP:LISTEN
```

它能关联本机进程、地址与端口，但输出字段会随平台与权限不同。Linux 常用 `ss`，Windows 有各自工具；本章未在这些平台实测，不把命令写成通用保证。

“列表中有监听”仍不证明服务业务健康。进程可能接受连接后卡住，可能运行了错误版本，也可能需要 TLS 而客户端发送了明文。监听只是进入 TCP 阶段的一个条件。

## TCP：有序可靠的字节流

### 连接建立的直觉

TCP 是面向连接的传输协议。双方通过交换控制信息建立连接状态，常用“三次握手”概括初始 SYN、SYN-ACK、ACK 的过程。初学阶段不必背每个报文位，但要理解：客户端的“连接成功”意味着针对某个源/目标地址和端口建立了 TCP 状态，不等于应用请求已经成功。

一条连接可用源 IP、源端口、目标 IP、目标端口和协议来区分。客户端源端口往往由系统临时选择，因此两次连接的源端口可以不同。

### TCP 是字节流，不保留业务消息边界

应用写入两次，不保证接收方也恰好读取两次。TCP保证的是字节的有序传送语义，而不是“每个 write 对应一个完整 JSON”或“一次 read 得到一条工单”。应用协议必须自己定义消息边界，例如长度、分隔符或更高层报文规则。

这条规则在后续 HTTP、数据库驱动和自定义设备协议中都会出现。把一次 `read` 当成完整消息，是网络程序常见缺陷。

### 连接成功能证明什么

较精确的表述是：在给定时刻、从给定客户端网络路径、向给定 IP 与 TCP 端口，连接建立完成。它不能单独证明：

- 名称仍指向该 IP；
- TLS 将成功；
- 对端身份正确；
- 应用会及时返回字节；
- 请求格式正确；
- 业务操作成功。

若日志只写 `connected=true`，应补充目标、耗时与下一阶段结果。

## 连接拒绝与等待超时

### 拒绝：收到了快速、明确的否定

当目标主机可达但相应 TCP 端口没有监听，系统常快速返回“连接被拒绝”。中间设备也可能主动拒绝。关键观察是：连接尝试很快得到明确失败，而不是一直等待。

在本机可重复地制造拒绝，可以先让系统分配一个回环端口，关闭监听，再立即连接。配套验证器正是这样做。它断言失败层为 TCP，且 TLS 未执行。

拒绝不一定等于“整个服务器宕机”。同一主机别的端口可能正常；服务可能监听了另一个地址；部署配置可能写错端口。结论应限制在本次 `IP:port/TCP`。

### 超时：预算内没有等到某个条件

“超时”不是原因名称，而是观察：在规定时间内，某一步没有完成。必须补齐三个问题：

1. 等待的是 DNS 回答、TCP 建连、TLS 握手，还是连接后的字节？
2. 超时预算是多少？
3. 在超时前已经完成并观察到什么？

连接超时可能来自丢包、过滤、路由错误、目标错误或预算过短；连接后的读取超时则说明 TCP 已建立但预期字节未在预算内出现。二者不能混写。

本章回环实验为了确定性，不假造公网黑洞。它让本地服务先接受 TCP、暂不发送字节，客户端等待 0.08 秒后结束。准确结论是“TCP 已连接，等待字节超时”，不是“TCP 连接超时”。

### 为什么重试不是首个动作

盲目重试可能偶然成功，却抹掉首次失败的阶段和时间；还可能加重故障服务负担。先保存目标、预算、错误与退出状态，再决定是否按已设计的退避策略重试。名称拼错、证书不匹配这类确定性错误也不会因高速重试自行修复。

## TLS：在传输之上建立受保护通道

### TLS 增加什么

TLS 在已有传输之上协商密码学参数，保护后续数据的机密性与完整性，并通常通过证书验证服务器身份。可以把它理解为三个同时需要回答的问题：

- 双方能否协商共同支持的协议与算法；
- 客户端能否建立从服务证书到受信任锚的验证关系；
- 证书标识的名称是否包含客户端原本要访问的主机名。

只回答其中一个不够。“证书没过期”不代表主机名匹配；“通信已加密”不代表终点是正确服务；“证书受信任”也不授予用户业务权限。

### TLS 握手的简化过程

以现代 TLS 的抽象流程看，客户端提出支持参数并携带目标服务器名称等信息，服务器选择参数并提供身份材料，双方验证并导出会话密钥，随后才能安全交换应用字节。真实握手包含更多消息、扩展与状态，本章只保留诊断所需边界。

TLS 建立在 TCP 之上时，如果 TCP 尚未连接，TLS 消息无处传输。于是“连接被拒绝同时证书错误”不能来自同一次严格顺序的探测；若工具同时显示多段历史日志，要按时间和连接实例区分。

### 证书链、信任与主机名

服务器证书包含公钥、名称、有效期、用途和签名等信息。客户端通常验证签名链是否连接到其信任存储中的锚，并验证输入主机名是否被证书允许。现代服务身份主要看 Subject Alternative Name（SAN）；不能因为证书 subject 里出现一个相似字符串就跳过标准主机名验证。

本章本地实验在内存中生成临时自签信任锚和仅覆盖 `localhost` 的证书。客户端显式信任该实验锚，因此 `localhost` 正常；把期望名称换成 `api.factorycare.invalid` 时，TCP 与密码学握手可以到达，但主机名验证失败。临时私钥不会写入仓库或系统证书库。

### SNI 与证书选择

同一 IP 与端口可以承载多个 TLS 名称。客户端在握手中提供服务器名称，服务端可据此选择证书。若客户端用 IP 连接却没有保留原名称，或代理/配置传了错误名称，服务端可能返回另一张证书。

因此诊断 TLS 时应同时记录：连接 IP、TCP 端口、期望主机名和实际证书名称。只记录 IP 会丢失身份校验最关键的输入。

### 不要把跳过校验当作修复

许多客户端提供忽略证书验证的选项。它可以在严格受控的对照实验中帮助回答“失败是否来自证书校验”，但不能作为生产修复。禁用校验会删除“对端确实是预期身份”的预言，使中间人或错误服务更容易被接受。

正确动作是核对：客户端输入名称、服务端部署证书、SAN、证书链、有效期、系统时间、信任锚与代理边界。只改变一项后，以严格校验重新运行。

### TLS 成功仍不能证明什么

TLS 成功证明的是该次通道的协商与身份/信任检查满足客户端策略。它不证明：

- 应用协议报文正确；
- 用户已认证或获授权；
- 服务数据无业务错误；
- 服务端没有漏洞；
- 客户端发送内容符合隐私要求；
- 后端依赖健康。

下一章才会在 TLS 之上研究 HTTP 请求与响应契约。

## 从输入到证据：固定诊断顺序

面对“连接不上”，按以下顺序操作，不同时修改多个变量。

### 第 0 步：冻结目标与观察窗口

记录输入名称、端口、传输协议、是否预期 TLS、开始时间和超时预算。先确认没有把开发、测试、生产名称混用，也没有把监听地址当成客户端目标。

### 第 1 步：名称解析

保存本次得到的地址列表与错误。若失败，结论止于名称解析；TCP、TLS、应用均标为未执行。

### 第 2 步：选择实际地址与端口

记录客户端实际选用的 IP、地址族和 TCP 端口。不要仅保存 DNS 列表中“看起来正确”的那个地址。

### 第 3 步：TCP 建连

设置有限预算，记录成功、拒绝或超时，以及耗时。若失败，TLS 与应用未执行。

### 第 4 步：TLS 握手与身份校验

记录期望主机名、证书名称、信任结果、协议协商和错误类型。失败时应用协议未执行。

### 第 5 步：交给应用协议

只有前四步通过，才进入 HTTP 或其他应用协议诊断。不要因收到若干加密字节就猜业务成功。

可以用状态表防止越层推断：

| 场景 | DNS | TCP | TLS | 应用 |
| --- | --- | --- | --- | --- |
| 名称非法 | 失败 | 未执行 | 未执行 | 未执行 |
| 端口关闭 | 成功 | 拒绝 | 未执行 | 未执行 |
| 证书名不匹配 | 成功 | 成功 | 失败 | 未执行 |
| 正常到 TLS | 成功 | 成功 | 成功 | 尚未判断 |

注意最后一格不是“成功”，而是“尚未判断”。这正是本章责任边界。

## 可运行示例：只使用本机回环

进入本章示例目录：

```bash
cd examples/encyclopedia/ch.foundations.network-layers
ruby verify.rb
```

验证器会：

1. 解析 `localhost`；
2. 在 `127.0.0.1` 的随机端口启动临时 TLS 服务；
3. 记录 TCP 对端、TLS 协议、临时证书 subject 与固定测试载荷；
4. 注入非法名称，断言执行记录只有 `dns`；
5. 注入关闭端口，断言执行记录只有 `dns,tcp`；
6. 注入证书主机名不匹配，断言失败层是 `tls`；
7. 注入连接后的有界读取等待，断言其不是 connect timeout。

预期摘要：

```text
normal: DNS -> TCP -> TLS -> trusted loopback payload
failure: invalid hostname stopped before TCP
failure: closed port stopped before TLS
failure: certificate hostname mismatch reached and failed at TLS
boundary: bounded local read wait expired after TCP connected
network-layers verification: PASS
```

最后一行与进程退出码 0 是自动断言通过的证据。它不证明公网、企业 DNS、真实 CA、Windows 或 Linux 已验证。

## 如何阅读三类典型错误

### 错误一：名称无法解析

可信的第一条信息通常含名称解析器或 `getaddrinfo` 失败。此时先核对输入、搜索域和解析环境。不要立即检查服务证书，因为根本没有进入 TLS。

推荐记录：

```text
target_name=bad host name
failed_layer=dns
tcp=not_run
tls=not_run
```

### 错误二：Connection refused

说明针对明确目标进行了 TCP 连接并快速收到拒绝。核对实际 IP、端口、监听地址、进程状态与防火墙主动拒绝策略。不要把它写成 DNS 失败，也不要猜证书。

推荐记录：

```text
resolved_ip=127.0.0.1
target_port=<closed-loopback-port>
failed_layer=tcp
result=refused
tls=not_run
```

### 错误三：certificate verify failed / hostname mismatch

这类错误意味着至少已经进入 TLS 处理。核对期望名称与证书 SAN、信任链、有效期和系统时间。若 TCP 失败，通常不会得到本次连接的证书主机名校验错误。

推荐记录：

```text
resolved_ip=127.0.0.1
tcp=connected
expected_name=api.factorycare.invalid
certificate_name=localhost
failed_layer=tls
application=not_run
```

错误文字可能随 TLS 库不同；稳定预言是失败层与验证关系。

## 常见错误与为什么不工作

### “能 ping 就说明服务正常”

`ping` 常使用 ICMP，目标服务可能使用 TCP；有些环境允许业务 TCP 却禁 ICMP，也可能相反。ping 成功至多提供一部分网络可达性线索，不证明目标 TCP 端口、TLS 或应用。ping 失败也不能单独证明业务端口不可达。

### “DNS 能解析，所以 443 肯定开着”

DNS 与 TCP 是不同阶段。解析只给地址信息；端口是否监听要通过 TCP 证据确认。

### “TCP 连上了，所以接口没问题”

TCP 不理解证书与业务请求。一个错误进程也能接受连接，一个卡住的服务也能完成握手。继续观察 TLS 与应用层。

### “换成 IP 就绕过所有问题”

直接用 IP 可能绕过名称解析，却破坏 TLS 主机名和 SNI 语义，导致服务选择错误证书或身份校验失败。若用 IP 作为诊断对照，仍需保留原始期望主机名，不能把对照方案直接变成生产配置。

### “把校验关掉就好了”

关闭 TLS 验证只是删除安全条件，不是修复证书。它会让“正确服务”和“攻击者/错误服务”都更容易被接受。

### “超时就是服务器挂了”

超时只说明在预算内未等到指定事件。错误路由、过滤、代理、名称结果、拥塞、服务阻塞和预算过短都可能产生类似观察。必须先写明超时阶段。

### “一次改 DNS、端口和证书，复跑成功就算定位”

同时改变多个条件只能证明组合状态不同，不能指出根因。单变量修复才保留因果证据：保持其他输入不变，只改名称、端口或证书中的一项，然后复跑同一预言。

## 调试记录模板

推荐把每次探测写成结构化记录：

```text
observed_at: 2026-07-16T10:00:00+08:00
environment: local-loopback-lab
input_name: localhost
resolved_addresses: [127.0.0.1]
selected_target: 127.0.0.1:<ephemeral>/TCP
connect_budget_ms: 500
tcp_result: connected
tls_expected_name: localhost
tls_result: verified
first_failed_layer: none
application_result: not_evaluated
```

失败记录仍保留同样字段。不要把缺失值默认为成功；使用 `not_run`、`not_observed` 或 `not_evaluated` 明确区分。

## 安全、隐私与操作边界

网络命令可能泄露内部域名、私有 IP、代理地址、用户名、Cookie、Token 与证书组织信息。分享前做最小脱敏，但保留诊断需要的层级关系。例如可把真实名称替换为一致的 `api.internal.example`，不要把不同目标全替换成同一个词导致证据失真。

基础学习中禁止：

- 扫描不属于你的主机或网段；
- 为了测试而关闭系统或企业防火墙；
- 把真实私钥、Token、内部证书包提交到仓库；
- 在不理解影响时修改 `/etc/hosts`、系统 DNS 或全局代理；
- 使用忽略证书校验作为长期配置；
- 对故障服务进行无界、高频重试。

配套资产只在回环地址创建临时监听，证书和私钥仅存在于进程内。即使是测试私钥，也不应让学习者形成“私钥可以随便提交”的习惯。

## FactoryCare 场景：工单 API 到底坏在哪一层

假设维修人员打开 FactoryCare 后提示“无法加载工单”。前端日志只写了 `NetworkError`，运维端知道正式名称是 `api.factorycare.example`、端口 443、预期 TLS。

### 场景一：名称拼写错误

客户端配置写成 `api.factorycare examlpe`。解析立即失败。结论应是“配置中的名称无法解析，TCP/TLS/HTTP 未执行”。下一动作是核对配置来源和变更记录，只修正名称后复跑。

### 场景二：服务只监听回环

服务器进程监听 `127.0.0.1:8443`，但另一台机器尝试连接服务器网卡地址的 8443。服务器本机测试成功，远端拒绝或超时。理想修复不是无条件绑定所有接口，而是先确认架构：是否应由反向代理对外监听、应用是否只应接受本机代理、主机防火墙如何限制来源。扩大监听面是安全决策。

### 场景三：证书仍覆盖旧名称

迁移后 DNS 与 TCP 都成功，但证书 SAN 只有 `old-api.factorycare.example`。这次故障首层是 TLS 身份校验。应用请求没有执行，不能声称后端返回 500。应修正部署证书或正式名称配置，并以严格验证复跑。

### 场景四：TCP 已连接但迟迟没有字节

这可能是 TLS 握手、应用处理、代理或资源耗尽等后续阶段等待。记录“TCP connected”和实际等待阶段，而不是笼统写 connect timeout。后续需要更细的 TLS 或 HTTP 计时证据。

### 一份合格故障摘要

```text
已确认：名称在客户端环境解析到目标地址，目标 TCP 端口建立连接；
首个失败：TLS 主机名校验，证书未覆盖输入名称；
未确认：HTTP 请求、鉴权、工单服务与数据库均未执行或未观察；
下一步：核对证书 SAN 与部署名称，只修复该项后严格复跑；
禁止动作：不使用忽略证书校验，不上传含内部凭据的详细跟踪。
```

它的价值不在于字多，而在于不越过证据边界。

## 与浏览器/前端错误的对照

浏览器或 JavaScript 往往把多种底层失败折叠成“fetch failed”或 `TypeError`，并出于安全原因隐藏部分细节。这不表示底层只有一个阶段。前端可记录脱敏目标、开始时间、超时/取消状态和是否收到 HTTP 响应；更底层的 DNS、TCP 与 TLS 证据通常要在受控终端、网关或服务端观测中补齐。

不要让前端根据一个通用异常自行宣告“DNS 故障”。它只能准确说“未获得可用响应”；具体首层需更多证据。

## 速查表

| 层/对象 | 主要问题 | 成功证据示例 | 常见失败 | 成功仍不证明 |
| --- | --- | --- | --- | --- |
| 名称/DNS | 名称对应哪些地址 | 本次地址列表 | 非法名、不存在、解析超时 | 端口监听 |
| IP | 数据发往哪个地址 | 实际选择地址与路由结果 | 无路由、错误地址 | 进程正确 |
| 端口/监听 | 主机上哪个 TCP 端点 | 明确地址、端口、协议 | 未监听、绑定范围错误 | 应用健康 |
| TCP | 能否建立字节流 | connected、对端、耗时 | refused、connect timeout | TLS/业务成功 |
| TLS | 能否加密并验证身份 | 协议、链、主机名通过 | 不信任、过期、名不匹配 | 鉴权与业务成功 |
| 应用 | 后续协议发生什么 | 本章不判断 | 本章不判断 | — |

### 四句边界口诀

1. 名称解析成功，不等于端口开放；
2. 端口连接成功，不等于身份正确；
3. TLS 验证成功，不等于业务成功；
4. 前层失败，后层只能写未执行。
