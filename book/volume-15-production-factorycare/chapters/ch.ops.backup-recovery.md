# 备份、恢复、RPO/RTO 与恢复演练

数据库执行了一次成功的备份命令，并不等于系统已经具备恢复能力。退出码只能证明某个进程在某个时刻按自身规则结束；它不能证明文件没有在传输后损坏、解密密钥仍可取得、所需 WAL 完整、恢复步骤可执行、恢复点符合业务容忍度，更不能证明恢复后的工单事实仍然成立。可靠的备份体系必须从业务损失目标倒推备份范围与频率，再用隔离恢复和业务不变量形成闭环。

本章只负责 FactoryCare PostgreSQL 数据的备份政策、校验、保留、恢复点和恢复演练。它会关联容器卷、事务一致性和领域不变量，但不替代对象存储/KMS 的完整建设，不把高可用副本当备份，也不承诺未经演练的命令能在事故中工作。Java 服务仍拥有工单状态、权限和最终写入规则；备份系统保存事实，恢复验收读取这些事实，不能借恢复脚本重写业务历史来让测试“变绿”。

稳定核心是：目标先于工具；备份与密钥隔离；校验不能替代恢复；恢复必须隔离；RPO/RTO 用时间线测量；数据库可连接不等于业务正确。PostgreSQL 18 的命令、增量备份能力、Docker/Compose 和 Ubuntu 26.04 是会变化的版本表面，执行前必须核对实际版本和官方文档。

## 1. 先定义损失，而不是先选命令

RPO（Recovery Point Objective，恢复点目标）回答“最多允许丢失多近的数据”。若事故发生在 12:10，最终可恢复到 12:05，则这次实际数据间隙是五分钟。声明 RPO 为五分钟，不代表每次都自动满足；它要求备份或 WAL 归档链在最坏情况下仍能覆盖该窗口，并要求测量最后一个可证明恢复点与事故时刻的差。

RTO（Recovery Time Objective，恢复时间目标）回答“从约定的事故起点到业务恢复到约定服务水平，最多允许多久”。起点必须写清：监控首次发现、人工宣布灾难、还是执行恢复命令；终点也必须写清：PostgreSQL 启动、只读查询通过、Java API 健康、还是完整业务不变量和关键路径通过。把下载备份的五分钟称为 RTO，会漏掉决策、取密钥、建隔离环境、回放 WAL、验证、切流和沟通时间。

RPO/RTO 是目标，不是观测结果。每次演练要同时记录 objective 与 actual。目标来自业务影响分析：设备报修现场能否重新提交？已完成工单丢失会不会造成合规问题？幂等记录丢失是否会让重试重复创建？高价值事实可能要求更小 RPO，辅助缓存可以重建。若所有表都简单写成“零丢失、五分钟恢复”，成本和技术约束通常没有被诚实讨论。

一个可审计声明应至少包含：系统和数据范围、灾难类型、目标 RPO/RTO、恢复终点定义、责任人、依赖、演练频率、例外与批准者。例如“单区域存储不可用时，将 FactoryCare 主库恢复到隔离的新集群；工单、状态历史、幂等记录和 Flyway 历史通过；实际恢复点距离宣布事故不超过五分钟，从宣布到代理关键路径通过不超过四十五分钟”。

## 2. 明确备份范围

PostgreSQL 官方文档把主要方法分为 SQL dump、文件系统级备份和连续归档/PITR。它们不是互斥的“高级/低级”排名，而是不同恢复需求的工具。逻辑 dump 便于选择数据库或对象、查看内容和跨某些环境迁移，但大库导出/导入耗时，不能单独提供任意时间点恢复。物理 base backup 复制整个集群，适合作为 PITR 起点；它包含集群级文件语义，不能像 SQL 文本那样任意挑表。连续归档保存 WAL，使 base backup 后的变化可回放到目标时间或恢复点。

范围清单不能只写 `factorycare` 数据库名。至少检查：业务 schema、角色与授权、扩展、序列、函数、触发器、行级安全策略、Flyway schema history、跨库依赖、tablespace、外部对象存储引用、消息积压、搜索索引以及配置。`pg_dump` 的数据库对象范围与 `pg_dumpall --globals-only` 的角色/表空间范围不同；物理集群备份又有不同边界。恢复方案必须说明哪些内容由数据库备份覆盖，哪些需要独立备份或可重建。

Compose 命名卷只解决容器删除后的本机持久化，不是备份。数据库副本也不是备份：误删、恶意更新和逻辑错误可能迅速复制到所有副本。快照若与源数据、凭据和管理员权限位于同一故障域，也可能在账号或区域事故中一起消失。真正的备份要有独立保留、不可变或受控删除策略，并能从主系统故障中幸存。

## 3. 备份计划与恢复链

计划由恢复链决定，而不是由 cron 表看起来整齐决定。若采用每周全量 base backup 加连续 WAL，任一恢复点依赖 base backup、相关增量链（若使用）和从起点到目标点的 WAL。删除链中间的一段，会让后续文件都失去恢复价值。若只做每日逻辑 dump，最坏 RPO 接近两个成功 dump 之间的间隔，而且导出完成时间、上传完成时间和可用恢复点并非同一时刻。

计划字段建议包含：作业 ID、工具与版本、源集群身份、备份类型、开始/结束时间、事务/LSN 边界、WAL 范围、备份内容位置、manifest 身份、加密 key ID、保留类别、校验状态、最近恢复演练、过期时间。不要在清单中保存密钥值；只保存可审计的密钥引用与版本。

高峰期备份会占用 I/O、CPU、网络和 WAL sender。排期要结合业务负载，但“避开高峰”不能成为永不测试高峰故障的理由。演练应覆盖正常备份、较大数据量、低带宽、密钥轮换和跨区域取回。并发运行多个 `pg_basebackup` 在技术上可能允许，但官方文档也提示通常从性能角度一次一个更好；实际限制必须在自身环境测量。

## 4. 保留策略与可删除性

保留策略回答“保留什么、多久、为什么、谁能删”。常见分层是近期高频恢复点、较长周期全量和合规归档，但不能机械照抄“日七、周四、月十二”。先列事故发现延迟：误删可能数小时发现，慢性数据污染可能数周才发现，勒索事件可能需要回到凭据泄漏前。然后让保留窗口覆盖这些威胁，同时计算存储、取回和恢复时间成本。

删除前必须证明剩余链完整。增量备份不能独立使用时，保留程序要理解其父链；WAL 的安全删除边界取决于所有需要的 base backup 与目标时间。生命周期规则若仅按对象年龄删除，可能先删掉仍被较新恢复点依赖的对象。每次删除动作应生成计划、依赖分析和审计记录，并留有取消窗口。

备份目录不是普通共享盘。写入主体与删除主体应分离，生产数据库凭据不应同时拥有历史备份批量删除权限。对象锁、版本化、跨账号/跨区域副本可以降低共同失效，但仍需验证成本、保留和紧急访问流程。保留过长也有风险：个人数据、密钥生命周期和法规删除要求可能冲突，需要安全与合规共同决策。

## 5. 加密与密钥故障域

需要区分传输加密、存储加密和应用层/备份层加密。TLS 保护传输链路；对象存储服务端加密保护介质；客户端或备份工具加密可以在上传前形成密文。选择哪层取决于威胁模型，但清单必须记录算法/服务、key ID、版本和解密权限证据。只写“云盘已加密”无法回答管理员误配和跨账号读取风险。

信封加密的基本思想是：随机数据密钥加密备份，受 KMS 管理的主密钥包裹数据密钥；备份保存密文和被包裹的数据密钥，不保存可直接使用的主密钥。密钥服务、备份对象和操作权限应尽量位于不同故障域。若加密备份和唯一解密密钥放在同一目录、同一账号且由同一删除权限控制，区域或账号事故会同时摧毁二者。

密钥轮换要回答旧备份如何解密。立即销毁旧 key 版本会让保留期内备份变成不可恢复密文；永不轮换又扩大暴露。策略应把备份过期、key 版本禁用、恢复演练和销毁审批连接起来。演练必须用与事故相同的受控取钥路径，不能临时从工程师电脑复制明文密钥来“证明”恢复。

本章示例中的 test-only 包络只用于验证流程和故障门禁，不是生产密码学。真实方案应使用经过评审的 KMS/加密库，不自创 XOR 或密钥派生算法。日志也不能输出连接串、备份口令、KMS 返回的明文数据密钥或完整用户数据。

## 6. 事务一致性与恢复点

一致备份必须对应数据库能够解释的状态，而不是把多个表在互不相关的时刻拼在一起。PostgreSQL 的逻辑导出和物理备份有各自的一致性机制；外部脚本逐表 `COPY` 而不使用一致快照，可能在工单更新事务中间读取：主表已变为 `CLOSED`，状态历史还未提交，或幂等记录存在但目标工单不可见。

领域不变量比“每张表能 SELECT”更强。FactoryCare 可验证：每个工单状态属于定义集合；状态历史序号连续；最后一条历史状态与工单当前状态一致；幂等键唯一；幂等结果引用存在的工单；外键和唯一约束有效；关键计数与备份清单预期一致。Java 状态机仍是规则来源，恢复脚本只能读并验证，不能看到不一致后自动补历史或改当前状态。

数据库与外部对象可能无法得到单一分布式快照。例如附件存对象存储，数据库只保存对象 key。策略要决定先写对象再提交引用、版本化对象、延迟删除和恢复后孤儿扫描，使某个数据库恢复点仍能解析附件。否则数据库恢复成功却丢附件，业务仍不可用。

## 7. PostgreSQL 18 物理备份与校验

截至 2026-07-24，PostgreSQL 18 官方文档说明 `pg_basebackup` 可从运行集群取得全量或增量 base backup。增量结果不能直接启动，必须先与其依赖链通过 `pg_combinebackup` 合成为全量。`pg_basebackup` 总是备份整个集群，不能选择单个数据库；选择性备份应使用 `pg_dump` 等工具。当前 18 系列文档页面显示 18.4，但实验必须记录实际服务端和客户端工具的完整版本，不能只写“18”。

base backup 可生成 backup manifest。manifest 描述预期文件、大小、修改时间和可选校验和，并包含自身 SHA-256。若威胁包括可修改备份的攻击者，manifest 本身应单独安全保存或验证；攻击者同时替换数据和 manifest 时，仅比较二者不足以建立可信来源。

`pg_verifybackup` 会检查 manifest、文件存在性/大小、校验和以及所需 WAL 的可读/解析范围（具体能力受格式和选项影响）。官方文档明确强调：它不能执行服务器实际恢复时的所有检查，即使用过它，仍应做 test restore，并确认数据库正常且包含正确数据。因此正确证据链是“作业成功 → 对象/manifest 身份 → `pg_verifybackup` → 隔离恢复 → 技术检查 → 业务不变量”，而不是在第一步停止。

客户端工具要与备份版本匹配，尤其 WAL 验证具有版本相关性。命令示例必须使用测试变量和隔离路径，先执行 `--help`/版本检查，再由双人评审确认目标。教材不提供可复制到生产的固定密码、主机名或删除命令。

## 8. WAL 归档与 PITR

PITR 的基础是一个可用 base backup 加连续 WAL。`wal_level`、`archive_mode`、归档命令/库、WAL 保留和监控需按官方版本配置。只看到 `archive_command` 最近返回零，不能证明所有段按顺序、安全、及时到达目标；要监控失败、积压、最后归档时间、对象身份和缺口。

事故恢复时选择目标时间、事务或恢复点。时间要带时区，且与事故时间线统一；“恢复到 10:30”在跨时区或夏令时环境中不够精确。目标太晚可能回放误删，太早会扩大业务丢失。先在隔离集群恢复候选点，验证包含最后一个应保留事实且不包含首个已知坏事实，再决定切换。

PostgreSQL timeline 让恢复后的集群形成新的历史分支。演练记录应保存源 system identifier、timeline、起止 LSN、目标和最终一致点，避免把来自另一集群或旧 timeline 的 WAL 混入。恢复后继续归档也要使用不会覆盖旧历史的命名与权限。

PITR 不能恢复被外部系统覆盖的事实，也不能自动撤销已发送通知、外部支付或设备动作。数据库回到过去后，与外部世界可能分叉；切换前要制定对账、补偿和幂等重放策略。

## 9. 隔离恢复的安全护栏

恢复演练必须创建新的、可销毁且网络隔离的目标。至少有三重护栏：目标环境标签不是 production；目标数据目录/数据库为空；网络和凭据无法写生产依赖。仅靠操作员目测终端提示符不够。脚本应对环境 ID、集群 ID、允许列表和空目标做 fail-closed 检查，任一未知值立即退出。

恢复实例不要复用生产服务发现名称、消息队列、邮件、Webhook、推送和对象删除权限。恢复出的应用若启动后台任务，可能向真实用户重复通知或消费生产消息。默认阻断外连，只开放验证客户端；若必须测试外部集成，使用专用 sandbox 和去敏数据。

生产数据进入隔离环境仍是敏感数据。访问、磁盘加密、日志、保留和销毁都应受控。性能测试或培训不应随意复用恢复的生产库；本章恢复演练与下一章的合成性能数据是不同用途。演练结束后按证据保留要求保存报告，然后可验证地销毁目标与临时密钥授权。

## 10. 恢复演练步骤

第一步冻结演练合同：事故类型、候选备份 ID、目标 RPO/RTO、起止事件、恢复终点、观察者和中止条件。第二步创建隔离目标并验证空、网络断开、制品版本和磁盘容量。第三步从独立位置取得 manifest、密文和 key 授权，保存每个对象身份与访问审计。

第四步在不修改备份的前提下执行完整性校验。第五步解密/组合备份并启动恢复；若做 PITR，配置目标并保存 WAL 取回证据。第六步等待数据库达到一致状态，但不能只看端口开放；检查服务日志、恢复终点、timeline、schema、扩展和 Flyway history。第七步执行技术检查和 FactoryCare 业务 oracle。第八步用同一声明计算 actual RPO/RTO，记录失败阶段、人工等待和可并行项。

第九步故意注入一个失败并验证门禁：破坏副本中的字节、撤销 key 权限、移除 WAL、指向非空目标或制造不一致夹具。第十步修复后从干净目标重跑原过程，不能只跑一个缩短版。最后形成改进项、责任人和日期；工具安装或文档修改不等于改进完成，下一次演练要验证。

## 11. FactoryCare 恢复 oracle

oracle 是对恢复结果的可执行判据。技术层可包括：数据库接受受限连接；预期数据库/schema/扩展存在；Flyway history 处于允许版本；约束校验；行数和抽样/聚合 hash；没有恢复错误。业务层可包括工单状态与历史一致、幂等记录唯一且可重放、设备引用存在、审计时间顺序合理、关键 API 只读 smoke 返回预期数据。

行数相同并不证明内容相同，整库 hash 也可能因物理顺序和非业务字段变化而不稳定。建立规范化业务摘要：按主键排序，选择受控字段，统一编码/时区，分别计算表级计数与摘要。对超大表可结合约束、分区统计、抽样和关键范围；但抽样未覆盖部分必须标记未验证。

涉及个人数据时，报告保存汇总和不可逆身份，不复制原始姓名、电话或附件。若需要展示一条工单，使用合成 fixture。测试查询账号应只读，恢复工具账号与业务验证账号分离，这能发现权限/角色漏备份，而不会给验证脚本修改事实的机会。

本仓库 `examples/encyclopedia/ch.ops.backup-recovery/` 的合成快照验证工单、状态历史和幂等记录。它的输出是“Python 夹具通过”，不是“PostgreSQL 已恢复”。`labs/...` 的记录门禁能拒绝只看退出码、密钥同故障域、生产目标和事务中间态；真实 T4 证据仍需独立 PostgreSQL 环境。

## 12. 测量 RPO 与 RTO

RPO actual 不是“备份每五分钟执行一次”。应以事故时刻减去最后一个经验证可恢复的一致点。作业每五分钟触发，但上传、归档或 manifest 校验延迟七分钟，实际 RPO 可能大于目标。PITR 中恢复到的终点可能因 WAL 缺口早于预期，也必须使用实际终点。

RTO 时间线建议包含：检测、宣布、授权、准备基础设施、取回、校验、解密/组合、数据库恢复、WAL 回放、业务验证、决策、切流、观察。总时间与各阶段同时保存。只优化数据库回放而忽略半小时审批等待，无法改进端到端 RTO。

演练环境比生产更小会低估时间；从本地缓存恢复会低估跨区域取回；预先解密会绕过密钥事故。报告必须记录环境差异，并把结果称为“该条件下测量值”。容量模型可以估计未来时间，但只有真实演练测量值能作为已验证证据。

## 13. 四个故障的首个可信证据

只验证命令退出码：失败阶段是备份验证。首个可信证据不是后续“数据库连不上”，而是缺少或失败的 manifest/校验记录。修复为保存对象身份、运行适配版本的校验，再做隔离恢复；残余风险是校验仍不能覆盖服务器启动与业务数据。

备份与密钥同位置：失败阶段是备份设计。首个可信证据是清单中 backup failure domain 与 key authority 相同或由同一删除权限控制。修复为分离存储、权限和恢复授权，并演练主账号不可用；残余风险包括共同身份提供商或网络依赖。

恢复覆盖生产：失败阶段是目标选择，必须在任何写入前中止。首个可信证据是目标环境/集群 ID 命中 production 或目标非空。修复为隔离账号、独立网络、目标 allowlist 和双重空目录检查；不能把“操作员很小心”当控制。

事务中间状态：失败阶段可能是备份捕获或业务 oracle。首个可信证据是恢复后最后状态历史与当前工单不一致、幂等记录悬空，随后才回溯一致快照/恢复点。修复备份方法或跨系统提交策略，重建干净恢复；不能直接改恢复数据掩盖来源缺陷。

## 14. 自动化、告警与运行手册

自动化要把每个阶段写为可重入步骤，并对身份严格校验。作业失败、持续时间异常、大小突变、WAL 归档滞后、manifest 缺失、key 即将禁用、恢复演练过期都要告警。零字节备份可能快速返回成功；大小突增可能来自配置泄漏或异常表，不能只监控退出码。

运行手册应在主系统不可用时仍可访问，包含责任角色、紧急权限、官方工具版本、依赖位置、恢复目标护栏、停止条件、验证 oracle 和沟通模板。不要在手册中写明文 secret。定期由不熟悉脚本的人按手册演练，能发现隐藏知识和失效链接。

自动恢复到生产通常风险很高。可以自动创建隔离目标、校验和生成候选报告，但最终灾难切换需明确授权与观测。若组织选择全自动，仍要证明错误目标、损坏备份、落后恢复点和外部副作用会 fail closed。

## 15. 版本事实与官方来源

本章于 2026-07-24 核对以下一手资料：PostgreSQL 18 [Backup and Restore](https://www.postgresql.org/docs/18/backup.html)、[`pg_basebackup`](https://www.postgresql.org/docs/current/app-pgbasebackup.html)、[`pg_verifybackup`](https://www.postgresql.org/docs/18/app-pgverifybackup.html) 和 [Backup Manifest Format](https://www.postgresql.org/docs/18/backup-manifest-format.html)。当前 18 文档展示 18.4；安装环境可能不同，执行时以 `server_version` 和工具 `--version` 证据为准。

Docker、Compose 和 Ubuntu 26.04 是本章版本表面，但本章合成资产没有启动容器或 Ubuntu 虚拟机。不能因主机安装了 Docker CLI 就声称 PostgreSQL 容器、卷或真实恢复已验证。真实验收要记录宿主架构、Engine/Compose、镜像 digest、PostgreSQL 服务端/客户端和操作系统版本。

## 16. 学习与验收

先运行示例和 lab 的 `verify.sh`，解释每个绿色断言实际证明什么、没有证明什么。公开练习故意是红色：当前实现只看目标为空，漏掉生产环境与密钥分离；学习者修复后要能说明为什么三个条件是“并且”关系。私有答案只用于提交后核对。

最终构建证据必须来自真实隔离 PostgreSQL：加密备份身份、外置 key 引用、manifest/校验、恢复日志、RPO/RTO 时间线、表级摘要、FactoryCare 不变量、四类故障注入、修复重跑。若没有 PostgreSQL、KMS 或对象存储，只能标为未验证，不能用合成 fixture 代替 T4 过关。

120 秒讲解应覆盖：RPO 与 RTO 的区别；逻辑 dump、物理 base backup、WAL/PITR 的范围；为什么退出码和 `pg_verifybackup` 都不足以单独证明可恢复；为什么目标必须隔离；为什么 Java 业务不变量是最终 oracle。越界反例是“恢复脚本发现历史不一致后自动改主表，使测试通过”——那是在制造新事实，不是在验证备份。

## 17. 复盘清单

- 目标是否由业务损失定义，并分别记录 objective 与 actual？
- 备份范围是否包含角色、扩展、迁移历史和外部依赖边界？
- 恢复链、WAL 与增量父链是否在保留删除前做依赖分析？
- 密文、manifest、key authority 和删除权限是否跨故障域？
- 是否在空的非生产目标完成过解密、启动、PITR 和业务验证？
- 是否验证工单状态历史、幂等记录、约束、计数和规范化摘要？
- RTO 是否从声明的事故起点量到真实服务终点，而不是只量命令？
- 是否保存工具版本、集群身份、timeline/LSN、制品身份和原始日志？
- 故障修复后是否从干净目标重跑原验证，并陈述仍未覆盖的风险？

能回答这些问题，才说明团队拥有一条有证据的恢复路径。备份文件的存在只是输入；隔离恢复后的正确业务事实、可重复步骤和实测时间，才是恢复能力。

## 18. 桌面推演、组件演练与完整演练

桌面推演让值班、数据库、安全和业务负责人沿时间线回答“谁发现、谁授权、从哪里取清单、密钥服务不可用怎么办、何时决定切换”。它成本低，适合发现责任与文档空白，但没有执行命令，不能证明字节或工具可用。报告必须写成 tabletop verified，而不是 restore verified。

组件演练可只验证对象取回、key 授权、`pg_verifybackup`、PITR 某一段或业务 oracle。它能缩短反馈，但结论只覆盖所测组件。完整演练从声明事故开始，在新的隔离基础设施完成取回、恢复、业务校验和候选切换，用统一时间线测 RPO/RTO。三个层级互补，不能用多次桌面会议替代至少定期一次完整恢复。

演练频率应由变化和风险触发：PostgreSQL 大版本、备份工具、KMS 权限、对象存储策略、schema/数据量、运行手册或人员职责变化后，应重新验证相关路径；仅按年度日历可能让新链路长期未测。反过来每次小改都做全量恢复成本过高，可用风险分层选择组件或完整演练，并明确剩余未验证范围。

对失败演练不要修改验收词义。例如 RTO 超时后把终点从“API 关键路径通过”改成“数据库启动”，会把红线改写成绿色。保留原目标与 actual，另开目标变更决策；若业务确实接受更宽目标，也应由业务负责人批准并重新计算架构和保留，而不是由执行者事后解释。
