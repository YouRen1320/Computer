# 需求、边界、容量、可靠性与系统设计取舍

<!-- BEGIN GENERATED LEARNING PREREQUISITES -->
## 学习前检查

以下章节是本章的硬前置。开始前，请先完成并验证对应能力：

- [《容量、负载模型、性能测试与瓶颈证据》](ch.ops.capacity-performance.md)：容量方案必须来自负载模型、尾延迟与瓶颈证据。
<!-- END GENERATED LEARNING PREREQUISITES -->

> 本章唯一职责：从功能需求、质量属性、数据与流量约束推导系统边界、容量、可靠性和一致性方案，写清取舍与演进路径。架构图不是把 Java、Redis、Kafka、微服务、Kubernetes 和 AI 图标连起来；每个组件都必须能追溯到需求或约束。

## 1. 学习结果与证据边界

学完后，你应能在 120 秒内解释：功能需求说明系统做什么，质量属性说明在什么条件下做到何种程度；系统上下文先划定人与外部系统的边界；服务或模块边界应从业务不变量、数据所有权、变化与团队约束推导；容量估算必须公开假设、公式和单位；可靠性设计要覆盖探测、缓解、恢复与残余风险；一致性是业务取舍，不是“强一致/最终一致”标签；ADR 记录决定、被拒方案和触发演进的证据。

本章独立构建任务是为“南昌现场服务平台”产出：需求假设、上下文、关键数据流、可复算容量、至少三类故障模式、SLO 和分阶段演进 ADR。你还要能诊断四类失败：先选微服务再找需求、容量单位混乱、只画成功路径、把一致性模型当免费标签。

附带工件有严格证据边界：`examples` 和 `labs` 只在固定合成输入上验证公式与设计门禁；`exercises` 故意为红；`solutions-private` 是参考结构。它们没有访谈真实南昌客户，没有读取生产遥测，没有压测 Java/PostgreSQL，也没有注入真实网络或数据库故障。因此绿色脚本只能证明“这个设计包内部可追踪、可复算”，不能证明系统达到真实容量或 SLO。

## 2. 系统设计从问题开始，而不是从组件开始

系统设计是把模糊目标逐步变成可验证决定的过程。一个可靠顺序是：

```text
业务目标与参与者
  → 功能需求与业务不变量
  → 质量属性、约束与优先级
  → 系统上下文和数据流
  → 容量假设与数量级
  → 边界、数据所有权与接口
  → 故障模式、SLO 和一致性取舍
  → 候选方案比较与 ADR
  → 原型、负载/故障实验、反馈
  → 分阶段演进
```

如果一上来就说“采用微服务、Kafka、Redis、Kubernetes”，你还无法判断这些成本是否解决了真实问题。每引入一个组件，都增加部署、监控、安全、数据一致性、备份、升级和人员认知成本。设计的价值不在组件数量，而在用可接受成本满足最重要的需求，并明确没有满足什么。

系统设计也不是预测未来十年。它需要选择今天足够简单、能验证、又留下合理演进接口的方案。过早为想象中的亿级流量建平台会拖慢交付；完全忽略增长与故障则会把迁移变成事故。好的设计用**触发条件**连接今天与未来，例如“当单一模块持续占 70% 资源且独立扩容通过成本评审时再拆分”，而不是“以后可能变大，所以现在微服务”。

## 3. 功能需求：谁在什么条件下完成什么结果

功能需求应围绕参与者与可观察结果，不围绕页面或技术。FactoryCare 的示例：

```text
FR-1：经授权的现场技术员可以更新自己租户内已分配工单的状态；
      非法状态迁移、跨租户访问和重复请求必须得到确定结果并写入审计。
FR-2：调度员可以分派未关闭工单；并发分派不能产生两个有效负责人。
FR-3：租户管理员可以查看本租户设备与工单统计；不能观察其他租户明细。
```

这比“做一个工单 CRUD”更有设计信息。它暴露身份、租户范围、状态机、并发、幂等和审计不变量。系统边界和事务选择由这些不变量驱动。

对每条功能需求追问：主要参与者是谁？前置条件是什么？输入、输出和失败分别是什么？状态如何改变？哪些规则必须在同一原子边界成立？谁是事实所有者？是否需要审计？重复、乱序、并发和超时会怎样？

功能需求也要声明非目标。例如第一阶段不提供离线冲突自动合并，不支持跨租户工单共享，不承诺 AI 自动改变工单状态。非目标可以防止架构被隐含需求无限扩张。

### 3.1 业务不变量先于数据库表

不变量是无论接口、客户端或后台任务如何变化都必须成立的规则。例如：

- 工单只能属于一个租户；
- 所有业务写入都经过当前身份和租户授权；
- `CLOSED` 工单不能未经批准回到 `IN_PROGRESS`；
- 同一个幂等键与同一语义请求最多产生一个业务结果；
- 每次受保护状态变更都有可关联审计；
- AI 建议不能直接成为业务事实。

这些规则决定 Java 业务 API 和 PostgreSQL 是权威边界。Vue、uni-app、Flutter 只是交互客户端；Python/AI 只产生可重建派生结果。若把同一个工单状态同时交给 Java、Python 和客户端写，冲突解决与审计会比业务本身更复杂。

## 4. 质量属性：在可测条件下定义“好”

“高性能、高可用、安全、易扩展”不是可设计需求。质量属性应写成场景：在某个来源和条件下发生刺激，系统哪个部分响应，响应结果和量度是什么。

示例：

```text
QA-1 可用性：在滚动 30 天窗口内，经过授权且语义有效的工单写请求，
              99.9% 返回约定业务结果；计划维护是否计入需预先声明。
QA-2 延迟：在声明峰值负载、固定制品与代表性数据集下，
            工单详情读取 p95 < 300ms，错误率 < 0.1%，生成器未饱和。
QA-3 恢复：数据库不可用演练中，核心业务在 30 分钟内恢复，
            数据恢复点损失不超过 5 分钟，并通过租户/状态/审计校验。
QA-4 安全：跨租户对象访问在 Java 授权层和数据库查询范围均被拒绝，
            拒绝事件有审计，但响应不泄漏对象存在性。
QA-5 可演进：第一阶段由一个小团队发布；模块接口必须允许未来在证据触发时抽取，
              当前不承担分布式事务和多服务值班成本。
```

质量属性经常冲突。同步复制可能降低数据丢失，但增加写延迟和可用性取舍；更长缓存提高读吞吐，但增加陈旧窗口；细粒度微服务提高独立部署潜力，却增加网络故障、观测与一致性成本。设计不是寻找所有属性同时最优，而是让优先级和代价透明。

### 4.1 约束不是偏好

约束包括法规、预算、团队、截止日期、已有系统、部署环境和技能。例如：团队三人、主要招聘市场偏 Java、已有 Vue3 与 Flutter 能力、部署在一组 Ubuntu 服务器、必须支持租户审计。偏好则是“我喜欢某框架”。约束可以决定方案；偏好只能在候选方案都满足需求时参与选择。

对每项约束标注来源、负责人、验证日期和可变性。所谓“必须微服务”若找不到业务、合规或组织来源，可能只是未经验证的偏好。

## 5. 系统上下文：先画边界，再画内部

上下文图回答系统是什么、谁使用、依赖哪些外部系统、哪些东西不属于它。不要一开始画类或容器。南昌现场服务平台的上下文可以描述为：

```text
技术员 / 调度员 / 租户管理员
              │ HTTPS
              ▼
     FactoryCare 业务系统
       │       │       │
       │       │       └── 通知提供商
       │       └────────── 身份提供商
       └────────────────── Python AI 派生服务

业务记录系统：FactoryCare Java API + PostgreSQL
客户端：Vue3 管理端、uni-app 小程序、Flutter App
AI：只返回建议/摘要/检索结果，不拥有工单状态和授权事实
```

每条跨边界数据流都应说明协议、身份、数据分类、重试/幂等、超时、事实所有者和失败语义。比如客户端请求超时后重试，Java API 必须用幂等键判断同一意图；不能让客户端直接连接数据库。Java 调 Python 时要限定时间和返回模式；Python 若需要业务数据，应通过 Java 以当前身份、租户、范围重新授权，不能持有“内部超级权限”。

上下文图还应标明信任边界。互联网、客户端、第三方通知和 AI 工具调用都不应被默认信任。认证证明是谁，授权决定当前动作能否访问当前对象；两者不能由客户端按钮是否显示来替代。

## 6. 模块与服务边界：围绕变化和不变量

边界可以是代码模块，也可以是独立进程。独立服务不是更“高级”的模块，而是增加网络、部署与运行成本来换取某些独立性。候选边界可从以下维度评估：

1. **业务能力与术语**：设备、工单、派工、租户身份是否有清晰职责？
2. **不变量和事务**：哪些状态必须原子改变？跨边界会不会引入补偿？
3. **数据所有权**：谁能写事实？其他模块如何读取？
4. **变化节奏**：是否由不同原因和团队频繁独立变化？
5. **容量特征**：某能力是否需要独立数量级扩容？
6. **故障隔离**：失败是否必须与核心流程隔离？
7. **安全边界**：是否需要不同权限、网络或数据保护？
8. **运维能力**：团队能否承担独立发布、监控、值班、备份与恢复？

对当前 FactoryCare，推荐目标是 **Java 模块化单体 + PostgreSQL 业务权威 + 可选 Python AI 派生服务**。工单、设备、租户、审计可有明确模块接口，但先作为一个部署单元，使核心状态机和审计能在清晰事务内完成。Python AI 因依赖、资源和失败语义不同，可以独立进程，但不能直接成为业务记录系统。

这不是永久拒绝微服务。如果出现多支独立团队、某模块有经测量的独立 10 倍扩容需求、发布耦合持续违反 SLO、法规要求物理隔离，才评估抽取。抽取前先验证模块边界和接口；代码内都互相访问表的“分布式单体”只会同时拥有两种缺点。

## 7. 容量估算：先算数量级，再谈机器

容量估算不是为了精确预测，而是暴露假设、找到数量级、识别最敏感变量并决定下一步测什么。所有数字必须写单位。`500 MB` 可能是十进制 500,000,000 byte，也可能有人误指 500 MiB=524,288,000 byte；混用会让复算失效。

### 7.1 一个可复算示例

假设全部为教学数据：

- 120 个组织（`org`）；
- 每组织 25 名技术员（`technician/org`）；
- 每人每天 80 次 API 请求（`request/technician/day`）；
- 活跃窗口 36,000 秒/天（`second/day`）；
- 峰值系数 6（无量纲 ratio）；
- 平均请求 1,200 byte/request，响应 2,800 byte/request；
- 每天新增 60,000 条记录（`record/day`）；
- 每条含索引等粗估 1,500 byte/record；
- 保留 365 day；两份存储副本。

日请求：

```text
120 org × 25 technician/org × 80 request/technician/day
= 240,000 request/day
```

峰值请求率：

```text
240,000 request/day ÷ 36,000 second/day × 6
= 40 request/second
```

峰值应用流量粗估：

```text
40 request/second × (1,200 + 2,800) byte/request
= 160,000 byte/second
```

一年含两份副本的记录容量粗估：

```text
60,000 record/day × 1,500 byte/record × 365 day × 2 copy
= 65,700,000,000 byte
```

这个结果没有包含 WAL、临时文件、膨胀、备份、日志、对象附件、索引差异、压缩和增长，因此不能直接拿去买 66GB 磁盘。它的作用是告诉你：附件可能比结构化记录更敏感；数据库与备份需分别建模；40 RPS 并不自动要求微服务；真实服务时间和连接等待仍需测量。

### 7.2 并发与 Little 定律

稳定区间可用 Little 定律做一致性检查：平均并发 `L = λ × W`。若到达率 40 request/s，平均在系统时间 0.125 s，则平均并发约 5。它不是线程池配置公式，因为尾延迟、突发、排队、外部调用和长连接会改变分布。它可以帮助发现报告矛盾：若声称稳定 40 RPS、平均 125ms，却观察到数百个持续请求，应继续找排队或度量口径问题。

### 7.3 从估算到验证

估算后设计负载实验：固定制品、配置、数据集和目标平台；区分热身与稳态；记录到达率、并发、p50/p95/p99、错误、资源、数据库等待和 trace；确认负载生成器没有先饱和；用同一输入比较修复前后；运行功能回归。静态计算和合成数组不是压测证据，开发机压测也不是生产容量证明。

应做敏感性分析：组织数翻倍、峰值系数从 6 到 12、附件比例上升、AI 调用延迟变大，哪个变量最先触发瓶颈？这比给出单一“最大 QPS”更能指导演进。

## 8. 关键数据流：写路径、读路径和派生路径

设计至少画三条数据流。

### 8.1 工单写路径

客户端携带身份、租户上下文、幂等键和期望版本调用 Java API；Java 认证、授权、校验状态迁移；在 PostgreSQL 事务中更新工单并写审计/可靠事件记录；提交后返回确定业务结果。若客户端超时重试，幂等记录返回原结果，不能重复推进状态。

该路径的业务权威在 Java/PostgreSQL。Redis 可加速读取但不拥有事实；消息投递可异步，但必须解决事务提交与消息发布的一致性，例如 outbox。直接让客户端写数据库会绕过授权和审计。

### 8.2 列表读取路径

客户端通过 Java API 提交过滤、分页和排序；Java 将当前租户与权限范围注入查询；PostgreSQL 返回业务事实；缓存命中时仍需确保键包含租户和授权语义。观察指标要区分总体延迟与特定租户/查询形状，避免平均值隐藏尾部。

### 8.3 AI 建议路径

客户端仍只调用 Java。Java 根据当前身份决定可访问对象，把最小必要内容传给 Python AI；Python 检索可重建索引、生成结构化建议并返回来源；Java重新校验对象范围和结果模式，把建议标记为派生内容。AI 超时、错误或索引陈旧时，核心工单流程应按声明策略降级，而不是把生成结果直接写为业务事实。

设计审查要问：Python 服务停一天，是否丢失唯一业务信息？如果答案是会，边界已经越权。正确答案应是可以从 Java 权威数据重建，最多损失缓存和派生结果。

## 9. 故障模式：设计失败路径，而不是只画箭头

故障模式记录至少包含：触发或原因、用户影响、探测、缓解、恢复、数据风险、残余风险和演练。以下三类是本章验收最低要求。

### 9.1 数据库不可用

影响：核心写入失败，读取可能部分可用。探测：业务写 SLI、连接/事务错误、数据库探针与资源指标关联。缓解：停止风险发布，明确拒绝写入或进入经过设计的只读模式，保留幂等键，避免无界重试。恢复：按批准 runbook 故障转移或隔离恢复，验证模式、租户、状态和审计。残余风险：RPO 内写入、复制滞后、逻辑破坏传播。

### 9.2 错误发布

影响：错误率、数据语义或兼容性回归。探测：canary 的功能 oracle、版本维度指标、错误预算和日志。缓解：停止 promotion、隔离 canary、保护数据库。恢复：若模式兼容则回到已验证制品，否则向前修复；运行原验收矩阵。残余风险：不可逆迁移、缓存/消息与旧版本不兼容。

### 9.3 Python/AI 不可用或派生索引陈旧

影响：建议、摘要、语义检索降级，核心工单仍应可用。探测：派生功能独立 SLI、索引新鲜度、调用超时与 trace。缓解：短超时、熔断、禁用建议并明确提示，不重试风暴。恢复：从 Java 授权数据重建派生索引，逐步开放。残余风险：短期建议缺失或陈旧；不能通过让 Python直接写工单来“提高可用性”。

还应考虑身份提供商失败、通知失败、磁盘满、证书过期、网络分区、热点租户、队列积压、备份不可恢复和观测链路失败。观测系统自身也会坏，因此关键验证需要业务探针和多源证据。

## 10. SLI、SLO 与错误预算：把可靠性变成可决策条件

SLI 是测量值，SLO 是目标，错误预算是允许未达成目标的空间。`99.9%` 必须说明事件、好事件、窗口和排除条件。例如：

```text
SLI = 约定时间内返回正确业务结果的授权、语义有效工单写请求数
      ÷ 全部授权、语义有效工单写请求数
SLO = 滚动 30 天 >= 99.9%
```

不能只统计 HTTP 2xx，因为返回 200 但没有持久化或跨租户错误属于坏事件。也不能把未授权请求全算失败，否则攻击流量会扭曲业务可用性。口径要在事故前定义。

错误预算策略把数字连接到行动：若短窗口和长窗口消耗都很快，暂停高风险发布、安排可靠性工作；若预算充足，可继续受控实验。SLO 不是承诺所有请求永不失败，也不是对每个内部组件都设同样目标。组件目标应从用户旅程推导。

截至 2026-07-24，OpenTelemetry 官方规范页面显示 Specification 1.59.0、Semantic Conventions 1.43.0，OTLP 页面显示 1.11.0。版本会变化。设计应依赖稳定的观测概念：资源标识、服务版本、trace/span 关联、指标属性基数控制、日志与 trace 关联；具体 SDK、collector 配置和语义字段要按目标版本重新核验。

## 11. 一致性取舍：先写业务异常，再选模型

“强一致”与“最终一致”不是架构装饰词。应先问某个延迟或冲突会造成什么业务错误、能否检测、能否补偿、用户能否理解。

### 11.1 核心状态机

工单从 `ASSIGNED` 到 `IN_PROGRESS`、从 `IN_PROGRESS` 到 `CLOSED` 涉及授权、当前版本和审计。两个调度员并发分派时，不能都成功覆盖。这里适合在单个 PostgreSQL 事务内用约束、条件更新或锁保护不变量，并返回冲突语义。把它拆成多个服务后，需要额外协议维持同样规则，没有免费收益。

### 11.2 通知

状态提交后发送短信可以异步。业务事实先在数据库提交，通过 outbox/可靠投递让通知最终发生；重复投递必须幂等。通知晚几秒通常可接受，但工单状态不能因通知提供商失败而回滚成未知。这里的最终一致有明确代价：延迟、重复和失败补偿。

### 11.3 AI 建议与检索索引

建议和向量索引是派生数据，可以落后权威数据一个声明窗口，并通过版本/更新时间提示新鲜度。若用户刚更新工单，旧建议不得覆盖新状态。删除或权限变化要优先传播；每次工具调用仍由 Java 当前授权过滤。所谓最终一致不能成为临时越权的借口。

### 11.4 可用性与分区

发生网络分区时，有状态系统无法同时无条件保证所有节点立即一致和所有请求成功。业务必须决定哪些操作宁可拒绝，哪些可排队，哪些可读取陈旧数据。对跨租户授权和关键状态迁移，错误接受通常比明确失败危险；对只读报表，标记新鲜度的旧数据可能可接受。设计文档要逐操作说明，而不是给整个系统一个标签。

## 12. ADR：记录为什么，而不只是记录什么

Architecture Decision Record 应短而可审计。建议字段：标题/状态/日期、上下文、需求与约束引用、候选方案、决定、理由、后果、被拒方案、验证计划、演进触发、回滚或替代路径。

FactoryCare 示例决定：

```text
决定：第一阶段采用 Java 模块化单体与 PostgreSQL 业务权威；
      Python AI 独立但只保存可重建派生数据；客户端只调 Java 公共 API。
理由：核心状态与审计需要清晰事务；当前团队和规模没有独立服务收益证据；
      AI 依赖与失败语义需要隔离，但不能拥有业务事实。
拒绝：立即微服务——增加网络、一致性和值班成本，无独立扩容/团队证据；
      Python 作为工单事实库——破坏授权、审计和恢复边界。
后果：必须执行模块依赖门禁；单制品发布影响范围较大；
      AI 服务失败可降级，派生索引需可重建。
触发：至少四支独立发布团队持续两个季度；某模块有实测 10 倍独立负载；
      模块化修复后发布耦合仍持续违反 SLO。
回滚：抽取失败时保留接口，恢复同制品部署，不迁移事实所有权。
```

ADR 不是永久圣旨。触发条件出现后重新评估；没有出现则不因潮流重写系统。若决定变更，新增 ADR 取代旧记录而不是抹掉历史。

## 13. 方案比较：显式展示成本与风险

对于第一阶段架构，可以比较：

| 方案 | 实现成本 | 迁移成本 | 主要风险 | 回滚难度 | 长期维护 |
| --- | --- | --- | --- | --- | --- |
| Java 模块化单体 + PostgreSQL + 派生 AI | 低到中 | 当前低；未来按证据抽取 | 模块边界退化、单制品影响范围 | 低 | 适合小团队，需依赖门禁 |
| 从第一天微服务 | 高 | 初始就承担 | 分布式事务、网络故障、观测和值班复杂度 | 高 | 只有独立团队/扩容收益时合理 |
| Java 与 Python 都写业务库 | 表面中 | 数据统一代价极高 | 权威冲突、越权、审计与恢复不清 | 很高 | 不推荐 |

推荐不是因为单体“永远最好”，而是当前证据下以最低不可逆成本满足不变量，并为演进保留接口。若真实需求显示法规隔离或多个团队独立发布，结论可以改变。

## 14. 分阶段演进路径

### 阶段 0：可验证单机/开发环境

建立 Java 模块、PostgreSQL 模式、客户端 API 合同、Python 派生边界；实现功能测试、租户/状态不变量、日志/指标/trace 基础和备份恢复练习。目标是正确性和可观察性，不声称生产高可用。

### 阶段 1：小规模生产

部署可追溯制品，建立反向代理/TLS、配置密钥、数据库备份、健康/就绪、SLO、告警、发布门禁和事故 runbook。以真实遥测替换部分容量假设。仍保持单一业务权威。

### 阶段 2：按测量扩容

针对实际瓶颈优化查询、索引、缓存、连接池、静态资源和读模型；使用同负载前后证据。不要因为 CPU 高就直接拆服务；先定位具体路径与等待。

### 阶段 3：有证据的抽取

若触发条件成立，选择边界最清晰、事务最少的模块试点。先定义接口、所有权、迁移与回滚；影子流量或双读验证，但避免长期双写。抽取必须带 SLO、值班、备份、恢复和安全能力，而不是只搬代码。

### 阶段 4：持续复核

需求、团队、流量与法规变化时更新上下文、容量和 ADR。删除没有需求来源的组件；演练失败路径；把真实事故和性能证据反馈到设计。架构不是一次性 PPT。

## 15. 实验：南昌现场服务平台设计包

进入 `labs/encyclopedia/ch.architecture.system-design/`，运行：

```bash
./verify.sh
```

脚本验证合成设计包是否包含功能/质量需求、上下文参与者、Java 业务权威数据流、组件需求追踪、明确单位与可复算容量、三类故障模式、SLO、ADR 的拒绝项/触发条件/回滚。输出会明确写 `UNVERIFIED`，防止把静态设计检查包装成负载证据。

### 15.1 阅读夹具，不要先改数字

先逐项标注 `design_packet.json` 中每个数字的来源。当前来源都是教学假设。问：真实岗位中谁能确认组织数？请求数来自产品估计还是日志？峰值系数有无节假日/集中派工证据？记录字节是否含索引、WAL、附件与备份？保留期来自业务还是法规？

### 15.2 重算容量

手工按单位消元重算四个结果，再与脚本输出比较。把 `peak_factor` 改为 12，预测峰值 RPS 和字节流量如何变化；把附件加入模型，观察存储是否成为主导。每次只改变一个假设，保存差异。

### 15.3 注入设计故障

添加 `kafka` 组件但不给 `requirement_ids`，门禁应指出技术先行；把 `request_bytes` 单位改成 `KB`，门禁应指出单位不匹配；删除数据库故障的 `recover`，门禁应指出只画成功路径；把某数据流权威改成 `python-ai`，门禁应阻止 AI 拥有业务事实。保存红色输出，修复后用同一验证转绿。

### 15.4 把合成假设升级为真实证据

在真实项目获得授权后，复制设计包并增加来源：访谈记录、匿名化遥测查询、数据集身份、负载脚本、目标主机、制品 digest、结果分布、数据库计划、资源指标、trace 与故障实验。不要直接覆盖教学包，也不要使用生产敏感明细。真实证据仍有有效期，应记录采集日期和适用环境。

## 16. 四种反模式如何诊断

### 16.1 先选微服务再找需求

**失败阶段**：需求与边界推导。**首个可信证据**：组件清单出现服务、队列和网关，却没有功能/质量需求 ID、数据所有权或独立扩容/团队约束。最后一张漂亮架构图不是证据。修复：暂时移除无来源组件，从上下文和不变量重建；把模块化单体作为候选而非默认结论；用比较表和 ADR 重新选择。残余风险：未来真触发抽取时仍需迁移。

### 16.2 容量单位混乱

**失败阶段**：容量模型。**首个可信证据**：输入表出现“500M”“每秒大概很多”或日请求直接与秒吞吐相乘，无法单位消元。修复：把每项改成 count、request/day、byte/request、second/day 等；写公式和舍入；区分 MB/MiB；增加上下界和敏感性。重跑脚本只验证计算，不验证机器能承载。

### 16.3 只画成功路径

**失败阶段**：可靠性设计。**首个可信证据**：数据流只有正常箭头，故障表缺少 detect/mitigate/recover；SLO 没有错误预算策略。修复：对每个外部依赖和状态边界写超时、重试、幂等、降级、恢复与残余风险，至少演练三类故障。注意重试可能放大故障，必须有预算和退避。

### 16.4 把强一致/最终一致当无成本标签

**失败阶段**：业务不变量与数据流。**首个可信证据**：文档给整个系统贴标签，却没写允许的异常、新鲜度、冲突、补偿和用户体验。修复：逐操作列出错误接受与错误拒绝成本；核心状态用事务/约束保护；通知和 AI 派生允许有界延迟；记录可观察的新鲜度和补偿。残余风险必须由业务负责人接受。

## 17. 设计评审问题清单

### 需求与边界

- 每个组件能否指向至少一个需求或约束？
- 哪些规则是业务不变量，在哪里强制？
- 谁是每类数据的唯一写入权威？
- 系统、外部系统和信任边界是否清楚？
- 非目标和假设是否显式？

### 容量

- 单位能否逐步消去？峰值、增长和保留是否分开？
- 数据是否包括索引、WAL、备份、附件和冗余？
- 平均值是否隐藏尾部和热点租户？
- 哪些是假设、哪些来自真实遥测、哪些来自压测？
- 生成器、网络或观测是否可能成为测量瓶颈？

### 可靠性与一致性

- 三个最重要故障如何探测、缓解、恢复？
- 健康检查通过是否真的代表核心业务正常？
- 重试是否幂等？超时和退避是否有预算？
- RTO/RPO 的起止点和业务校验是什么？
- 每个最终一致路径允许多旧，冲突如何处理？

### 演进与运维

- 当前团队能否值班、观察、备份和恢复每个组件？
- 被拒方案为何被拒？什么证据会改变决定？
- 迁移与回滚是否避免长期双写？
- 版本表面和官方文档是否在目标环境重新核验？
- 哪些结论仍未验证？

## 18. 常见误区

**“用户可能很多，所以要微服务。”** 用户数不等于负载；先算请求形状、数据和团队约束。

**“用了缓存就高性能。”** 缓存带来失效、穿透、权限键和陈旧问题。先证实瓶颈并定义一致性窗口。

**“数据库有副本就高可用和有备份。”** 副本、故障转移、备份和恢复解决不同问题，都需要演练。

**“平均 100ms 很快。”** p99 可能数秒；还要看错误、吞吐、资源、生成器和功能正确性。

**“内部服务可以互相信任。”** 内部调用仍需身份、授权、最小权限、审计和输入验证；尤其 Java 对 Python 的数据/工具请求要按当前上下文判定。

**“最终一致就是以后会对。”** 必须定义多久、如何知道已对、失败如何补偿以及用户看到什么。

**“增加队列可以防止所有高峰。”** 队列只是搬移等待；若消费能力长期不足，会增加延迟、存储和恢复复杂度。

**“可观测性就是安装 collector。”** 需要从用户旅程定义 SLI、资源/版本标识、可关联 trace/log、低基数指标和可操作告警。

**“架构图完成就是设计完成。”** 没有可运行原型、公式、故障演练和 ADR 的图只能表达意图。

## 19. 口头检查与练习

### 120 秒讲解

请不用术语堆砌，回答：为什么先写功能需求和质量属性？为什么每个组件要追踪需求？如何用单位证明容量公式可复算？FactoryCare 为什么让 Java/PostgreSQL 拥有业务事实、Python/AI 只持有派生数据？举一个一致性越界反例和一个触发微服务演进的可测条件。

### 纸面推导

假设 200 个组织、每组织 40 人、每人每天 100 请求、活跃 8 小时、峰值系数 8、每次往返 6,000 byte。先写单位，再计算日请求、峰值 RPS 和峰值 byte/s。然后列出至少三项这个估算没有覆盖的因素。若没有真实服务时间，不要推断服务器数量。

### 故障推演

选择工单分派路径，分别注入数据库超时、重复请求、Python AI 超时和通知提供商失败。为每个故障写：用户影响、最早探测、缓解、恢复、数据风险、是否影响核心 SLO、可重放验证。说明为什么对四种故障采用同一“重试三次”策略可能错误。

## 20. 本章完成判据

提交物应同时满足：

1. 功能需求、质量属性、假设和非目标清楚；
2. 上下文包含主要参与者、外部系统、信任和业务权威；
3. 关键写/读/AI 数据流说明身份、事务、事实所有者和失败语义；
4. 每个组件可追溯到需求或约束；
5. 容量数字写来源、单位、公式、结果、上下界和未覆盖项；
6. 至少三类故障都有探测、缓解、恢复和残余风险；
7. SLI/SLO 有事件口径、窗口和错误预算动作；
8. 一致性逐业务操作说明，不给全系统贴空标签；
9. ADR 包含决定、后果、被拒方案、验证、演进触发与回滚；
10. 至少完成一次技术先行、单位混乱或失败路径缺失的红→修复→绿；
11. 清楚区分合成公式、静态门禁、真实遥测、负载测试和现场故障证据。

本章 oracle 是：每个组件可追溯到需求或约束；容量数字单位可复算；故障模式对应探测、缓解和恢复；ADR 明确被拒方案与触发条件。实验脚本验证的是这个静态 oracle，不验证真实容量、SLO 或灾备。
