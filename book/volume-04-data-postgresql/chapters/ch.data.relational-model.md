# 数据库、schema、表、行、键与关系模型

> 本章状态为 `drafting`。正文以稳定的关系模型为核心，并用 PostgreSQL 18.4 的官方术语核对数据库、schema、表和约束边界；复核日期为 **2026-07-17**。配套 oracle 只读取仓库内固定 CSV/JSON，不安装 PostgreSQL、不连接任何数据库，也不执行 DDL。自动检查通过不等于零基础试读、人工审查或真实数据库验证完成，因此本章不能晋升为 `verified`。

## 1. 为什么先学“数据是什么”，而不是先背 SQL

FactoryCare 要保存设备、故障、工单、维修人员和处理时间。最直接的做法似乎是开一个表格，把所有信息都塞进一行：

| 工单号 | 设备编号 | 设备名称 | 设备位置 | 故障摘要 | 维修人 |
| --- | --- | --- | --- | --- | --- |
| WO-101 | D-01 | 1号空压机 | A-1 | 压力异常 | 陈工 |
| WO-102 | D-01 | 1号空压机 | A-1 | 温度过高 | 李工 |

这两行看起来方便，却重复了同一个设备名称和位置。设备位置改成 A-2 时，应改一行还是两行？如果只改一行，两个互相矛盾的“事实”同时存在。若把某设备最后一张工单删掉，设备资料是否也会意外消失？问题不在 SQL 拼写，而在数据事实没有被清楚拆分。

关系模型首先要求回答：

1. 一行代表什么；
2. 哪些列描述同一类事实；
3. 什么值能稳定标识一行；
4. 一行怎样引用另一类事实；
5. 值未知、尚未发生和空字符串是不是同一件事；
6. 一对一、一对多、多对多分别允许多少个匹配。

只有这些问题有明确答案，后续的查询、约束、事务、索引和代码映射才有可靠地基。SQL 是操纵关系数据的语言，不会自动替你发明正确的数据含义。

### 本章完成标准

学完后，你应能在不写建表语句的情况下：

- 用自己的话区分数据库、schema、表、行、列和域；
- 为设备与工单指出候选键、选定主键并说明取舍；
- 从外键列画出“引用方 → 被引用方”的方向；
- 从固定样例手算 1:N 基数和可选性；
- 区分 `NULL`、空字符串、零、`false` 与“没有这一行”；
- 识别宽表里的重复事实、更新异常和不稳定身份；
- 用 oracle 证明结论，而不是凭表格看起来整齐就宣布正确。

本章不要求编写 `CREATE TABLE`、`ALTER TABLE` 或修复真实约束。DDL 与约束落地属于后续 `ch.data.ddl-constraints`；查询语法属于后续 SELECT 章节。

## 2. 从世界里的对象到关系中的事实

数据库不保存“现实本身”，只保存系统选择记录的事实。FactoryCare 中一台真实空压机有重量、声音、磨损、所属车间等无数属性，系统只选择业务需要的部分，例如：

- 设备：`device_id`、资产编码、名称、安装区域、启用状态；
- 工单：`work_order_id`、所涉设备、故障摘要、创建时间、解决时间；
- 技师：`technician_id`、工号、姓名。

这一步叫建模：把业务语义投影成可以保存、验证和关联的数据结构。模型一定有边界。“设备名称”不是设备本身，“工单状态”也不是整个维修过程。模型遗漏重要事实会限制业务；模型混合不同事实会制造矛盾。

判断表的第一问不是“有哪些列”，而是：

> 这张表的一行，独立地陈述了什么事实？

若答案是“有时代表设备，有时代表工单”，说明行语义不唯一。若答案包含很多“以及”，例如“一行代表设备以及它当前或历史上的某张工单以及维修人”，通常意味着多种生命周期被挤进同一行。

## 3. PostgreSQL 中数据库、schema 与表的层次

“数据库”在日常对话中常泛指整套数据系统，但 PostgreSQL 有更精确的层次：

```text
一个 PostgreSQL server/cluster
├── 数据库 factorycare_training
│   ├── schema factorycare
│   │   ├── 表 device
│   │   └── 表 work_order
│   └── schema audit
│       └── 表 event_log
└── 数据库 postgres
```

- **server/cluster**：一个 PostgreSQL 服务器实例管理的数据库集合。这里的 cluster 不是“多机集群”承诺，而是 PostgreSQL 官方对一个数据目录及其实例所管理集合的术语。
- **database**：一次普通客户端连接只进入一个数据库。连接到 `factorycare_training` 后，不能把另一个数据库里的表当作同库表直接访问。
- **schema**：数据库内部的命名空间，容纳表、视图、类型、函数等对象。两个 schema 可以各有一张同名 `device` 表。
- **table**：同一类行的命名集合，每行具有同一组命名列，每列有规定的数据类型或业务域。

因此 `factorycare.device` 是 schema 限定的对象名，不是文件路径，也不是“数据库名.表名”。schema 类似目录只是一种入门类比：它帮助理解命名分组，但 schema 不能嵌套，权限和 `search_path` 也与文件目录规则不同。

角色不属于某一个 schema。PostgreSQL 角色在整个 cluster 范围存在；角色可以被允许连接某数据库并访问其中某些 schema/对象。角色管理将在后续章节教授，本章只把它当作“谁在观察这些数据”的边界。

## 4. 关系、表与集合思维

关系模型中的“关系”来自数学关系，可以直观理解为满足同一结构的一组元组。表是它在数据库中的常见表现：

- 关系的属性对应列；
- 元组对应行；
- 域限制某列允许表达的值；
- 关系的每个元组有同样的属性集合；
- 数学集合没有天然顺序，也不保留完全相同的重复成员。

但不要把理论与 SQL 实现机械画等号。PostgreSQL 表如果没有适当约束，可以存在内容完全相同的行；SQL 查询的中间与输出结果通常按多重集（bag）语义保留重复。另一方面，表中的物理存储顺序也不是业务顺序，官方教程明确说明：没有显式排序时，SQL 不保证行的返回顺序。

所以“集合思维”在本章意味着：

1. 关注一组满足共同结构的事实，而不是第 3 行、第 8 行的屏幕位置；
2. 用值和键标识成员，不用行号或当前显示顺序；
3. 先预测集合中应有哪些成员、是否允许重复，再观察输出；
4. 把筛选、投影、组合看作“旧关系 → 新关系”的变换；
5. 不用偶然顺序、手工颜色或空白行承载业务含义。

电子表格中的“第 12 行”在插入、排序后可能变化；数据库键的目的正是让身份不依赖位置。

## 5. 表、行、列和域

### 5.1 表：同类事实的契约

`device` 表应只陈述设备事实，`work_order` 表应只陈述工单事实。表名是对行语义的承诺。把“设备或工单”混在一张表中，会产生大量只对部分行有意义的列和模糊的键。

### 5.2 行：一次完整陈述

一行不是 Java 对象的永久镜像，也不是日志文本。它是按表契约给出的一组列值。例如：

```text
device:
device_id | asset_code | name        | area | enabled
D-01      | AC-0001    | 1号空压机   | A-1  | true
```

这行表达“系统认识一台标识为 D-01、资产编码 AC-0001 的设备”。如果 `name` 改了，仍是同一设备，因为身份由选定键而非名称决定。

### 5.3 列：命名属性

列给出属性名，并让每行在同一位置表达同一种含义。好列名应回答“谁的什么”，而不是把单位、显示格式和多个值藏进一个自由文本。例如 `installed_at` 比 `data1` 可解释，`area_code` 比 `location_or_owner` 单一。

列的排列顺序主要影响展示和某些接口，不应承担业务身份。业务代码最好按列名和明确契约理解结果，而不是把“第二列永远是名称”当成跨版本保证。

### 5.4 域：允许值及其意义

域不仅是 `text`、整数、时间等存储类型，还包括业务语义：

- `device_id` 必须是系统认可的设备标识；
- `enabled` 表达启用/停用，而不是“是否故障”；
- `resolved_at` 是工单解决时间，未解决时可以未知；
- `priority` 只能取业务定义的优先级集合。

同为文本的设备编号和工单编号并不属于同一业务域。仅因两列底层都是字符，就拿它们比较或互换，是类型层面允许、语义层面错误。

## 6. NULL 不是空字符串

`NULL` 表示缺少一个值，常用于“未知”“尚未发生”或“不适用”，但具体含义必须由列契约说明。例如未完成工单的 `resolved_at = NULL` 可以表示“解决时间尚未产生”。

下面五种状态不能混同：

| 表现 | 可能含义 |
| --- | --- |
| `NULL` | 当前没有值；原因由列契约定义 |
| `''` 空字符串 | 已知值就是零个字符，或输入被清空 |
| `0` | 数值零，是一个已知数值 |
| `false` | 已知的逻辑假 |
| 没有这一行 | 相应实体/关系事实不存在 |

如果把未知维修人写成空字符串，就无法区分“尚未分派”和“系统确实保存了空工号”这两种情况。若用 `0` 代表未知时长，平均值会把未知误当成零分钟。若用虚构日期 `1970-01-01` 代表未解决，排序与统计都会得到貌似正常却错误的结果。

SQL 对 `NULL` 采用三值逻辑：比较结果可能是 true、false 或 unknown。具体查询语法留到 SELECT 章节；此处先记住，`NULL` 不是一个可以像普通值那样直接断言相等的“特殊字符串”。建模时要问：

1. 此列缺值是否合法；
2. 合法时缺值精确代表什么；
3. 是否应把不同缺失原因拆成状态或额外列；
4. 下游统计如何处理缺值；
5. CSV 等交换格式如何区分 `NULL` 与空字符串。

配套 CSV 故意同时包含未引号的空字段和 `""`。Ruby CSV 读取前者为 `nil`、后者为空字符串，oracle 会证明二者没有被混同。这是交换格式约定，不是所有 CSV 工具都自动采用同一规则。

## 7. 键：让行拥有稳定身份

键是一组能区分行的属性。先区分几个概念：

- **超键**：能够唯一标识行的任意属性集合，可能包含多余列；
- **候选键**：已经最小化的超键；去掉其中任一列就不再保证唯一；
- **主键**：从候选键中选出的主要身份；
- **备用键**：未被选为主键的其他候选键；
- **复合键**：由两列或多列共同构成；
- **自然键**：来自业务世界，例如受治理且不可重复的资产编码；
- **代理键**：系统引入的标识，例如 `device_id`。

假设 `device_id` 与 `asset_code` 都稳定、非空且唯一，那么二者都是候选键。选 `device_id` 为主键不会让 `asset_code` 失去唯一性要求；它仍应作为业务候选键被保护。

名称通常不是好键：

- 设备可能重名；
- 名称会因纠错或业务调整而改变；
- 大小写、空格、语言和格式会变化；
- 把名称传播到所有引用行，改名成本大。

“当前样例里没有重复”也不能证明候选键。候选键是面向所有合法未来状态的规则，需要业务确认。三行样本只能发现反例，不能穷尽证明永远唯一。

### 复合键何时合理

工单与标签的关联表可以用 `(work_order_id, tag_id)` 表示“同一工单不能重复关联同一标签”。两个外键共同标识一条关联事实。若另加代理键，也不能因此忘记这对业务列仍需要唯一。

选择键时检查：

- 唯一：不同合法行不会得到同一键；
- 非空：身份不应缺失；
- 稳定：普通业务修改不会改变身份；
- 最小：没有无关列；
- 可引用：其他关系能够明确指向它；
- 范围清楚：租户内唯一还是全局唯一必须写明。

## 8. 约束：把合法状态写成可检查的不变量

约束说明哪些数据库状态合法。即使本章不写 DDL，也必须能读懂它们的意图：

| 约束概念 | 保护的问题 |
| --- | --- |
| 数据类型/域 | 值的基本种类和格式边界 |
| 非空 | 必需事实不能缺失 |
| 唯一 | 候选键不能重复 |
| 主键 | 选定行身份必须唯一且非空 |
| 外键 | 引用值必须指向被引用关系中的合法键 |
| 检查规则 | 单行内的业务条件，例如结束时间不早于开始时间 |

约束不是表单提示的替代品。界面校验帮助用户尽早修正输入，数据库约束保护所有写入路径和并发情况下的最终状态。反过来，约束也不能表达全部业务：权限、跨时间流程、复杂聚合规则可能需要服务或事务逻辑。

本章只观察“预建 schema 声称有什么约束”和样例是否符合，不执行修复。没有 DDL 证据时，不能把 JSON 模型里的 `primary_key` 字段冒充成 PostgreSQL 已经真正强制的约束。

## 9. 外键方向与参照完整性

`work_order.device_id` 保存设备键，并引用 `device.device_id`：

```text
work_order.device_id  ───────▶  device.device_id
        引用方                       被引用方
```

箭头从“持有外键的列”指向“被引用的候选键/主键”。业务语言常说“设备有许多工单”，容易把箭头画成设备指向工单；那描述的是阅读方向，不是外键存放方向。

外键保护的是参照完整性：一个非空设备引用不能凭空指向不存在的设备。它不自动保证：

- 每台设备至少有一张工单；
- 一张工单最多有一个处理人；
- 删除设备时应拒绝、级联还是置空；
- 引用列是否被索引；
- 当前用户是否有权查看两边数据。

这些都是额外契约。不要从“有外键”推断出所有关系规则。

## 10. 基数与可选性

基数回答“一边的一条记录最多能匹配另一边多少条”。常见形式：

- **1:1**：一个设备至多一个当前遥测配置，每个配置只属一个设备；
- **1:N**：一台设备可以有多张工单，每张工单只指向一台设备；
- **N:M**：一张工单可以有多个标签，一个标签可以用于多张工单；通常用关联关系拆成两个 1:N。

还要说明最小基数，也叫可选性：

- 设备可以暂时没有工单：设备到工单是 `0..N`；
- 工单必须属于设备：工单到设备是 `1`；
- 工单可以尚未分派技师：工单到技师可能是 `0..1`。

用乌鸦脚图、文字或范围都可以，但必须同时说清两侧：

```text
device 1 ───── 0..N work_order
每张工单恰属一台设备；一台设备可以没有或拥有多张工单。
```

基数不是由当前行数决定。今天每台设备刚好一张工单，不代表关系是 1:1；要看业务允许的所有合法状态。反过来，样例里同一设备出现两张工单，足以推翻“设备最多一张工单”的错误断言。

## 11. 用固定 FactoryCare 样例手算

预建模型包含两张表：

```text
device(device_id, asset_code, name, area, enabled)
work_order(work_order_id, device_id, summary, resolved_at)
```

样例设备：

| device_id | asset_code | name | area | enabled |
| --- | --- | --- | --- | --- |
| D-01 | AC-0001 | 1号空压机 | A-1 | true |
| D-02 | AC-0002 | 冷却泵 | B-2 | true |

样例工单：

| work_order_id | device_id | summary | resolved_at |
| --- | --- | --- | --- |
| WO-101 | D-01 | 压力异常 | NULL |
| WO-102 | D-01 | 空字符串 | 2026-07-16T09:30:00Z |
| WO-103 | D-02 | 温度过高 | 2026-07-16T10:00:00Z |

逐项观察：

1. `device_id` 和 `asset_code` 在设备样例中均不重复；它们是候选键的候选，需要业务规则确认长期唯一。
2. `work_order_id` 唯一且稳定，可作为工单主键。
3. 所有非空 `work_order.device_id` 都能在设备键集合中找到。
4. D-01 匹配两张工单，D-02 匹配一张，样例支持 1:N 而否定 1:1。
5. WO-101 的解决时间未知；WO-102 的摘要明确是空字符串，两者不同。
6. 屏幕中的行顺序没有业务承诺；不能称 WO-101 为“第一张工单”并把它当永久身份。

## 12. 宽表为什么会失败

把设备和工单放在一张宽表会产生三类经典异常：

### 更新异常

设备 D-01 在十张工单行中重复十次区域。搬迁时必须十处同步；漏一处就矛盾。

### 插入异常

新设备尚无工单时，若表的行键是工单号，就无法只登记设备，或被迫制造空工单。

### 删除异常

删除某设备最后一张历史工单时，若设备资料只存在该行，设备事实也被一并删除。

修正关系图的思路不是“多加一列唯一编号就好了”。代理编号只能让宽表每行唯一，不能消除设备名称和位置的重复事实。应先按行语义拆出设备与工单，再用设备键关联。具体建表和数据迁移在后续章节进行。

## 13. 一行一个事实，不等于一行一个现实对象

有些表记录实体当前状态，例如 `device`；有些表记录事件或关系，例如 `work_order_event`、`work_order_tag`。它们都可以有清晰行语义：

- 设备行：一台被管理设备；
- 工单行：一次维修请求；
- 工单状态事件行：某工单发生的一次状态变化；
- 工单标签关联行：某工单与某标签的一次关联。

“每个对象一张表”过于粗糙。更准确的规则是：同一表的每行应属于同一种事实类型，拥有可解释身份和共同属性域。

事件表通常不能用 `work_order_id` 单独作键，因为一张工单会有多个事件；可能需要事件 ID，或由工单 ID、事件序号等组成复合候选键。先问行语义，再选键。

## 14. 关系名称和方向必须可朗读

画图后用两句话朗读每条关系：

1. 一张工单引用恰好一台设备；
2. 一台设备可以被零到多张工单引用。

如果两句话不能同时与数据和业务规则一致，图还不完整。常见错误包括：

- 只写“设备与工单有关”，没有方向或数量；
- 用复数表名误判基数；
- 把“当前样例有几个”当“业务最多允许几个”；
- 外键画在被引用表；
- 用可空外键却声称每行必须有匹配；
- 把 N:M 直接塞进逗号分隔文本列。

逗号分隔的 `tag_ids = 'T1,T2'` 看似省表，却让每个值不再是清晰的单个关系成员，也难以逐项约束。关联关系更能表达“一条工单—一个标签”的原子事实。

## 15. 集合操作的预告

后续 SQL 会把关系变成新关系：

- 从工单集合选择未解决成员；
- 只保留工单号和设备号等部分属性；
- 按相等键组合设备与工单；
- 对成员分组和聚合；
- 合并结构兼容的集合。

此时最重要的习惯是先写预言：

```text
输入设备键集合 = {D-01, D-02}
工单引用集合   = {D-01, D-01, D-02}
不同被引用设备 = {D-01, D-02}
D-01 的匹配数 = 2
```

注意集合与多重集的区别：引用值列表中 D-01 出现两次，代表两张不同工单；去重后的设备键集合只有一个 D-01。盲目“去重”可能掩盖真实的一对多，盲目保留重复又可能把同一事实计算多次。选择哪种语义必须由问题决定。

## 16. 诊断顺序：从第一处可信证据开始

看到“设备重复”“工单找不到设备”或“数量翻倍”时，按层取证：

1. **行语义**：每张表的一行究竟代表什么；
2. **样例原文**：是否真的有重复键、空值或孤儿引用；
3. **键规则**：唯一性来自业务契约，还是只在小样本里碰巧成立；
4. **关系方向**：外键在哪一边，引用哪个候选键；
5. **基数预言**：手算每个键应匹配多少行；
6. **交换格式**：CSV 的空字段有没有把 `NULL` 和空字符串混掉；
7. **数据库证据**：等后续进入 DDL 章，再检查真实约束定义和失败错误。

不要先加 `DISTINCT`、删除“重复”行或生成随机 ID。那可能让症状消失，却没有回答重复是合法多条事实、意外复制，还是模型混合。

## 17. 可重复 oracle 如何证明模型

[最小示例](../../../examples/encyclopedia/ch.data.relational-model/README.md)读取固定模型与两份 CSV，验证：

- 表名和列集合与模型一致；
- 主键字段非空且唯一；
- 备用候选键在样例中无重复；
- 每个工单设备引用都存在；
- D-01 的两张工单证明 1:N；
- `NULL resolved_at` 与空摘要分别计数。

[实验](../../../labs/encyclopedia/ch.data.relational-model/README.md)增加一张故障宽表，要求先预测再核对重复设备事实、缺失稳定键和错误基数。[公开练习](../../../exercises/encyclopedia/ch.data.relational-model/README.md)故意给出错误答案，验证脚本应确认 starter 处于红灯；答案隔离在私有目录。

oracle 只证明固定输入符合声明，不能证明 PostgreSQL 已建立约束，也不能证明模型适合所有未来需求。它的价值是把“我看起来觉得对”变成明确 expected/actual。

## 18. 安全与隐私边界

即使只是建模，也要避免把真实生产数据复制进练习：

- 使用合成设备、工单和人员编号；
- 不保存客户名称、真实厂区、电话号码、邮件或凭据；
- 不把生产数据库导出当样例；
- 错误日志若含连接串、用户名或路径，发布前脱敏；
- 样例 ID 不应可反查真实资产。

本章所有数据均为合成。离线验证不会读取环境变量、用户主目录或网络，不会连接本机或远程 PostgreSQL。

## 19. 与 Java/TypeScript 对象的类比及失效边界

一行可以类比为 Java record 或 TypeScript 对象：列名像字段名，域像类型，主键像稳定 ID。这个类比能帮助初学者理解结构一致。

但它很快失效：

- 对象引用是进程内身份，外键是持久化值与约束；
- Java `null`、JavaScript `undefined/null` 与 SQL `NULL` 的运算规则不同；
- List 有顺序和重复，数学关系无顺序，SQL 结果又常是多重集；
- 对象图可以直接嵌套，关系模型通常把不同事实拆成表再通过键组合；
- 数据库约束面对所有写入者和并发，不等于单个类构造器校验。

因此 ORM 生成的对象形状不能替代关系建模。先能画出表、键与基数，再讨论对象映射。

## 20. 预测—构建—破坏—修复

### 预测

不运行 oracle，先回答：

1. `work_order.device_id` 能否作为工单主键？为什么？
2. D-01 对应几张工单？这能推翻哪种基数？
3. 未解决时间与空摘要各应计数多少？
4. 如果新增工单引用 D-99，第一项失败应是什么？

### 构建

从固定样例画出：

```text
device
PK device_id
AK asset_code

work_order
PK work_order_id
FK device_id -> device.device_id

device 1 -> 0..N work_order
```

在每个可空列旁写出缺值含义，而不是只画“允许 NULL”。

### 破坏与诊断

依次注入：

- 两行设备使用同一 `device_id`；
- 工单引用不存在的 D-99；
- 把 `work_order.device_id` 误选为工单主键；
- 把 CSV 中 `nil` 统一转成 `''`；
- 把关系写成设备最多一张工单。

每次只改一项，记录第一个失败断言，再恢复并重跑原 oracle。这样才能知道是哪条不变量产生证据。

## 21. AI 协作检查单

让 AI 提议模型时，至少追问：

- 每张表一行的精确定义是什么？
- 候选键来自哪个业务规则，还是只根据样例猜测？
- 外键在哪一边，是否允许 `NULL`？
- 两侧最小/最大基数是什么？
- `NULL` 在每列分别代表什么？
- 哪些事实会重复，更新一次需要改几处？
- 哪些结论已经由数据库约束验证，哪些只是设计草图？
- 需求变化时，例如一张工单允许多人协作，模型怎样改？

AI 很容易生成“看起来专业”的 ER 图，却把名称当键、遗漏租户范围或把 1:N 画反。必须以业务句子、样例反例和 oracle 复核。

## 22. 故障速查

| 现象 | 优先检查 | 不要立即做 |
| --- | --- | --- |
| 同一设备出现多次 | 行语义、设备键、是否是合法的多张工单 | 全表去重 |
| 更新设备位置要改很多行 | 设备事实是否混进工单宽表 | 加更多同步脚本 |
| 工单找不到设备 | 外键值、被引用键集合、缺值契约 | 创建虚构设备 |
| 统计数量翻倍 | 关系基数、组合前后行数 | 无条件 DISTINCT |
| 空值统计异常 | NULL/空串/零的交换格式 | 统一替换为 0 |
| 主键“偶尔重复” | 候选键规则、范围、并发写入 | 改用当前行号 |
| 设备没工单就无法登记 | 插入异常、行语义混合 | 制造空工单 |

## 23. 120 秒复述模板

> 关系模型把同类事实组织为关系，数据库中的表是常见实现。表的一行必须有唯一语义，每列有命名和业务域；行顺序不是身份。候选键是最小的唯一标识集合，主键是其中选定的一组，外键放在引用方并指向被引用键。设备到工单通常是 1 对 0..N，但每张工单恰属一台设备。NULL 表示缺值，不能和空字符串、零、false 或缺行混同。约束用于排除非法状态，但本章只读取预建模型和固定样例，不写 DDL。宽表反例会重复设备事实，造成更新、插入和删除异常。

复述时再补一个失败反例：若把 `device_id` 当工单主键，同一设备的第二张工单就无法拥有合法身份，暴露出把关系基数误判成 1:1。
