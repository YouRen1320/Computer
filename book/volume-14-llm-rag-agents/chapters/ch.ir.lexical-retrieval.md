# 词项、倒排索引、TF-IDF 与 BM25

> 稀疏检索并不“低级”。当用户输入设备编号、故障码、零件名或一句维修现象时，词法匹配往往是最清楚、最便宜、最容易复算的基线。本章从一张能手工检查的倒排表开始，逐步推到 TF-IDF 与 BM25。范围止于候选检索：不调用向量数据库，不生成回答，也不把索引当成 FactoryCare 的业务真相。

## 1. 学完到底要会什么

完成本章后，你应能不依赖搜索框架完成四件事：

1. 给定短语料，按一份明确的规范化合同得到 token、词频和倒排表；
2. 区分词频 `tf`、文档频率 `df`、集合频率，并解释混淆后哪条不变量最先破坏；
3. 手算一个文档对查询的 TF-IDF 或 BM25 分数，并指出长度归一化和词频饱和分别做什么；
4. 用测试证明固定语料的统计、逐项贡献、排名和并列规则，而不是只看到程序“运行成功”。

这和前端搜索框的关系可以这样理解：输入框只产生字符串；检索器把字符串转换为查询词项，访问预先构建的索引，输出带证据的候选列表。Vue 组件可以展示结果，却不应该决定 `df` 怎么算。相同地，Java 业务服务拥有工单与权限，Python 检索投影只回答“在这批已授权、已索引的文本中，哪些候选更匹配”。

## 2. 先建立完整数据流

词法检索最小数据流是：

```text
原始文档 -> 规范化/分词 -> 文档 token 列表 -> 倒排索引与统计
原始查询 -> 同一规范化/分词 -> 查询词项 -> 查 postings -> 评分 -> 排序
```

这里有三个必须固定的合同。

- **文档与查询使用同一规范化器。** 文档把 `PUMP` 变成 `pump`，查询却保留大写，那么逻辑上相同的词不会相遇。
- **索引对应一个可识别的语料版本。** 文档更新后若统计未重建，`N`、`df`、平均长度与 posting 可能来自不同快照。
- **排序必须确定。** 分数相同不能依赖哈希表遍历顺序；本章夹具用 `score DESC, doc_id ASC`。

倒排索引是派生物。删除它会让搜索暂时不可用，但不能删除业务工单；它应能从带版本的来源重新构建。若索引反过来成为状态机或 ACL 的唯一记录，边界已经错了。

## 3. token 不是“天然存在”的东西

文本必须经过规则才会得到 token。最简单的英文规则可以是：大小写折叠后提取连续字母和数字。于是：

```text
"Pump, PUMP! 42" -> ["pump", "pump", "42"]
```

这个规则可复现，但不等于适合中文。中文没有天然空格，真实系统可能使用字粒度、词典、统计分词或子词模型。课程夹具使用空格分隔的英文维修词，是为了让每个 token 都能手算，不是声称真实中文搜索应照搬正则表达式。

一份规范化合同至少说明：

- Unicode 规范化采用哪一种形式；
- 大小写、全角半角、标点和连字符如何处理；
- 型号 `AB-12` 是一个词、两个词还是同时产生原词与拆分词；
- 停用词表、同义词表和领域词典的版本；
- 空文本、纯标点、超长 token 和不可见字符如何处理；
- 文档与查询是否完全相同，若不相同，差异为何是有意设计。

不要看到分词库返回数组就认为合同已经存在。可审计合同需要输入、版本和期望输出。例如型号规则升级后，旧索引不能悄悄沿用旧 token，而查询改走新规则。

## 4. 从正向列表到倒排表

假设有三篇文档：

```text
D1: pump motor noise
D2: pump leak seal
D3: motor vibration
```

正向列表按文档记录 token：

```text
D1 -> [pump, motor, noise]
D2 -> [pump, leak, seal]
D3 -> [motor, vibration]
```

倒排表反过来按词项记录出现它的文档及文档内次数：

```text
pump     -> {D1: 1, D2: 1}
motor    -> {D1: 1, D3: 1}
noise    -> {D1: 1}
leak     -> {D2: 1}
seal     -> {D2: 1}
vibration-> {D3: 1}
```

一个 posting 通常包含文档 ID 和词频，还可以包含位置、字段、偏移等信息。仅做本章 BM25 时，文档 ID 与词频已足够。短语查询或高亮需要位置与偏移，但那是额外合同，不能凭空从词频恢复。

构建时最容易犯的错误是每遇到一次 token 就把 `df` 加一。正确做法是先对单篇文档做 `Counter`，每个不同词项只给该文档一个 posting；posting 中的值才是这篇文档里的 `tf`。

## 5. 三种频率不能混

对词项 `pump`，常见统计是：

| 名称 | 含义 | 三文档示例 | 必须满足 |
| --- | --- | ---: | --- |
| `tf(t,d)` | 词 `t` 在文档 `d` 内出现次数 | `tf(pump,D1)=1` | `0 <= tf <= 文档长度` |
| `df(t)` | 至少含一次 `t` 的文档数量 | `df(pump)=2` | `0 <= df <= N` |
| collection frequency | `t` 在全部文档出现总次数 | `2` | 可大于 `N` |

若 `D1` 改成 `pump pump pump`，`df(pump)` 仍只增加一个文档，而集合频率会增加三次。`df > N` 是首个非常强的错误证据；但 `df <= N` 还不能反证实现正确，因为错误数据也可能碰巧没越界。因此还要对 postings 的键集合做手工 oracle。

文档总数记作 `N`。文档长度 `|d|` 是规范化后的 token 数，而不是字符数或字节数。平均长度：

```text
avgdl = (所有文档 token 数之和) / N
```

三文档长度分别为 `3,3,2`，所以 `avgdl=8/3`。若一个实现用原始字符数，长度归一化从源头就不再可比。

## 6. 倒排表为什么能加速

没有索引时，查询 `pump noise` 可能扫描每篇文档并重新分词。倒排表让检索器只访问 `pump` 和 `noise` 的 postings，候选集合是这些 posting 文档的并集。对 AND 查询则可取交集。

这一点解释了“稀疏”：词表可能很大，但一篇维修说明只包含少量词，绝大多数词项与该文档的权重为零。倒排表只保存非零项。

复杂度不能只写一个大 O 就结束。真实代价还取决于 posting 长度、压缩、缓存、跳表、字段和过滤。但在课程小语料中，最重要的是看见查询不必遍历整个词表，也不必逐文档重新解析。

## 7. TF-IDF 是一族公式

TF-IDF 的共同直觉是：

- 一个词在当前文档多次出现，通常更能代表这篇文档；
- 一个词在所有文档都出现，区分能力较弱；
- 一个词只在少数文档出现，区分能力较强。

最朴素写法可能是：

```text
tfidf(t,d) = tf(t,d) * log(N / df(t))
score(q,d) = 查询词项对应 tfidf 之和
```

但工程中存在平滑、对数词频、子线性缩放、向量归一化等变体。例如 `df=0` 时直接除法无定义；常见实现会平滑。教材不能只写“TF-IDF”而不记录公式，否则两段都叫 TF-IDF 的代码可能产生不同排名。

TF-IDF 仍有两个明显问题。第一，原始 `tf` 线性增长，重复一百次会得到一百倍贡献；第二，长文档天然有更多机会匹配词项。BM25 用可解释参数处理这两点。

## 8. BM25 的明确版本

本章可执行资产采用下式，对每个去重后的查询词项求和：

```text
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))

norm(d) = k1 * (1 - b + b * |d| / avgdl)

termScore(t,d) = idf(t) * tf(t,d) * (k1 + 1)
                              / (tf(t,d) + norm(d))

BM25(q,d) = Σ termScore(t,d)
```

夹具固定 `k1=1.2`、`b=0.75`。这不是唯一合法参数，也不是对所有语料最佳的值。重要的是保存参数和公式，使排名可复算。

### 8.1 `idf` 在做什么

当 `df` 小时，分母较小，`idf` 较大；当一个词出现在多数文档中，它的区分力下降。本章的 `ln(1 + ...)` 形式保证正值。其他 BM25 文献或实现可能采用不同 IDF 形式，甚至出现负值；比较系统前必须先对齐公式。

### 8.2 词频为什么“饱和”

固定文档长度时，`tf` 从 1 变 2 会提升分数，但继续增大时，分式逐渐趋近 `k1+1`，不会线性无限增长。这不是忽略重复词，而是表达“第一次出现很重要，后续重复的边际收益递减”。

### 8.3 长度归一化方向

当 `b>0` 时，长于平均值的文档使 `norm(d)` 增大，分母增大，单次命中的贡献降低；短文档相反。若把 `|d|/avgdl` 写成 `avgdl/|d|`，方向会翻转，长文档反而得到额外奖励。

`b=0` 关闭长度归一化；`b=1` 完全按相对长度参与。参数含义应通过曲线和边界例验证，而不是背诵默认值。

## 9. 完整手算 D1

仍用三篇文档，查询为 `pump noise`。统计为：

```text
N = 3
avgdl = 8/3
|D1| = 3
df(pump) = 2
df(noise) = 1
tf(pump,D1) = 1
tf(noise,D1) = 1
```

两个 IDF：

```text
idf(pump)  = ln(1 + 1.5/2.5) ≈ 0.4700
idf(noise) = ln(1 + 2.5/1.5) ≈ 0.9808
```

D1 的长度归一化项：

```text
norm(D1) = 1.2 * (0.25 + 0.75 * 3/(8/3))
         = 1.2 * 1.09375
         = 1.3125
```

因为两个词的 `tf` 都是 1，它们共享饱和因子：

```text
saturation = 1 * 2.2 / (1 + 1.3125) ≈ 0.95135
```

所以：

```text
score(D1) ≈ (0.4700 + 0.9808) * 0.95135 ≈ 1.380
```

D2 只匹配 `pump`，D3 一个查询词都不匹配，因此固定排名是 `D1, D2, D3`。最后一个零分文档仍出现在夹具中，是因为示例把全部文档排序；真实 API 通常会规定是否返回零分候选。这个行为也必须写进合同。

## 10. 查询重复词要有明确政策

查询 `pump pump noise` 是否让 `pump` 贡献两次？不同检索模型可以做不同选择。本章夹具用 `dict.fromkeys` 保留首次顺序并去重，因而重复查询 token 不会无限放大分数。这是课程合同，不是声称所有 BM25 实现都如此。

若决定保留查询词频，就要引入明确的 query-term frequency 公式，并测试上限。最危险的状态是文档端去重、查询端不去重，却没有任何说明；攻击者或偶然粘贴重复文本都能支配排名。

## 11. 从 Python 容器看索引结构

最小实现通常用这些容器：

```python
tokens_by_doc: dict[str, list[str]]
postings: dict[str, dict[str, int]]
lengths: dict[str, int]
```

内层 `dict[str,int]` 把 `doc_id` 映射到 `tf`。`df(term)` 应是 `len(postings[term])`，而不是内层数值之和。这个区别与 TypeScript 的 `Map<string, Map<string, number>>` 完全一致：键的个数回答“多少篇文档”，值的和回答“总共出现多少次”。

可执行示例在 `examples/encyclopedia/ch.ir.lexical-retrieval/`；五文档实验在 `labs/encyclopedia/ch.ir.lexical-retrieval/`。验证脚本不只看最终第一名，还检查 posting、`df`、总词数、`avgdl`、逐项贡献、未知词和错误参数。

## 12. 确定性比“看起来合理”重要

一个相同输入每次得到不同并列顺序，会让回归测试、缓存和评估都变得不稳定。课程规则是：

```text
主要键：score 降序
次要键：doc_id 升序
```

浮点数比较还需注意误差。手算验证用 `math.isclose`，排名夹具则选择差距明确的分数；不要把两个几乎相同的浮点数硬编码成必须逐位相等。若生产需要稳定分页，还要保存索引版本、评分参数和游标排序键。

## 13. 停用词、词干与同义词不是免费升级

停用词可以减少极高频、低区分词，但领域里普通语言的“停用词”可能承载故障含义。删除规则必须由评估证明，而不是照搬通用列表。

词干化或词形归一可以合并 `repair/repairs/repairing`，也可能把不同零件名错误合并。中文同义词如“泵体异响/水泵噪声”能提高召回，但查询扩展会改变候选集合和分数解释。

每项变化都应：

1. 版本化规则；
2. 重建索引；
3. 在同一个冻结查询集做消融；
4. 保存哪些查询改善、哪些退化；
5. 能回滚到旧规则。

“加了同义词，所以更智能”不是证据。

## 14. 字段权重与业务过滤要分层

设备编号、标题、正文可能需要不同权重。可为每个字段建统计并组合分数，或使用搜索引擎提供的字段模型。但不要把 ACL 作为一个普通加分项：无权限文档不是低分候选，而是必须排除的候选。

FactoryCare 的安全顺序应是：Java 根据当前用户、租户和业务规则产生授权边界；检索层只在授权范围中找候选，或在可信数据库过滤条件中强制应用边界。把 `is_admin`、工单状态或权限真相复制进 Python 后自行解释，会造成规则漂移。

同理，搜索结果里的状态只用于展示和定位。用户点击“关闭工单”仍必须调用 Java 业务 API，由 Java 状态机重新鉴权与校验，不能因为索引文档写着 `IN_PROGRESS` 就直接更新。

### 14.1 多字段评分必须保留字段统计

假设一篇知识文档包含 `title`、`fault_code`、`body`。最直观做法是分别计算三个字段的 BM25，再按固定权重组合：

```text
score = 3.0 * title_score
      + 5.0 * fault_code_score
      + 1.0 * body_score
```

但这要求每个字段有自己的长度和文档频率统计。把标题 token 与长正文混成一个列表，再给命中标题额外乘权，会让长度归一化仍由正文主导。实现选择必须写清楚，不能只在 UI 上显示“标题命中”。

字段权重是相关性参数，不是权限或业务优先级。`URGENT` 工单是否应排前属于产品排序规则，若把它混进 BM25 总分，就必须单独记录业务 boost，做相关性与业务目标消融。否则排错时无法知道第一名是文本更相关，还是状态被加权。

### 14.2 布尔过滤与评分的顺序

设备类别、文档语言、有效期可以作为结构化过滤，而不是先转成文本 token。安全过滤应在候选可见前执行；普通质量过滤也要测对召回的影响。

例如用户选择 `category=pump`，可只在该类别索引分区或 posting 交集内评分。若先全库取 top-10，再过滤类别，可能十条全被删除；此时不是 BM25 分数错，而是候选阶段顺序错。实验应包含“最高分均不满足过滤”的边界例。

### 14.3 短语、位置和邻近度

词袋 BM25 不区分 `motor drives pump` 与 `pump drives motor`，也不保证 `high temperature` 两词相邻。若需求含精确短语，就要在 posting 保存词项位置，查询时验证位置序列；邻近度可作为单独特征。

位置索引增加存储与构建成本。没有位置数据时，应用不能从高 BM25 分数推断短语确实出现。调试证据应区分“两个词都出现”和“连续短语命中”。

### 14.4 索引更新不是修改一个字典就结束

添加、更新、删除文档会改变 `N`、`df`、平均长度和 postings。若直接原地更新，读请求可能看到新 posting 配旧统计。小型系统可以全量构建新版本，验证后原子切换；大规模系统可增量维护，但要有一致性和恢复协议。

全量重建流程可以是：

```text
读取固定来源水位 -> 构建临时索引 -> 验证数量与黄金查询
-> 标记 ready -> 原子切换 current pointer -> 保留旧版本回滚
```

增量流程需要幂等事件、删除处理、乱序/重复事件政策和周期性全量对账。索引水位落后时，API 应暴露新鲜度或告警，而不是把旧结果当当前业务事实。

### 14.5 复杂度与容量估算

课程实现把全部 postings 放进 Python 内存，便于阅读，不适合直接承载生产语料。容量估算至少需要：文档数、token 总数、唯一词项数、posting 数、每 posting 字节、位置数据和版本保留。

若一百万篇文档平均 200 token，最坏原始 token 事件约两亿；实际 posting 数取决于单文档去重。只说“字典查询 O(1)”会忽略构建、序列化、缓存与长 posting 遍历。

优化顺序应先测：查询分布、最长 postings、候选数、缓存命中和慢查询。不要为三文档夹具添加压缩算法；也不要把夹具速度当容量证明。

### 14.6 分数解释必须与实际运行一致

有些系统为了展示解释，会在检索后用另一段代码重新计算分量。若两段公式或统计快照不同，解释可能不等于实际排名。更可靠方式是评分路径直接产生结构化贡献，或让解释记录足够的原始统计并用同版本公式复算。

抽样审计可验证：总分等于分量和、每个 `df` 对应索引快照、排序参数与请求版本一致。解释本身也可能泄露敏感词或文档统计，生产日志要遵守数据政策。

### 14.7 一个参数变更的发布与回滚

假设要把 `b` 从 `0.75` 改为 `0.5`。安全步骤不是直接改常量：

1. 建立配置版本 `bm25-v2`，保留 `v1`；
2. 在同一冻结查询集输出逐查询差值；
3. 检查型号、短文档、长文档、零召回切片；
4. 设定收益、退化和延迟通过线；
5. 灰度时让请求记录配置版本；
6. 监控退化后可把路由指针切回 `v1`；
7. 不删除旧索引/配置，直到回滚窗口结束。

参数没有改 schema，也可能是行为变更。缺少版本字段时，同一查询日志无法解释为何昨天和今天顺序不同。

## 15. 词法检索的天然盲区

词法检索擅长精确字符串、型号、代码和术语，却可能漏掉没有共享词面的语义同义表达。例如文档写“轴承发出尖锐声”，查询写“设备异响”，若没有同义规则，共享 token 可能为零。

它也无法仅凭词频理解否定、时间和复杂关系：

- “没有漏油”仍包含“漏油”；
- “更换前振动，维修后正常”仍包含“振动”；
- “不要重启网关”与“重启网关”共享多数词。

这些局限不是立即换成向量检索的理由。先把词法基线和失败切片固定，后续才能判断向量、混合或重排是否真的增加价值。

## 16. 故障诊断：先找首个可信证据

### 16.1 文档频率误用词频

症状：重复词文档让 IDF 异常，可能出现 `df>N`。首个证据应是倒排表/统计不变量，不是最终排名截图。修复后重跑重复词夹具与全部排名。

### 16.2 规范化不一致

症状：索引中有 `pump`，查询 `PUMP` 却零命中。先分别记录文档与查询的规范化输出、规则版本和索引版本。只给查询临时 `.lower()` 会掩盖其他差异。

### 16.3 长度归一化反向

症状：同样一次命中，越长文档反而贡献越高。构造两个内容相同但附加无关词数量不同的文档，固定 `tf=1`，观察分母和贡献；不要用复杂线上语料猜测。

### 16.4 重复查询无限放大

症状：重复粘贴一个词能改变所有排名。检查 query-term policy。若合同规定集合语义，先看去重后的查询词列表；若规定查询词频，则看饱和公式和上限。

### 16.5 “分数变了但不知道为什么”

只返回总分不可诊断。每个命中至少应能在调试证据中拆出 `term, tf, df, idf, document_length, avgdl, contribution` 以及评分参数和索引版本。

## 17. 测试金字塔与 oracle

本章适合四层验证：

1. **规范化单测**：固定原始字符串到 token 列表，包括大小写、标点、数字与空输入；
2. **索引不变量**：`df<=N`、posting 的 `tf>0`、长度和 token 数一致、平均长度可复算；
3. **手算分数**：三文档语料逐项与独立公式对照；
4. **黄金排名**：五篇维修说明的固定查询、分数解释、并列规则和未知词边界。

公开练习故意把集合频率当 `df`，所以 `verify.sh` 应稳定失败并打印 `EXPECTED RED`。私有解答修复后应绿。这种红不是“测试坏了”，而是保存一个可复现的诊断训练点。

测试通过仍不证明真实中文质量。它只证明声明范围内的算法合同。真实质量需要下一章的冻结查询集、独立标签和逐查询指标。

## 18. 一个完整的学习实验顺序

建议按证据循环完成实验：

1. 不运行代码，先写出五篇文档的 `N`、每篇长度、`pump` 与 `bearing` 的 postings；
2. 预测查询 `pump bearing noise` 的第一名和理由；
3. 运行示例并检查逐项贡献，不只看 PASS；
4. 把 `df` 故意改成 `sum(tf)`，预测哪个断言先红；
5. 修复并添加一篇含三次 `pump` 的文档，证明 `df` 只加一；
6. 改变 `b=0`，解释长短文档差异为什么消失；
7. 用 60—120 秒复述倒排索引、`tf/df`、饱和与长度归一化。

如果只能说“BM25 是搜索算法”，还没有达到门禁。合格解释应能指向公式、数据结构、首个失败证据和安全边界。

## 19. 可观测性与重建元数据

检索请求的诊断记录可以包含：请求 ID、查询规范化版本、索引快照 ID、BM25 参数、候选数、零命中标志和耗时分段。不要默认记录完整敏感查询；日志策略应按数据分级、脱敏与保留期执行。

索引构建元数据至少包含：来源水位、文档数量、token 总量、词表大小、构建代码版本、规范化规则版本、开始/结束时间和失败摘要。重建前后应做数量、不变量和冻结查询回归，再切换别名或版本指针。失败时保留旧索引回滚，不要把半成品声明为当前版本。

## 20. 版本与资料边界

本章算法核心是稳定数学概念；可执行资产以 CPython 3.14 运行，未依赖搜索服务。版本核对日期为 **2026-07-24**。Python 小版本和测试工具可能继续更新，所以命令证据比“我机器应该一样”更可靠。

正文没有宣称某个搜索引擎的默认 BM25 公式与本章完全相同。若以后接入 PostgreSQL 全文检索、Lucene、Elasticsearch 或 OpenSearch，必须查其对应版本的官方文档，记录分词器、相似度、字段统计和默认参数，再用本章手算夹具做差异说明。
