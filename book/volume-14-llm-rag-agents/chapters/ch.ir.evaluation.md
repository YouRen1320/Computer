# 固定查询集、相关性标签、Precision、Recall 与排序指标

> “第一条结果看起来不错”不是检索质量证据。检索评估必须先有独立查询与相关性判断，再冻结数据，用同一批输入比较系统。本章只评价候选排名，不调用生成模型补答案，也不允许生成文本掩盖零召回。

## 1. 为什么先评检索，再谈 RAG

RAG 的回答可能写得流畅，即使检索到的依据完全错误；也可能碰巧依靠模型记忆答对，但没有从指定知识库找到证据。如果只评价最终文本，你无法区分：

- 检索没有找到相关文档；
- 找到了，但排在上下文窗口之外；
- 上下文正确，生成却曲解内容；
- 输出正确但引用错误；
- 标签本身不完整或有争议。

本章把问题缩小为：对一条查询，系统返回的有序文档 ID 中，相关文档出现了多少、出现得多早、顺序有多好。这个层次的输入和输出都能保存、手算和回归。

前端类比是组件测试与端到端测试的关系。页面最终可见不代表每个 composable 正确；同样，回答可读不代表检索正确。先隔离候选层，才能定位首个失败阶段。

## 2. 评估数据的三个组成部分

最小离线检索集包含：

1. **查询集**：稳定的 `query_id`、查询文本与切片元数据；
2. **文档集合版本**：每个 `doc_id` 指向哪一个语料快照；
3. **相关性判断**：对 `(query_id, doc_id)` 给出等级、判断状态和依据。

常见文件会把相关性判断称为 qrels。不要只保存自然语言查询和一个“正确答案字符串”。检索指标需要知道哪些文档相关，分级指标还需要相关程度。

数据版本还应包含规范化器、文档切块和索引水位。文档 ID 不变但内容改变，会让旧标签含义漂移；所以 `doc_id` 之外通常还要绑定来源版本或内容哈希。

## 3. 查询集不是随手写十个例子

一个有用查询集应覆盖真实任务分布和重要风险。FactoryCare 维修知识库可以设计这些切片：

- 精确型号、故障码、设备编号；
- 短症状，如“泵异响”；
- 多约束查询，如“夜班压缩机高温且电流波动”；
- 同义表达或口语；
- 否定、时间先后和维修前后对比；
- 本应零结果或需要澄清的问题；
- 长尾设备类别；
- 对权限敏感、不能跨租户暴露的查询。

查询可以来自脱敏日志、支持工单、领域专家和系统性模板，但采样来源必须记录。只由开发者编写的“标准查询”常常过于接近索引词汇，形成乐观偏差。

不能因为某个新参数在 Q7 上失败，就删除 Q7 或改写成系统容易理解的表达。那是在修改考试题迎合答案。查询修订必须走独立的数据版本流程，并保留旧版本结果。

## 4. 相关性不是模型自评

相关性标签必须独立于被评系统。让当前 BM25、向量模型或 LLM 产生标签，再用这些标签证明自己优秀，会形成循环论证。

一份判断指南至少回答：

- “相关”是能直接解决问题，还是只需提供部分背景？
- 过期维修手册是否相关？
- 同一内容不同版本如何取舍？
- 文档提到关键词但语义相反时如何标？
- 权限外文档在质量评估和安全评估中如何处理？
- 信息不足时标不相关、未判断，还是提交仲裁？

二元标签可以用 `0/1`；分级标签可用例如 `0=不相关,1=有帮助,2=高度相关,3=直接依据`。等级名称必须配例子。数字更大不等于标注者天然一致。

重要样本最好由至少两名合格标注者独立判断，再计算一致性并仲裁分歧。小课程夹具没有做真实多人标注，因而不能声称真实标注可靠性已经验证。

## 5. “未标注”不等于“不相关”

大语料无法为每条查询判断所有文档，常通过候选池选择待标注文档。因此一个返回结果可能有三种状态：相关、不相关、未判断。

把缺失键直接当绝对不相关很方便，却可能惩罚新系统找到的有效文档。报告应至少记录 top-k 中未判断数量，并说明指标采用何种政策：

- 未判断按零处理；
- 只在已判断集合计算某些指标；
- 扩充池并补标；
- 使用专门处理不完整判断的评估方法。

本章小夹具为了能手算，在具体指标函数中把字典缺失视为零，但实验报告同时显式列出 `unjudged_top_k`。这不是宣称缺失就是真负例，而是让局限可见。

## 6. 冻结到底冻结什么

可复现比较要求冻结：

- 查询 ID、文本与切片；
- 相关性标签及指南版本；
- 文档集合/切块版本；
- `k`、指标公式与未判断政策；
- 被比较系统的配置、索引版本和随机种子；
- 逐查询原始排名，而不只保存平均分。

实验资产把查询与标签规范化成排序确定的 JSON，再计算 SHA-256。哈希不是质量证明，只是检测数据是否悄悄变化。两份同义但序列化顺序不同的数据若未先规范化，会产生不同哈希，所以规范 JSON 合同也是冻结的一部分。

调参可以使用开发集；最终结论应在未参与调参的测试集复核。反复查看测试集并据此选参数，会让测试集变成开发集。

## 7. 从一条查询定义集合

对查询 `q`：

- `R_q`：所有被标为相关的文档集合；
- `A_q@k`：系统排名前 `k` 的文档集合；
- `hits = |R_q ∩ A_q@k|`。

排序指标还保留每个命中的名次和等级。先用集合思维理解 Precision/Recall，再引入位置折损，会更不容易混淆。

同一文档不能在排名中重复出现。重复 ID 会虚增命中或占用多个位置，因此指标入口应拒绝重复候选，而不是默默去重后假装系统正常。

## 8. Precision@k：前面有多“干净”

本章定义：

```text
P@k = top-k 中相关文档数量 / k
```

若前 3 条有 2 条相关，`P@3=2/3`。即使系统只返回 2 条，本合同分母仍是 3，缺失位置相当于未命中。其他实现可能以实际返回数为分母，比较前必须对齐定义。

Precision 适合用户只看前几条的场景，但不告诉你漏掉多少相关文档。一个系统只返回最确定的一条，`P@1` 很高，却可能遗漏大部分证据。

## 9. Recall@k：相关文档找回多少

定义：

```text
R@k = top-k 中相关文档数量 / 全部已知相关文档数量
```

已知有 4 篇相关，前 5 找到 3 篇，则 `R@5=3/4`。若标签中没有任何相关文档，分母为零。不要悄悄返回 0 或 1；本章实现抛出明确错误，让数据治理决定这是零答案查询、漏标还是应使用其他指标。

Recall 依赖相关性判断覆盖率。若只标注旧系统返回的候选，新系统找到的相关文档可能被当成未知或负例，所谓“全部相关文档”只是已知集合。

## 10. MRR：第一个相关结果有多早

对单条查询，reciprocal rank 是第一个相关文档名次的倒数：

```text
RR(q) = 1 / rank_of_first_relevant
```

第一名相关得 `1`，第二名得 `0.5`，第五名得 `0.2`，没有相关结果得 `0`。MRR 是多条查询 RR 的算术平均。

MRR 只关心第一个相关结果。第二、第三个相关文档排得再好也不会继续加分，因此不适合需要多份证据覆盖的唯一指标。它适合“找到一个正确入口即可”的导航式任务。

## 11. DCG 与 nDCG：让等级和位置同时起作用

分级相关性需要区分“直接依据”和“略有帮助”。本章采用：

```text
gain(rel) = 2^rel - 1
discount(rank) = log2(rank + 1)

DCG@k = Σ gain(rel_i) / discount(i)
```

第一名分母为 `log2(2)=1`；越靠后折损越大。指数增益让高等级文档比多个低等级文档更重要，这是一个设计选择，必须记录。

不同查询的相关文档数量和等级不同，原始 DCG 不易横向比较。先把同一查询的标签按等级降序排列得到理想排名，计算 `IDCG@k`：

```text
nDCG@k = DCG@k / IDCG@k
```

有正相关标签时，理想排序应得到 1。若没有任何正增益，本章返回 0，但报告仍应标记该查询的标签问题。

最典型错误是直接用系统排名计算 `IDCG`，令分子等于分母，于是糟糕排序也得到 1。公开练习专门保存这个稳定红。

## 12. 一条查询的完整手算

固定排名与等级：

```text
ranking = [D2, D1, D3, D4]
grades  = {D1:2, D2:0, D3:1, D4:0}
k = 3
```

相关集合是 `{D1,D3}`。前三名包含两篇相关：

```text
P@3 = 2/3
R@3 = 2/2 = 1
RR = 1/2
```

DCG：

```text
rank1 D2: (2^0-1)/log2(2) = 0
rank2 D1: (2^2-1)/log2(3) = 3/log2(3)
rank3 D3: (2^1-1)/log2(4) = 1/2
```

理想顺序是 `D1,D3`：

```text
IDCG@3 = 3/log2(2) + 1/log2(3)
nDCG@3 = (3/log2(3)+1/2) / (3+1/log2(3))
```

可执行示例对每一项使用独立手算式，不调用被测试的 `dcg_at_k` 来生成期望值。若测试与业务实现共享同一个错误函数，绿色没有鉴别力。

## 13. 平均值会隐藏失败查询

三条查询 recall 分别为 `1,1,0`，平均值约 `0.667`。只报告平均值，很容易漏掉第三条完全零召回。至少同时报告：

- 查询数量和每条原始排名；
- 均值、中位数和适当分位数；
- 零召回数量/比例；
- 预先定义切片的指标；
- 未判断结果数量；
- 与基线逐查询差值，而不是只有总体差。

宏平均先算每条查询指标再平均，让每条查询权重相等。微平均先汇总命中与分母，会让相关文档较多的查询权重更大。二者没有绝对谁对；必须匹配产品目标并命名清楚。

不要从结果中临时挑“提升最大”的切片做报告。切片应在实验前定义，或明确标为探索性发现并在新数据复核。

## 14. 歧义查询与零答案查询

“device alarm” 可能对应多个设备、告警类型或时间范围。低指标不一定只说明算法差，也可能说明查询需要澄清。评估集应给它 `ambiguous` 切片，并规定期望：返回通用排障文档、覆盖多个意图，还是触发澄清。

零答案查询指知识库确实没有依据。它不适合用普通 recall 分母评估；更适合判断系统是否拒绝、澄清或明确“无证据”。不要为了让 recall 有定义，随便标一篇边缘文档相关。

这两类必须与“漏标”区分。标签状态、仲裁记录和失败分析是指标之外的必要证据。

## 15. 基线、候选与实验协议

一次可比较实验可按以下顺序：

1. 固定语料快照、查询集与 qrels 哈希；
2. 记录 BM25 基线的代码、参数、索引版本；
3. 对每条查询保存 top-k 文档 ID 与分数解释；
4. 计算逐查询指标和预定义切片；
5. 只在开发集选择参数；
6. 在测试集一次性复核，并报告相对基线的收益与退化；
7. 对新出现的未判断候选补标时，创建新数据版本并重跑所有系统。

同一个系统也要保存运行失败、超时和空列表。删除失败查询会造成幸存者偏差。

若比较两个系统，应使用成对分析：对同一查询计算差值，观察提升是否集中在极少数样本。样本很小时，不要用一个小数点后四位的均值营造精确感。

## 16. 统计不确定性

离线指标是查询样本上的估计。查询数量有限时，均值会随样本变化。可以通过 bootstrap 等方法估计置信区间，但前提是抽样单位、独立性假设和过程记录清楚。

“均值提高 0.01”不能自动推出真实用户体验改善。还要考虑：

- 区间是否高度重叠；
- 提升是否来自重复或相似查询；
- 关键安全切片是否退化；
- 延迟、成本与索引新鲜度是否恶化；
- 标注误差是否大于观察差异。

课程小夹具只有三条查询，没有统计功效，验证的是指标实现和报告结构，不是显著性。

## 17. 离线指标与线上指标不是替代关系

离线评估快速、可复现，适合回归和消融；线上实验能观察真实交互，却受界面、用户群、位置偏差和反馈回路影响。

线上可观察点击、停留、任务完成、改写、人工升级等，但点击不等于相关：第一名更容易被点，用户也可能因标题误导进入后立刻退出。必须配合实验设计和安全护栏。

离线好是上线候选的必要证据之一，不是充分条件。线上数据也不能直接回填成无偏标签；被旧系统曝光的文档更容易获得反馈。

## 18. 用 pandas 做报告时的边界

`pandas.DataFrame` 适合保存每条查询一行的结构化报告：`query_id`、切片、四个指标、未判断列表、排名和系统版本。`groupby` 可做预定义切片聚合。

但 DataFrame 不会自动保证实验有效。常见错误包括：

- join 后一条查询重复多行，平均时被重复加权；
- 缺失值被默认丢弃，失败查询消失；
- 不同系统使用不同 query 集，均值不可比；
- 只保存聚合 CSV，没有原始排名；
- 读取文件时类型推断改变文档 ID，例如前导零丢失。

资产把 pandas 固定为 `3.0.5` 并断言版本，是为了让运行证据可复现，不表示 DataFrame 本身是 oracle。

### 18.1 一份可执行的标注指南

“请判断是否相关”太模糊。指南应给标注者一组可观察问题：文档是否针对指定设备/故障；信息是否在有效版本；能否直接支持诊断动作；是否只是出现关键词；是否与查询结论相反；证据不足时如何处理。

例如四级合同可以写成：

```text
3：直接回答核心故障，设备范围和版本匹配，可作为主要依据
2：提供关键排查步骤，但仍需另一份文档补全
1：提供背景或邻近故障信息，不能单独解决
0：无关、对象错误、版本失效或语义相反
U：未判断/证据不足，不能自动当 0
```

每级至少准备正例、反例和边界例。指南改变时创建新版本；不要把旧标签的数字原样搬到新语义下。仲裁记录应保留原始两名标注者结果、最终结果和理由，不能只覆盖成一个数字。

### 18.2 候选池如何构建

若语料很大，可把多个有差异的检索器 top-N 取并集，形成待判断池。只用当前系统建池会让评估偏向当前系统。池应包括词法、稠密、历史系统、规则/人工候选，并记录来源。

新系统出现大量池外候选时，先把它们标为 `U`，再按盲化流程补标。不能只审查看起来能提升新系统的结果。补标后数据集版本变化，所有基线都应重跑，以相同新 qrels 比较。

池化仍无法保证发现全部相关文档，所以 Recall 是对已知相关集合的估计。报告要说明池深、参与系统和未判断率，不把有限池描述为完整宇宙。

### 18.3 标签审计的抽样策略

可以优先审计：标注者分歧、系统差值大、top1 改变、未判断、零召回、关键安全切片和模型高置信但人工判零的样本。同时保留随机样本，避免只看异常而无法估计整体错误率。

审计人不应看到“哪个系统返回”再判断相关性，否则品牌/方案偏好会影响标签。盲化 doc 顺序和系统来源，记录标注时可见的信息。若文档访问本身受权限约束，标注平台也必须执行相同数据治理。

### 18.4 指标对排名扰动的敏感性

用本章手算例做三个变换：

1. 把第一个相关文档从 rank2 移到 rank1：P@3、R@3 不变，RR 和 nDCG 提高；
2. 把第二个相关文档移出 top3：P@3、R@3、nDCG 降低，RR 可能不变；
3. 在 top3 内交换两个同等级相关文档：四个指标都不变。

这个练习说明指标回答不同问题。若产品要求“用户看到第一条即可行动”，RR/top1 更重要；若需要多份依据覆盖，Recall/nDCG 更重要。不能看到某指标提升就反向声称用户目标已改善。

### 18.5 截断深度与指标曲线

只报告 `k=10` 会隐藏用户只看前三条的体验。建议预先选择 `k∈{1,3,5,10}`，绘制 P/R/nDCG 曲线。k 越大，Recall 通常不降，但 Precision 可能下降；MRR 不需要 k（若定义截断 MRR 则必须命名）。

不同系统返回长度不足时保留空位政策。一个系统超时只返回两条，不能在 `P@10` 中把分母偷偷改成 2。若 API 本身规定“最多返回可用结果”，可以另报实际返回精度，但名称和公式要分开。

### 18.6 回归门禁与非劣阈值

发布门禁不能只写“平均指标不能下降”，因为浮点波动和样本噪声会让规则不稳定。可预先定义：总体 nDCG 提升下限、关键切片最大允许退化、零召回不得增加、ACL 泄漏为零、未判断率上限与延迟预算。

某些切片可以采用非劣门禁：新系统未必提升，但不能低于基线超过容忍值。安全切片通常没有“平均抵消”；任何跨租户泄漏都直接失败。

门禁失败后保存完整报告和配置，不要只重跑到偶然通过。若算法含随机性，固定种子并评估多次分布；选择最好一次是另一种 cherry-picking。

### 18.7 数据变更、代码变更与结论变更

实验记录应把三类版本分开：

```text
dataset_version = 查询 + 标签 + 文档快照
system_version  = 检索代码 + 模型/索引 + 参数
evaluator_version = 指标公式 + k + 未判断政策
```

只改 evaluator 的 nDCG bug，所有历史系统都要在同一修正版上重算；只改 qrels，也要重算基线；只改系统则保持数据与 evaluator 不动。三者混在一个 `v2` 字符串中，会让结果无法归因。

### 18.8 一个最小实验清单

提交评估报告前逐项核对：数据哈希是否一致；query ID 数是否相同；是否有重复排名；是否保留空/失败查询；top-k 未判断率；指标单位测试；逐查询文件；预定义切片；基线与候选配置；环境和运行时间；已验证/未验证声明。

如果任何一项缺失，报告可以标为探索性结果，但不能作为发布门禁完成证据。把不确定性写清楚比补一个漂亮图表更重要。

### 18.9 文件合同与逐查询可复算性

不要把查询、标签、排名和指标全塞进一张不断覆盖的 Excel。更稳定的最小布局是：

```text
dataset/queries.jsonl       # query_id、文本、预定义切片
dataset/qrels.jsonl         # query_id、doc_id、grade、判断状态、指南版本
runs/bm25-v1.jsonl          # query_id、按顺序的 doc_id、原始分数、系统版本
reports/per-query.csv       # 每条指标、未判断数、错误状态
manifest.json               # 文件哈希、语料水位、evaluator 版本、命令
```

JSONL 每行使用稳定 ID，排序和编码政策写入 manifest。排名文件必须保留完整顺序，不能只存 top1；分数可保留用于诊断，但指标以名次和标签为 oracle。系统超时也写一行 `{status:"timeout"}`，使查询数不悄悄减少。

报告生成器应能从 dataset + run 完全重算，而不是依赖 notebook 内存。CI 可核对哈希、ID 集相等、重复文档、等级范围和行数，再计算指标。图表只是这个结构化报告的视图。

### 18.10 评估代码自己的测试

评估器也是软件，需要比被评系统更可信的测试。至少包含：完美排名得到 nDCG=1；完全无命中 Recall=0；第一相关名次移动时 RR 正确；重复 ID 被拒绝；`k<=0` 被拒绝；无正标签的 Recall 明确失败；同等级交换不改变 nDCG；系统顺序不能充当 IDCG。

还可做性质测试：把不相关文档从 top-k 移到 k 之外，指标不应下降；把最高等级文档向前移动，nDCG 不应下降。性质不能替代手算固定例，但能覆盖更多组合。

任何评估器版本修复都要重算历史 run。不要只重算新系统，否则基线仍带旧 bug，比较失真。

## 19. 失败诊断路径

### 19.1 用系统生成标签

首个问题在数据来源，不在指标公式。检查 qrels 的创建者、输入和审批记录。修复是独立重标和版本化，不是换一个更好看的指标。

### 19.2 查询集随调参变化

比较前先核对哈希与 query ID 集。如果不同，任何均值差都不能直接归因于算法。恢复相同冻结集后重跑。

### 19.3 平均值提高但关键查询失败

查看逐查询差值、零召回和安全切片。若某个故障码切片退化，不能用其他简单查询的提升抵消风险，除非产品事先定义了这样的权衡。

### 19.4 nDCG 总是 1

先用“最高等级故意放最后”的两文档例。若仍为 1，检查 `IDCG` 是否独立排序。首个可信位置是指标中间量，不是最终图表。

### 19.5 新系统大量“错误”来自未标注

检查 `unjudged_top_k`。抽样复标新候选，扩展判断池，创建新数据版本，并在新旧系统上共同重算，不能只补新系统有利的文档。

## 20. 安全与 FactoryCare 所有权

质量评估不能替代权限测试。一个系统 nDCG 很高却返回其他租户文档，是严重失败。至少分开保存：

- 内容相关性指标；
- ACL 泄漏计数，目标必须为零；
- 索引陈旧、已删除文档残留；
- PII 或敏感字段暴露；
- 无证据时的拒绝/澄清行为。

Java 仍拥有用户身份、租户、工单状态与 ACL 决策。评估夹具可以复制匿名文档 ID 和预期授权集合做回归，但不能把 Python 报告升级为授权来源。搜索索引、查询集报告和排名均是可重建派生数据。

## 21. 可执行资产如何证明什么

`examples/encyclopedia/ch.ir.evaluation/` 用一条查询手算四类指标。`labs/encyclopedia/ch.ir.evaluation/` 使用三条固定查询，输出零召回与歧义切片、未判断候选和数据哈希。

三类应绿资产已经覆盖：公式、无相关标签错误、重复排名、哈希顺序稳定与 pandas 报告。公开练习保留错误 `IDCG`，因此应稳定红。私有解答构造独立理想排序。

这些验证没有证明：真实查询代表性、标签者一致性、生产召回、统计显著性、线上效果或安全性。任何报告都必须把这段“未验证”保留，而不是因为脚本 PASS 就删除。

## 22. 学习实验

按以下顺序完成：

1. 手算本章 `D2,D1,D3` 例的四个指标，再运行脚本；
2. 预测把 `D1` 移到第一名会改变哪些指标、哪些不变；
3. 给实验增加一条没有正相关标签的查询，观察失败阶段；
4. 给 top-k 增加未标注文档，解释为何不能直接断言它不相关；
5. 把 `IDCG` 故意复制系统顺序，观察稳定红并定位中间量；
6. 写一份包含查询来源、指南版本、哈希和非目标的实验卡；
7. 用 120 秒解释为什么生成答案不能修复检索零召回。

## 23. 版本与资料边界

版本核对日期为 **2026-07-24**。资产目标是 CPython 3.14、pandas 3.0.5。指标公式属于稳定核心；库的聚合、缺失值和排序行为可能随版本变化，所以脚本固定并打印/断言运行版本。

一手版本入口：[Python 3.14 官方文档](https://docs.python.org/3.14/)、[pandas 3.0.5（PyPI）](https://pypi.org/project/pandas/3.0.5/)。实际验证使用的是本机由 `uv --python 3.14` 解析出的解释器；不能仅凭官方当前补丁号声称本机已经运行该补丁。

正文未把某个第三方 RAG 评估框架当作真值，也未声称自动 LLM judge 等于领域专家标签。若以后使用自动判断器，应保存模型、提示、随机性、校准集、人与模型分歧和成本，并继续保留独立人工审计。
