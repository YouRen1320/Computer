安全工作最常见的次序错误，是先说“上 WAF、加密、JWT、验证码”，再寻找这些技术能解决什么。控制如果没有对应资产、攻击者、数据流和失败场景，就无法判断必要性，也无法验证是否真正降低风险。威胁建模把次序反过来：先说明正在保护什么、系统怎样工作、哪里跨越信任，再从攻击者视角问哪里会出错，最后选择控制并给出验证证据。

## 2. 安全目标：先定义什么算失败

安全目标描述系统必须保持的性质。没有目标，“漏洞严重吗”“控制值得吗”都缺少判断依据。经典 CIA 三元组是起点：

| 目标 | 要保护的性质 | FactoryCare 例子 | 典型失败证据 |
| --- | --- | --- | --- |
| 机密性 Confidentiality | 只有获准主体能读取信息 | A 租户看不到 B 租户工单和附件 | 越权响应包含他租户字段 |
| 完整性 Integrity | 数据和处理结果未经未授权修改，变更可验证 | 工单状态只能按状态机迁移 | 客户端直接把 CLOSED 改回 CREATED |
| 可用性 Availability | 获准主体在约定条件下能获得服务 | 创建与派单在容量边界内可用 | 单一通知故障拖垮写事务 |

CIA 不足以表达所有系统目标。身份真实性回答“当前主体是谁”；授权回答“这个主体能做什么”；可追责性要求关键行为能关联到主体、时间、对象和结果；隐私关注收集、使用、保留和披露是否正当；安全性 safety 关注数字错误是否造成现实伤害。它们可能重叠，却不能互相替代。例如 TLS 能保护传输机密性与完整性，不证明调用者有权读取该工单。

目标应可观察。把“高安全”“军工级”“完全合规”写成目标无法产生断言。更好的写法是：“任何工单读取都必须同时满足当前成员关系、角色和租户范围；删除成员后，下一次请求不得继续依赖旧声明放行。”后者能映射到具体入口、状态和失败测试。

目标也有冲突。把所有字段无限期写入审计日志可能提高追责，却破坏最小化和隐私；严格锁死账号可能降低猜测风险，却给攻击者制造拒绝服务。模型必须记录权衡、风险接受人和复审条件，而不是假装一个控制只带来收益。

## 3. 资产、主体与攻击者不是同一个列表

**资产**是组织需要保护、攻击者想获得或可用作跳板的对象。数据只是资产的一类。FactoryCare 的资产包括工单及状态历史、租户成员关系、角色与范围、附件、审计轨迹、通知能力、服务凭据、数据库可用性，以及客户对系统结论的信任。密钥是资产，能签发密钥的管理流程也是资产。

资产清单至少记录：标识、所有者、业务价值、数据分类、CIA 优先级、生命周期、存储/流经位置和受损影响。不要只写“数据库”；数据库中不同对象的敏感度、完整性要求和恢复目标不同。也不要把“个人信息”当成永恒不变的一个桶，应说明哪些字段、为谁、在哪个目的和保留期内敏感。

**主体 subject** 是进行操作并被系统判断的实体，可以是人、服务、设备或批处理任务。**角色**是授权属性，不等于主体。**账号**是系统内承载身份状态的记录，也不等于现实中的人。共享管理员账号把多个自然人压成一个主体标识，会削弱追责。

**模型对象 subject under analysis** 则是本次建模的范围，例如“创建工单 API 及其异步通知”，不要与身份领域的 subject 混淆。范围应写入版本、入口、依赖、部署假设和明确不包含项。

**攻击者**按能力和位置描述，不按“坏人”描述。至少考虑：

- 未认证互联网调用者，可批量构造 HTTP 消息；
- 已认证低权限成员，拥有合法账号并能修改资源 ID；
- 被控制的浏览器或移动端，能读取客户端可见材料；
- 恶意或被盗用的管理员身份，能调用高权限功能；
- 内部运维或开发人员，可能误用查询、日志和备份权限；
- 被攻陷的第三方通知服务，能观察请求或返回恶意/异常响应；
- 自动化攻击者，预算有限但能并发、重试和轮换来源；
- 偶发故障与误操作。威胁不一定出于恶意，错误配置和依赖故障同样破坏目标。

能力假设决定威胁是否成立。若假设攻击者已经取得数据库快照，就要分析离线破解与租户批量泄露；若假设只能访问公开 API，就要分析枚举、速率和业务逻辑。把“内部网络可信”当作结论会遗漏内部人、凭据泄露和横向移动。

## 4. 威胁、攻击、漏洞、风险与控制

这些词必须分开：

- **威胁**：可能破坏安全目标的情景，如低权限成员读取他租户工单；
- **攻击**：攻击者为实现威胁采取的动作，如替换路径中的 `orderId` 并重放请求；
- **漏洞/弱点**：让攻击成功的条件，如仓储查询只按工单 ID，不带租户和成员约束；
- **影响**：成功后对业务、用户或系统的后果；
- **可能性**：在当前能力、暴露和控制下发生的相对机会；
- **风险**：不确定性下的可能性与影响组合；
- **控制/缓解**：预防、检测、响应或恢复风险的措施；
- **剩余风险**：控制实施后仍保留的风险。

“使用 PostgreSQL”“安装了 Spring Security”不是控制说明。可验证控制应包含执行位置、输入、决策、拒绝行为、失败模式和证据。例如：“仓储端所有按 ID 查询同时绑定 `tenant_id`；应用层从当前成员关系构建租户上下文；跨租户 ID 返回统一不可见结果；集成测试用两个租户的同值资源重放。”

同一控制可能缓解多个威胁，一个威胁也通常需要多层控制。认证不能替代授权；输入校验不能替代参数化查询；加密不能替代访问控制；日志不能预防越权，但可以检测和调查。防御纵深的意义是某一层失效时仍有限制，不是重复堆叠相同检查而无人知道哪一层负责。

## 5. 攻击面：攻击者能触达的可变边界

攻击面是攻击者可影响、观察或滥用的入口和依赖集合。HTTP 路由只是其中一部分，还包括：

- 请求方法、路径、查询、头、Cookie、正文和文件上传；
- WebSocket、消息队列、定时任务、导入文件和管理命令；
- 数据库账号、备份、对象存储、缓存和搜索索引；
- CI/CD、制品仓库、配置中心、密钥管理与运维控制面；
- 第三方回调、通知、支付、身份提供者和 AI 服务；
- 日志、指标、追踪和错误页面等旁路输出；
- 人工恢复、客服、管理员批量操作和 break-glass 流程。

攻击面不是漏洞数量。一个正确校验的公开入口仍属于攻击面；一个从不暴露但权限过大的备份账号同样属于攻击面。攻击面会随新功能、部署拓扑、依赖升级和运维流程变化，因此威胁模型必须随系统维护，而不是立项时一次性归档。

对每个入口记录：谁可达、协议、认证前后状态、数据分类、速率、解析器、下游副作用、超时与失败回退。对每个出口记录目的地、允许字段、凭据、完整性保护、重试/幂等和依赖失效影响。

## 6. 信任域与信任边界

**信任域**是一组在当前目的下接受相似安全假设与控制的组件。**信任边界**是数据、控制或执行权从一个域进入另一个域的地方。边界不是防火墙图标，也不是“内外网”的同义词；进程、容器、账号、租户、权限级别、管理员控制面和第三方组织都可能形成边界。

“信任”是带条件的。后端可以信任 PostgreSQL 按协议返回字节，却不能因此跳过行级范围约束；可以信任身份提供者签名，却仍要检查发行者、受众、时效和当前成员关系；可以信任应用服务创建领域命令，却仍应由领域对象维护状态不变量。

每次跨界都要重建或验证所需上下文：

1. 对端身份和连接是否符合预期；
2. 消息是否完整、在时效内且未被重放；
3. 主体是否对目标动作和数据范围有权限；
4. 输入是否满足当前边界的结构与业务约束；
5. 输出是否只含允许披露的数据；
6. 超时、重试、降级和异常是否保持安全默认；
7. 事件是否留下足以调查、又不泄密的证据。

边界要画在数据流上，而不是只列在说明文字里。一个流可能穿过多个边界，例如浏览器 → CDN/WAF → Java 公共适配器 → 应用服务 → PostgreSQL。每一跳的责任不同，不能用“入口已经验证”覆盖后续所有决策。

## 7. 用 DFD 描述系统怎样工作

数据流图 DFD 不是部署图。它用少量元素描述数据怎样被处理：

- 外部实体：浏览器、管理员、第三方通知；
- 处理过程：Java API、领域服务、通知适配器；
- 数据存储：PostgreSQL、对象存储、审计存储；
- 数据流：HTTP 请求、SQL 参数/结果、outbox 事件、通知载荷；
- 信任边界：互联网到公共入口、应用账号到数据库、组织到第三方。

每个节点应有稳定 ID、类型、所有者和信任域；每条流应有方向、协议、数据分类、认证/授权上下文及失败行为。双向交互要画两条流，因为请求和响应的数据、威胁与控制不同。不要用一个“API”箭头隐藏认证前入口、业务写入和异步通知。

可以先画上下文级，再分解高风险过程：

```text
[E1 浏览器 / UNTRUSTED]
        | F1 创建工单 HTTP（身份声明、租户、正文）
        v  ===== TB1 互联网 → 公共应用 =====
(P1 Java 公共适配器 / APP)
        | F2 已校验命令 + 当前成员上下文
        v
(P2 工单应用服务 / APP)
        | F3 参数化写入 + tenant_id
        v  ===== TB2 应用账号 → 数据库 =====
[(D1 PostgreSQL / DATA)]
        ^ F4 写入结果
        |
(P2) -- F5 outbox 事件 --> (P3 通知适配器 / APP)
        -- F6 最小通知载荷 --> ===== TB3 组织 → 第三方 ===== [E2 通知商]
```

图必须与代码和部署事实相符。若真实系统通过 outbox 异步通知，图却画成事务内直接调用，超时、重试和一致性威胁都会分析错。模型审阅时应让开发、运维、产品和安全共同核对，尤其询问“还有没有批处理、管理员、回调、备份或人工流程绕过这张图”。

## 8. 数据流逐项提问

对每条流至少问：

- 来源可以伪造吗？接收方怎样确认对端与主体？
- 内容能被篡改、截断、重复、乱序或替换吗？
- 流中包含哪些资产，是否过量披露？
- 接收方是否把来源域的声明当成自己的授权事实？
- 解析器面对超长、嵌套、重复字段和非法编码怎样失败？
- 失败会重试吗，重试是否造成重复副作用或放大？
- 依赖不可用时是安全拒绝、排队、降级还是错误放行？
- 能否把行为关联到主体、对象和结果，日志是否泄露载荷？

对每个存储问：谁能读写、以什么账号、如何分租户、备份到哪里、保留多久、删除如何传播、恢复后旧凭据是否复活。对每个处理过程问：以什么权限运行、如何取得密钥、哪些输入决定资源范围、异常是否暴露内部细节。

“有 HTTPS”只回答部分传输威胁。浏览器可能已被控制，Java 适配器可能对正文过度信任，数据库查询可能漏租户条件，第三方仍可能保存通知内容。模型必须沿整条流继续问。

## 9. STRIDE 是提问器，不是盖章器

STRIDE 把常见威胁分成六类：

| 类别 | 破坏的性质 | 对数据流的提问 | FactoryCare 场景 |
| --- | --- | --- | --- |
| Spoofing 身份伪造 | 真实性 | 能否冒充主体或服务？ | 接受错误 issuer 的身份声明 |
| Tampering 篡改 | 完整性 | 能否未授权修改消息/存储？ | 客户端改写工单状态或 tenantId |
| Repudiation 抵赖 | 可追责性 | 行为能否可靠归因和调查？ | 管理员恢复无 actor/result 审计 |
| Information Disclosure 信息泄露 | 机密性 | 是否向无权方披露？ | IDOR 返回他租户附件元数据 |
| Denial of Service 拒绝服务 | 可用性 | 哪个有限资源可被耗尽？ | 通知超时占满请求线程/连接 |
| Elevation of Privilege 权限提升 | 授权 | 能否获得不应有的能力？ | 普通成员调用管理员恢复接口 |

STRIDE 的价值在于让团队系统提问，不在于每个格子都填满。它不自动覆盖隐私目的限制、欺诈、供应链、现实安全、社会工程或组织流程。可按领域补充 abuse case、attack tree、LINDDUN、MITRE ATT&CK 或业务风险工作坊，但不同方法的适用范围要标明。

也不要把类别直接当漏洞名。“数据库有 Tampering”不够可行动；应写成攻击者、前置条件、动作、目标、影响和当前控制，例如：“已认证的 A 租户成员把请求路径 ID 换成 B 租户工单；仓储若只按 ID 更新，会破坏租户完整性并泄露存在性。”

## 10. 滥用场景让威胁可执行

滥用场景以攻击者目标描述系统被怎样使用，格式可固定为：

> 给定【攻击者能力与起点】，当其【动作/路径】，若【薄弱条件】，则【资产与安全目标】受损；系统应由【控制】阻止/检测，并由【证据】证明。

创建工单 API 至少包含：

1. **认证绕过**：未认证调用者伪造身份头；入口必须只接受受支持认证上下文，测试应删除/伪造上下文并得到一致拒绝。
2. **越权/跨租户**：低权限 A 成员替换 tenant/order ID；当前成员关系、角色和仓储范围共同约束，两个租户夹具应可重放。
3. **篡改**：客户端提交服务端拥有的状态、创建者或审计字段；输入 DTO 采用允许列表，领域状态机拒绝非法迁移，持久化前后有断言。
4. **泄露**：错误响应、通知载荷或日志包含正文、附件地址、身份声明；契约测试断言字段允许列表，日志测试断言无凭据和敏感正文。
5. **拒绝服务**：超大正文、批量请求或通知超时消耗解析器/线程/连接；限制大小和速率、异步隔离、超时与容量测试共同证明。
6. **内部滥用**：管理员或运维绕过普通 UI 批量查看/恢复；独立高权限入口、最小权限、强认证、审批和不可篡改审计降低风险。

只列 CVE 或技术漏洞会漏掉业务流程和内部边界。反过来，只写故事却不绑定具体数据流，也无法知道控制应实施在哪里。

## 11. 风险排序：透明表达不确定性

团队资源有限，需要排序，但一个漂亮分数不等于客观真相。可以用低/中/高，或“可能性 × 影响”的有限矩阵；必须同时记录：

- 评分时的架构版本与攻击者假设；
- 影响涉及哪些资产、租户和现实后果；
- 可利用性、暴露、检测能力和现有控制；
- 证据来源与置信度；
- 未知项、模型盲区和复审日期；
- 处置：消除、缓解、转移或由明确责任人接受。

不要把不确定性伪装成小数精度。一个未暴露的管理入口上线后，可能性会变化；一个新数据类别进入通知，影响会变化。风险条目应能关联代码/架构变更，而非永远留在电子表格。

优先级还要考虑控制成本、可逆性和爆炸半径。移除不必要的数据流往往比给它叠加多个控制更可靠；把通知移出数据库事务既减小可用性耦合，也改变一致性模型，需另行验证 outbox 与重试。

## 12. 控制分为预防、检测、响应和恢复

预防控制降低攻击成功机会，如认证、最小权限、租户范围查询、输入允许列表和出站字段最小化。检测控制提高发现能力，如高风险操作审计、异常速率指标和跨租户拒绝事件。响应控制规定告警、隔离、凭据撤销和沟通。恢复控制包括可靠备份、恢复演练、重放保护和一致性校验。

每个控制条目至少包含：

- `control_id` 与负责人；
- 缓解的 `threat_id`；
- 实施位置和安全默认；
- 预期失败行为；
- 验证方式与证据路径；
- 依赖和绕过条件；
- 上线状态、复审时间与剩余风险。

孤儿控制——没有威胁引用的控制——可能是范围遗漏，也可能是无目的成本；无控制威胁则必须标记计划、接受或阻塞上线。一个控制写成“检查权限”仍不够，应说明依据哪个当前主体、哪份成员关系、哪个资源范围，在缓存/依赖失败时拒绝还是放行。

## 13. 验证：模型必须落到测试和运营证据

威胁模型的第四问是“做得够好吗”。答案不能只是开会签字。不同控制对应不同证据：

| 控制 | 合适证据 | 一个反例 |
| --- | --- | --- |
| 跨租户授权 | 两租户集成测试、仓储查询约束、拒绝审计 | 只测自己的合法 ID |
| 请求完整性/校验 | 边界值、非法编码、未知字段与超长输入测试 | 只测 happy path JSON |
| 通知最小化 | 出站契约字段允许列表 | 人工看一封通知 |
| 超时与隔离 | 故障注入、资源上限、事务边界断言 | 配了 timeout 字符串却未触发 |
| 审计 | actor/action/object/result/correlation schema 与不可泄密测试 | 只有自由文本 message |
| 恢复 | 定期恢复演练、校验和、RPO/RTO 证据 | 看到备份任务显示 green |

验证条目要有 expected/actual，失败时指出第一处可信偏差。不要从最后的 `MODEL_INVALID` 倒猜；验证器应先报告缺失节点、未知边界、孤儿控制或未映射威胁。修复后必须重跑同一故障输入，防止“换了一个更容易的样例”。

自动化只能检查可编码不变量，例如 ID 引用完整、每条流有信任域、每个威胁有控制和验证、关键滥用类别齐全。它不能判断团队是否遗漏了全新攻击路径，也不能证明控制实现正确。因此机器断言、跨角色评审、代码测试和运行演练要组合使用。

## 14. FactoryCare 的模型边界

FactoryCare 的权威安全边界见[项目威胁模型](../../../factorycare-design/security/threat-model.md)。本章实验只截取“创建工单并发送通知”这一纵切片；不能把实验简化结果回写成全系统事实。

本切片的关键资产：租户成员关系、工单正文与状态、创建者归属、附件引用、outbox 事件、通知最小载荷、审计轨迹。关键主体：浏览器中的成员、Java 公共适配器、应用服务、数据库账号、通知适配器、第三方通知商、管理员和内部运维。

关键边界：

- 不受信客户端 → Java 公共适配器：重建并校验安全上下文，不信任客户端 tenant/role；
- Java 应用 → PostgreSQL：使用受限账号，查询和写入绑定租户，事务保持工单与 outbox 一致；
- Java → 第三方通知：只发送目的所需字段，设置超时/重试/幂等，第三方结果不能改写授权事实；
- 管理员/运维 → 控制面：与普通成员路径分开建模，要求更强控制、审批和审计；
- 日志/审计出口：允许调查但不得记录密码、Token、完整附件内容或可重放链接。

项目 ADR 已决定生产身份由外部 OIDC 提供者负责；即便身份声明签名有效，Java 仍要用当前成员关系、角色和数据范围授权。身份协议细节属于后续章节，本章只把它当作信任边界与假设。

## 15. 一份可维护的威胁条目

建议条目采用稳定结构：

```text
id: TM-WO-02
asset: A-WORK-ORDER
actor: ATTACKER-LOW-PRIVILEGE-MEMBER
flow: F1 create-work-order-request
boundary: TB1 untrusted-client-to-public-adapter
category: Elevation of Privilege / Information Disclosure
scenario: A 租户成员替换 tenantId 以在 B 租户创建或探测工单
impact: 跨租户完整性与机密性受损
control: C-AUTHZ-02 当前成员关系 + 租户范围命令 + 仓储 tenant_id 约束
validation: V-AUTHZ-02 两租户重放测试；未知/他租户结果一致不可见
residual_risk: 受损管理员与内部数据访问另建条目
owner: identity-and-organization
review_trigger: 成员缓存、仓储查询或 OIDC 映射变化
```

ID 让图、条目、控制、测试和变更记录可以互相引用。描述若不含攻击者、动作和影响，后续团队只看到模糊标签；验证若不含边界与失败输入，上线后也无法确认控制仍有效。

## 16. 常见失败与诊断顺序

**失败一：只列技术漏洞。** 先核对范围和数据流，再找缺失的业务滥用、管理员、备份和第三方。技术扫描结果可以成为输入，不是完整模型。

**失败二：把网络位置当信任。** 找每条跨进程、账号、租户、权限和组织边界的数据流；问接收方实际验证了什么。

**失败三：图与代码漂移。** 从真实路由、消息、仓储和部署清单核对；新增流若没有模型 ID，应成为交付门禁。

**失败四：控制无对应风险。** 先检查引用完整性；孤儿控制需补威胁或说明删除。不要为保住既有技术而虚构威胁。

**失败五：威胁无验证。** 控制“已实现”不是证据；补成功、边界、非法和依赖故障输入，并保留结果。

**失败六：遗漏内部人。** 管理员、客服、运维、开发、备份操作和 break-glass 都有独立能力与审计要求。

**失败七：把风险接受写成关闭。** 接受必须有责任人、理由、期限、触发条件和剩余影响；风险并未消失。

诊断时从最早的结构证据开始：节点/流是否存在 → 信任域是否标明 → 引用是否有效 → 关键场景是否覆盖 → 控制是否映射 → 验证是否可重放。后面的总分或“通过”不能覆盖前面的结构缺口。

## 17. 实验工作流

实验提供一份固定的 FactoryCare DFD、资产/主体/边界/威胁/控制/验证清单，以及四类注入故障。执行前先预测第一条失败：遗漏管理员时应先报主体覆盖，而不是孤儿控制；删除边界时应报告具体 flow；删除控制映射时应报告 threat/control ID；删除验证时应报告 threat/validation ID。

推荐循环：

1. 阅读模型文件，画出你理解的数据流；
2. 为每个节点和存储写信任域；
3. 对每条流标注是否跨界和边界 ID；
4. 用 STRIDE 与滥用场景发现威胁；
5. 把控制和验证回链；
6. 运行基线，保存 expected/actual；
7. 逐个运行注入故障，确认第一处可信证据；
8. 修复公开练习并重跑原验证器；
9. 最后才与私有解析比较。

实验验证器不是通用威胁建模工具。它只识别仓库定义的教学 schema；未报错不代表模型完整。真实项目还需架构、业务、运维和隐私相关方共同审阅。

## 18. 120 秒讲解模板

可以这样组织：

> 威胁建模先定义安全目标和资产，再描述主体、攻击者能力、DFD、攻击面与信任跨越。对每条流用 STRIDE 和滥用场景问“会怎样失败”，把威胁写成攻击者—动作—薄弱条件—影响，并按证据与不确定性排序。控制必须回指风险，且有成功、边界、非法或故障注入证据。它适合在设计期开始并随系统维护；不替代代码测试、渗透测试和运行响应。失败反例是只列 CVE 和 WAF，却遗漏管理员与跨租户数据流，最终控制没有对象也无法验证。

若讲解只背出 STRIDE 六个字母，却说不出资产、边界、控制映射和验证反例，尚未达到本章目标。

## 19. 自检清单

- 范围、版本、部署和明确不包含项是否写清？
- CIA、真实性、授权、追责、隐私/安全目标是否按场景取舍？
- 数据、凭据、流程、可用性和信任是否都进入资产清单？
- 未认证者、低权限成员、管理员、内部人、第三方和故障是否建模？
- 每个外部实体、过程、存储、流和信任域是否有稳定 ID？
- 请求与响应、同步与异步、普通与管理路径是否分开？
- 认证绕过、越权、篡改、泄露和拒绝服务是否有可执行场景？
- STRIDE 是否被当作提示而非完整性证明？
- 每个控制是否引用威胁，每个威胁是否有处置和剩余风险？
- 每项关键控制是否有可重放验证，日志是否避开秘密？
- 架构、依赖、数据或事故变化时是否触发复审？
