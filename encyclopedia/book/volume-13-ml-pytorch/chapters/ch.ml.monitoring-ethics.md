# 漂移、监控、公平性、伦理与使用边界

<!-- BEGIN GENERATED LEARNING PREREQUISITES -->
## 学习前检查

以下章节是本章的硬前置。开始前，请先完成并验证对应能力：

- [《保存、加载、推理、批处理与服务边界》](ch.pytorch.inference.md)：监控必须围绕版本化推理输入、输出和制品身份建立。

> 离线评估通过只是“在一个已知数据切片上达到过指标”。上线后，输入会变化、标签会延迟、流程会改变、不同群体可能承受不同错误。监控的职责是产生可调查的信号和证据，不是用一条绿色曲线宣布模型永远正确。本章设计监控合同与人工兜底，不搭建生产平台，也不伪造真实人群公平性或线上漂移证据。

## 1. 为什么普通服务监控不够

HTTP 成功率、延迟、CPU、内存和队列积压能说明服务是否运行，却不能说明模型建议是否正确。一个模型可以在 20ms 内稳定返回完全错误的结果；也可以预测质量尚可但接口不可用。

因此至少分四层：

1. 服务健康：请求量、错误率、延迟、资源、超时；
2. 数据健康：缺失、范围、类别、schema、分布、特征新鲜度；
3. 模型行为：预测分布、置信区间、拒绝/回退率、版本；
4. 结果质量：标签回填后的准确率、召回率、校准和分组指标。

伦理与治理贯穿四层：谁受影响、谁可覆盖、如何申诉、事件如何审计、模型何时必须停用。只部署图表而没有责任人和动作阈值，不构成有效监控。

## 2. 先写监控合同

每个监控项至少定义：

- 指标名称和业务含义；
- 数据来源、事件时间和处理时间；
- 参考窗口、当前窗口与最小样本量；
- 计算公式、分桶和缺失处理；
- 标签是否可用及延迟分布；
- 告警阈值、持续时间和严重级别；
- owner、排查手册、回退和关闭条件；
- 模型、特征、代码和数据版本；
- 隐私、保留期与访问权限。

“准确率下降就报警”不是完整合同：标签何时到、在哪个时间窗口 join、取消工单如何处理、哪个版本的预测被评估都尚未定义。

## 3. 漂移不是一种现象

### 3.1 数据漂移

输入分布 `P(X)` 改变，例如夏季温度更高、设备类型构成改变、采集单位从摄氏误变华氏。数据漂移可以是正常季节性，也可能是采集故障。

### 3.2 标签漂移

目标比例 `P(Y)` 改变，例如紧急工单比例上升。它可能来自真实环境变化、标签政策变化或抽样方式变化。

### 3.3 概念漂移

输入与目标关系 `P(Y|X)` 改变。例如同样振动值在新设备代际上代表不同故障风险。概念漂移通常需要标签或专门实验才能确认，单看输入分布无法证明。

### 3.4 预测漂移

模型输出分布改变。它可能由输入变化、模型版本、预处理错误或阈值改变造成。预测稳定也不证明质量稳定：模型可能对新环境持续输出旧分布。

精确措辞很重要：“检测到输入分布差异”不等于“准确率下降”；“没有检测到漂移”不等于“没有漂移”，更不等于“模型公平”。

## 4. 参考窗口与当前窗口

参考数据可以来自训练集、上线前验证期或经审核的稳定生产期。训练集方便但未必代表线上流量；生产参考更贴近实际但可能已经含问题。

窗口设计需考虑：

- 固定窗口还是滚动窗口；
- 事件时间还是采集时间；
- 日/周季节性；
- 节假日和维护周期；
- 迟到、重复与回补事件；
- 模型切换和灰度流量；
- 样本量不足时是否延长窗口。

比较不同版本混合流量会把版本差异误当时间漂移。至少按 `model_version`、`feature_contract_version` 和关键流量来源切分。

## 5. 为什么只监控均值会漏报

两组值：

```text
reference = [0, 0, 2, 2]
current   = [1, 1, 1, 1]
```

均值都为 `1`，但分布完全不同。反过来，均值小幅改变也可能只是抽样波动。数值特征至少结合分位数、缺失率、范围、固定分桶比例或适合的统计检验。

固定分桶边界必须由参考期确定，不能分别按每个窗口重新分桶，否则变化会被“自适应边界”隐藏。超出参考范围的值要进入显式溢出桶。

## 6. 可手算的分布距离

### 6.1 总变差距离

对同一组类别或桶比例 `p_i,q_i`：

\[
TV(P,Q)=\frac{1}{2}\sum_i|p_i-q_i|
\]

范围 `[0,1]`。例如参考类别比例 `[0.8,0.2]`，当前 `[0.4,0.6]`：

```text
TV = 0.5 * (|0.8-0.4| + |0.2-0.6|) = 0.4
```

它直观且易验证，但阈值仍需结合样本量与业务波动校准。

### 6.2 PSI

常见 Population Stability Index：

\[
PSI=\sum_i(q_i-p_i)\ln\frac{q_i}{p_i}
\]

零比例需要平滑，分桶选择显著影响结果。行业经验阈值不是自然法则，不应无验证地复制。记录平滑常数和桶边界，否则不同实现不可比较。

### 6.3 统计检验

KS、卡方等可检验样本是否与参考分布一致，但 p 值受样本量强烈影响：样本巨大时微小差异也显著，样本很小时重大差异可能无力检出。统计显著不等于业务重大。应同时报告效应量、样本数与业务阈值。

本章资产用固定类别集合和 TV 建立手算 oracle，不把它包装成通用生产漂移系统。

## 7. schema 与语义漂移

有些最危险问题无需复杂统计：

- 列缺失或多出；
- dtype 改变；
- 单位改变；
- 枚举新增；
- 时间戳时区改变；
- 特征计算版本漂移；
- 缺失值从 `null` 变为魔法数；
- ID 被误当连续数值。

schema 校验能快速阻断明显破坏，但“字段仍叫 temperature、数值范围也正常”不能证明单位没变。特征合同应包含单位、来源、有效时点和生成版本。

## 8. 没有标签时能知道什么

实时阶段通常只有输入与预测，可以监控：

- schema、缺失、范围和分布；
- 预测类别/分数分布；
- 低置信、拒绝和回退率；
- 服务错误、延迟和特征新鲜度；
- 与规则或旧模型的不一致率。

这些是代理信号，不能直接计算真实准确率。正确状态应是 `quality_status = pending_labels` 或 `unavailable`，而不是沿用上个月准确率显示“当前稳定”。

若使用人工操作作为弱标签，要分析选择偏差：只有被人工查看的高风险样本可能有反馈；人工也可能受模型建议影响。弱标签不等于独立真值。

## 9. 延迟标签回填

每条预测需记录不可变关联信息：

```text
prediction_id
entity_id / work_order_id
prediction_time
model_version
feature_contract_version
score / class / threshold
decision_context
```

真实结果到达后，根据已定义键和观察期回填：

- 标签成熟窗口有多长；
- 多次结果取首次、最终还是窗口内聚合；
- 被取消、丢失随访和重复记录如何处理；
- 后来修改标签是否重算历史；
- 时区和事件时间如何统一。

只评估“已快速得到标签”的样本可能产生幸存者偏差。监控需同时报告标签覆盖率、成熟度和未匹配原因。

## 10. 性能监控必须复用离线定义

分类任务可监控准确率、精确率、召回率、F1、ROC-AUC、PR-AUC、校准和混淆矩阵；回归可监控 MAE、RMSE、分位误差。选择取决于错误成本和样本结构。

线上指标应与离线指标在以下方面一致：

- 正类定义；
- 阈值；
- 标签观察窗；
- 去重与样本单位；
- 权重与缺失处理；
- 宏/微/加权平均；
- 版本和分组。

总体准确率可能被多数类主导。对紧急工单漏报，正类召回通常比总体准确率更关键，但还要结合误报成本和人工容量。

## 11. 监控不确定性与最小样本量

指标是样本估计，不是精确真理。小群体一天只有两个样本时，`50%` 与上周 `100%` 的变化未必可稳定解释。至少同时展示分子、分母、窗口与置信区间或不确定性说明。

可以设定：不足最小样本量时不触发常规性能判断，而输出“证据不足”；但不能因此隐藏该群体。可延长窗口、合并合理时间段或发出数据覆盖告警。严禁为了数字稳定随意合并本应独立审查的受影响群体。

## 12. 分组性能是发现平均数掩盖问题的工具

按设备类型、地域、客户层级、班次或与权益相关的群体切片，分别计算同一指标。示例：

```text
group A: 8/8 correct = 1.00
group B: 2/4 correct = 0.50
overall: 10/12       = 0.83
```

总体指标看似可接受，B 组却明显较差。报告至少包含每组样本数、标签覆盖、指标、差距和版本。

分组本身涉及治理：敏感属性是否可以合法采集、如何最小化使用、谁可访问、交叉小群体是否会重识别。完全不采集可能无法审计差异，随意采集又会增加隐私风险，需要法律、业务和受影响方共同决策。

## 13. 常见公平性定义与冲突

公平没有一个脱离场景的万能数字。

### 13.1 人口统计平等

不同组获得正向预测的比例相近。若基础发生率不同，这可能与准确性或其他公平标准冲突。

### 13.2 机会均等

在真实正类中，各组真阳性率相近，关注谁更容易被漏掉。

### 13.3 均等化机会

同时要求真阳性率和假阳性率跨组接近，比只看正向率更接近错误分配，但仍有权衡。

### 13.4 校准

同样预测分数在各组中对应相近真实发生率。基础率不同时，校准与某些错误率平等通常无法同时完美满足。

选择标准必须从具体伤害、权利、资源和法律要求出发，并记录为何选择、牺牲什么、谁参与决策。不能让工程师凭一个库的默认指标替组织做伦理决策。

### 13.5 阈值本身也是政策

同一风险分数可以用不同阈值转换为“建议紧急/普通”。降低阈值通常提高召回、增加误报和人工负担；提高阈值通常相反。阈值即使不在模型权重中，也会强烈改变伤害分配，因此必须版本化、评审和监控。

按群体使用不同阈值有时可改善某个公平指标，也可能引发法律、伦理、可解释性和一致性问题。不能只为让仪表盘差距归零而自动部署。应先明确目标、依据、受影响方、申诉和替代方案，再由有权限的治理流程决定。

人工容量也是阈值约束。若每天只能复核 50 条，模型产生 500 条高风险告警会导致队列延迟；只监控模型召回却不监控审核等待时间，会把风险转移到流程。端到端指标需要连接“预测—展示—人工动作—结果”。

### 13.6 交叉群体与多重比较

单独看地域和设备类型可能都正常，但某一地域的某一设备类型表现很差。交叉切片能发现被边际平均隐藏的问题，也会迅速产生小样本和隐私风险。

同时扫描大量切片会提高偶然极端值出现概率。报告应区分预先指定的关键群体与探索性发现，提供样本量、不确定性和复核流程。不能看到一个小样本差距就宣布系统歧视，也不能以“小样本”为由永久不调查高风险信号。

## 14. 指标差距不是因果归因

发现 B 组召回较低说明“观察到性能差异”，不自动说明模型是唯一原因，也不说明群体属性导致结果。差异可能来自标签质量、覆盖、传感器、流程、历史不平等或抽样。

下一步是调查数据生成过程、错误样本、标签一致性和业务流程，并与领域专家和受影响方评审。不要把群体属性直接加进模型就声称“修复公平性”；这可能引入新的法律与伦理风险。

## 15. 人工兜底必须真实可用

“有人在环”不等于安全。有效人工覆盖需要：

- 人能看到足够上下文和模型局限；
- 有时间、权限和能力覆盖；
- 覆盖不会受到惩罚；
- 自动化偏见得到培训和界面缓解；
- 高风险/低置信结果自动进入复核；
- 有申诉、升级、停止和回滚路径；
- 记录模型建议、人工决定、理由和版本；
- 定期审查人工是否只是机械确认。

人工覆盖率过低可能表示模型很好，也可能表示人无权覆盖；覆盖率过高可能表示模型差，也可能表示业务政策改变。指标必须结合流程证据解释。

## 16. 使用边界与禁止自动化

模型卡应明确允许和禁止用途。例如 FactoryCare 优先级模型可以作为调度提示，却不应：

- 自动关闭工单；
- 绕过安全检查；
- 自动惩罚员工；
- 在未验证客户/设备类型上使用；
- 把分数当故障事实；
- 在服务失败时静默给默认低优先级。

高影响决定可能要求始终人工确认。回退可以是规则排序、原流程或明确“无法建议”，不能用一个未经监控的备用模型掩盖故障。

## 17. 模型卡是可审查合同

一份实用模型卡至少包括：

- 模型名称、版本、owner、发布日期；
- 预期用途、用户和禁止用途；
- 训练/验证数据范围与时间；
- 标签、样本单位、划分与已知泄漏风险；
- 特征合同和预处理版本；
- 总体与关键分组指标及样本量；
- 阈值、错误成本与选择理由；
- 已知限制、未覆盖环境与伦理风险；
- 人工覆盖、申诉、回退和停用条件；
- 监控计划、标签延迟和重训触发；
- 依赖、制品哈希和变更记录。

模型卡不是营销页。未知项要写“未验证”，不能删掉。每次模型、数据、阈值或用途重大改变都要更新。

### 17.1 数据文档、模型卡和事件记录互补

模型卡描述模型用途、评估和限制；数据文档描述来源、采集、覆盖、许可、字段与已知偏差；事件记录描述一次具体失败的时间线、影响和处置。三者不能互相替代。

例如模型卡写“只用于泵类设备”，数据文档应证明训练/验证覆盖哪些泵型，运行时合同应拒绝或回退其他类型，监控应统计越界请求。仅在文档中写限制、系统却继续接受任意设备，不是有效控制。

文档还必须可追溯到制品版本。复制旧模型卡并只改版本号会造成证据漂移；发布门应校验必要字段、评估工件和监控配置是否与新版本对应。

## 18. 从告警到行动

告警需映射到动作，例如：

```text
schema 破坏 -> 立即拒绝输入，切回规则并通知数据 owner
严重缺失率 -> 降级/暂停建议，检查上游采集
输入 TV 超阈持续两窗 -> 调查数据来源，不宣称质量下降
成熟标签召回下降 -> 分版本/分组复核，必要时回滚
关键组差距超限 -> 暂停高影响自动化，启动公平性评审
申诉激增 -> 人工审核产品流程与模型错误
```

阈值应通过历史回放和演练校准，控制误报与漏报。告警风暴会让人麻木；过度平滑则延迟发现。严重事件需要审计时间线、影响范围、处置、恢复验证和复盘。

### 18.1 告警演练与静默失败

上线前应注入已知异常：缺列、单位变化、分布改变、标签断流、关键组指标下降和人工申诉激增，确认信号抵达正确 owner，值班人员能按手册回退。只测试“指标函数返回 True”没有验证通知、权限、审批和恢复链。

还要演练监控自身静默：采集任务停止、时钟偏移、版本标签缺失、回填 join 暴跌。任何关键监控都应有最后成功时间与数据新鲜度；没有数据应显示未知，而不是沿用最后一个绿色点。

恢复不能只看服务重新 200。需要确认输入合同、积压处理、模型版本、质量信号和人工流程均恢复，并评估故障期间已受影响的工单。

### 18.2 变更管理与回滚判据

模型、预处理、阈值、特征来源、标签定义和用途任何一个变化，都可能让原监控基线失效。发布记录应说明哪些基线继续有效、哪些需要重新建立。不能在新版本上线后立刻拿旧分布阈值报警，再把所有报警都标为“预期”。

灰度或影子运行可比较新旧版本，但两者必须接收可比流量并避免新模型影响标签生成。回滚触发条件、目标版本、特征兼容和数据迁移要预先演练。本章没有运行部署系统，因此只能定义这些合同，不能声称回滚已可用。

## 19. 可观测性设计注意事项

指标标签不要放 `user_id/work_order_id` 等高基数字段，否则时间序列数量爆炸。个案 ID 应进入受控日志或追踪系统，并遵守脱敏和保留期。

日志至少关联 `request_id/prediction_id/model_version`，但不记录原始敏感文本、令牌或不必要特征。指标、日志和追踪用于不同问题：指标发现趋势，日志查看事件，追踪连接调用链。

监控系统自身也会失败。需要观察数据延迟、任务最后成功时间、样本覆盖、join 失败率和规则版本。仪表盘没有新数据不应显示绿色；应明确 stale/unknown。

## 20. 训练—服务偏差与版本追踪

生产监控必须知道某条预测用了什么：

- 模型权重哈希；
- 推理代码版本；
- 特征合同和预处理版本；
- 阈值/校准版本；
- 运行环境与依赖；
- 输入事件有效时点。

若训练时温度单位是摄氏、线上变成华氏，输入分布会剧变；若线上仍落在训练范围内，简单范围检查甚至可能漏掉。黄金样例、训练—服务一致性测试和版本化特征能补充统计监控。

## 21. 反馈回路

模型建议会改变人的行为，进而改变未来数据。例如高优先级建议得到更快维修，故障后果被避免；若直接用结果作为标签，模型可能看起来“预测错了”。只有被展示或执行的建议得到反馈，也会产生选择偏差。

因此记录曝光、人工决定和干预，区分“自然结果”与“干预后结果”。重训不能把所有新日志无条件拼回训练集。因果评估、随机试验或策略评估超出本章，但必须把反馈回路标为风险。

## 22. FactoryCare 的所有权边界

```text
Java：工单/设备事实、用户权限、最终优先级、人工申诉、审计
Python：版本化特征上的模型建议、可重建监控聚合、离线报告
监控：读取最小必要事件，不直接改核心业务状态
```

Python 告警不能直接关闭、升级或重分配工单；它可以向 Java/运维通道提交带证据的信号。Java 负责执行经过授权的业务动作。监控存储若包含敏感分组，只允许治理所需的最小访问和保留。

如果 Python 模型服务不可用，Java 必须有明确回退，而不是让客户端转而直接调用 Python。模型输出字段应命名为 `priority_hint`、`risk_score` 等，附 `model_version` 与适用范围。

## 23. 合成演练的正确结论

本章实验构造小型合成窗口，用于证明监控逻辑：

- 两个窗口均值相同，但固定桶分布变化，漂移信号触发；
- 未回填标签时，质量状态为未知；
- 回填后计算确定的总体和分组准确率；
- 总体可接受但一个小组较差时，分组告警触发；
- 模型卡包含人工覆盖和禁止用途。

它只能证明代码对这些固定输入按合同工作。合成的 `group_a/group_b` 不是现实人群，阈值不是生产标准，报警输出不是生产监控证据。不能写“模型已公平”或“线上漂移已验证”。

## 24. 常见失败与第一可信证据

### 24.1 只监控均值

第一证据是相同均值下固定桶计数显著不同。修复为同时监控分布、缺失、范围和业务切片，并保留原反例测试。

### 24.2 无标签时宣称质量稳定

第一证据是性能查询分母为零或标签成熟度不足。修复为三态/多态质量状态：`available/pending/insufficient`，不沿用旧值冒充当前值。

### 24.3 敏感分组被总体平均隐藏

第一证据是混淆矩阵按组拆分后差距明显。修复不是简单删掉总体指标，而是同时报告总体、各组、样本量、不确定性和数据覆盖，并启动治理评审。

### 24.4 自动决策无申诉

这通常不会触发代码异常。第一证据是流程图和产品行为中没有覆盖、申诉、升级或停用路径。修复需业务、法务、领域与受影响方共同参与，不能仅增加一个布尔字段。

### 24.5 监控任务停止却显示绿色

第一证据是最新事件时间和任务心跳已过期。仪表盘应把缺数据标成 unknown/stale，并对监控管道自身告警。

## 25. 发布与持续复核清单

- 模型卡经 owner 和领域评审；
- 使用与禁止边界进入产品流程；
- 模型/特征/阈值/代码版本可追踪；
- 服务、数据、预测、标签质量四层信号齐全；
- 参考/当前窗口、桶、阈值、样本量已定义；
- 标签延迟、覆盖和 join 失败可观察；
- 总体与关键分组指标均有分子分母；
- 公平性目标与权衡有治理记录；
- 人工覆盖、申诉、回退和停用演练完成；
- 监控管道 stale/unknown 不显示绿色；
- 隐私、访问、留存和删除策略生效；
- 无标签时不声称质量稳定；
- 漂移信号不被误写为准确率下降。

## 26. 自测问题

- 服务 200 且延迟正常，为什么模型仍可能失效？
- 数据漂移和概念漂移的区别是什么？
- 为什么预测分布稳定不能证明准确率稳定？
- 相同均值怎样隐藏分布改变？
- 标签延迟期间应显示什么质量状态？
- 回填标签为什么要记录预测时使用的模型版本？
- 总体准确率如何隐藏小组伤害？
- 人口统计平等、机会均等和校准为何可能冲突？
- “有人在环”何时只是橡皮图章？
- 模型卡为什么必须写禁止用途和未知项？
- Python 监控为何不能直接修改工单？
