# 文件、路径、字符与编码

<!-- BEGIN GENERATED LEARNING PREREQUISITES -->
## 学习前检查

本章无编程先修。零基础读者可以直接从本章开始，并按正文中的预测、操作、验证和复述步骤建立第一份学习证据。
<!-- END GENERATED LEARNING PREREQUISITES -->

初学编程时，很多错误看起来像“代码坏了”，其实程序还没有读到你以为的那个文件：编辑器打开的是副本，运行配置从另一个目录出发，文件名末尾多了隐藏扩展名，中文被错误编码解释，或者两台机器只在换行符上不同。

本章先建立一张基础地图：文件与目录如何组成树，路径如何从起点定位目标，扩展名和隐藏属性是什么，字符如何变成字节，UTF-8 如何保存中文，LF 与 CRLF 为什么会产生看不见的差异。你暂时不需要学习 `cd`、`cp`、`mv`、通配符或权限命令；这些属于后续终端章节。本章只用图示、编辑器项目面板、状态栏和少量只读验证器观察现象。

## 本章要解决的问题

完成本章后，你应当能够：

1. 在项目树中区分文件与目录，并说明目录不是“特殊格式的正文文件”；
2. 给定明确起点和目标，分别解释绝对路径与相对路径指向哪里；
3. 识别同名文件、隐藏文件和双重扩展名造成的误判；
4. 区分字符、编码后的字节和屏幕上的字形；
5. 说明 UTF-8 是字符到字节的编码方式，不是“中文字体”；
6. 用编辑器观察当前文件编码和换行符，并让中文保存、关闭、重开后保持一致；
7. 区分 LF 与 CRLF，解释为什么视觉相同的两份文本可能字节不同；
8. 面对“文件不存在”或“中文乱码”，先检查起点、目标、实际文件与解码方式，而不是立刻重装工具。

本章的成功标准不是背诵路径符号，而是能从一个明确起点沿目录树找到目标，并能用字节与解码模型解释文本为何正常或异常。

## 零基础补救：先认识文件管理界面

如果你只用过手机，不熟悉桌面文件系统，可以把编辑器左侧的项目面板理解为一个可展开的收纳树：带展开箭头的节点通常是目录，叶子节点通常是文件。目录可以继续包含目录和文件；文件保存一串字节，并由软件按某种格式解释。

先观察，不要移动任何东西：

1. 在 VS Code 或 IntelliJ 中打开一个**目录**作为项目；
2. 展开项目根、`book`、某个 volume 和 `chapters`；
3. 点击一个 Markdown 文件，观察编辑区标签与项目树高亮；
4. 看窗口标题、面包屑或状态栏，它们会显示当前文件所在层级；
5. 关闭标签再从项目树重开，确认仍是同一文件。

“项目根”是本书人为选定的起点，不是电脑唯一的根。后续所有相对路径都必须说明相对于哪个起点；不说明起点的相对路径是不完整信息。

## 直觉模型：城市地址、树和翻译表

路径可以类比地址。绝对路径像写出国家、省、市、街道、门牌，从文件系统根开始；相对路径像说“从当前教室出门，向右走到资料室”，它只有结合出发点才有意义。

文件系统可以画成树：

```text
Computer/                         ← 项目根目录
├── book/                         ← 目录
│   └── volume-00-computer-foundations/
│       └── chapters/
│           └── ch.foundations.files-paths-encoding.md  ← 文件
├── examples/
│   └── encyclopedia/
└── .gitignore                    ← 名称以点开头的文件
```

字符编码则像翻译表。人想表达字符“修”，文件只能保存字节。编码器按 UTF-8 规则把字符映射为若干字节；读取时，解码器用同一规则把字节还原为字符。若保存与读取采用不同规则，原始字节没有自动改变，但显示出的字符可能错误或出现替代符号。

```text
人理解的字符  --UTF-8 编码-->  文件中的字节
人看到的字符  <--UTF-8 解码--  文件中的字节
```

字体负责把字符绘制成字形，编码负责字符与字节之间的映射。换字体可能改变外观，不会把 UTF-8 文件改成另一种编码。

## 文件、目录与文件树

### 文件是什么

对本章而言，文件是文件系统中有名称、位置和内容字节的对象。文本文件、图片、PDF、class 文件都由字节组成；“文本”或“图片”是软件解释这些字节的方式。

文件通常还带有大小、修改时间等元数据。不同系统还会记录权限、所有者、扩展属性等，本章暂不展开。不要把修改时间当成内容正确证据：文件可能只被打开保存，内容也可能来自旧副本。

### 目录是什么

目录用于组织名称与层级，它可以包含文件和子目录。图形界面常用文件夹图标表示目录，因此日常说“文件夹”通常没有问题；在编程文档与错误信息中更常见“目录”。

同一个目录内通常不能同时存在两个完全相同的名称，但不同目录可以各有一个 `README.md`。因此只说“打开 README”不够，至少要给出所在目录或完整路径。

### 根、父、子与叶子

- **根**：一棵路径树的起点；可以是系统根，也可以是我们讨论时选定的项目根；
- **父目录**：直接包含当前节点的目录；
- **子目录**：当前目录直接包含的目录；
- **叶子**：图中不再展开的节点，常见为文件；
- **路径段**：由分隔符隔开的每个名称。

在 `book/volume-00-computer-foundations/chapters/a.md` 中，`book`、volume 名、`chapters` 与 `a.md` 都是路径段。路径描述的是定位关系，不等于文件内容。

## 绝对路径：从文件系统根开始

在当前 macOS 学习机上，一个绝对路径可能是：

```text
/Users/youren/Desktop/Study/Computer/book/volume-00-computer-foundations/chapters/ch.foundations.files-paths-encoding.md
```

开头的 `/` 表示从文件系统根开始。这个路径在当前机器上明确，但它含有用户名和本机目录布局，复制到另一台电脑通常无效。教材、代码和团队文档不应把个人绝对路径当成可移植合同。

Windows 常见绝对路径以盘符或 UNC 位置开始，例如：

```text
C:\Users\Learner\FactoryCare\README.md
```

两种系统的分隔符和根表示不同。Web URL 也使用斜杠，但 URL 的语义由 URL 标准定义，不能直接套用本地文件路径规则。

绝对路径的优点是起点明确，适合诊断“工具实际读了哪里”；缺点是与机器布局绑定，容易泄露用户名或内部目录，也不适合提交到跨机器项目配置。

## 相对路径：必须绑定一个起点

相对路径不从系统根开始。假设当前观察起点是项目根 `Computer/`，则：

```text
book/volume-00-computer-foundations/chapters/ch.foundations.files-paths-encoding.md
```

指向上面同一个文件。若起点换成 `book/volume-00-computer-foundations/`，同一个目标要表示为：

```text
chapters/ch.foundations.files-paths-encoding.md
```

因此问“这条相对路径对不对”之前，先问“从哪里出发”。编辑器中的项目根、程序进程的工作目录、当前文件所在目录、构建工具的模块目录可能不是同一个起点。

### `.` 与 `..`

路径图中，`.` 表示当前目录，`..` 表示父目录。它们不是文件扩展名。假设起点在 `book/volume-00-computer-foundations/chapters/`：

```text
./ch.foundations.files-paths-encoding.md
```

仍指当前 `chapters` 下的文件；而：

```text
../../../examples/encyclopedia/ch.foundations.files-paths-encoding/README.md
```

需要沿父目录向上三层，再进入 `examples`。手算时每遇到一个 `..`，就在树上移到父节点；不要凭视觉猜。

过多的 `..` 会降低可读性，也可能造成安全问题。服务端若把不可信输入直接拼进路径，攻击者可能用 `../` 逃出允许目录，这叫路径遍历。初学实验只使用仓库给定路径，不把用户输入拼入读写路径。

## 路径解析的五步法

遇到“文件不存在”，按固定顺序画图：

1. **确认起点**：项目根、当前文件目录还是程序工作目录；
2. **拆分路径段**：逐段写出名称；
3. **逐层移动**：进入子目录或沿 `..` 回父目录；
4. **核对目标类型**：最后是文件还是目录；
5. **核对真实名称**：大小写、空格、点、连字符、扩展名是否完全一致。

例如起点为 `labs/encyclopedia/ch.foundations.files-paths-encoding/`，目标写成 `fixtures/device.csv`。先确认本实验根下是否真有 `fixtures`，再确认其中是 `device.csv` 而不是 `devices.csv`、`device.csv.txt` 或另一个同名目录。

不要把“编辑器搜索能找到某个名字”当作程序必然能找到。搜索可能跨整个工作区，程序只按自己的起点与路径规则读取。

## 文件名、扩展名与隐藏文件

### 扩展名是名称的一部分

`report.md` 的 `.md` 通常称为扩展名，软件可以据此选择语法高亮或默认打开方式。但扩展名不是内容真实性证明：把图片改名为 `.txt` 不会把图片字节变成文字；把 Java 文件命名为 `.java.txt` 也不会成为编译器期望的 `.java` 源文件。

常见双重扩展名陷阱：图形界面可能隐藏“已知扩展名”，用户看到 `config.json`，实际名称却是 `config.json.txt`。在编辑器项目树或文件属性中查看完整名称，不要只看桌面图标。

### 点开头名称与隐藏属性

在 macOS/Linux 生态中，名称以 `.` 开头的文件常被界面默认隐藏，例如 `.gitignore`、`.env`。隐藏主要影响展示，不是加密，也不是访问控制。显示隐藏文件后，任何有权限的程序仍可读取。

`.env` 常被用来存环境变量，但名字隐藏不意味着安全。包含 Token 的文件不能提交到公开仓库；误提交后，仅加入 `.gitignore` 只能阻止未来新跟踪，不能自动删除历史，更不能撤回已经泄露的密钥。

Windows 还存在文件属性形式的隐藏标记。跨平台时，不要把“点开头”与所有系统的隐藏机制完全等同。

### 大小写与 Unicode 名称

不同文件系统对名称大小写的比较策略可能不同。在某些 macOS 默认卷上，`Device.md` 与 `device.md` 会被视为同名；在常见 Linux 文件系统上它们可能是两个不同文件。团队项目应固定一致大小写，并让导入路径与真实名称逐字匹配。

Unicode 还允许视觉接近但码点序列不同的名称。不要用看起来相同的全角标点、不同连字符或尾随空格命名源码。重命名时在项目树中操作并检查版本差异。

## 字符、码点、字形与字节

这四个概念经常被一句“文字”混在一起：

| 概念 | 本章理解 | 例子 |
| --- | --- | --- |
| 字符/抽象字符 | 文本系统中要表达的抽象单位 | 拉丁字母 A、汉字 修、换行 |
| Unicode 码点 | Unicode 给抽象字符分配的编号 | `A` 为 U+0041，`修` 为 U+4FEE |
| 字形 | 字体把字符绘制出来的视觉形状 | 同一“修”在不同字体中外观不同 |
| 字节 | 文件和网络实际保存、传输的 8 位单位 | UTF-8 中 `A` 一个字节，`修` 三个字节 |

日常说“字符串长度”时要先问测量单位：字节数、Unicode 码点数、编程语言的代码单元数，还是用户看到的字素簇数。一个表情可能由多个码点组合，一个带重音字符也可能有预组合与组合序列。不同语言的 `length` 不一定等于“用户看到几个字”。本章先建立区别，具体 API 留到各语言章节。

## Unicode 与 UTF-8

Unicode 为世界文字与符号定义统一编号空间；UTF-8 是把 Unicode 码点编码为一到四个字节的方式。ASCII 范围 U+0000 到 U+007F 在 UTF-8 中使用同值单字节，因此纯英文配置常在多种环境中“看起来都正常”，中文问题却暴露得更早。

以三个字符为例：

| 文本 | Unicode 码点 | UTF-8 十六进制字节 | 字节数 |
| --- | --- | --- | ---: |
| `A` | U+0041 | `41` | 1 |
| `修` | U+4FEE | `E4 BF AE` | 3 |
| `🔧` | U+1F527 | `F0 9F 94 A7` | 4 |

“A修🔧”直觉上有三个符号，UTF-8 文件内容却占八个字节。若再加行尾换行，字节数还会增加。不要用“中文一个字等于两个字节”这类来自特定旧编码的经验解释 UTF-8。

UTF-8 没有为每个字符使用固定字节数。解码器根据前导字节判断序列长度，并验证续字节。非法序列可能被拒绝、替换为 U+FFFD `�`，或被软件用其他方式处理。

## 编码与解码必须成对

保存文本时发生编码，打开文本时发生解码。最小往返是：

```text
字符序列 “设备已关闭”
        ↓ 用 UTF-8 编码
E8 AE BE E5 A4 87 E5 B7 B2 E5 85 B3 E9 97 AD
        ↓ 用 UTF-8 解码
字符序列 “设备已关闭”
```

若同一字节被错误地按其他编码读取，可能出现乱码。乱码不是“中文字符坏了”的统一现象，而是字节与解码规则不匹配。修复前先保护原始字节，确认文件真实编码，再选择正确解码；不要对乱码文本反复保存，否则可能把错误字符重新编码，造成不可逆损失。

### UTF-8 与 BOM

UTF-8 可以在文件开头出现字节顺序标记 `EF BB BF`，但 UTF-8 本身没有字节序问题，很多工具不要求 BOM。有些旧工具用 BOM 猜编码，有些脚本会把它误当正文开头。团队应明确约定“UTF-8 无 BOM”或工具兼容策略，不要在文件间随机混用。

### 声明与真实字节

HTML、HTTP、CSV 导入工具可能声明编码。声明写 `UTF-8` 不会自动转换已有字节；若声明与真实字节不一致，消费者仍会错误解码。判断时既看声明，也看生产这些字节的程序和实际样本。

## 用编辑器观察编码，不靠猜

在 VS Code 中打开文本后，状态栏通常显示 `UTF-8` 和 `LF` 或 `CRLF`。点击编码项时要区分两类动作：

- **Reopen with Encoding（使用编码重新打开）**：不先改写字节，尝试用另一规则解释现有文件；
- **Save with Encoding（使用编码保存）**：把当前字符按所选编码重新写为字节。

诊断乱码时优先保留副本，并用“重新打开”验证假设；不要一上来“另存为”覆盖原件。确认正确显示后，再根据项目约定转换。

IntelliJ 的状态栏也会显示文件编码与换行符。项目级、全局和单文件设置可能不同；看到一个文件正常，不代表全部文件相同。保存中文样例后关闭标签，再从项目树重新打开，才完成最小往返观察。

本章实验配套 Ruby 校验器会按字节检查 UTF-8 与换行符，但它是验证辅助，不要求你先学 Ruby 语法。

## 换行符：看起来空白，实际有字节

文本中的“下一行”也需要编码。常见约定：

- **LF**：一个换行字符 U+000A，字节 `0A`，macOS/Linux 与现代开发工具常用；
- **CRLF**：回车 U+000D 加换行 U+000A，字节 `0D 0A`，Windows 文本传统上常用；
- **CR**：历史系统曾单独使用 U+000D，现代项目较少作为统一行尾。

两份文件在编辑器里都显示三行，但若一份每行以 LF 结束，另一份以 CRLF 结束，它们的字节长度与摘要不同。版本控制可能把每行都标为变化；严格字符串比较也可能失败。

不要把“行数”与“换行符数量”机械等同。一个文件末尾是否有换行会影响计数：文本 `A\nB\n` 有两个换行并常被视为两行；`A\nB` 只有一个换行但仍显示两行。POSIX 文本文件传统上要求行以换行结束，具体工具的显示与计数仍要看定义。

### 为什么复制粘贴也会改变换行

编辑器可能按当前文件或项目设置统一行尾。复制的可见文本相同，保存后字节却按目标文件规则写出。自动格式化器、Git 配置和构建脚本也可能转换。团队应提交 `.editorconfig` 或一致的仓库规则，并在变更中警惕“整文件只有行尾变化”。相关 Git 自动转换机制留到版本控制章节。

## 三类典型故障

### 故障一：起点错误，文件“消失”

项目树中明明有 `fixtures/device.txt`，程序却说不存在。先不要新建同名文件。可能是程序工作目录在仓库根，而路径是按实验目录编写；也可能运行配置从模块目录出发。

诊断证据应包含：实际起点、传入的相对路径、逐段解析后的绝对目标，以及该目标是否存在。修复可以统一起点或从可靠配置构造路径，而不是在多个目录复制文件。

### 故障二：同名文件或隐藏扩展名

你修改了 `config.json`，程序行为没有变化。项目里也许还有另一个 `config.json`，或实际文件是 `config.json.txt`。在编辑器中使用“复制路径”或查看文件属性，比较运行日志记录的目标；确认修改与读取的是同一个对象。

### 故障三：解码方式错误，中文乱码

文件的原始字节是 UTF-8，工具却按其他编码打开。第一步保留原件和摘要；第二步用 UTF-8 重新打开；第三步确认中文往返；最后再修复工具或导入设置。若原始字节本身已被错误二次保存，单纯切换显示编码无法还原，需要从可信来源恢复。

### 故障四：换行差异导致“全部修改”

代码内容没变，差异视图却显示每一行。查看状态栏的 LF/CRLF、项目约定与 Git 差异设置。只做行尾转换的提交应与业务修改分开，否则真实变化会被噪声淹没。

## 失败时的诊断顺序

把“找不到/乱码”拆成下面的证据链：

```text
程序或编辑器从哪里开始？
→ 实际请求的路径是什么？
→ 逐段解析后目标是什么类型、真实名称是什么？
→ 实际读取了哪些字节？
→ 用什么编码解码？
→ 行尾与项目约定是否一致？
```

一次只改变一个条件。若同时移动文件、重命名、转换编码和更换工具，即使现象消失，也不知道哪个假设成立。修复后关闭并重新打开原目标，或按同一读取流程复跑，证明不是只修了编辑器缓存。

## 路径与编码的安全边界

- 不把未经验证的用户输入直接拼到服务器文件路径；要限定根目录、规范化并检查解析结果仍在允许范围内；
- 不相信扩展名就代表真实格式，上传文件还需内容类型、魔数、大小与解析器校验；
- 不让用户提供的文件名覆盖已有配置，保存时使用受控名称并隔离目录；
- 不在错误页面回显服务器绝对路径、用户名或内部目录结构；
- 处理压缩包时防止条目名称含 `../` 或绝对路径逃出目标目录；
- 文本解析失败时保留原始字节和来源，不对乱码反复覆盖保存；
- 隐藏文件不是秘密存储，`.gitignore` 也不是加密或访问控制；
- 不在教材截图和示例树中暴露真实客户名、私钥文件或生产数据位置。

这些安全规则在后续 Web、上传、部署章节会实现。本章只需知道：路径是输入，编码也是输入；二者都不能靠外观盲信。

## 与前端开发经验对照

如果你熟悉 Vue/TypeScript，可用以下桥梁，但不要直接等同：

| 本章概念 | 前端常见场景 | 需要保留的边界 |
| --- | --- | --- |
| 相对路径 | `import './styles.css'` | 解析起点由模块系统/构建器定义，不一定是终端工作目录 |
| 绝对路径 | 开发服务器文件位置 | 浏览器 URL 的 `/` 往往指站点根，不是电脑文件系统根 |
| 扩展名 | `.vue`、`.ts`、`.json` | 扩展名影响工具选择，但不证明内容合法 |
| UTF-8 | HTML、JSON、源码 | HTTP 声明、真实响应字节和 JS 字符串层次不同 |
| LF/CRLF | Git 差异、lint | 浏览器显示正常不代表仓库字节完全相同 |

当 Vite 报“模块找不到”时，先核对导入者位置、别名配置、文件名大小写与扩展名；不要把浏览器地址、源码导入路径和磁盘绝对路径混成一种。

## FactoryCare 中的实际落点

FactoryCare 会遇到大量路径与编码边界：设备导入 CSV、工单图片、巡检附件、日志、配置、前端资源与备份文件。

### 设备 CSV 导入

运营人员上传包含 `设备名称,位置` 的 UTF-8 CSV。系统必须知道上传字节的编码、分隔规则、是否有 BOM、换行符和字段约束。若用错误编码读取，“一号泵房”可能乱码；若只看扩展名 `.csv`，恶意或错误内容可能进入解析器。

### 工单附件

用户原文件名可以用于展示，但服务端存储路径不能直接信任 `../../config.yml` 之类名称。应生成受控对象键，把展示名作为经过限制的元数据，并校验 MIME、大小和权限。

### 配置与部署

开发机绝对路径不能写进生产配置。项目内资源使用稳定相对位置或配置项，运行时记录解析后的安全位置。日志中应提供足够诊断信息，但不向普通用户暴露服务器目录。

### 多端中文

Java 后端、Vue 管理端、uni-app、Flutter 与 Python 服务之间通过 HTTP/JSON 传输。各层都应按协议声明和处理 UTF-8；数据库、日志和导出文件还需各自验证。页面显示中文正常，只证明最终一条路径的某个样本正常，不等于所有导入导出往返无损。

## 公开示例与实验

可观察示例位于 [`examples/encyclopedia/ch.foundations.files-paths-encoding`](../../../examples/encyclopedia/ch.foundations.files-paths-encoding/README.md)。它提供一棵固定项目树、中文 UTF-8 样本和生成 LF/CRLF 对照文件的 Ruby 标准库脚本。你先在编辑器里预测节点与状态栏，再选择运行验证器比较字节。

实验位于 [`labs/encyclopedia/ch.foundations.files-paths-encoding`](../../../labs/encyclopedia/ch.foundations.files-paths-encoding/README.md)。实验不要求使用 Shell 移动或复制文件，所有编辑与观察都可在编辑器中完成：

1. 根据给定起点为三个目标写相对路径；
2. 绘制一个包含隐藏文件和双扩展名反例的树；
3. 新建 UTF-8 中文文件，记录字符、码点与字节数的区别；
4. 保存 LF 与 CRLF 两份视觉相同文本，比较状态栏和验证结果；
5. 故意从错误起点解释路径，再修正；
6. 用错误编码“重新打开”副本观察乱码，不覆盖唯一原件；
7. 关闭标签并重新打开，证明中文往返无损。

自动验证器只检查固定夹具，不会替你判断手绘树与解释是否正确。

## 五类练习

练习入口位于 [`exercises/encyclopedia/ch.foundations.files-paths-encoding`](../../../exercises/encyclopedia/ch.foundations.files-paths-encoding/README.md)。

### 预测练习

给定项目根与 `book/volume-00.../chapters/a.md`，预测从项目根、volume 根、chapters 三个起点分别应写什么路径。每个答案都必须同时写起点，不能只给路径字符串。

### 构建练习

在纸上或 Markdown 中绘制一棵包含 `README.md`、`.env.example`、`config.json.txt`、`data/设备.txt` 的树，标注哪些是目录、文件、隐藏名称、双扩展名和 UTF-8 中文路径段。

### 故障练习

分析三个现象：“存在却读不到”“修改后行为不变”“中文打开乱码”。为每个现象列出至少两个原因假设、第一项观察和只改变一个条件的修复方式。

### 需求变更练习

原项目只支持英文 LF 文本；新要求是允许中文，并能导入 Windows 产生的 CRLF 文件。先写新的往返预言和边界，再说明程序、测试与文档分别需要补什么；不要直接宣布“改成 UTF-8 就全部解决”。

### 无 AI 练习

关闭 AI，限时 35 分钟：根据一张树图写出两条绝对路径模型、六条相对路径，解释一个双扩展名陷阱，手算 `A修🔧` 的 UTF-8 字节数，并完成一段 120 秒复述。允许看本章速查表，不看私有解析。

答案位于 `solutions-private/encyclopedia/ch.foundations.files-paths-encoding/`，不会进入公开教材。先保存自己的预测，避免答案识别流畅感冒充独立能力。

## 边界与失败案例清单

学习时至少口述以下边界：

- 起点不同时，同一相对路径可能指向不同对象；
- 不同目录可有同名文件；
- 文件可能没有扩展名，也可能有多个点；
- 隐藏只影响常见展示，不等于不可读取；
- 文件名大小写在不同文件系统上的行为可能不同；
- ASCII 正常不证明中文编码正常；
- 一个可见符号不一定对应一个码点或固定字节数；
- UTF-8 文件可能带或不带 BOM；
- LF 与 CRLF 可见效果相近但字节不同；
- 文件最后一行可能有或没有终止换行；
- 声明 UTF-8 不会自动转换错误字节；
- 重新打开编码与保存编码不是同一操作；
- 修复显示乱码不等于原始数据已经无损恢复；
- 本机绝对路径正常不证明其他机器可用。

能解释边界不等于会写安全上传系统；后者留到有语言、HTTP 和安全前置后实现。

## 120 秒复述模板

合上正文，按顺序说明：

1. 文件与目录在树中的职责；
2. 绝对路径与相对路径的起点差异；
3. 为什么相对路径必须和起点一起判断；
4. 扩展名、内容格式和隐藏属性为何不能等同；
5. 字符、码点、字形、字节分别是什么；
6. UTF-8 编码和解码如何形成往返；
7. LF 与 CRLF 的字节差异；
8. “文件不存在”与“中文乱码”各自先检查什么；
9. 一个路径安全反例和一个尚未验证边界。

若只能说“路径就是地址、UTF-8 支持中文”，说明模型仍太粗。回到路径解析五步法与编码往返图。

## 间隔复习计划

- **第 1 天**：只看一张项目树，给三个不同起点写目标路径；
- **第 3 天**：不看正文解释 `A修🔧` 为什么是三个可见符号但 UTF-8 占八字节；
- **第 7 天**：诊断一个同名文件与一个 LF/CRLF 全文件差异；
- **第 21 天**：在 FactoryCare 的 CSV 或附件设计中指出路径与编码的信任边界。

每次复习都要先预测再查看文件属性。把未遇到的平台写成未验证，不凭 macOS 经验宣称 Windows/Linux 完全相同。

## 速查表

| 问题 | 第一项观察 | 常见误区 |
| --- | --- | --- |
| 文件找不到 | 起点、实际解析目标、真实名称 | 立刻新建副本 |
| 修改没生效 | 编辑文件路径与程序读取路径是否相同 | 只看文件名 |
| 双扩展名 | 编辑器项目树/属性中的完整名称 | 相信桌面隐藏显示 |
| 中文乱码 | 原始字节来源、实际解码方式 | 对乱码反复保存 |
| 全文件变化 | LF/CRLF、格式化与仓库规则 | 逐行手改业务代码 |
| 跨机器失效 | 是否硬编码个人绝对路径、大小写差异 | 假设所有系统相同 |

路径判断句式：

```text
起点是 ______。
路径段依次是 ______。
逐层解析后的目标是 ______，类型应为 文件/目录。
实际名称、大小写和扩展名是 ______。
该结论尚未覆盖的平台或文件系统是 ______。
```

编码判断句式：

```text
原始字符/字节来自 ______。
保存时编码是 ______，读取时解码是 ______。
实际状态栏/验证器观察是 ______。
修复时保留了原件，并只改变 ______。
关闭重开后的往返结果是 ______。
```

## 术语表

- **文件**：文件系统中带名称、位置、内容字节和元数据的对象。
- **目录**：组织名称、文件和子目录的层级节点。
- **路径**：从某个起点按路径段定位文件系统对象的表示。
- **绝对路径**：从文件系统根或平台定义的绝对位置开始的路径。
- **相对路径**：相对于明确起点解释的路径。
- **工作目录**：进程解析普通相对路径时常用的起点；不一定等于当前源码目录。
- **扩展名**：文件名末尾常用于提示格式或工具关联的部分，不证明真实内容。
- **隐藏文件**：被界面默认省略展示的文件；隐藏不是加密。
- **Unicode 码点**：Unicode 编号空间中的一个数值位置。
- **字形**：字体对字符的视觉绘制。
- **字节**：存储与传输的八位数据单位。
- **编码**：把字符序列转换为字节序列的规则。
- **解码**：按指定规则把字节序列解释为字符序列。
- **UTF-8**：Unicode 的可变长度编码形式，每个标量值使用一到四字节。
- **BOM**：文件开头可用于提示编码/字节序的标记；UTF-8 可有但通常不必需。
- **LF/CRLF**：两种常见行结束表示，分别为 `0A` 与 `0D 0A`。

## 来源与复核日期

本章只覆盖稳定心智模型，不把某个编辑器菜单名称当作永久规范。VS Code、IntelliJ 的界面可能随版本变化，实际操作以当前状态栏和官方文档为准。

- 复核日期：2026-07-24。
- Unicode Consortium，[The Unicode Standard, Version 17.0.0](https://www.unicode.org/versions/Unicode17.0.0/)：支持抽象字符、码点、编码形式与 Unicode 术语；该固定版本链接避免 `latest` 入口的协议降级重定向。
- Unicode Consortium，[Unicode Standard Annex #29: Unicode Text Segmentation](https://www.unicode.org/reports/tr29/)：支持码点与用户感知字素边界不能简单等同。
- IETF，[RFC 3629: UTF-8, a transformation format of ISO 10646](https://www.rfc-editor.org/rfc/rfc3629)：支持现代 UTF-8 一至四字节结构与有效范围。
- WHATWG，[Encoding Standard](https://encoding.spec.whatwg.org/)：支持 Web 平台编码、解码和错误处理的规范背景。
- Microsoft，[Visual Studio Code: Basic Editing](https://code.visualstudio.com/docs/editor/codebasics)：支持 VS Code 文件、编码和行尾观察入口；具体界面以安装版本为准。
- EditorConfig，[EditorConfig Specification](https://spec.editorconfig.org/)：支持项目级字符集与行尾约定的配置语义。
- MITRE，[CWE-22: Improper Limitation of a Pathname to a Restricted Directory](https://cwe.mitre.org/data/definitions/22.html)：支持路径遍历风险与限制边界。

这些来源支持技术定义与风险边界；本章“路径解析五步法”是课程为零基础调试设计的教学顺序，不是所有操作系统唯一规定的诊断流程。
