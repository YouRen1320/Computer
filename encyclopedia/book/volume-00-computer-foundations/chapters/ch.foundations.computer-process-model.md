# CPU、内存、磁盘、程序与进程

<!-- BEGIN GENERATED LEARNING PREREQUISITES -->
## 学习前检查

以下章节是本章的硬前置。开始前，请先完成并验证对应能力：

- [《终端、Shell、命令与引用规则》](ch.foundations.terminal-shell.md)：独立完成计算机资源、程序与进程前，必须先具备「终端、Shell、命令与引用规则」已经验证的知识与失败边界
<!-- END GENERATED LEARNING PREREQUISITES -->

双击一个应用，或者在终端运行 `ruby verify.rb`，屏幕上只是多了一个窗口或几行文字，计算机内部却发生了一连串不同层次的事情：磁盘上的程序字节被读取，操作系统为一次运行建立进程，内存保存运行期代码与数据，CPU 执行指令，进程获得临时 PID，父进程可以等待它结束，程序还可能在磁盘上留下配置或日志。

初学者常把这些对象压成一句“程序在电脑里跑”。结果一遇到故障，就会说“程序文件只有 20 MB，所以不可能占 2 GB 内存”“磁盘还有空间，所以内存不会满”“关掉窗口就是删掉程序”“看见同一个 PID 就一定是昨天的任务”。这些说法把存储介质、运行实例、资源测量与身份混在了一起。

本章建立一张最小但能用于诊断的运行地图：CPU、内存与磁盘分别承担什么；易失状态和持久状态如何区分；资源有容量、配额和竞争边界；程序文件与进程不是同一对象；PID 只标识某段时间内的进程；进程如何经历创建、运行或等待、退出与回收；父子关系描述创建链，而不是文件所有权或业务权限。

我们只用上一章学过的终端运行固定 Ruby 验证器。验证器只启动自己的两个短子进程，让它们自然结束，不遍历全机进程，不终止陌生 PID，不制造 CPU、内存或磁盘耗尽，也不使用进程间管道。标准流、进程间通信、信号控制、线程和调度算法将在后续章节正式学习。

## 学完后你必须能做什么

完成正文、实验与无 AI 练习后，你应当能够：

1. 用自己的话区分 CPU 执行、内存运行期保存和磁盘持久保存，不把三类指标互相替代；
2. 解释“易失”和“持久”描述的是生命周期承诺，不等于数据永远只位于某一种物理器件；
3. 给资源故障写出容量、当前用量、变化速率、限制和竞争者，而不是只报一个百分比；
4. 区分磁盘上的程序文件与一次运行的进程，说明一份程序为什么能产生多个进程；
5. 解释 PID、PPID 与父子关系，并指出 PID 会复用、不能作为永久业务身份；
6. 画出创建、可运行/运行、等待、退出、回收的简化生命周期，知道“等待”不等于“消失”；
7. 启动固定短进程与持续进程，预测并观察 PID、PPID、程序文件及退出前后差异；
8. 面对“很慢”“内存大”“磁盘满”时，选择与主张同层级的第一处证据；
9. 纠正一份混淆程序、进程、内存和磁盘的故障报告，并在修复动作后重测原指标；
10. 识别危险诊断动作：不结束不属于实验的进程，不故意填满资源，不把一次快照当成根因证明。

本章成功标准不是背出硬件定义，而是能够给每个主张找对对象、时间与指标。自动验证器 PASS 只证明固定生命周期预言，不证明你已经会分析真实生产故障。

## 直觉模型：厨房、工作台与仓库

可以把一次程序运行想成厨房完成订单：

- **磁盘**像仓库，长期保存菜谱文件、原料清单和已归档记录；
- **内存**像工作台，摆放当前订单正在使用的菜谱副本、原料状态和中间结果；
- **CPU**像厨师的执行时间，按步骤进行切配、计算与判断；
- **程序**像保存下来的菜谱；
- **进程**像“今天 10:05 按这份菜谱做的一次订单”；
- **PID**像这次订单在厨房系统中的临时号码；
- **父进程**像创建这张子订单的上级任务。

这个类比帮助入门，但不能无限延伸。CPU 可以有多个核心，操作系统会在许多任务间调度；内存不是一张连续可见的桌子，进程通常看到自己的虚拟地址空间；磁盘也有缓存、文件系统和设备差异；父子进程不是现实家庭，不自动共享全部数据。类比建立方向，精确定义负责守边界。

```text
磁盘上的程序文件
        ↓ 被加载、映射或解释
操作系统创建进程 ── 分配 PID、资源视图与运行状态
        ↓
CPU 执行指令 ↔ 内存中的运行期代码与数据
        ↓
进程退出；内存状态被回收，明确写入的磁盘文件可继续存在
```

## CPU：执行指令的计算资源

### CPU 在本模型中的职责

CPU（central processing unit）执行机器指令。加法、比较、分支、函数调用、数据转换最终都需要 CPU 时间。现代电脑通常有多个核心，每个核心还涉及复杂流水线、缓存与调度；本章不要求理解微架构，只需知道“程序运行”不是磁盘文件自己变化，而是处理器在操作系统安排下执行进程中的指令。

一个进程显示 100% CPU 的含义依赖监控工具、核心数量和统计窗口。有的工具把一个核心满载记为 100%，有的用整机容量作为基准。不能脱离工具口径比较两个百分比。持续高 CPU 可能符合预期，例如批量计算；也可能来自忙等、死循环或算法低效。指标支持“CPU 时间大量被使用”，不自动证明具体代码根因。

### CPU 繁忙与“程序卡住”不同

界面没有变化时，进程可能正在高强度计算，也可能等待磁盘、网络、锁或用户输入。只看“没有输出”不能区分。诊断应先收集同一时间窗口的 CPU 使用、任务状态和需求预言，再选择更深入工具。

例如 FactoryCare 批量计算 10 万张工单的 SLA，CPU 长时间较高、内存稳定、处理计数持续增长，可能是正常工作；如果处理计数不增长且单核持续满载，才进一步怀疑无进展循环。两者不能只凭“风扇响”区分。

### CPU 资源限制与竞争

CPU 总量有限，多个进程会竞争可运行时间。容器、操作系统或平台还可能设置配额。某进程本身算法没有改变，但同机任务增加后完成时间变长，这属于共享资源竞争的可能性。反过来，CPU 使用不高也不保证性能正常；进程可能在等待别的资源。

记录 CPU 问题时至少写：统计窗口、测量口径、进程或整机范围、工作量、进度指标、并发数量和限制。孤立的“CPU 80%”信息不足。

## 内存：运行期可直接访问的状态空间

### 内存保存什么

进程运行时需要存放代码、对象、变量、调用状态、缓存和运行时元数据。操作系统为进程提供地址空间模型，进程看到的地址不等于一眼可见的物理内存排布。学习 Java、Python、浏览器或数据库时，会遇到堆、栈、映射、缓存等更细概念；本章只把它们归为“运行期需要被访问的内存状态”。

程序文件大小与进程内存占用没有固定相等关系。一份 20 MB 可执行文件可以加载大量数据、建立缓存并使用数 GB 内存；一份很大的磁盘文件也可以按块读取，不必同时全部进入内存。若报告把二者直接等同，第一步就是拆开测量对象。

### 易失不等于“每个字节永远只在内存芯片”

通常说内存是易失的，意思是运行期状态不应被当成断电或进程退出后仍可靠存在的持久记录。操作系统可能把部分内存页面暂时换出到磁盘，硬件与系统也有缓存；这些实现细节不把普通内存对象自动变成业务持久数据。

如果 FactoryCare 在内存中把工单状态改为 `CLOSED`，却没有按设计写入数据库或持久日志，那么进程崩溃后不能声称状态已可靠保存。即使某些字节短暂出现在交换空间，也没有形成可用的持久业务合同。

### 内存指标与限制

监控工具常展示常驻内存、虚拟内存、内存压力、交换使用等不同指标。数字大不必然是泄漏：运行时可能保留堆、文件可能映射到地址空间、缓存可以在压力下回收。数字持续增长也不自动证明泄漏，要结合相同工作负载、回收后基线、限制与时间趋势。

资源限制很重要。进程可能面对容器限制、系统可用量或运行时上限。整机还有空闲内存，不代表某个受限进程一定能继续分配；反之，监控显示物理内存紧张时，系统可能通过压缩或交换维持运行但性能下降。报告必须写清指标范围。

## 磁盘：持久字节与有限容量

### 磁盘保存程序与数据

本章把 SSD 等持久存储统称为磁盘。程序源码、可执行文件、配置、数据库文件和日志通常以文件形式保存。上一章学习过文件是有路径和内容字节的对象；本章增加生命周期：进程退出不会自动删除程序文件，写入完成的持久文件也可以在进程结束后继续存在。

“持久”不是“永不丢失”。用户删除、程序覆盖、磁盘损坏、文件系统故障、加密密钥丢失或备份缺失都会造成数据不可用。持久表示跨进程和重启保留的设计目标，可靠性还需要写入语义、同步、备份与恢复验证。

### 容量、吞吐与等待

磁盘问题至少有三类：空间容量不足、读写吞吐受限、访问延迟高。磁盘还有 100 GB 只反对“立即因为容量为零而失败”这一小部分假设，不能证明读写速度正常，也不能证明内存充足。

进程写报告文件失败时，应观察目标文件系统剩余空间、配额、路径、权限和实际诊断。不要为了证明磁盘满而在真实机器生成巨大文件；使用固定数值夹具或受限制临时环境即可。生产容量测试需要专门计划和清理方案。

### 磁盘文件与运行实例

同一个 `worker.rb` 文件可以先后或同时被多个 Ruby 进程解释。程序文件字节没有因为多次启动而自动复制多份；每个进程却有自己的 PID、生命周期和运行期内存。程序更新时，已运行进程是否立即采用新字节取决于运行时与加载方式，不能只凭磁盘修改时间推断。本章固定示例不在进程运行时修改程序文件。

## CPU、内存、磁盘不能互相替代

三类资源会协作，但指标不能互相证明：

| 观察 | 直接支持 | 不能单独证明 |
| --- | --- | --- |
| CPU 长时间接近工具上限 | 大量处理器时间被使用 | 一定是死循环；内存充足；磁盘正常 |
| 常驻内存接近进程限制 | 内存容量压力值得调查 | 一定泄漏；磁盘已满；CPU 是根因 |
| 目标磁盘剩余空间低于写入需求 | 容量不足能解释新写入失败 | 计算错误；程序文件太大；进程已退出 |
| 程序文件只有 20 MB | 磁盘上该文件大小 | 进程最多使用 20 MB 内存 |
| 磁盘还有 100 GB | 当前测量范围内有可用容量 | 进程内存一定够；读写一定快 |

真实故障可以同时涉及多类资源。例如内存不足导致交换增加，进而增加磁盘访问并让 CPU 等待。即便如此，诊断仍应保留指标层次和时间顺序，而不是把所有症状改名为“电脑资源不够”。

## 易失状态与持久状态

### 用恢复问题来区分

判断一个状态是否属于持久合同，可以问：“进程退出、应用重启或机器重启后，系统是否承诺还能按业务方式重新得到它？”如果答案依赖“也许那块内存还没被覆盖”，就不是可靠持久化。

FactoryCare 中，页面当前选中的筛选项可以只是内存状态；已关闭工单的最终状态通常必须持久保存。两者都可能在运行时位于内存，但生命周期要求不同。把界面状态误当数据库事实，或把数据库文件误当当前页面对象，都会造成错误诊断。

### 写入文件也不自动等于可靠提交

程序调用写文件后，数据可能经过缓冲、文件系统缓存与设备。崩溃一致性和强制落盘属于后续 I/O、数据库与事务章节。本章只建立谨慎结论：明确写入并在进程结束后重新读取同一路径，是比“变量还在”更强的持久证据，但仍不能替代备份和事务保证。

### 临时文件是一种有意限定的持久字节

验证器会在系统临时目录写入子进程记录。它确实是磁盘文件，但生命周期由实验目录限定，测试结束后清理。暂时写在磁盘与“业务永久记录”不是同义词。讨论持久性要同时写介质、路径、拥有者、保留期限与恢复合同。

## 资源上限、配额与竞争

“机器总共有多少”只是资源问题的一部分。进程能用多少还可能受到：

- 操作系统与用户限制；
- 容器或服务配置的 CPU/内存配额；
- 文件系统剩余空间与用户配额；
- 同机其他进程的竞争；
- 应用运行时自己的堆或并发限制；
- 安全策略和权限。

因此故障报告应包含五项：**容量、当前用量、限制、竞争者、时间变化**。例如“10:05，导入进程常驻内存 4015 MiB，进程限制 4096 MiB，新分配失败；CPU 18%，目标磁盘尚有 8000 MiB”。这比“电脑内存高”更可证伪，也避免拿不相关指标替代。

不要用耗尽实验验证上限。教材用固定 JSON 快照表达边界；真实系统需要隔离压测环境、监控、停止条件和回滚。故意占满个人电脑内存或磁盘既危险，也不能代表生产配置。

## 程序：可保存的指令与资源

### 程序不是正在运行的东西

程序可以是编译后的可执行文件，也可以是由运行时解释的脚本与关联资源。它作为文件存在于磁盘时，即使没有任何进程执行它，仍然是程序工件。源代码、构建产物和运行时之间还有更细关系，后续语言章节会展开。

你可以检查 `child_probe.rb` 文件存在并计算摘要，但这只能证明磁盘字节。要证明它运行，需要观察某次进程生命；要证明功能正确，还需要输入与输出预言。文件存在、进程存在与功能正确是三种不同主张。

### 一份程序，多次运行

每次启动通常产生新的进程实例。两次实例可以先后存在，也可以并发存在；它们通常有不同 PID 和独立运行状态。一个实例崩溃不自动修改另一个实例的内存，一次退出也不删除程序文件。

配套验证器用同一 `child_probe.rb` 启动一个短进程和一个持续 0.40 秒的进程，记录两个不同 PID，并在运行前后核对程序文件 SHA-256 摘要未变。摘要不是功能证明，只用于显示磁盘工件没有被实验改写。

## 进程：一次运行的资源与状态容器

### 精确定义

进程是操作系统管理的一次程序执行实例，带有进程标识、地址空间、打开的资源、凭据、当前工作目录和生命周期状态等。不同操作系统细节不完全相同，本章采用足以解释基础现象的模型。

进程不是窗口。后台任务可以没有窗口，一个应用也可能创建多个进程，关闭某个窗口不必然等于整个应用所有进程结束。进程也不是线程；一个进程可以包含多个执行流，线程模型留到并发章节。

### 进程拥有 cwd

上一章学到 cwd 是相对路径起点。更精确地说，cwd 属于进程状态。zsh 进程改变自己的 cwd 后，它启动的子进程通常从这个上下文开始；另一个终端里的 zsh 是另一个进程，有自己的 cwd。这个模型解释为什么两个终端可以同时位于不同目录。

### 进程拥有资源视图，不等于拥有磁盘程序

父子、PID 与内存状态都属于运行模型；文件所有权和权限属于文件系统与安全模型。某进程使用一个程序文件，不表示它在业务或文件权限意义上“拥有”该文件。不要从 PPID 推断谁有权读取数据。

## PID：临时进程标识，不是永久身份

### PID 的作用

操作系统给活动进程分配一个数值标识 PID。观察工具与系统 API可以在某一时刻用 PID 指向进程。配套子程序写下自己的 `Process.pid`，父验证器同时保存 `Process.spawn` 返回的 PID；两者相等构成一次固定观察。

### PID 会复用

进程退出并被系统回收后，它的 PID 数值未来可能分配给另一个无关进程。因此“昨天 PID 1234 是导入任务”不能推出“今天 PID 1234 仍是同一个任务”。可靠业务身份应使用工单 ID、任务 ID、开始时间、程序身份等上下文，PID只适合操作系统级临时定位。

### 不硬编码、不结束陌生 PID

不要把示例 PID 写进配置，也不要复制教程中的 PID 去终止进程。数字在另一台机器或另一个时刻可能指向完全不同的程序。教材验证器只探测自己刚创建、仍由它等待的子 PID，并让它自然退出。

## 生命周期：创建、运行或等待、退出与回收

### 简化状态图

不同系统和工具对状态名称有差异，本章使用概念图：

```text
创建
  ↓
可运行 ←→ 正在执行
  ↘        ↙
    等待某事件
        ↓ 条件满足后重新可运行
      退出
        ↓ 父进程或系统完成回收
      不再是活进程
```

“可运行”表示具备运行条件、等待 CPU 调度；“正在执行”表示此刻占用处理器执行；“等待”可能是在等待计时、磁盘、网络、锁或其他事件。等待状态仍是进程生命的一部分，不等于程序消失。

### 短进程为什么难观察

一个只运行几毫秒的命令可能在你打开监控界面前已经退出。没有看到它不证明它从未运行。配套示例让一个进程持续固定短时间，并由父验证器在其写下记录后立即探测，减少人工竞态；另一个短进程展示“退出后旧 PID 不再表示活进程”。

### 退出与回收

进程完成或失败后进入退出过程，操作系统释放其大部分运行资源；父进程通常需要取得结束信息，系统再完成回收。某些系统可短暂显示已退出但尚待父进程回收的状态，具体机制留待操作系统与并发章节。

本章的重要不变量是：退出后的进程内存不能继续当作业务状态来源；程序文件与已明确持久写入的数据可以继续存在；旧 PID 不能永久代表原实例。

## 父进程与子进程

### 创建关系

当一个进程请求操作系统创建另一个进程时，通常形成父子关系。子进程可观察父进程标识 PPID。配套验证器是父，两个 `child_probe.rb` 运行实例分别是子；子写下的 PPID 应等于当时验证器的 PID。

终端场景中，zsh 常启动 Ruby，Ruby 又可能启动别的任务。父子树描述创建链，有助于回答“谁启动了谁”和“谁可能等待谁”。它不自动说明业务负责人、租户、文件所有者或网络调用方。

### 父子不等于共享全部内存

父子进程拥有各自进程身份和地址空间模型。具体系统可以通过特定机制共享或传递数据，但那需要显式接口与合同。本章不教授进程间通信，也不使用管道作为实验数据通道。子进程只把记录写入受控临时文件，父进程稍后读取该文件。

### 父进程结束后的边界

父进程结束后，子进程是否继续、由谁接管、会收到什么通知，取决于平台、会话、信号与程序设计。不能用“现实家庭”类比推出结果。本章实验让父进程始终等待自己创建的子进程自然结束；其他行为明确标为未验证。

## 使用已学终端安全观察

示例目录提供固定验证器。先读 README 与 `child_probe.rb`，预测：磁盘上有一份程序文件；第一次和第二次启动得到两个进程 PID；子 PPID 等于验证器 PID；退出后程序文件仍存在；退出的 PID 不再表示活进程。

进入示例目录后运行：

```text
ruby verify.rb
```

你已经会解释这行：当前 zsh 从 cwd 找到相对脚本路径，`ruby` 是命令，`verify.rb` 是一个参数。验证器内部使用 Ruby 进程 API，不要求你提前学习 API 语法。它输出五条摘要，最后一行必须是：

```text
process-model verification: PASS
```

“expected absence”表示进程退出后再次按旧 PID 查找活实例得到不存在，属于预期失败证据。不要把该反例替换为人工结束某个系统进程。

## 固定资源案例：证据要与主张同层级

配套 `resource-cases.json` 有三行教学数据：

1. CPU 96%，内存远低于限制，磁盘空间充足；
2. CPU 18%，常驻内存达到限制的 95%以上，磁盘空间充足；
3. CPU 11%，内存低，磁盘可用量低于固定写入需求。

验证器按明确、有限的教学规则把它们分别标为 CPU、内存、磁盘主要嫌疑。这个分类器不是生产监控算法，不能复制到真实应用后自动诊断根因。它的价值是强迫你承认三种指标不同，并用反证排除“所有变慢都是内存”这种混淆。

真实诊断还需要时间序列、工作负载、应用进度、系统限制和日志。教材数据只证明在固定假设下选择了与主张一致的首个资源方向。

## 常见故障报告及纠正

### “程序占了 4 GB，删掉程序文件就会释放内存”

这里把进程内存占用叫成程序文件占用。删除磁盘文件不是释放活进程内存的安全方法，还可能破坏下次启动。先确认 4 GB 指哪一个进程、哪项内存指标、什么时间窗口和什么限制。若进程完成工作后仍异常增长，应在隔离环境分析对象生命周期；不能用删除程序文件替代。

### “磁盘有空间，所以不可能内存不足”

磁盘剩余容量与进程内存上限不是同一资源。即便系统可交换部分页面，也不等于磁盘空间自动满足进程分配合同。第一处可信证据是进程/容器内存使用、限制和分配失败，而不是 Finder 中的磁盘容量。

### “进程退出，所以数据都没了”

运行期未持久状态会丢失，但已明确写入持久存储的数据与程序文件可以继续存在。应在退出前后检查同一路径、内容或数据库事实；不能把某个临时文件仍在扩展为“全部业务已提交”。

### “PID 一样，所以一定还是原任务”

PID 可复用。需要结合观察时间、程序、父子关系和业务任务 ID。若只有一个旧截图，结论应标为未验证，不应据此操作当前进程。

### “等待状态说明进程死了”

等待是活进程的常见状态。它可能等待计时器、I/O 或同步条件。应观察等待是否符合需求、是否能恢复和进度是否变化；本章不深入具体等待原因。

## 诊断框架：对象—时间—指标—限制—动作

面对资源报告，按顺序提问：

1. **对象**：说的是程序文件、某个 PID 的进程、整机还是容器？
2. **时间**：启动前、运行中、退出后，还是一段趋势？
3. **指标**：CPU、常驻内存、虚拟内存、磁盘容量、读写等待中的哪一个？
4. **限制**：进程、用户、容器、文件系统或整机上限是什么？
5. **竞争**：还有哪些进程或任务同时使用资源？
6. **预言**：若假设成立，改变一个条件后哪个原指标应改变？
7. **动作**：能否在隔离环境用低风险方式验证，而不是破坏真实系统？
8. **复测**：修复后是否重测同一对象、时间窗口和指标？

“重启后好了”不是完整根因。重启会同时改变进程、内存、缓存、连接与时间，很难归因。它可以是恢复动作，但需要在报告中与根因证据分开。

## 安全边界

### 只观察自己创建的进程

真实电脑上有操作系统、IDE、浏览器和同步服务进程。初学者无法仅凭名称判断可否结束。本章实验只持有验证器刚创建的子 PID，并让子进程自然退出。不要扩展为列出所有用户进程并逐个试验。

### 不制造资源耗尽

不要写无限循环“看看 CPU 会怎样”，不要分配内存直到崩溃，不要生成大文件填满磁盘。这些实验可能导致数据丢失和系统不稳定。边界行为使用固定小数值、短睡眠与临时目录模拟。

### PID 不是授权

知道 PID 不表示有权观察、控制或读取该进程数据。公司设备还可能有审计和管理策略。任何诊断都要遵守权限、隐私和变更流程。

### 监控快照需要脱敏

进程命令行可能含路径、用户名、URL 甚至错误放入参数的秘密。不要把整份进程列表或环境变量上传给外部 AI。本章固定验证器清空继承环境，不输出用户主目录和其他进程信息。

## FactoryCare 场景：批量导入任务

运维管理员启动一次设备导入。磁盘上的导入程序没有变化，操作系统创建一个进程并分配 PID；进程在内存中建立解析对象，CPU 执行校验，成功记录最终写入持久存储。

若导入变慢，团队收集到：CPU 持续接近监控口径上限，常驻内存平稳，磁盘空间充足，已处理计数仍增长。合理结论是“CPU 是当前主要资源嫌疑，任务仍有进展”，不是“已经证明算法有死循环”。替代假设还包括并发竞争、输入复杂度增加或监控口径变化。

需求随后改为允许同时启动两个导入进程。不能只把单进程数字乘二。需要重新验证：两个 PID 与各自业务任务 ID 的映射；总 CPU 竞争；每进程与总内存限制；磁盘临时空间；父进程是否等待和回收；一个失败是否影响另一个；进程退出后哪些业务状态已经持久提交。

本章只负责资源和进程模型，不设计并发锁、事务或消息队列。把尚未教授的机制标为后续工作，比用术语假装解决更可靠。

## 速查表

| 概念 | 最小定义 | 第一处证据 | 常见误解 |
| --- | --- | --- | --- |
| CPU | 执行指令的计算资源 | 同口径时间窗口使用与进度 | 高就一定死循环 |
| 内存 | 运行期直接访问的代码与数据状态 | 进程指标、限制、趋势 | 等于程序文件大小 |
| 磁盘 | 持久保存文件字节的介质/文件系统空间 | 目标文件系统容量与文件 | 有空间就无性能问题 |
| 易失状态 | 不承诺跨进程/重启保留的状态 | 退出后恢复测试 | 字节绝不会触及磁盘 |
| 持久状态 | 按合同可跨进程恢复的状态 | 重新打开/读取与一致性证据 | 永远不会丢失 |
| 程序 | 可保存的指令与资源工件 | 路径、字节、摘要 | 就是正在运行的进程 |
| 进程 | 一次程序执行实例及其资源状态 | 创建时 PID、运行/退出观察 | 就是一个窗口 |
| PID | 某段时间内的进程标识 | 系统 API/观察工具 | 永久业务 ID |
| PPID | 进程记录的父进程标识 | 子记录与父 PID 对照 | 文件所有者或权限 |
| 资源限制 | 可用量的策略或容量边界 | 限制与当前用量同范围 | 整机空闲即进程可用 |

## 术语表

- **CPU**：执行机器指令的中央处理资源；本章不展开微架构。
- **core / 核心**：可执行指令流的处理单元之一；监控百分比需结合核心与工具口径。
- **memory / 内存**：进程运行期代码与数据所在的可寻址状态空间模型。
- **resident memory / 常驻内存**：某时刻实际驻留物理内存的一类指标，定义依工具而异。
- **virtual memory / 虚拟内存**：操作系统向进程提供的地址空间抽象，不等于实际占用同量物理内存。
- **disk / 磁盘**：本章对 SSD 等持久存储和其文件系统容量的统称。
- **volatile / 易失**：不承诺跨进程终止或重启可靠恢复的生命周期属性。
- **persistent / 持久**：按明确合同跨进程或重启仍可恢复的生命周期属性。
- **program / 程序**：磁盘上可被加载、解释或执行的指令与资源工件。
- **process / 进程**：操作系统管理的一次程序执行实例。
- **PID**：进程标识符，生命周期有限且数值可复用。
- **PPID**：父进程的进程标识符。
- **parent/child process / 父子进程**：由进程创建关系形成的运行时关系。
- **lifecycle / 生命周期**：从创建到运行/等待、退出和回收的状态变化。
- **resource limit / 资源限制**：系统、容器、用户或运行时对可用资源设置的边界。

- 不教授进程间管道、共享内存、套接字、消息队列或其他 IPC；
- 不系统教授标准流、重定向、退出码、信号和作业控制；
- 不遍历、终止或修改其他用户与系统进程；
- 不通过无限循环、海量分配或大文件制造资源耗尽；
- 不把固定 JSON 分类规则宣传为生产监控算法；
- 不把 PID、PPID 或父子关系当成业务身份、权限或数据所有权；
- 不把一次快照、一次 PASS 或一次重启当成根因证明。

下一阶段的语言与工具课程会反复使用这张地图：Java 的 JVM 是进程，变量与对象占运行期内存，class 与配置保存在磁盘，Maven 会启动构建进程；后续每次诊断都应先确认对象、时间与资源层级。
