# 事故响应、灾难恢复、复盘与改进闭环

> 本章唯一职责：用严重度、角色、时间线和证据组织事故响应，执行已演练恢复/部署决策，并把复盘行动转为可验证工程门禁。它不把一次静态脚本通过包装成真实灾备能力，也不把“赶快恢复”当成破坏证据和覆盖数据的授权。

## 1. 学完以后，你应当真正会什么

你需要能够在两分钟内说明四件事：事故响应是在不确定和时间压力下控制影响的协作机制；灾难恢复是把服务与数据恢复到约定目标的、需要预演的工程能力；复盘是解释系统条件和决策过程而非寻找“犯错的人”；改进闭环则要求每项行动都有负责人、期限、验收判据和回归证据。四者互相关联，但不能混成一句“出了问题就回滚”。

本章的可考核结果是：

1. **解释**：说清事故严重度、指挥角色、沟通节奏、证据时间线、RTO、RPO、恢复检查点、无责复盘和改进行动之间的关系，并举出一个越界反例。
2. **构建**：为“数据库不可用叠加错误发布”主持一次隔离的桌面推演或现场演练，保存严重度、角色、事件时间、命令、配置、制品身份、沟通、恢复决策和至少三项工程改进。
3. **诊断**：面对边调查边删容器或日志、未经授权直接覆盖唯一数据、只写“加强监控”、按个人追责等故障，找到最早可信证据，修复流程或工件，并用原验证重新判定。

教材附带工件分成四层。`examples` 是确定性合同示例；`labs` 是合成桌面推演，不执行真实 PostgreSQL 恢复；`exercises` 故意为红；`solutions-private` 是参考实现。它们能验证字段与判断逻辑，**不能**证明真实备份可恢复、真实切流成功或生产 RTO/RPO 达标。真实证据只能来自隔离环境中执行过的 runbook、实际制品、实际计时、实际校验和明确审批。

## 2. 先建立正确心智模型：事故不是普通缺陷

普通缺陷通常有可重复步骤、明确所有者和可接受的修复节奏。事故则正在造成或可能迅速造成用户影响、数据风险、安全风险或关键业务中断。它有三个特点：信息不完整、时间成本持续增长、多人并行操作可能互相干扰。因此事故响应首先是一种**控制系统**：确定谁做决定、谁操作、谁记录、谁沟通；建立共同事实；限制危险动作；不断比较用户影响和恢复风险。

“数据库连接失败”不自动等于最高严重度；“接口还能返回 200”也不自动代表没有事故。严重度应由用户影响、影响范围、持续时间、数据完整性、安全与合规风险、替代路径和扩散速度决定。例如：单个测试租户偶发超时可能是较低级别；所有租户无法更新工单且现场人员无法派工，可能是高严重度；若出现跨租户数据暴露迹象，即使流量很小也需要按高安全影响处置。

事故生命周期可以记成：

```text
信号出现 → 确认用户影响 → 宣告事故/定级 → 建立角色与频道
       → 稳定影响/保全证据 → 形成假设并验证 → 决定缓解或恢复
       → 验证业务与数据 → 持续沟通 → 关闭响应
       → 无责复盘 → 行动进入工程门禁 → 回归验证
```

这里的箭头不是严格单线程。操作、调查、沟通和记录会并行，但必须由事故指挥者协调。关键动作应进入时间线；猜测必须标记为猜测；已经证伪的假设也应保留，以免下一班重复走弯路。

### 2.1 事故、问题、灾难和恢复的边界

- **事件/告警**是一个信号，可能是真事故，也可能是噪声。
- **事故**是需要协调响应的实际或迫近影响。
- **问题管理**关注事故背后的长期条件，不必在止血阶段一次解决。
- **灾难**通常表示正常冗余与日常修复不足以恢复，需要备用站点、备份、重建或重大流量切换。
- **灾难恢复**是事先定义并演练过的能力，不是事故发生后临时搜索命令。

一次错误发布可以触发事故，但回滚部署不一定恢复数据库状态；数据库故障转移可以恢复可用性，却不等于拥有可用备份；备份文件存在也不等于已经通过恢复验证。这些边界是本章最重要的判断基础。

## 3. 严重度：用影响驱动资源与节奏

严重度不是工程师能力评分，而是调动响应机制的标签。团队可以采用 `SEV-1` 到 `SEV-4`，也可以用 P0/P1；名称不重要，重要的是定义一致、触发条件可观察、每一级对应明确动作。

一个适合小团队的示例矩阵如下：

| 级别 | 示例影响 | 响应要求 | 沟通建议 |
| --- | --- | --- | --- |
| SEV-1 | 大范围关键流程中断、数据完整性或安全风险 | 立即宣告，设事故指挥，暂停高风险发布，召集数据/业务负责人 | 先快速确认影响，随后固定节奏更新 |
| SEV-2 | 重要功能显著降级，有替代路径但成本高 | 值班负责人协调，限定时间内升级 | 定期内部更新，必要时用户更新 |
| SEV-3 | 局部影响或低扩散风险 | 正常缺陷流程并保留可诊断证据 | 按工单状态沟通 |
| SEV-4 | 咨询、无用户影响异常或已知噪声 | 排期处理或改进告警 | 无需事故频道 |

定级后仍应重新评估。影响扩大、发现数据破坏或恢复时间将超目标时升级；确认影响受控后降级。不要为了“指标好看”压低级别，也不要因为某位高层关注就跳过事实。严重度改变的是资源、权限升级和沟通频率，不改变证据标准。

事故宣告至少包含：事件编号、当前严重度、开始时间、已知用户影响、未知项、事故指挥者、协作频道、下一次更新时间。一个合格的首条消息可以是：

```text
INC-2026-071：SEV-1。10:00 起，租户工单写入失败率约 82%，读取暂时可用；
是否发生数据丢失尚未知。IC=张某，Ops=李某，Comms=王某，Scribe=赵某。
已暂停发布，下一次状态更新 10:10。证据面板：dashboard-17，发布制品：sha256:...
```

它没有把“数据库坏了”当成已经证明的根因，也没有承诺尚未验证的恢复时间。

## 4. 事故指挥：把并行工作变成可控工作

Google SRE 的一手事故管理指南强调清晰指挥、定义角色、保存工作记录、持续沟通和无责复盘。小团队可以一人临时兼任两个角色，但角色职责仍要显式，重大恢复的操作人与审批者最好分离。

### 4.1 四个核心角色

**事故指挥者（Incident Commander）**负责整体优先级和最终协调。他不必是数据库最强的人。他要维护当前目标、批准高风险动作、分配调查线、决定升级/降级和交接。IC 若亲自陷入终端调试，往往无人维护全局。

**操作负责人（Operations）**执行或委派诊断、缓解、恢复与验证。每个命令应说明目的、预期、风险和回退，不允许多人同时对同一数据库执行冲突操作。

**沟通负责人（Communications）**把内部事实转成面向用户、支持、管理层的更新。沟通不应复制未证实根因，也不应长时间沉默。即使没有进展，也可以说明“影响未变、正在验证什么、下一次更新时间”。

**记录员（Scribe）**维护时间线、证据链接、假设、决定、批准与结果。时间线不是会议纪要文学，而是以后能从日志复核的索引。

还可以有主题负责人，例如数据库、发布、网络或业务验证负责人。每条工作线都应有一个负责人和结束条件。`去看看数据库` 不是任务；`在 10:12 前比较主库连接拒绝时间与发布事件，回报证据链接，不做写操作` 才是可控任务。

### 4.2 指挥循环

IC 可以每五到十分钟执行一次简短循环：

1. 当前用户影响和严重度是什么？
2. 最新已确认事实是什么？哪些只是猜测？
3. 正在进行的工作线各自负责人和期限是什么？
4. 下一项危险决定是什么，需要谁审批、什么检查点？
5. 下一次沟通何时发出？
6. 有没有疲劳、权限、交接或证据丢失风险？

这个循环降低“所有人都很忙但没人知道在做什么”的概率。若某条假设没有可证伪条件，IC 应要求改写。例如“也许网络有问题”要改为“若 10:00 后应用到数据库端口的 TCP 探针失败而数据库本地 socket 正常，则支持网络路径假设；证据为探针日志 A/B”。

## 5. 沟通节奏：事实、影响、动作和下一次更新

事故沟通的目标不是展示技术细节，而是让不同受众做正确决定。内部工程频道需要证据与任务；用户状态页需要影响、可用替代方案和更新节奏；管理层需要范围、业务风险、资源需求和决策点。三者不应互相矛盾，但粒度不同。

一条状态更新可以固定为：

```text
时间：10:12
状态：仍为 SEV-1，工单写入失败；只读查询正常。
已确认：失败从 10:00:31 开始；10:00 发布的 API 制品与数据库连接池错误同时出现。
未确认：是否存在已确认但未持久化的写入。
动作：停止新发布；已保存数据库与部署证据；正在隔离环境验证上一个制品和恢复点。
用户建议：暂缓重复提交；客户端保留幂等键。
下次更新：10:22，或影响发生重大变化时提前。
```

不要说“马上恢复”，除非有经过演练且当前条件满足的明确路径。不要把内部人员名字和推测根因直接发给用户。不要因为团队还在调查就跳过固定更新；稳定节奏本身能降低重复询问和干扰。

## 6. 时间线与证据：先保全，再解释

事故中人会记错顺序，聊天时间可能与服务器时间不同，容器重建会删除现场，日志轮转会覆盖内容。因此“我记得先发布后报错”不是足够证据。可信时间线应明确时区、时钟来源、事件来源和不可变引用。

一个时间线事件至少包含：

- 统一格式时间，如 `2026-07-24T10:03:21+08:00`；
- 事件类型：告警、用户报告、发布、假设、命令、决定、审批、恢复、验证；
- 行为者或系统来源；
- 证据 ID：日志查询、trace、发布清单、镜像 digest、配置版本、备份清单、命令输出；
- 事实与解释分离；
- 对用户影响或下一决策的意义。

**最早可信证据**是能证明流程在哪个阶段首次偏离的原始或接近原始记录。例如测试断言错误时，失败断言比最后的 `BUILD FAILURE` 更有诊断价值；事故中，发布平台记录的制品 digest 和数据库日志时间通常比群聊中的“好像刚发布完”更可信。最终错误摘要只说明结果，不自动说明根因。

### 6.1 证据保全检查点

在执行重启、删除容器、故障转移、恢复覆盖、清理磁盘或回滚迁移前，先问：

1. 当前证据是否会被动作销毁？
2. 是否保存了日志窗口、配置、制品身份、数据库状态、连接状态和时钟信息？
3. 是否有数据快照或只读副本？
4. 谁批准动作？依据是什么？
5. 若动作失败，回退点在哪里？

检查点不是无限拖延。若安全或生命相关影响要求立即隔离，可以先执行最小遏制，但要记录为什么来不及完整采集。普通服务故障中，“先 `docker compose down -v` 再看看”几乎总是错误动作：它可能同时销毁容器现场与命名卷数据。

## 7. 灾难恢复的基本量：RTO、RPO 与恢复正确性

**RTO（Recovery Time Objective）**是业务可接受的恢复时间目标。例如 RTO=30 分钟，表示从约定起算点到达到约定服务状态不应超过 30 分钟。起算点是故障发生、被检测还是宣告事故，必须预先写清。

**RPO（Recovery Point Objective）**是可接受的数据时间损失目标。例如故障发生在 10:00，最新一致恢复点是 09:56，则恢复点间隔为 4 分钟；若目标是 5 分钟，合成计算满足目标。它不代表每条业务记录一定完整，还需业务校验。

不要混淆：

- RTO 不是平均修复时间，也不是供应商宣传的启动时间。
- RPO 不是备份周期的同义词。备份耗时、上传失败、WAL 缺口和不可恢复都会改变实际恢复点。
- 高可用减少某些中断，但复制可能同步传播误删除与逻辑破坏，所以副本不是备份。
- “服务端口打开”不等于恢复完成。要验证鉴权、租户隔离、核心读写、幂等、审计、消息副作用和数据一致性。

恢复验收应分层：进程启动；依赖健康；数据库可连接；模式与制品兼容；核心业务 smoke；数据对账；只读或降级限制解除；观察窗口稳定；用户沟通完成。每层都有明确 oracle，而不是凭页面“看起来正常”。

## 8. PostgreSQL 18 恢复表面：知道工具边界再决定

截至本章核验日 2026-07-24，PostgreSQL 官方 18 文档当前小版本显示为 18.4。官方备份章节将方法分为 SQL dump、文件系统级备份和连续归档；连续归档结合 WAL 可用于时间点恢复（PITR）。当前版本号会变化，操作前必须重新读取目标版本官方文档和实际集群配置。

### 8.1 SQL dump

`pg_dump`/`pg_restore` 适合逻辑导出导入、选择对象、跨某些版本迁移与验证。优点是对象级可见；代价是大型数据库恢复时间可能很长，而且它不是持续时间点恢复。事故中不能因为有一个 `.dump` 文件就宣称 RPO 达标：必须知道生成时间、是否成功结束、校验值、加密与权限、目标版本和最近一次真实恢复结果。

### 8.2 文件系统级备份

物理文件备份与数据库运行状态、文件一致性和版本强相关。直接复制一个正在变化的数据目录通常不足以构成一致备份。使用何种工具、是否需要停机或协调备份模式，应遵循目标 PostgreSQL 版本官方文档和组织 runbook。恢复时应先到隔离目标，保留原源数据，不要未经授权覆盖唯一副本。

### 8.3 连续归档与 PITR

PITR 依赖基础备份、连续且可读取的 WAL 归档、正确恢复配置和目标时间/LSN 判断。任何 WAL 缺口都可能使期望恢复点不可达。演练需要验证：基础备份身份、归档连续性、恢复目标、时间线选择、恢复日志、提升后的数据校验、应用兼容与重新建立备份链。只检查归档目录“有文件”远远不够。

### 8.4 高可用、复制与故障转移

故障转移是把服务角色交给可接受的副本；它需要判断副本滞后、事务丢失风险、脑裂、客户端路由、只读/可写状态和回切路径。自动故障转移也必须有清晰防护。若错误发布执行了逻辑删除，副本可能已经复制错误，此时快速切副本并不能恢复正确数据。

决定前要明确故障类型：主机不可达、数据库进程失败、存储损坏、网络分区、凭据/配置错误、模式不兼容、逻辑破坏还是容量耗尽。每种故障的最安全动作不同。

## 9. 错误发布与数据库故障叠加时如何选择

当发布和数据库告警同时出现，团队容易立即把两者做因果绑定。正确做法是建立可检验假设：

1. 发布制品、配置或迁移是否改变数据库连接、SQL 或模式？
2. 错误时间是否从发布后开始，还是发布前已有资源异常？
3. 上一个制品与当前数据库模式是否兼容？
4. 回滚代码会不会遇到已经不可逆的迁移？
5. 数据库恢复会不会覆盖事故后仍有效的写入？

**缓解**的目标是尽快降低影响，例如暂停写流量、停止继续发布、把客户端置为明确只读、限流或隔离故障租户。**恢复**是回到满足验收的状态。缓解不必解决根因，但不能制造更大数据风险。

部署决策至少比较三种路径：回滚到已验证制品、向前修复、恢复/故障转移数据库。比较维度包括预计时间、制品与模式兼容、数据损失上限、证据保留、可回退性、审批要求和已演练程度。没有演练过的“快命令”应视为高风险，不应因事故压力获得默认授权。

一个安全的恢复决定记录应包含：当前事实；被拒方案及原因；所选动作；预期影响；RTO/RPO 推断；检查点；操作人和审批人；停止条件；验证步骤；回退方案。这样复盘时能够评价当时信息下的决策，而不是用事后结果倒推个人对错。

## 10. 容器、Compose、Nginx、Ubuntu 与遥测证据

本章版本表面还包括 Docker、Docker Compose、Nginx、Ubuntu Server 26.04 与 OpenTelemetry。它们在事故中提供的是运行环境和证据来源，不改变业务真相的所有权。

截至 2026-07-24 的一手版本快照：Docker Engine 29 系列官方发布说明列出 29.6.2；Docker Compose 官方 GitHub Releases 列出 v5.1.4；Nginx 官方新闻列出 stable 1.30.4、mainline 1.31.3；Ubuntu 26.04 LTS 官方发布说明标注 2026-04-23 发布，标准安全维护到 2031 年 4 月；OpenTelemetry Specification 页面显示规范 1.59.0、Semantic Conventions 1.43.0、OTLP 1.11.0。它们只是核验日快照，不应写死为所有环境事实。

事故证据应首先记录实际环境：

- Docker：`docker version`、容器 ID、镜像 digest、启动参数、挂载、网络、健康状态、退出码和有限时间窗口日志；
- Compose：解析后的配置、profile、环境变量来源（敏感值脱敏）、服务/卷/网络身份与事件；
- Nginx：实际加载配置、证书身份、访问/错误日志、上游状态和 reload 时间；
- Ubuntu：内核与系统版本、systemd 单元状态、journal、磁盘/内存/文件描述符、时间同步；
- OpenTelemetry：资源属性、服务版本、trace/span ID、采样配置、导出失败和时间范围。

不要在事故报告里只写“Docker 29”“Ubuntu 26.04”；版本号不能证明运行了什么制品。镜像 tag 可变，digest 才能更可靠标识内容。日志与 trace 也不是绝对真相：采样可能遗漏，时钟可能漂移，collector 可能丢数据。应交叉验证发布清单、应用日志、数据库日志、指标和用户请求。

## 11. FactoryCare 的业务权威边界

FactoryCare 的核心工单状态、租户授权、审计与交易事实由 Java Spring Boot API 和 PostgreSQL 负责。Vue、uni-app、Flutter 等客户端只能调用 Java 公共 API；Python/AI 服务只计算建议、摘要、向量和其他可重建派生结果。这个边界在事故中尤其重要。

若 Python AI 服务不可用，正确降级通常是关闭建议、返回明确的派生能力不可用状态，让核心工单流程继续，而不是允许客户端绕过 Java 直接写数据库。若向量索引损坏，应从 Java 已授权的数据重新构建，不应把索引当唯一业务事实。Python 请求 Java 数据时，Java 每次仍需依据当前身份、租户和权限判定；不能因为“内部服务”而长期缓存越权数据。

恢复顺序也受边界约束：先恢复身份、Java 业务 API、PostgreSQL 业务事实与审计；再恢复可重建缓存、搜索、向量和 AI 建议。若派生服务先恢复但业务权威仍不可靠，页面“有建议”没有意义，甚至会让用户误以为操作成功。

越界反例：事故中发现 AI 索引有较新字段，于是直接用它覆盖 PostgreSQL 工单状态。错在把可能陈旧、缺失授权语义的派生数据升级为系统记录。正确做法是保全两个数据源、由业务规则和审计证据判断恢复点，必要时通过批准的补偿流程写回 Java API。

## 12. 无责复盘：不等于没有责任

无责（blameless）复盘不是“谁都不负责”，而是避免把解释停在个人疏忽。人在当时的界面、权限、流程、激励和信息下为何认为动作合理？哪些系统条件让一个错误能扩大？哪些防线缺失或同时失效？这样才能产生可复用改进。

一份复盘建议包含：

1. 摘要、严重度、用户影响、开始/检测/缓解/恢复时间；
2. 数据影响和仍未知内容；
3. 可由证据复核的时间线；
4. 检测有效与失效之处；
5. 响应、沟通、恢复有效与失效之处；
6. 技术与组织促成条件；
7. 哪些偶然因素避免了更坏结果；
8. 攎进行动、负责人、期限、优先级、验收和回归；
9. 残余风险与需要接受风险的责任人。

“小王执行了错误 SQL，所以事故发生”不是足够分析。应继续问：为何生产权限允许无检查执行？为何工具未显示租户和影响行数？为何没有事务/预览/双人审批？为何备份恢复未演练？为何告警晚十分钟？个人动作仍可如实记录，但改进目标是让系统在普通人会犯错的现实中更安全。

## 13. 攼进行动必须成为闭环

“加强监控”“提高意识”“后续优化”都无法验收。合格行动采用如下合同：

```text
ID: CA-2
问题: 不兼容迁移能与旧制品同时进入生产
负责人: release-team
期限: 2026-08-03
变更: 发布门禁增加 expand/contract 兼容检查和旧制品 smoke
验收: 故意提交破坏性迁移时，promotion job 在生产前失败并指向规则 ID
验证命令/证据: ./verify-migration-compatibility.sh + CI run URL
回归频率: 每次迁移；季度抽查
残余风险: 数据量相关锁等待仍需预演
```

行动关闭条件不是 PR 合并，而是验收通过并产生证据。高风险行动应进入 CI、发布门禁、备份演练计划、告警合同或访问控制，而不是永远留在文档待办。若行动逾期，需要重新评估风险与优先级，不应静默关闭。

三类常见行动：**预防**减少事件发生，如迁移兼容门禁；**检测**缩短发现时间，如业务 SLI 与告警上下文；**缓解/恢复**缩短影响或控制数据损失，如季度隔离恢复演练。只做更多告警可能增加噪声，不能替代恢复能力。

## 14. 实验：数据库不可用叠加错误发布

本章实验目录是 `labs/encyclopedia/ch.ops.incident-dr/`。默认夹具是静态、合成的桌面推演，它故意声明：`live_drill_verified=false`、`real_rto_rpo_verified=false`、`commands_executed=false`。先运行它理解门禁：

```bash
cd labs/encyclopedia/ch.ops.incident-dr
./verify.sh
```

绿色只表示 JSON 事故包拥有合成场景要求的结构。真正现场实验应另建隔离环境，并完成以下阶段。

### 阶段 A：演练前安全设计

确定非生产环境、数据分类、允许破坏范围、停止条件和审批者；声明 RTO/RPO 起止点；确认备份不会访问或覆盖生产；固定 Java API、数据库、Nginx 与 Compose 配置身份；准备用户影响探针、核心业务 smoke、数据校验与回退方案；设置观察者，任何人可喊停。

### 阶段 B：建立基线

验证工单创建、分派、状态迁移、租户隔离、审计和幂等；记录 API 延迟/错误、数据库连接、资源指标与 trace；保存制品 digest 和数据库数据集校验。没有基线，恢复后“看起来一样”无法比较。

### 阶段 C：注入组合故障

由演练控制者注入数据库不可用和错误制品，但不提前告诉响应者具体原因。事故团队从用户信号定级、分配四个角色、暂停风险发布、建立时间线。调查者必须先保全证据，不能删卷、覆盖源库或绕过审批。

### 阶段 D：作出恢复决定

比较回滚、向前修复、数据库故障转移/恢复。明确制品与模式兼容性、数据风险和检查点。若选择恢复，先恢复到隔离目标；通过数据与业务验证后再切合成流量。记录每个命令的目的、操作者、开始/结束、退出码、关键输出和证据路径。

### 阶段 E：业务验证和关闭

验证的不只是 `/health`：还要验证身份、租户范围、核心状态机、数据库提交、审计、幂等、副作用和派生服务降级。确认 RTO/RPO 的实际算法和结果；继续观察一段声明时间；发送恢复更新；记录尚未解决的风险后再关闭事故响应。

### 阶段 F：复盘和三项行动

在记忆仍新鲜但不妨碍恢复时整理证据时间线。至少输出一项预防、一项检测、一项恢复行动；每项满足负责人、期限、验收、验证命令和回归。随后故意重新注入原故障，证明门禁能阻止或更快恢复。

## 15. 四类故障注入与首个可信证据

### 15.1 边调查边销毁证据

症状是运行 `compose down -v`、删除 Pod/容器、清空日志或重建主机后才开始分析。失败阶段在**证据保全**。首个可信证据通常是操作审计或 shell/平台事件，显示破坏动作发生在快照、日志导出之前。修复是停止进一步变化，记录已丢证据范围，从外部日志/遥测/发布平台补证，并把“危险动作前检查点”写入 runbook 和权限门禁。残余风险是已销毁现场无法完全重建。

### 15.2 未经授权直接恢复并覆盖数据

失败阶段在**恢复决策与执行控制**。先看审批记录、恢复目标、备份身份和命令参数，而不是最后健康检查。若没有审批与独立目标，即使服务恢复也属于过程失败。修复是暂停覆盖，保全源与目标，评估差异，在隔离目标重做，经业务与数据负责人审批后切换。残余风险包括事故期间有效写入的合并与审计缺口。

### 15.3 只写“加强监控”

失败阶段在**改进闭环定义**。首个可信证据就是复盘行动表：没有负责人、期限、明确 SLI/告警条件、验证和回归。修复是把口号改成可失败的门禁，例如“向测试环境注入数据库连接拒绝，五分钟内告警必须包含租户影响、runbook 和 dashboard；CI/季度演练保存结果”。残余风险是告警能发现却不保证恢复。

### 15.4 复盘追责个人

失败阶段在**系统性分析**。首个可信证据是根因段落只写个人行为而没有权限、界面、流程、审核、测试、组织和防线条件。修复不是删掉行为事实，而是重构因果：行为为何可能、为何未被阻止、为何影响扩大、哪些控制可验证。残余风险包括文化压力导致信息隐瞒，需要管理层持续支持。

```text
1. 适用范围与严重度触发
2. 值班、升级和权限入口
3. IC/Ops/Comms/Scribe 角色卡
4. 用户影响与数据风险确认
5. 只读证据采集命令和保存位置
6. 危险动作清单、检查点与审批
7. 已演练的缓解/回滚/恢复步骤
8. 每一步预期、超时、停止和回退条件
9. 核心业务与数据验证矩阵
10. 状态更新模板和节奏
11. RTO/RPO 计时规则
12. 交接与关闭条件
13. 复盘模板与行动门禁
14. 最近演练时间、环境、结果和已知限制
```

runbook 必须可执行但不能盲执行。环境差异、版本变化、证书、权限和数据规模都可能使旧命令失效。每次演练更新“最后验证于何时、在哪个版本和什么环境”，避免文档长期漂移。

## 17. 验证矩阵：什么结果允许声称什么

| 证据 | 可以声称 | 不能声称 |
| --- | --- | --- |
| Python 静态门禁绿色 | 事故包字段完整，已编码部分规则成立 | PostgreSQL 可恢复、真实 RTO/RPO 达标 |
| 桌面推演完成 | 角色和决策流程得到练习 | 命令、权限、容量和真实切流有效 |
| 隔离环境恢复成功一次 | 该制品/数据/环境下 runbook 成功 | 所有故障、所有数据量、生产必然成功 |
| 定期恢复演练与趋势 | 能估计恢复分布和文档漂移 | 可忽略生产差异或停止备份监控 |
| 真实事故时间线与复盘 | 对该事故有可复核学习 | 已经自动消除未来同类风险 |

这种证据语言很重要。工程师在简历、评审或事故会上说“做过灾备”，应能回答：什么数据、什么恢复方式、哪个环境、最后一次演练何时、RTO/RPO 如何计算、失败过什么、证据在哪里。否则它只是配置存在。

## 18. 常见误区与纠正

**误区：看到错误就重启。** 重启可能暂时缓解，也会改变现场。先判断证据和状态是否会丢失，明确重启的假设与停止条件。

**误区：监控全绿就是无事故。** 指标覆盖可能不足，业务错误可能返回 200，租户隔离问题也未必影响延迟。结合业务 SLI、日志、trace、数据库和用户反馈。

**误区：备份任务成功等于可恢复。** 任务成功只证明命令某一步成功。恢复验证、校验、依赖、权限、版本和耗时才接近业务能力。

**误区：最快动作永远最好。** 未经验证的快速覆盖可能永久扩大数据损失。比较恢复时间与不可逆风险。

**误区：无责复盘不记录错误动作。** 无责不隐藏事实；它要求用公平的当时视角分析，并改造系统条件。

**误区：事故结束就恢复发布。** 先确认错误预算、残余风险、监控、数据一致性和必要的临时门禁；高风险修复可能要求延长冻结。

**误区：AI 可以在事故中自动执行所有修复。** AI 可总结时间线、检索 runbook、生成候选命令，但输出可能错误或越权。危险动作必须由真实身份、当前权限、审批和确定性验证控制；业务写入仍走 Java 权威边界。
