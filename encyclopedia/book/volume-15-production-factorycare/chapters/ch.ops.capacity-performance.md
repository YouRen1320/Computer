# 容量、负载模型、性能测试与瓶颈证据

“我的电脑能跑一千 QPS”不是容量结论。它没有说明请求组合、数据规模、并发到达方式、错误率、尾延迟、持续时间、生成器是否饱和、服务端资源、数据库计划、网络和目标平台。容量工程要从业务需求建立可审查的工作负载模型，在受控环境得到吞吐—延迟—错误—资源曲线，再用指标、trace、日志和查询计划解释瓶颈；最终保留同输入修复前后与功能回归证据。

本章不追求排行榜，不把单次微基准外推成生产规模，也不教你对线上用户数据做压测。它负责 FactoryCare 的到达率、并发需求、增长/突发、容量余量、受控负载、p50/p95/p99、瓶颈诊断和性能回归。Java 服务继续负责业务事实与状态机；压测客户端只能发合法请求和观察结果，不能为提高数字绕过鉴权、幂等或事务规则。

这里的稳定核心不依赖某一个负载工具：可复现输入、生成器有余量、热身与稳态分离、看分布不只看平均值、相关而非猜测、一次只验证一个假设、优化后重跑同一 oracle。PostgreSQL 18、OpenTelemetry、Docker 和 Ubuntu 26.04 是版本表面，工具参数和默认值必须按实际版本核对。

## 1. 容量问题要先改写成业务问题

“系统能承受多少用户”太含糊。在线用户可能停留阅读，不产生请求；一个批处理账号可能每秒写入数百条。更可测的描述是：工作日 09:00—10:00，每秒平均创建 12 个工单、查询列表 45 次、读取详情 30 次、状态变更 8 次；月末突发倍率 1.8；未来十二个月增长 1.5；在允许错误率 0.1% 下，写请求 p95 不超过 300ms、读请求 p95 不超过 200ms，资源保留 30% 故障余量。

每个数字都要标来源：生产观测、产品预测、合同、历史峰值、还是暂定假设。没有数据时可以用假设启动，但报告必须写“未验证假设”，并计划用真实去敏指标校正。把假设写成事实，会让精确计算产生虚假的可信度。

业务操作不是单个 URL。创建工单可能包含鉴权、校验、幂等记录、主表写入、状态历史、事件/outbox 和响应；列表查询受过滤、分页、权限范围和数据倾斜影响。模型应按业务旅程命名，记录 API 组合、请求体分布、成功判据、思考时间、重试与幂等语义，而不是只打最轻的 `/health`。

## 2. 到达率、服务时间与并发

到达率 λ 表示单位时间来到系统的工作量，例如每秒 40 个请求。服务时间 W 是一个工作在系统中停留的平均时间。在稳定系统、观察边界一致的条件下，Little 定律给出平均在途数量 L = λ × W。若 40 req/s、平均 125ms，则平均在途约 5；这不是说配置 5 个虚拟用户一定能稳定产生同样流量，因为用户模型、思考时间、连接和调度会改变闭环到达。

开放模型按预定速率产生到达，更接近外部流量不会因服务变慢而自动停下；闭环模型由固定并发用户发出下一个请求，服务变慢时到达率自然下降。闭环测试可能在系统饱和时看见吞吐下降，却误以为“请求不多所以没问题”。选择模型要对应真实来源，并在报告中说明。

并发还有多种边界：HTTP 在途、线程/虚拟线程、数据库连接、事务、锁等待、消息消费和外部依赖请求。不能把 200 个虚拟用户直接等同于 200 个数据库连接。trace 与池指标能展示一次业务请求在哪些阶段占用哪些资源。

## 3. 峰值、突发、增长和余量

平均日请求量不能代表峰值。先按时间窗口聚合历史到达率，找工作日峰值、班次交接、月末、批量导入和事故重试。窗口太大会平滑尖峰，例如一分钟均值会隐藏一秒内的连接风暴；窗口太小又可能被噪声主导。根据队列和超时尺度选择窗口，并保存原始聚合方法。

增长因子用于未来规划，突发因子用于短时尖峰。若当前稳态 40 req/s、增长 1.5、突发 1.25，则候选峰值 75 req/s；但两个因子是否可以直接相乘取决于业务。容量模型应保存公式和依据，不只保存结果。

容量余量不是“CPU 还有一点”。节点故障、滚动发布、备份、索引维护、GC、数据库 failover 和外部延迟都可能消耗余量。N+1 场景要在少一个实例时仍满足关键 SLO；若正常必须用 95% CPU 才过关，发布或故障时没有安全空间。余量目标可按资源和吞吐分别表达，并以演练验证。

## 4. 定义场景与测试层级

smoke 性能测试用很小负载确认脚本、数据和指标链正确；平均负载测试验证日常运行；stress 逐步超过预期峰值寻找拐点；spike 验证突然到达与恢复；soak 长时间暴露泄漏、缓存增长和连接耗尽。不同场景回答不同问题，不能用十秒 spike 证明八小时稳定性。

微基准适合比较一个纯函数、序列化或查询片段，但缺少网络、连接池和真实业务。组件测试可对数据库查询或 API 做隔离测量；端到端测试包含代理、应用、数据库和可观测链。结论的适用范围必须与层级一致：JMH 或 Python 循环更快，不代表 FactoryCare p95 改善。

每个场景至少包含：工作负载版本、数据集身份、制品 digest、环境/平台、热身、升压、稳态、降压、到达模型、请求组合、阈值、停止条件和功能 oracle。脚本本身也版本化，修改请求组合后产生新 workload ID。

## 5. 数据集是性能输入的一部分

空表查询快，不代表百万工单快；均匀数据不代表热点设备、少数大客户和状态倾斜。数据集要模拟规模、分布、关联、文本长度、历史深度和索引选择性。保存生成种子、schema 版本、行数、分布摘要与数据集 digest，使前后测试使用同一输入。

禁止在无隔离的生产库上为学习或调参发压测流量。写测试可能创建工单、触发通知和锁；读测试也会消耗连接、I/O 和缓存，影响真实用户。使用合成或经批准去敏的隔离数据，阻断邮件、Webhook 和推送。恢复演练得到的生产副本并不自动获得性能测试授权。

缓存状态也要控制。冷缓存回答重启/首次访问，暖缓存回答稳态；两者都可测，但不能把修复前冷缓存与修复后暖缓存比较。数据库统计信息、autovacuum、JIT、连接池和应用缓存状态写入运行记录。

## 6. 固定环境和制品身份

可比运行要固定应用 commit/digest、镜像平台、JDK、PostgreSQL、配置、资源限制、节点类型、网络拓扑、数据集、负载脚本和可观测采样。CPU 型号、虚拟化邻居和电源模式也会影响本机测试。无法固定的因素要记录并通过多次运行估计波动。

在 Apple Silicon 笔记本测 arm64 容器，不能直接外推 Linux amd64 服务器。Docker Desktop 的虚拟机、文件共享和资源配额与原生 Ubuntu 不同。本地结果适合验证脚本和找明显回归；生产容量需要目标相似平台，或明确校准模型。

每次运行生成 run ID，关联 release digest、workload ID、dataset ID、开始时间、操作者和环境。指标、trace、日志、查询计划和测试摘要都带 run ID，避免从不同运行拼图得出不存在的因果链。

## 7. 热身、升压和稳态

应用刚启动时有类加载、JIT、连接建立、缓存填充和数据库页读取。若无热身就取最开始几秒，可能夸大稳定延迟；若把长热身隐藏不报，又会漏掉发布后的冷启动风险。正确做法是分别测冷启动，并为稳态场景声明热身区间且从稳态统计中排除。

升压应让系统有时间到达新的平衡，观察队列、连接池和资源。一步跳到极高负载会发现 spike 能力，但无法定位饱和拐点。分级到达率如 20、40、60、80 req/s，每级维持足够长，绘制吞吐、p95/p99、错误和资源曲线，通常比只报一个最高点更有解释力。

稳态时长要覆盖 GC、检查点、autovacuum、缓存淘汰和依赖周期。一次三十秒绿色不能证明小时级稳定。soak 中监控内存基线、线程/任务、连接、临时文件、WAL、磁盘和队列随时间斜率，而不只看结束值。

## 8. 负载生成器也会成为瓶颈

客户端 CPU、内存、网络、文件描述符、连接数、DNS、TLS 和结果解析都可能先饱和。此时服务端还有余量，但生成器无法继续提升到达率；测到的“系统上限”其实是客户端上限。每次运行同时记录生成器 CPU、事件循环延迟、丢弃迭代、实际到达率和网络。

生成器应保留明确余量，例如稳态最大 CPU 低于团队验证的阈值；具体 70% 只是本仓库夹具的政策示例，不是通用常数。高负载可分布到多节点，并用时间同步和聚合验证。分布式生成器也要证明协调器没有成为瓶颈。

脚本中的日志和断言也有成本。每请求打印正文会压垮客户端磁盘；完全不校验响应又会把错误页面当成功。采用轻量语义检查、聚合错误样本和受控采样，保留足以诊断的失败证据。

## 9. 吞吐、错误和延迟分布

吞吐是单位时间成功完成的工作量，必须和到达率、错误、超时、取消一起看。系统收到 100 req/s、成功 60、超时 40 时，报“吞吐 100”会误导；只报成功 60 又会隐藏积压。记录 offered、started、completed、successful、failed 与 dropped 的定义。

平均延迟容易隐藏尾部。十九个 20ms 和一个 900ms 的平均约 64ms，看起来不错，但最慢用户经历完全不同。p50 表示中位体验，p95/p99 展示尾部；计算方法、采样窗口和样本量要固定。最近秩算法只是一个明确例子，监控系统可能使用直方图近似，跨实例聚合也有误差。

百分位不是最大值，也不是“95% 请求都恰好等于该值”。样本很少时 p99 几乎等于最大值，波动很大。报告样本数、置信区间或多次运行分布，避免比较 201ms 与 199ms 就宣称显著改善。

超时请求必须进入延迟/错误解释。只统计成功响应会在饱和时把最慢请求排除，使 p95 反而变好。排队等待、客户端超时和服务端取消边界要一致。若工具存在 coordinated omission 风险，说明到达模型和测量方法，并用开放模型或校正策略验证。

## 10. 指标、trace、日志与计划形成证据链

延迟曲线告诉“何时变坏”，资源指标帮助回答“什么同时饱和”，trace 展示请求时间花在哪一段，日志提供离散错误，查询计划解释数据库如何执行。单一信号很少足以证明根因。CPU 90% 与 p95 同时上升只是相关；还需 profile、trace span 或实验改变来证明哪个路径消耗 CPU。

OpenTelemetry 把 traces、metrics、logs 和 baggage 作为信号。trace ID 应从入口传播到 Java、数据库相关 span 和下游，性能测试记录抽样策略。低采样率可能漏掉尾部；全采样又增加开销。保存采样配置，并比较启用/禁用观测的开销，不能在修复前后改变采样而不说明。

关键指标包括入口到达/完成/错误/延迟，实例 CPU/内存/GC，线程或任务队列，连接池 active/wait，数据库会话、锁等待、缓存命中、I/O、WAL/checkpoint、查询耗时和下游连接。高基数标签如完整工单 ID 会破坏指标系统；用路由模板、操作类型和状态聚合，具体 ID 留给采样 trace/日志。

## 11. PostgreSQL 查询计划证据

`EXPLAIN` 展示规划器选择和成本估计，`EXPLAIN ANALYZE` 实际执行并报告真实行数与时间。估计行数与实际行数差距大，可能指向统计信息、数据倾斜或表达式；计划节点、循环次数、排序、临时文件和 buffer 证据帮助定位。但计划只是某次参数、数据和配置下的结果，不能截一行“Index Scan”就宣布优化成功。

PostgreSQL 官方文档提醒 `EXPLAIN ANALYZE` 会真正执行语句。对 `INSERT`、`UPDATE`、`DELETE`、`MERGE` 或 `CREATE TABLE AS` 等有副作用语句，可在受控事务中 `BEGIN`、运行分析、再 `ROLLBACK`，但仍需理解序列、外部函数、锁和非事务副作用。绝不能直接在生产写查询上复制教材命令。

分析前记录完整 SQL 形状、参数类别、schema/index、统计更新时间、数据集和服务器设置。优化后比较同一业务查询、同一数据集、相同缓存条件的计划与端到端 p95；查询快了但写入、锁或功能变坏，不能通过。

## 12. 用饱和曲线定位拐点

逐级增加 offered load，并画出成功吞吐、p95/p99、错误、队列和资源。低负载时吞吐随到达率线性增长、延迟稳定；接近容量时某个资源/队列增长，尾延迟上升；饱和后吞吐持平甚至下降、错误增加。容量点不是 CPU 100% 的瞬间，而是在目标 SLO、错误和余量约束下可持续的最高工作量。

若生成器先饱和，整次高负载区间无资格用于服务容量结论。若数据库 wait 增长、trace 多数时间在同一查询且计划实际行数异常，可提出数据库路径假设；随后改变索引或查询并做同输入 A/B。若应用 CPU 高但数据库等待低，使用 profile 或 span 细化，不要凭感觉加索引。

资源没满也可能过载：串行锁、连接池上限、外部限流、单线程队列和磁盘延迟都能限制吞吐。反过来 CPU 高不一定有问题，只要仍满足 SLO 且有故障余量。瓶颈是限制当前目标吞吐/延迟的约束，不是“看起来最大的数字”。

## 13. 一次只验证一个修复假设

性能调优流程是：建立可重复红线；定位首个可信证据；写出假设；做最小相关改变；在同环境/负载/数据集重跑；比较原始分布、错误、资源和功能；必要时回滚。一次同时改 JVM、索引、缓存和实例规格，即使变快也不知道原因，后续无法迁移结论。

常见假设如“列表过滤缺少选择性索引导致扫描与数据库等待”“序列化重复构造对象导致应用 CPU”“连接池过小导致排队”“无界并发导致下游超时”。每个假设都需要可证伪预测，例如加索引后同查询计划扫描行数下降、db span p95 降低，而写入功能仍绿。

优化不能删除业务工作。跳过权限过滤、状态历史、幂等或响应字段会让数字变好，却改变合同。Java 契约测试、数据库约束和端到端 smoke 与性能回归一起运行。Python 分析工具可生成报告，但无权改变 FactoryCare 最终事实。

## 14. 性能回归门禁

回归基线不是永远固定一个毫秒数。环境噪声、依赖和数据增长会改变分布；应保存一组近期可比运行，定义允许退化与统计规则。小项目可先用多次运行的中位 p95 和明确容差，随后引入置信区间。不要只比较各一次运行。

门禁要区分硬失败与观察告警。错误率/SLO/功能失败可硬阻断；轻微波动可记录趋势。若 CI 共享 runner 噪声大，CI 做小型回归探针，定期在受控性能环境做完整场景。共享 runner 的绿色不能替代容量认证。

版本升级、schema 迁移和基础镜像改变都需要重建基线，但旧结果保留以解释变化。报告要写“在指定环境、数据与制品下”，不说“系统最多支持 X”。容量随业务组合和依赖变化。

## 15. 五类故障的首个可信证据

无热身直接取峰值：失败阶段是测试设计。首个证据是 run metadata 没有热身/稳态边界，或冷启动样本混入摘要。修复为单独保留冷启动场景，并在稳态测试排除声明热身；重跑同工作负载。

客户端先饱和：失败阶段是生成。首个证据是 generator CPU、事件循环或 dropped iterations 达阈值，同时实际到达率低于目标。修复为降低客户端开销或扩展生成器，再重跑；旧结果不能作为服务上限。

只看平均延迟：失败阶段是结果判断。首个证据是摘要缺少样本数、p95/p99、超时和错误。修复为保存直方图/原始样本与尾部，重算后可能发现原绿色结论无效。

使用生产数据无隔离：失败阶段是环境授权，应在发流量前停止。首个证据是连接目标、环境 ID 或数据治理记录指向 production。修复为合成/去敏隔离数据，阻断副作用；不能以“只读”作为默认豁免。

优化后未做回归：失败阶段是验证。首个证据是只有修复后局部 benchmark，没有同 workload/dataset 的前后和功能套件。修复为恢复基线输入、重跑原 oracle；若原环境已丢失，只能把改善标为未验证。

## 16. FactoryCare 受控实验流程

先从合成观测提出三场景：工作日峰值、短突发、增长后峰值。为创建、列表、详情、状态变更分配比例，使用合法 token、唯一幂等键和合成设备/人员。定义 p95/p99、错误、目标速率、生成器余量和功能断言。

固定 Java/Vue/代理/PostgreSQL 制品、目标平台、资源、配置和数据集身份。先 smoke，确认响应与指标/trace 关联；热身后逐级运行，保存 offered/achieved、延迟分布、错误、服务资源、连接池、数据库 waits 与代表性计划。测试中出现数据损坏、生产目标或生成器饱和立即停止。

从曲线选一个真实拐点，写最小假设并只改一个因素。使用同一数据集快照和 workload 重跑至少多次，验证 p95/p99、错误与资源改善，同时运行 Java 契约和数据库不变量。最后恢复配置，确认回滚路径和残余风险。

本仓库 `examples/encyclopedia/ch.ops.capacity-performance/` 只用固定数组演示 Little 定律、最近秩百分位、生成器门禁、数据库等待分类和前后比较；`labs/...` 把证据资格写成故障注入测试。它没有 HTTP、PostgreSQL、k6 或 Collector，因此不能作为实际容量数字。

## 17. 版本事实与官方来源

本章于 2026-07-24 核对 PostgreSQL 18 [`Using EXPLAIN`](https://www.postgresql.org/docs/18/using-explain.html) 与 [`EXPLAIN`](https://www.postgresql.org/docs/18/sql-explain.html)，其中实际执行与写语句副作用是关键边界。也核对 OpenTelemetry [Signals](https://opentelemetry.io/docs/concepts/signals/) 对 traces、metrics、logs、baggage 的当前分类。

Grafana k6 当前官方文档的 [performance testing guide](https://grafana.com/docs/k6/latest/testing-guides/automated-performance-testing/) 用 smoke、average、stress、spike、soak 组织场景，并提醒仅看阈值通过可能产生错误安全感。k6 不是本章规范版本表面，本仓库也未安装或运行它；链接只用于工具无关方法的当前参考。

PostgreSQL 当前 18 文档展示 18.4，但真实实验以服务端和客户端完整版本为证据。Docker/Ubuntu/OpenTelemetry SDK/Collector 也要记录实际版本、镜像 digest 和配置；仅存在 CLI 不证明服务已运行。

## 18. 学习、练习与过关

公开练习故意把 percentile 写成平均值，所以应稳定红。修复时实现边界检查和明确的最近秩算法，并解释它与监控系统直方图近似可能不同。示例与私有答案绿色只证明算法/门禁夹具，不证明真实性能。

独立构建必须在受控隔离环境生成真实流量，至少保存工作日峰值、突发和增长场景；p50/p95/p99、错误、offered/achieved；生成器和服务端资源；trace/日志/查询计划；一个瓶颈假设；同输入修复前后；功能回归。报告逐项区分 verified 与 unverified。

120 秒讲解要回答：业务流量如何变成到达率和请求组合；并发为何不等于用户数；为何需要余量、热身和生成器监控；平均值为何隐藏尾部；指标、trace 和计划如何组合；为什么最高 QPS 不是容量。越界反例是为了提高数字关闭权限与幂等逻辑。

## 19. 复盘清单

- 工作负载是否来自已标注来源的业务峰值、突发与增长假设？
- 到达模型、思考时间、并发边界和请求组合是否明确？
- 数据集规模、分布、种子、schema 与身份是否可复现且隔离？
- 制品、平台、资源、配置、缓存和可观测采样是否固定？
- 冷启动、热身、升压、稳态和降压是否分开？
- 生成器是否有证据证明未先饱和？
- 是否同时报告 offered/achieved、成功、错误、超时、p50/p95/p99 与样本数？
- 是否用 run ID 关联服务资源、数据库等待、trace、日志和计划？
- 修复是否只验证一个假设，并在同输入下多次重跑？
- Java 业务合同、数据不变量和失败路径是否仍然绿色？
- 结论是否限定在该环境/制品/数据，而没有外推成市场宣传数字？

容量工程的产物不是一个漂亮 QPS，而是一条可复现的推理链：业务假设产生负载，负载产生曲线，曲线与观测暴露约束，受控改变验证假设，功能回归守住正确性。缺少任何一环，都只能称为线索，不能称为容量结论。

## 20. 重复运行与不确定性

同一配置的性能运行也不会得到完全相同数字。调度、GC、缓存、邻居负载、网络和后台数据库任务都会产生波动。至少重复运行，并先约定如何汇总，避免看到有利的一次才停止。可以报告多次 p95 的中位值、范围和每次 run ID；更成熟时用置信区间或非参数方法。方法必须在看结果前确定。

丢弃异常运行需要客观理由，例如生成器饱和、环境发生已记录维护、指标链中断或制品身份不一致；“这个结果太慢”不是理由。异常运行仍保留，标记 invalid 及首个可信证据。若删掉慢运行而不披露，会系统性高估容量。

百分位比较还要考虑样本数和直方图桶。一个窗口只有几十个请求，p99 的稳定性很差；聚合多个实例的预计算 p95 也通常不能再直接求平均得到全局 p95。优先汇总可合并直方图或一致边界的原始分布，并记录遥测系统的聚合算法。不能获得原始分布时，把精度限制写入结论。

## 21. 安全停止、成本与伦理边界

压测前设置硬停止：生产环境身份、数据不变量失败、错误预算耗尽、生成器失控、磁盘/WAL 接近上限、复制严重落后、关键依赖告警或观测失联。停止动作应逐步降载而非突然杀死所有连接，以免把客户端中断误判为服务故障；严重数据风险则立即阻断写入。

云负载生成、日志、trace 和数据库 I/O 都有成本。先用 smoke 验证脚本，再逐级扩展；给项目和资源加预算/标签，测试后销毁临时资源。成本优化不能通过关闭语义断言或安全控制来换取。第三方 API 有配额与合同，未经许可不能用性能测试轰击。

测试数据不得包含未经授权的个人信息，报告也不保存 token、完整响应或用户标识。合成数据要避免看似真实的电话和地址；去敏流程需证明不可逆性与访问范围。性能工程的目标是保护用户体验，不是把线上用户当实验对象却不设影响预算。

## 22. 从容量结果到工程决策

如果受控结果表明目标峰值 75 req/s 下满足 SLO 且一个节点故障后仍有 30% 余量，可以形成该环境和 workload 的部署建议；不能直接换算“支持十万用户”。若结果不达标，决策不只有扩机器：可优化查询/索引、限制昂贵请求、增加缓存、拆分异步工作、改变批处理时窗或重新协商 SLO。每个选择都要评估正确性、复杂度和失败模式。

容量计划应连接发布和告警：正常副本数、扩缩容阈值、最大实例、数据库连接预算、队列上限、限流与降级。扩容不是瞬时，启动、镜像拉取、JIT 和缓存预热有延迟；突发需要预留或排队。限流响应也属于 API 合同，要让客户端可重试且幂等。

最终结论写成条件句：“在 release digest X、数据集 Y、Ubuntu/容器配置 Z、工作负载 W 和观测配置 O 下，多次运行在 offered rate 75 req/s 时达到某分布；生成器余量和功能 oracle 绿色；尚未覆盖跨区域故障与八小时 soak。”这种表述不漂亮，但可复现、可审查，也能告诉下一次变化后该重测什么。
