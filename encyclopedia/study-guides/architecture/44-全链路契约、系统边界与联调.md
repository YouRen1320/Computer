# 全链路契约、系统边界与联调

## 1. 这一章解决的是“多个系统怎样不靠猜测合作”

FactoryCare 已经有 Java 后端、Web 和移动端、Python AI 服务，还可能通过 MCP 对外提供能力。每一部分单独能运行，并不等于它们组合后就可靠。

联调真正困难的地方通常不是语法，而是双方对同一件事理解不同：字段叫什么、空值代表什么、失败怎样表达、请求能否重试、旧客户端还能用多久。

把这些约定明确写下来，就是建立契约。

## 2. 契约不只是接口文档

接口文档常常只列 URL 和字段；完整契约还应说明：

- 输入允许什么、不允许什么；
- 成功与各种失败分别长什么样；
- 身份、权限和租户怎样传递；
- 分页、排序、时间、金额怎样解释；
- 超时、重试、幂等和兼容性怎样处理；
- 哪一方负责哪条业务规则。

只有字段表而没有这些语义，仍然会出现“格式相同、意思不同”的问题。

## 3. 先画清系统边界

一个适合 FactoryCare 的简化边界是：

```text
Vue / Flutter 客户端
        ↓ HTTP
Java 业务 API：身份、权限、工单规则、事务、审计
        ↓ 受控调用
Python AI 服务：分类、摘要、检索、建议
        ↓ 可选协议
MCP Server：把受控能力提供给 AI Host
```

Java 服务是核心业务事实的所有者。AI 服务可以建议优先级，但不能绕开 Java 直接改工单表。

## 4. 边界的判断标准是“谁拥有事实”

不要只按编程语言拆系统，要问：

- 谁拥有这份数据的最终解释权？
- 谁保证状态变化合法？
- 谁负责事务和审计？
- 出错时谁能决定补偿或重试？

例如“工单是否已经关闭”应由工单领域判断；Python 模型给出的文本不能成为最终事实。

## 5. 每条规则只保留一个权威实现

如果前端、Java、Python 都各写一套“优先级计算规则”，它们迟早会分叉。正确做法是：

- Java 保留权威业务规则；
- 前端可以做即时提示，但提交后以服务端结果为准；
- AI 返回建议和依据，不冒充业务决策；
- MCP 调用已有业务 API，不复制领域逻辑。

这是 Single Source of Truth（单一事实来源）的实际含义。

## 6. HTTP 请求是跨边界的一次消息交换

一次 HTTP 调用至少包含方法、地址、请求头和可选正文。响应包含状态码、响应头和可选正文。

```text
POST /work-orders
Authorization: Bearer ...
Content-Type: application/json

{ ... }

→ 201 Created
→ Location: /work-orders/WO-123
→ { ... }
```

调试时要看完整交换，不能只看 JSON 正文。

## 7. 方法表达调用意图

常用方法可先这样理解：

- `GET`：读取资源，不应产生业务修改；
- `POST`：创建资源或发起一个命令；
- `PUT`：用完整表示替换指定资源；
- `PATCH`：修改资源的一部分；
- `DELETE`：删除或撤销资源。

方法会影响缓存、中间代理、重试和调用者预期，不只是路由名字的装饰。

## 8. URL 应围绕资源，而不是页面按钮

优先使用稳定的业务名词：

```text
GET  /work-orders/WO-123
POST /work-orders
POST /work-orders/WO-123/assignments
```

对于明显的领域动作，命令式子资源也可以：

```text
POST /work-orders/WO-123/close
```

重点不是机械追求某种风格，而是让含义稳定、权限清楚、文档一致。

## 9. 状态码先表达结果类别

可以先记住几组：

- `2xx`：请求被成功处理；
- `400`：输入整体无法理解或校验失败；
- `401`：没有有效身份；
- `403`：有身份但没有权限；
- `404`：资源不可见或不存在；
- `409`：当前状态冲突；
- `429`：调用过于频繁；
- `5xx`：服务端或依赖出现故障。

状态码负责粗分类，错误正文再给稳定的业务细节。

## 10. 错误响应需要统一形状

如果每个接口随意返回字符串，客户端只能为每条文案写特殊判断。统一错误结构更可靠：

```json
{
  "type": "https://factorycare.example/problems/version-conflict",
  "title": "工单已经被其他操作更新",
  "status": 409,
  "code": "WORK_ORDER_VERSION_CONFLICT",
  "traceId": "..."
}
```

`Problem Details` 是 HTTP API 常用的标准错误模型。项目可以扩展稳定的 `code`，但不要让客户端解析自然语言文案。

## 11. 给用户看的文字与给程序看的代码分开

`title` 或 `detail` 可以翻译、改善措辞；`code` 应保持稳定。客户端依据 `code` 决定界面行为，再把合适的文字呈现给用户。

数据库异常类名、SQL、堆栈和内部路径不应跨出服务边界。

## 12. 校验错误要指出具体字段

一次提交可能有多个输入问题。错误响应可包含字段路径、规则代码和安全说明：

```json
{
  "code": "VALIDATION_FAILED",
  "violations": [
    {"field": "affectedUsers", "code": "must_be_non_negative"}
  ]
}
```

字段级校验解决格式和范围；领域冲突则使用单独错误代码，不要全部压成“参数错误”。

## 13. JSON 只有有限的数据类型

JSON 有对象、数组、字符串、数字、布尔值和 `null`，没有 Java 的 `long`、日期对象或枚举类型。

因此跨语言时必须约定：

- 金额使用整数最小单位还是小数；
- 日期时间采用什么字符串格式和时区；
- 大整数是否会超过 JavaScript 安全整数范围；
- 缺少字段与显式 `null` 是否含义相同。

## 14. 金额不要使用二进制浮点数

FactoryCare 的费用适合用整数“分”表示，例如 `5997` 表示 59.97 元。若金额可能很大，Java 使用 `long` 并用精确运算检查溢出。

跨到 JavaScript 时还要确认数值是否处于安全整数范围；超出时应使用字符串或双方明确支持的十进制格式。

## 15. 时间必须携带明确语义

区分三个概念：

- 一个全球唯一的时间点，例如带 `Z` 或偏移量的 ISO 8601 字符串；
- 某地墙上时钟时间，例如“上海 09:00”；
- 纯日期，例如保养日期 `2026-07-29`。

不要用没有时区的字符串表示发生时刻，也不要把服务器本地时区当成系统契约。

## 16. 空值、缺省值与空字符串不是一回事

以更新接口为例：

```text
字段没出现：保持原值
字段为 null：清除现有值（如果允许）
字段为 ""：一个空字符串，通常应被校验拒绝
```

这三种行为必须在 Schema 和业务说明中一致，否则前端很容易意外清空数据。

## 17. 枚举是受控词汇

`OPEN`、`IN_PROGRESS`、`CLOSED` 这类值应有固定集合。新增枚举值可能让旧客户端遇到未知状态，所以客户端展示层最好有安全兜底，业务逻辑仍要显式处理。

不要把可变的中文显示文字当成传输值。

## 18. OpenAPI 是可执行的接口说明

OpenAPI 可以描述路径、方法、参数、请求/响应 Schema、安全方式和示例。它能够生成文档、客户端类型和契约检查，但前提是描述与真实服务一致。

文档生成成功不等于业务语义完整；幂等、权限、状态转换等仍需文字说明。

## 19. 契约应尽量从权威实现产生

Java API 可以从控制器和 DTO 生成 OpenAPI，再在 CI 中导出固定文件。FastAPI 会从路径声明和 Pydantic 模型生成 OpenAPI。

生成结果要进入版本审查。不能一边维护手写文档，一边让真实代码悄悄变化。

## 20. Schema 描述结构，不代替运行时校验

TypeScript 类型会在编译后消失，所以从网络收到的数据仍然是不可信的。正确路径是：

```text
未知 JSON
  → 运行时 Schema 校验
  → 可信领域输入
  → TypeScript 类型收窄
```

`as WorkOrder` 只是告诉编译器“相信我”，并没有验证服务器实际返回的数据。

## 21. Python 边界也要重新校验

FastAPI 和 Pydantic 能把请求转换为模型并报告校验问题。它们解决输入形状，不自动解决：

- 当前用户能否访问该工单；
- 工单状态是否允许此操作；
- 请求是否属于正确租户；
- 相同命令是否已经执行。

这些仍由应用和领域层负责。

## 22. 认证回答“你是谁”

客户端向 API 提供可验证凭据，API 校验签发者、受众、有效期和签名等信息，形成认证上下文。

不能因为请求带了某个用户 ID 字段就相信身份，也不能把前端隐藏按钮当作认证。

## 23. 授权回答“你能对什么做什么”

授权至少要结合：

```text
主体 + 动作 + 资源 + 租户 + 当前领域状态
```

同一个技术员可能能查看所属站点工单，却不能查看其他租户，也不能关闭尚未完成检查的工单。

## 24. 身份信息跨服务传播要受控

Java 调用 Python 时，不应把浏览器 Token 原样转交给任意下游。服务间调用使用面向目标服务的身份，并明确传递必要的用户、租户和关联信息。

每个服务仍在自己的边界重新认证和授权。

## 25. 分页是数据规模契约

没有分页的列表接口会随着数据增长变慢并占用大量内存。常见方式有：

- 偏移分页：容易理解，适合小规模后台列表；
- 游标分页：用稳定排序字段继续读取，适合大量或持续变化的数据。

无论哪种，都要限制最大页大小并定义稳定排序。

## 26. 排序必须有最终稳定键

只按 `createdAt` 排序时，多条记录可能时间相同。增加唯一 ID 作为最后排序键：

```text
ORDER BY created_at DESC, id DESC
```

游标要包含所有参与排序的值，否则翻页时可能重复或漏项。

## 27. 过滤参数必须有白名单

客户端可以选择服务端明确支持的状态、日期范围和排序字段。不要把用户传来的字段名或 SQL 片段直接拼接到查询中。

公开查询能力越强，越需要复杂度限制、超时和权限过滤。

## 28. 缓存是契约的一部分

HTTP 缓存涉及 `Cache-Control`、验证器和资源可见性。私人、租户相关的数据不能误标为公共缓存。

对可缓存的读取，可用 ETag 表示当前版本。客户端发送条件请求，未变化时服务端返回 `304`，减少正文传输。

## 29. 缓存一致性要接受明确取舍

缓存提高速度，却可能返回稍旧数据。必须说明：

- 哪些数据允许短暂陈旧；
- 最长可以旧多久；
- 写入后怎样失效；
- 权限变化时怎样避免继续命中旧数据。

“加一个缓存”不是无成本优化。

## 30. 幂等表示重复请求不会重复产生业务结果

网络超时后，客户端不知道请求是否已经成功。对于创建、扣费、发送等操作，可提交 `Idempotency-Key`：

```text
同一调用方 + 同一幂等键 + 同一操作
→ 只产生一次业务结果
```

服务端需要持久记录键、请求摘要、结果和有效期，不能只在单机内存里记一下。

## 31. 幂等与数据库唯一约束互相补充

幂等记录帮助返回第一次结果；唯一约束在并发竞争时提供最终防线。两者通常放在同一个事务边界中。

如果同一幂等键携带不同正文，应返回冲突，不能悄悄复用旧结果。

## 32. 乐观锁防止覆盖别人的更新

客户端读取工单版本 `7`，提交修改时带上版本。若数据库已经是版本 `8`，服务端返回 `409` 或 `412`，要求客户端刷新并决定怎样处理。

这比“最后一次写入无条件覆盖前一次”更能保护用户数据。

## 33. 超时必须分层设置

一次用户请求可能经过网关、Java、Python、模型和数据库。每层超时若毫无关系，外层可能已经放弃，内层仍长时间工作。

总体时间预算应逐层传递，内层留出错误处理和返回时间。超时不代表操作一定没有发生，因此写操作仍需要幂等和状态查询。

## 34. 重试只用于合适的失败

短暂网络故障、限流或依赖暂时不可用，有时可以退避后重试。输入错误、权限拒绝和确定的业务冲突不应重试。

写操作只有在幂等得到保障时才能自动重试。退避应加入随机抖动，避免大量客户端同时再次冲击服务。

## 35. 关联 ID 把一次调用串起来

入口生成或接受可信格式的 request/trace ID，随后传给下游并写入日志。这样可以从前端失败追到网关、Java、Python和数据库相关记录。

关联 ID 只用于定位，不是用户身份，也不能替代认证。

## 36. MCP 是另一种边界，不是绕过 API 的捷径

MCP Tool 应调用受控的 FactoryCare API 或应用服务：

```text
AI Host → MCP Tool → 认证/授权/校验 → FactoryCare API
```

Tool Schema 说明参数形状，却不是权限。模型提出调用后，服务端仍要执行租户隔离、领域校验、幂等和审计。

## 37. 联调先从一条真实链路开始

选择一条代表性流程，例如“创建工单并获取 AI 分类建议”，依次确认：

1. 客户端发出的真实 HTTP 请求；
2. 网关是否正确转发头和正文；
3. Java 校验、权限和事务结果；
4. Python 接收到的最小数据；
5. 返回值怎样映射到客户端；
6. 日志和 trace 是否能串联；
7. 任一依赖失败时用户看到什么。

先打通纵向切片，比同时联调所有接口更容易定位问题。

## 38. 契约检查分成几个层次

```text
Schema 检查：字段、类型和必填项是否一致
Provider 检查：服务实际响应是否符合声明
Consumer 检查：客户端依赖的行为是否仍成立
端到端检查：部署后的关键链路是否可用
```

每层发现的问题不同。端到端检查很重要，但不应承担所有细节，因为它慢且难定位。

## 39. 兼容变化与破坏性变化要分开

通常较容易兼容的变化包括增加可选字段、增加新接口；可能破坏旧客户端的变化包括删除/改名字段、改变类型、收紧必填条件、改变状态含义。

兼容与否还取决于消费者实现。例如新增枚举值对没有兜底的旧客户端也可能是破坏性变化。

## 40. 版本策略是迁移策略

不要一遇到变化就创建新版本。能通过新增可选能力演进时，保持原接口更简单。确实无法兼容时才引入新版本，并明确：

- 新旧版本同时存在多久；
- 哪些消费者尚未迁移；
- 怎样监控旧版本调用；
- 何时拒绝旧请求；
- 出问题怎样回滚。

版本号本身不能完成迁移。

## 41. 契约变更应进入 CI

持续集成可以导出当前 OpenAPI，与主分支版本比较，并运行服务端、客户端和契约检查。发现破坏性差异时要求人工确认和迁移说明。

生成客户端后仍应审查变化，不能把自动生成当作正确性的证明。

## 42. 联调问题用证据定位

推荐按这个顺序收集证据：

```text
用户看到的结果
→ 浏览器/客户端真实请求
→ 网关访问日志
→ API 状态码与错误 code
→ trace 与服务日志
→ 下游响应
→ 数据库最终状态
```

不要一开始就猜“肯定是跨域”或“肯定是后端”。每一步都确认输入、输出和责任方。

## 43. OpenAPI、日志和抓包各自回答不同问题

- OpenAPI 回答“系统承诺怎样工作”；
- 日志与 trace 回答“这次运行经过了什么”；
- 网络面板或抓包回答“边界上实际传输了什么”；
- 数据库与审计记录回答“最终事实发生了什么变化”。

把四种证据对照，才能区分契约错误、实现错误、部署错误和数据问题。

## 44. 系统设计从质量目标开始

设计接口前先明确调用量、延迟目标、可用性、数据敏感度、一致性要求和故障容忍度。同一个查询在内部管理后台和公开高流量 API 中，设计会不同。

数字不必一开始非常精确，但必须写明假设，后续才能用监控修正。

## 45. 这一章形成的整体地图

```text
业务事实和系统边界
  → HTTP 资源与状态语义
  → JSON / OpenAPI / 运行时校验
  → 认证、授权与租户隔离
  → 分页、缓存、幂等、乐观锁
  → 超时、重试与关联 ID
  → Java / Python / MCP 受控协作
  → 契约检查、兼容演进与证据化联调
```

需要真正实现某项协议字段、OpenAPI 版本或 MCP 能力时，再查询当时的官方文档。讲义保留的是长期稳定的判断方法。
