# Redis、缓存、幂等与限流

## 1. Redis 是一个快速的远程数据结构服务

Redis 常被叫作“内存数据库”，但更有用的理解是：多个应用实例可以通过网络共享字符串、哈希、集合、有序集合、流等数据结构，并对单条命令执行原子操作。

常见用途：

- 缓存数据库查询结果；
- 保存短期 Session 或一次性状态；
- 记录幂等键；
- 计数和限流；
- 保存排行榜、集合成员关系；
- 轻量消息或任务协调。

“很快”不代表无成本。它仍有网络延迟、内存上限、故障、持久化和一致性边界。

## 2. 先从数据结构选择，而不是把一切都当字符串

| 结构 | 直观用途 |
| --- | --- |
| String | JSON、计数器、标记、锁值 |
| Hash | 一个对象的多个小字段 |
| Set | 无重复成员、标签关系 |
| Sorted Set | 带分数排序、时间窗口 |
| List | 两端队列类操作 |
| Stream | 带 ID 的消息序列与消费组 |

数据结构影响可用命令、原子性和内存占用。不要为了少写一个类，把巨大对象永久塞成一个 JSON 再频繁整体读写。

## 3. Key 是公共命名空间，要包含业务边界

清楚的 Key 可以形如：

```text
factorycare:tenant:{tenantId}:device:{deviceId}
factorycare:tenant:{tenantId}:rate:login:{userId}
factorycare:tenant:{tenantId}:idem:create-work-order:{key}
```

Key 应包含租户和用途，避免不同模块、环境或租户碰撞。不要放密码、Token、完整邮箱等敏感值；Redis 管理工具、监控和错误日志都可能看到 Key。

Key 长度和数量也占内存。命名要可理解，但不必复制整份 URL 和请求体。

## 4. 缓存解决的是“重复计算或读取太贵”

数据库是真实数据源时，缓存保存一份可丢弃的较快副本：

```text
请求 → 先查缓存
         ├── 命中：直接返回
         └── 未命中：查数据库 → 写缓存 → 返回
```

这叫 **cache-aside（旁路缓存）**。应用明确控制读缓存、回源和失效，容易理解，也意味着一致性责任在应用。

缓存适合读取频繁、计算昂贵、允许短暂旧值的数据。若每次读取都必须绝对最新，缓存可能增加问题而不是优化。

## 5. Cache-aside 的读路径

概念伪代码：

```text
value = cache.get(key)
if value exists:
    return value

value = database.find(...)
cache.set(key, value, ttl)
return value
```

读取必须区分：

- Key 不存在；
- 缓存中有“业务值为空”的结果；
- Redis 请求失败；
- 缓存值格式过旧或损坏。

把所有情况都当“数据库不存在”会把基础设施故障伪装成业务 404。

## 6. TTL 让缓存副本自动过期

TTL（Time To Live）表示 Key 还可存活多久。它是缓存最终重新回源的上限，不是数据一定新鲜的证明。

选择 TTL 要权衡：

- 越短：数据更新更快可见，但回源更多；
- 越长：命中率高，但旧数据持续更久；
- 无 TTL：容易变成无法治理的第二数据库。

相似热点 Key 若同一秒到期，会瞬间把流量压向数据库。可给 TTL 添加小幅随机抖动，分散到期时间。

## 7. 写入后要定义缓存失效策略

常见策略：

1. 数据库提交成功；
2. 删除对应缓存；
3. 下一次读回源并重建。

删除通常比“同时精确更新所有缓存视图”简单，因为一个修改可能影响详情、列表、聚合和搜索多个 Key。

但数据库提交和 Redis 删除不是同一事务。删除失败会留下旧值，需要：

- 合理 TTL 作为上限；
- 重试或事件驱动失效；
- 监控失败；
- 对极高一致要求避免依赖缓存结果。

## 8. 先删缓存再写数据库也可能出错

一个并发时序：

```text
A 删除缓存
B 读缓存未命中，读到数据库旧值
A 提交数据库新值
B 把旧值写回缓存
```

因此常见顺序是数据库成功后删除缓存。但任何双写仍有故障窗口，应从“允许旧多久、如何修复”设计，而不是宣称强一致。

复杂的延迟双删、订阅数据库日志等方案有自己的边界，真正需要时再引入。

## 9. 缓存穿透是反复查询根本不存在的数据

攻击者或错误客户端持续查询不存在的 ID，缓存每次未命中，数据库每次都查空。

可选控制：

- 输入格式和范围校验；
- 对“不存在”结果短时间缓存；
- 布隆过滤器用于大规模存在性初筛；
- 按主体限流；
- 监控异常未命中率。

负值缓存 TTL 通常较短，否则对象刚创建后仍可能被当作不存在。布隆过滤器会有假阳性，不能作为权限或绝对存在事实。

## 10. 缓存击穿是一个热点 Key 到期后大量并发回源

```text
热点 key 到期
1000 个请求同时 miss
1000 个请求同时查数据库
```

可使用：

- 单飞（single flight）：一个请求加载，其他等待；
- 互斥锁：只让一个实例重建；
- 逻辑过期：先返回可接受的旧值，后台刷新；
- 提前刷新与 TTL 抖动。

锁必须有超时、唯一所有者和安全释放，等待也要有上限。不要让“保护数据库”的锁变成新的单点阻塞。

## 11. 缓存雪崩是大量 Key 或整个缓存同时失效

原因可能是：

- 大批 Key 同时到期；
- Redis 集群故障；
- 网络隔离；
- 错误发布清空命名空间。

应组合 TTL 抖动、数据库容量保护、请求限流、降级、热点预热和 Redis 高可用。缓存恢复后还要控制重建速度，不能瞬间回填全部数据。

## 12. 淘汰策略决定内存满时谁被删除

Redis 达到内存上限后，根据配置可能：

- 拒绝新写入；
- 从带 TTL 的 Key 中淘汰；
- 从所有 Key 中按近似 LRU/LFU 或随机策略淘汰。

如果同一实例混放缓存、幂等记录和重要协调状态，缓存淘汰可能顺带删除本应可靠保存的幂等事实。不同可靠性需求最好分离实例、数据库或至少明确内存与淘汰边界。

## 13. 序列化格式也是缓存合同

应用升级后类字段变化，旧缓存 JSON 可能无法读取。应考虑：

- 显式 schema/version；
- 向前或向后兼容字段；
- 发布时变更 Key 前缀；
- 解析失败时安全回源而不是反复报错；
- 防止反序列化不可信类型。

缓存可丢失，所以迁移策略往往是换命名空间并让旧 Key 自然过期，不必像主数据库一样原地迁移所有值。

## 14. Redis 故障时要按功能决定失败方式

```text
设备名称缓存失败 → 可回源数据库（fail open for cache）
登录限速器失败 → 可能必须拒绝或使用本地保守限制
幂等记录失败 → 继续执行可能产生重复业务
Session 存储失败 → 无法确认身份，应拒绝
```

“Redis 挂了就跳过”不是统一降级策略。缓存是性能优化时可以绕过；安全和正确性状态丢失时通常不能假装正常。

## 15. Redis 命令的原子性有明确范围

单条 Redis 命令执行时不会被另一条命令插入中间。例如 `INCR` 本身原子。但：

```text
INCR key
EXPIRE key 60
```

是两条命令。进程若在中间崩溃，Key 可能没有过期时间。

需要把多步“读、判断、写、设 TTL”作为一个原子决策时，可以使用带条件的命令、事务、Lua 脚本或 Redis Functions。原子脚本也要短小，长脚本会阻塞其他请求。

## 16. 幂等记录保存第一次业务意图的结果

对创建工单接口，客户端发送：

```http
Idempotency-Key: 75b8...
```

服务端可按租户、操作和 key 保存：

```text
requestHash  请求内容摘要
status       PROCESSING / SUCCEEDED / FAILED
resourceId   WO-42
response     必要的稳定响应
expiresAt    保留边界
```

重复同 payload 返回第一次结果；同 key 不同 payload 返回冲突。不能只用 `SETNX` 成功后就忘记持久业务结果。

## 17. 幂等记录和业务事务要协调

危险流程：

```text
数据库创建工单成功
进程崩溃
还没把 Redis key 标为成功
客户端重试 → 再创建一张
```

Redis 和 PostgreSQL 默认没有一个简单共同事务。可选设计：

- 把关键幂等表放在与业务同一数据库事务；
- 使用业务唯一键，让重复写在数据库层冲突并复用结果；
- Redis 只做前置加速，数据库仍提供最终重复防护；
- 根据风险设计恢复中的 `PROCESSING` 状态。

幂等正确性不能只依赖一个随时可能被淘汰的缓存 Key。

## 18. 分布式锁不是普通 Java 锁搬到 Redis

多个应用实例需要协调时，常见基本模型：

```text
SET lock-key unique-owner NX PX timeout
```

释放时必须“仅当值仍是自己的 unique-owner 才删除”，通常用原子脚本。否则客户端暂停到锁过期后，另一个客户端获得新锁，旧客户端恢复后可能误删新锁。

即便这样，锁持有者在停顿期间也可能继续执行过期工作。对数据库写入可用 fencing token、版本号或数据库约束拒绝旧持有者。锁不是数据正确性的唯一防线。

## 19. 限流控制一定时间内允许多少请求

限流（rate limiting）用于：

- 防止登录暴力尝试；
- 保护昂贵搜索和 AI 调用；
- 执行租户套餐配额；
- 防止一个客户端占满共享容量。

要先定义维度：按 IP、账号、租户、API key、端点或组合。只按 IP 可能误伤共享网络；只按账号又无法限制匿名攻击。

## 20. 固定窗口简单，但边界会突发

规则“每分钟最多 100 次”：

```text
12:00:00—12:00:59：100 次
12:01:00—12:01:59：100 次
```

客户端可在 12:00:59 发 100 次，再在 12:01:00 发 100 次，两秒内通过 200 次。固定窗口实现简单、内存小，适合允许边界突发的粗粒度配额。

Redis 中计数和首次 TTL 设置必须原子，否则计数器可能永久存在。

## 21. 滑动窗口更平滑但成本更高

滑动日志可以在有序集合中保存最近时间范围内的请求时间：

```text
删除窗口外记录
统计窗口内数量
未超限则添加当前请求
```

多步操作需要原子执行。每个请求一条记录会占更多内存；滑动窗口计数器可降低成本但精度有取舍。

不必因“更精确”默认选择最复杂算法，先看业务是否真的在意窗口边界。

## 22. Token Bucket 允许受控突发

令牌桶把容量想成一个桶：

- 令牌按固定速率补充；
- 请求消耗令牌；
- 桶容量决定最大突发；
- 没有足够令牌就拒绝或等待。

```text
平均补充 10 token/s
桶容量 50
→ 平均速率受控，但空闲后可短暂突发 50 次
```

它适合既要限制长期平均，又要允许正常瞬时批量的 API。

## 23. 429 响应应该帮助客户端正确退避

超限通常返回 `429 Too Many Requests`，并可提供：

- 稳定错误码；
- `Retry-After` 或重试时间；
- 合理的剩余额度信息；
- request ID。

客户端应退避并加入随机抖动，不能所有实例在同一秒再次冲击。服务端不要把内部 Key、用户是否存在等敏感策略直接暴露。

## 24. 配额和速率是不同概念

```text
速率限制：一分钟最多 100 次
配额：一个月最多处理 10 万条或使用 1000 元 AI 成本
并发限制：同时最多执行 20 个昂贵任务
```

三者可组合。只有限流不能控制长期成本，只有月配额又挡不住一秒钟内的洪峰。

## 25. 限流也有一致性和可用性取舍

Redis 不可用时：

- 公开登录端点若全部放行，会失去暴力破解保护；
- 核心内部读取若全部拒绝，可能造成更大事故；
- 多地域独立计数会允许总量超过全局限制；
- 全局强一致计数又增加延迟和故障范围。

应为每类端点明确 fail-open、fail-closed 或本地保守额度，并监控降级发生。

## 26. 监控应围绕“为什么使用 Redis”

基础指标包括：

- 命中率与未命中率；
- Redis 延迟、错误和超时；
- 内存、淘汰、过期 Key；
- 热点 Key 和大 Key；
- 数据库回源量；
- 限流拒绝数及维度；
- 幂等重复、冲突和长时间 PROCESSING；
- 连接池和复制状态。

总体命中率高也可能掩盖一个关键端点 0% 命中。指标要能关联到功能，同时避免把 userId、workOrderId 直接当 metric label 造成高基数。

## 27. 这篇的整体地图

```text
Redis 数据结构与原子命令
  ├── 缓存：cache-aside + TTL + 失效 + 故障降级
  ├── 幂等：识别重复意图 + 保存稳定结果 + 数据库最终防线
  ├── 锁：带所有者和超时，仍需版本/约束保护
  └── 限流：固定窗口 / 滑动窗口 / 令牌桶 + 明确失败策略
```

必须掌握：缓存不是事实来源；Key 要包含租户边界；TTL 不等于强一致；两条原子命令组合后不自动原子；幂等不能只靠可淘汰缓存；限流算法必须连同维度、响应和故障策略一起设计。

Redis Cluster 槽位、复制选举、Lua 语法和各客户端配置键属于“需要时查询”。
