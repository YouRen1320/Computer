# 领域事件、Outbox 与 RabbitMQ

## 1. 异步是把“现在必须完成”和“之后可以完成”分开

关闭工单后，系统可能还要：

- 发消息给报修人；
- 更新报表；
- 计算技师绩效；
- 建立搜索索引；
- 调用外部邮件服务。

若全部放在同一个 HTTP 请求中，任何外部服务慢或失败都会拖住核心操作。异步让关闭工单先提交，再由其他处理者完成后续工作。

代价是：结果不再同时可见，消息可能延迟、重复、乱序或永久失败，系统必须显式处理这些情况。

## 2. 事件描述已经发生的事实

好的事件通常用过去式：

```text
WorkOrderClosed
TechnicianAssigned
SlaBreached
```

它不是命令“请关闭工单”，而是事实“工单已经关闭”。消费者可以决定发送通知、更新读模型或忽略。

事件名称应表达领域含义，不要只有 `RowUpdated`。否则消费者必须重新猜数据库字段变化代表什么。

## 3. 领域事件和集成事件关注范围不同

- **领域事件（domain event）**：在当前业务模型内表达事实，可先作为内存对象；
- **集成事件（integration event）**：跨模块、进程或系统传递的稳定合同。

领域事件可以包含丰富的内部类型；集成事件应只暴露接收方真正需要且能长期兼容的字段。

```text
领域模型产生 WorkOrderClosed
  → 提交时转成版本化集成事件
  → 外部通知模块消费
```

不必把内部实体完整序列化后广播出去，那会把所有消费者绑在内部结构上。

## 4. 直接“先提交数据库，再发消息”会丢事件

危险时序：

```text
1. 更新工单并提交成功
2. 进程崩溃
3. 还没向 RabbitMQ 发送消息
```

数据库显示已关闭，但通知、报表等永远不知道。这叫双写问题：一个业务动作要同时可靠写两个独立系统，而普通本地事务只能保证其中一个。

反过来先发消息再提交也不安全：消费者可能处理“已关闭”，随后数据库事务却回滚。

## 5. Outbox 把业务事实和待发送记录写进同一事务

Transactional Outbox 的核心流程：

```text
数据库事务：
  1. 更新 work_order
  2. INSERT outbox_event
  3. 一起 COMMIT

独立 relay：
  4. 读取未发布 outbox_event
  5. 发送到 RabbitMQ
  6. 标记发布状态/记录尝试
```

只要数据库事务提交，待发布事实一定存在；若回滚，两者都不存在。这样消除了“业务成功但根本没有事件记录”的窗口。

## 6. Outbox 行是一份可恢复的发送工作

常见字段：

```text
event_id          全局唯一
aggregate_type    WorkOrder
aggregate_id      WO-42
aggregate_version 8
event_type        WorkOrderClosed
schema_version    1
tenant_id         tenant-A
occurred_at       业务发生时间
payload           稳定事件数据
status            PENDING / PUBLISHED / FAILED
attempt_count     已尝试次数
next_attempt_at   下次时间
created_at
```

不要把 Java 类的任意序列化结果当长期合同。显式事件类型和 schema 版本让消费者能演进。

## 7. Outbox 解决不丢事实，但通常仍可能重复发送

relay 的故障窗口：

```text
1. 发送消息成功
2. relay 在标记 PUBLISHED 前崩溃
3. 重启后再次发送同一 event_id
```

因此现实目标通常是 **at-least-once（至少一次）**：已提交事件最终会送达，但可能重复。消费者必须幂等。

声称“exactly once”要说明边界。即使 Broker 内部某一步只执行一次，数据库副作用、外部邮件和重试跨系统后仍可能重复。

## 8. Relay 要安全领取工作并允许故障恢复

多个实例可并行处理 Outbox，但不能每个都无控制读取同一批。常见方式包括：

- 数据库行锁配合跳过已锁行；
- 原子更新状态并返回领取结果；
- 使用 lease：记录 owner 和过期时间；
- 按分区或聚合分配。

`PROCESSING` 不能永久卡死；实例崩溃后 lease 到期应可重新领取。attempt、错误摘要和下次重试时间要可观测。

## 9. 轮询和 CDC 是两种发布方式

轮询发布者定期查询 Outbox：实现直观，数据库会有轮询负载和小延迟。

CDC（Change Data Capture）从数据库变更日志捕获新增行：延迟低、吞吐高，但部署和运维更复杂，仍要处理 schema、重复和下游故障。

先根据规模选择最简单可靠方案。中小型模块化单体通常可从批量轮询开始，并通过索引、批次和退避控制负载。

## 10. RabbitMQ 在生产者和消费者之间保存并路由消息

核心组件：

```text
Producer → Exchange → Binding → Queue → Consumer
```

- Producer 把消息发给 Exchange；
- Exchange 按类型和 routing key 路由；
- Binding 定义 Exchange 到 Queue 的规则；
- Queue 保存等待消费的消息；
- Consumer 从 Queue 取消息并确认。

生产者通常不直接指定“某个消费者”，而是发布事实；队列代表某类处理职责。

## 11. Exchange 类型决定路由方式

常见类型：

- `direct`：routing key 精确匹配；
- `topic`：按点分词模式匹配，如 `workorder.*.closed`；
- `fanout`：广播到所有绑定队列；
- `headers`：根据 header 条件匹配。

例如通知和报表都关心工单关闭，可以各有自己的 Queue，并绑定同一事件 Exchange。一个 Queue 被多个同类消费者竞争消费用于扩容；不同职责应使用不同 Queue，避免一条消息只能被其中一方拿到。

## 12. Queue、Exchange 和消息持久性要共同配置

若要求 Broker 重启后保留消息，通常需要：

- durable exchange；
- durable queue；
- 消息发布为持久；
- 合适的 RabbitMQ 队列类型和复制策略；
- 生产者确认。

只设置消息 durable，不代表未声明持久 Queue 时仍能恢复。持久性也不替代备份、容量和故障演练。

## 13. Publisher Confirm 说明 Broker 是否接受了发布

生产者把消息写到网络缓冲区，不等于 RabbitMQ 已可靠接收。Publisher Confirm 让 Broker 对发布返回确认或否认。

relay 应根据 confirm 决定是否把 Outbox 标为已发布。超时属于“不确定”：消息可能没到，也可能已到但确认丢了，安全做法通常是重试，因此仍会重复。

若 routing key 没有任何 Queue 接收，还要根据发布配置处理 unroutable 消息，不能把“Exchange 接受”误当“业务消费者一定有队列”。

## 14. Consumer Ack 决定消息什么时候可从队列移除

```text
消息到达消费者
  → 执行业务
  → 成功提交本地副作用
  → ack
```

如果处理前就 ack，随后进程崩溃，消息会丢。若业务成功后、ack 前崩溃，Broker 会再次投递，所以消费者会看到重复。

手动 ack 让“成功”边界清楚，但代码必须区分可重试、不可重试和已经完成的情况。

## 15. 幂等消费者让重复事件不重复产生副作用

可在消费者数据库中保存已处理 `event_id`：

```text
本地事务：
  1. INSERT processed_event(event_id)，唯一约束
  2. 执行业务更新
  3. COMMIT
随后 ack
```

重复消息再次插入时命中唯一约束，消费者确认它已经完成并 ack。

这有时叫 Inbox 模式。若副作用是发送外部短信，数据库去重和外部调用仍有故障窗口，应优先使用外部服务的幂等键，或把发送动作本身也变成可靠任务。

## 16. event_id 和 business key 解决不同重复

同一个 `event_id` 重投是传输重复；两个不同事件可能表达同一业务结果，例如错误代码产生两次 `WorkOrderClosed`。

消费者可以同时使用：

- event ID 去除传输重投；
- aggregate ID + version 拒绝旧版本；
- 业务唯一约束防止重复通知批次或付款。

幂等不能只靠“如果当前状态已经是 CLOSED 就什么也不做”，因为事件可能还包含一次性副作用或审计事实。

## 17. 重试只适合可能恢复的失败

适合有限重试：

- 临时网络超时；
- 数据库连接短暂不可用；
- 下游返回可恢复的 5xx；
- 限流后按 `Retry-After` 等待。

不适合原样重试：

- schema 无法解析；
- 必填字段永久缺失；
- 资源违反业务不变量；
- 权限或租户合同错误；
- 接收方明确返回不可重试的 4xx。

所有错误无限 requeue 会形成毒消息循环，持续占用消费者。

## 18. 退避和抖动避免故障时集体重试

重试间隔可指数增长：

```text
1 秒 → 2 秒 → 4 秒 → 8 秒 → ... → 上限
```

再加随机抖动，避免所有消费者同一时刻攻击刚恢复的依赖。RabbitMQ 中可通过延迟机制、重试队列加 TTL、插件或应用调度实现；具体实现要确认消息过期和队首阻塞等边界。

重试次数和总时间应有上限，并记录最后失败原因。

## 19. 死信队列保存自动处理不了的消息

超过重试次数或确认不可恢复后，将消息路由到 DLQ（Dead Letter Queue，死信队列）。DLQ 不是垃圾桶，而是一条需要运营闭环的队列：

- 有告警和负责人；
- 能查看脱敏错误与原事件标识；
- 修复代码或数据后可受控重放；
- 重放仍保持 event ID 和幂等；
- 有容量、保留和清理策略。

只配置 DLQ 却无人查看，相当于把丢消息推迟发生。

## 20. 消息顺序通常只在有限边界内成立

多生产者、多 Queue、重试和并行消费者都会改变顺序。即使同一 Queue 大致按入队顺序投递，失败重投也可能让后来的消息先完成。

若工单事件带 `aggregateVersion`：

```text
WO-42 version 8 arrives
WO-42 version 7 arrives later
```

消费者可以识别旧版本并忽略或暂存。但不同工单无需全局排序，强求全局顺序会严重降低吞吐。

## 21. 事件 schema 要可演进

事件一旦被其他模块消费，就是合同。演进原则：

- 使用稳定 event type 和 schema version；
- 新增可选字段通常比删除/改义容易；
- 不复用旧字段表达新含义；
- 时间、金额、ID 格式明确；
- 消费者对未知字段宽容，对关键缺失字段明确失败；
- 重大不兼容变化使用新版本事件并提供迁移期。

不要把 Java 全限定类名当跨系统事件类型，否则包重构就成为协议破坏。

## 22. 大 payload 和敏感数据不适合随事件广播

事件应包含消费者做决定所需的最小事实。大附件、完整工单描述和个人信息会：

- 增大 Broker 内存和磁盘；
- 复制到更多队列和日志；
- 增加隐私删除难度；
- 让消费者依赖旧快照。

可以只发资源 ID 和必要摘要，让有权限的消费者通过 API 查询；也可以发布完整事实以减少耦合，但必须明确权限、快照语义和数据治理。不存在机械统一答案。

## 23. 事务监听不等于可靠跨进程投递

在应用内“事务提交后调用一个 listener”可以保证不会在回滚前执行，但进程若在提交后、listener 完成前崩溃，任务仍会丢。

```text
afterCommit callback：适合低风险的进程内动作
Outbox：适合必须在崩溃后恢复的外部投递
```

要根据失败后果选择，不要把注解名称里的 `Transactional` 误解成横跨数据库和 Broker 的原子事务。

## 24. 可观测性要串起业务提交到最终消费

应能从 `event_id` 看到：

```text
业务事务何时提交
Outbox 何时创建
relay 领取和尝试次数
Broker confirm 是否成功
进入哪个 Queue
消费者何时处理、是否重复
重试或 DLQ 原因
最终业务副作用
```

指标包括 Outbox backlog、最老待发年龄、发布失败、Queue depth、unacked、消费延迟、重试和 DLQ 数。只看“RabbitMQ 进程存活”无法证明业务链健康。

## 25. 背压防止消费者被积压压垮

生产速度持续大于消费速度时，Queue 会增长。可以：

- 扩容消费者，但确认下游数据库容量；
- 设置合理 prefetch，限制单个消费者未确认消息数；
- 对生产入口限流；
- 批处理但保留单条失败边界；
- 按租户或 key 公平调度；
- 对非关键事件定义丢弃或合并策略。

无限 Queue 不是容量方案，最终会耗尽磁盘或让恢复时间不可接受。

## 26. 删除和重放同样是生产操作

清空 Queue、重放 DLQ、重新发布 Outbox 都可能造成大规模副作用。需要：

- 明确范围和事件筛选；
- 预估消费者容量；
- 先确认幂等；
- 记录操作者和批次；
- 可停止或限速；
- 重放后核对业务结果。

不能因“消息本来就处理过”而假设重放安全。

## 27. 这篇的整体地图

```text
领域状态成功变化
  → 同一数据库事务写 Outbox
  → relay 可恢复地领取
  → RabbitMQ Exchange 路由到 Queue
  → Broker confirm 证明接受
  → Consumer 处理并提交本地副作用
  → 幂等后 ack
  → 可恢复失败重试，永久失败进入 DLQ
```

必须掌握：异步带来最终一致和重复；Outbox 防止已提交事实完全丢失，但不消除重复；ack 必须在副作用成功后；消费者必须幂等；重试要分类、有上限，DLQ 要有人处理。

RabbitMQ 运维参数、集群队列类型、CDC 产品和具体 Spring AMQP API 属于“需要时查询”。
