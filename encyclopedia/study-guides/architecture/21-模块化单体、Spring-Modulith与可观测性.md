# 模块化单体、Spring Modulith 与可观测性

## 1. 单体不等于所有代码混在一起

单体应用表示主要功能作为一个部署单元运行。它可以内部边界清楚，也可以成为所有类互相调用的“大泥球”。

模块化单体（modular monolith）保留一个部署单元，同时按业务能力建立明确模块：

```text
FactoryCare 应用
  ├── identity
  ├── devices
  ├── workorders
  ├── notifications
  └── audit
```

目标是让每个模块拥有自己的模型和数据访问，只通过公开合同协作。

## 2. 模块边界优先按业务能力划分

纯技术分层：

```text
controller/
service/
repository/
entity/
```

项目变大后，一个工单功能会横跨所有目录，很难看出归属。按业务模块组织可以是：

```text
workorders/
  api/
  application/
  domain/
  infrastructure/
```

技术层仍然存在，但先回答“代码属于哪个业务能力”。这让修改工单规则时范围更清楚。

## 3. 一个模块要拥有自己的规则和数据

模块所有权包括：

- 领域模型和不变量；
- 用例入口；
- Repository 和表的写入责任；
- 对外公开的 API、事件或 DTO；
- 相关配置、测试和运行指标。

`devices` 模块不能因为方便直接更新 `work_order` 表；`workorders` 也不应直接拿 `users` 模块的 Repository 查询内部实体。否则目录看似分开，运行边界仍不存在。

## 4. 公开 API 要比内部实现小

模块可以公开：

```text
WorkOrderOperations.assign(...)
WorkOrderSummaryReader.find(...)
WorkOrderClosed 事件
```

内部保留：

```text
WorkOrderJpa/MyBatis mapper
内部实体
状态转换辅助类
表结构细节
```

外部模块只依赖公开能力。内部类可以通过包可见性、模块结构和结构测试防止被直接访问。

## 5. 共享实体会制造隐蔽耦合

如果所有模块共享同一个 `UserEntity`：

- 通知模块可能依赖密码字段；
- 工单模块可能直接修改身份状态；
- 用户表字段变化会迫使所有模块一起改；
- 事务边界和所有权不清楚。

模块间更适合传稳定 ID、明确 DTO 或领域事件。每个模块按自己需要维护表示，例如工单只保留 `AssigneeId` 和必要快照，不持有身份模块完整实体。

## 6. 依赖方向应有意设计

例如：

```text
notifications → workorders public event
workorders → identity public query
```

若 identity 又反向直接调用 notifications 内部类，很容易出现循环依赖。循环意味着两个模块不能独立理解、测试或演进。

解决方法不是给 Spring 加 `@Lazy` 掩盖循环，而是重新判断：

- 是否应由第三个协调模块编排；
- 是否可发布事件；
- 是否把合同放在真正拥有者一侧；
- 是否两个模块其实应该合并。

## 7. 同步调用和事件协作各有用途

同步调用适合调用者必须立即得到结果：

```text
分派工单前确认 technicianId 是否属于当前租户且有效
```

事件适合告知已经发生的事实，多个模块可独立响应：

```text
WorkOrderAssigned → 通知模块发送消息、报表模块更新统计
```

不要为了“解耦”把所有调用都改异步。关键校验若异步才执行，业务可能先提交非法状态。也不要让一个事件消费者同步链式触发几十层且没有失败边界。

## 8. 一个数据库也可以保持模块数据所有权

模块化单体常共享 PostgreSQL 实例和同一本地事务，但可以：

- 每张表有明确模块所有者；
- 其他模块不直接写；
- 读跨模块数据经公开查询或专门读模型；
- 外键是否跨模块按迁移与独立性权衡；
- 迁移脚本按模块命名和管理。

共享数据库能简化一致事务，但也让越界 SQL 很容易。结构和审查必须补上边界。

## 9. 本地事务是模块化单体的重要优势

一个进程和数据库内，创建工单和写 Outbox 可以使用同一事务，不需要分布式事务。跨模块的强一致操作也可能在同一数据库事务完成。

但不要因此把任意模块都纳入一个巨大事务。事务越长、对象越多，锁和失败范围越大。优先让一个用例由明确模块主导，其他非关键后续通过提交后事件处理。

## 10. 模块事件不自动等于可靠消息

Spring 进程内发布的事件可让模块减少直接调用，但：

- 同步 listener 失败可能回滚主事务；
- 异步 listener 可能在崩溃时丢失；
- 事务提交前消费会看到未提交事实；
- 重试可能产生重复。

Spring Modulith 能帮助组织和验证模块事件流程，并提供事件发布登记等能力，但具体可靠性仍要根据所用配置和版本确认。跨进程或必须恢复的事实仍要理解 Outbox 与幂等。

## 11. Spring Modulith 用来表达和验证 Spring 应用模块

它可以基于包结构识别应用模块，并帮助：

- 生成模块文档；
- 验证模块依赖；
- 测试单个模块；
- 支持模块间事件协作；
- 观察模块级交互。

工具不能替你决定边界。如果包按错误业务划分，验证通过只证明代码符合错误结构。先确定所有权和公开合同，再用工具防止退化。

## 12. 结构测试把架构约定变成可失败的证据

可以验证：

- `workorders` 不能依赖 `notifications.internal`；
- Controller 不能直接依赖 Repository；
- 模块间不能出现循环；
- 内部包只被本模块访问；
- 领域层不依赖 Spring Web 或数据库实现。

这类测试不验证业务结果，但能防止“临时方便的一次越界”逐渐摧毁边界。规则应少而关键，错误信息要能指导修复。

## 13. 模块测试关注公开行为和真实边界

测试层级可以是：

- 领域规则小测试；
- 单模块 Spring 上下文测试；
- 含数据库的持久化/事务验证；
- 少量跨模块集成流程；
- 结构依赖测试。

不必每个模块复制整个端到端套件。把高风险边界留给真实依赖，把纯规则保持快速。

## 14. 模块化单体不是未来必拆微服务的临时品

一个边界清楚的单体可以长期满足业务，具有：

- 部署和本地开发简单；
- 本地事务方便；
- 调试链路短；
- 基础设施成本低；
- 重构跨模块合同时更直接。

微服务增加独立部署和扩缩容，但也引入网络失败、版本兼容、分布式数据和可观测成本。应由具体问题驱动拆分，不以服务数量衡量架构成熟度。

## 15. 出现这些信号时才评估拆分

可能的拆分信号：

- 某模块有明显不同的扩缩容需求；
- 团队需要真正独立发布，当前协调成为主要瓶颈；
- 故障必须隔离，单进程影响不可接受；
- 技术或合规边界确实不同；
- 模块数据与接口已经稳定独立；
- 单体构建、启动或发布无法通过合理优化解决。

“代码很多”“想用 Kubernetes”“公司都在微服务”不是充分理由。

## 16. 可观测性回答系统内部正在发生什么

Observability（可观测性）不是安装一个监控页面，而是能根据外部信号解释内部状态，尤其是没预先想到的故障。

常用三类信号：

- **日志（logs）**：某个离散事件的上下文；
- **指标（metrics）**：随时间聚合的数值；
- **链路追踪（traces）**：一次请求跨组件的因果路径。

它们互补，不是三选一。

## 17. 结构化日志让机器和人都能筛选

相比拼接自然语言：

```text
closed order 42 by bob
```

结构化字段更稳定：

```json
{
  "event": "work_order_closed",
  "workOrderId": "WO-42",
  "actorId": "user-17",
  "tenantId": "tenant-A",
  "traceId": "...",
  "result": "success"
}
```

日志消息仍应便于阅读，但关键字段不要藏在无法可靠解析的长句中。字段命名和级别要一致。

## 18. 日志级别表达处置意义

大致原则：

- `DEBUG`：开发诊断细节，生产通常受控开启；
- `INFO`：重要正常生命周期和业务事实；
- `WARN`：异常但已处理、需要关注的退化；
- `ERROR`：操作失败且需要处置。

用户输入错误通常不应每次打印 ERROR 堆栈；数据库不可用也不能只记录 INFO。级别影响告警、成本和排查信噪比。

任何级别都不能记录密码、完整 Token、Session ID 和不必要个人信息。

## 19. Correlation ID 和 Trace ID 串起一次请求

一个请求可能经过网关、应用、Redis、RabbitMQ 和消费者。每处日志若有相同 trace/correlation 标识，就能按一次业务流程检索。

```text
HTTP request traceId=T1
  ├── workorders module span
  ├── PostgreSQL span
  └── publish event carries trace context
        └── consumer creates linked span
```

不要信任客户端任意提交的 ID 作为唯一日志标识；入口应验证格式或生成新值。异步消息需要显式传播追踪上下文，同时保留独立的 event ID。

## 20. 指标适合回答趋势和规模

常见服务指标可用 RED 思路：

- Rate：请求速率；
- Errors：错误比例；
- Duration：延迟分布。

资源指标可用 USE 思路：

- Utilization：利用率；
- Saturation：排队或饱和；
- Errors：资源错误。

业务指标还可包括工单创建、关闭、SLA 超时和 Outbox 积压。技术和业务信号结合，才能判断“服务在线但功能不可用”。

## 21. 延迟要看分布，不只看平均值

平均 100 ms 可能掩盖少量用户等待 10 秒。应关注 p50、p95、p99 等分位数：

```text
p95 = 500 ms
表示约 95% 的观测不超过 500 ms
```

分位数仍要和请求量、窗口及端点范围一起解释。不要把所有 URL 混成一个指标，也不要为每个 workOrderId 建 label。

## 22. 高基数标签会拖垮指标系统

适合 label：

```text
method=POST
route=/api/work-orders/{id}
status=403
```

危险 label：

```text
userId=每个用户不同
workOrderId=每张工单不同
rawUrl=包含任意 query
```

每种 label 组合形成时间序列。高基数标识应放日志或 trace，不应机械加入 metric labels。

## 23. Trace 由 Span 组成

一次完整请求是 trace，其中每一步是 span：

```text
Trace T1
  ├── HTTP POST /work-orders          220 ms
  ├── validate                        2 ms
  ├── PostgreSQL INSERT              35 ms
  └── Outbox INSERT                   4 ms
```

span 包含开始/结束、状态、父子关系和有限属性。Trace 能展示时间花在哪里，但采样意味着不是所有请求都保留；错误和关键业务可能使用更积极的采样策略。

## 24. SLI 是测量，SLO 是目标

- **SLI（Service Level Indicator）**：实际测量指标；
- **SLO（Service Level Objective）**：在窗口内希望达到的目标；
- **SLA**：对外合同，通常还包含违约后果。

例如：

```text
SLI：有效创建工单请求中成功且 2 秒内完成的比例
SLO：过去 30 天达到 99.9%
```

必须先定义哪些请求进入分母。客户端非法请求、健康检查和内部压测是否计算，要与用户体验和责任边界一致。

## 25. 错误预算把可靠性目标变成可消耗空间

若 SLO 是 99.9%，相应窗口有 0.1% 不达标空间，这叫错误预算。

它可用于平衡：

- 新功能发布速度；
- 可靠性修复；
- 高风险迁移；
- 实验流量。

错误预算不是允许随意制造事故，而是让“必须 100%”与“只追功能”之间有可量化决策依据。

## 26. 告警应指向用户影响和可采取行动

差的告警：CPU 一次超过 70% 就立刻叫醒所有人。

更好的告警关注：

- SLO 消耗速度；
- 持续错误率和高延迟；
- Outbox/Queue 最老积压年龄；
- 核心依赖不可用；
- 数据正确性或安全边界异常。

告警应带仪表盘、近期变更、Runbook 和负责团队。没有动作的高噪声告警最终会被忽略。

## 27. Liveness 和 Readiness 回答不同问题

- **Liveness（存活）**：进程是否已陷入无法恢复、需要重启；
- **Readiness（就绪）**：此实例现在能否接收业务流量。

数据库暂时不可用时，把 liveness 设失败可能导致所有实例循环重启；readiness 失败则可暂时摘流。探针必须轻量，并避免每秒执行昂贵全链路查询。

Spring Boot Actuator 可暴露健康、指标和管理端点，但管理端点本身是攻击面，只开放必要内容并限制网络、身份和敏感详情。

## 28. 模块边界也应进入可观测字段

日志、Span 和指标可以标记稳定模块名：

```text
module=workorders
operation=assign
```

这样能看出错误和延迟归属，而不是只看到某个 Java 包。模块事件的发布和处理延迟也可单独观察。

模块名是低基数稳定维度；不要把内部每个类名都当业务指标。

## 29. 一次排障从症状到证据闭环

例如“工单关闭后通知延迟”：

```text
1. 指标：通知延迟 SLI 恶化
2. trace：HTTP 关闭很快，异步链断在消费者
3. Queue 指标：积压年龄上升
4. 日志：下游邮件服务限流
5. Runbook：降低 prefetch、按 Retry-After 退避、扩容是否有用
6. 修复后：指标恢复，积压消退，抽样核对事件
```

日志、指标和 trace 应互相导航，不能各自成为孤岛。

## 30. 这篇的整体地图

```text
业务模块
  → 明确所有权、公开 API 和依赖方向
  → 同步调用处理必要即时结果
  → 事件处理已发生事实
  → 结构测试防止边界腐化
  → 有证据时再考虑拆服务

运行信号
  → 结构化日志记录上下文
  → 指标显示趋势和规模
  → Trace 串起因果链
  → SLI/SLO 定义可靠性目标
  → 告警 + Runbook + 复盘形成闭环
```

必须掌握：模块化单体不是大泥球；共享数据库也要有表所有权；进程内事件不自动可靠；日志、指标、Trace 各自回答不同问题；SLO 必须建立在明确 SLI 上；健康端点不能无保护公开。

Spring Modulith DSL、OpenTelemetry 采样器和监控系统查询语言属于“需要时查询”，真正学习时按当时官方版本复核。
