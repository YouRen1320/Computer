# 领域模型、工单状态机、SLA 与乐观锁

## 1. 领域模型是把业务规则变成代码中的明确结构

如果所有代码只是“接 JSON → 改数据库字段 → 返回 JSON”，规则会散落在 Controller、SQL、前端和定时任务里。需求变化后，很难判断真正的业务边界。

领域模型（domain model）尝试用代码表示业务中的对象、值、状态和规则，例如：

- 工单是什么；
- 哪些状态转换允许；
- 谁能分派；
- SLA 截止时间怎样计算；
- 同一工单被两人同时修改时怎么办。

目的不是把每个名词都建成类，而是让重要规则有唯一、可理解的落点。

## 2. 先区分业务规则和技术流程

```text
业务规则：已关闭工单不能重新开始处理
技术流程：通过 HTTP 接收请求、用 MyBatis 更新 PostgreSQL
```

业务规则应尽量不依赖 Controller、数据库驱动或消息队列。这样它可以在 HTTP 请求、批处理和消息消费者中一致使用，也更容易用小范围例子验证。

技术层负责把输入转成领域能理解的命令、加载对象、保存结果和发布已发生的事实。

## 3. 实体由身份延续，而不是由所有字段相等决定

工单标题、状态和负责人都会变化，但只要 `workOrderId` 相同，业务仍认为它是同一张工单。这类对象叫**实体（entity）**。

```text
WorkOrder WO-42：
  昨天 status=ASSIGNED
  今天 status=IN_PROGRESS
  仍是同一实体 WO-42
```

实体的相等性和生命周期围绕稳定身份设计，不能把所有可变字段都放进 `equals` 后再放进 `HashSet`，否则修改字段可能破坏集合行为。

## 4. 值对象由内容定义，通常应该不可变

金额、时间范围、设备编码、优先级等更适合表示为**值对象（value object）**。

```text
Money(1999, CNY) 与另一个 Money(1999, CNY) 表示相同的值
```

值对象可以集中保证规则：

- `Money` 不允许币种为空；
- `SlaDuration` 不允许负数；
- `TenantId` 与 `WorkOrderId` 不会被误传；
- `EmailAddress` 在创建时完成格式规范化。

Java 的 `record` 常适合简单不可变值，但构造时仍要验证不变量。

## 5. 不变量是对象在任何可观察时刻都必须成立的规则

例如：

- 已分派工单必须有技师；
- `CLOSED` 工单必须有关闭时间；
- SLA 截止时间不能早于创建时间；
- 工单和设备必须属于同一租户。

这些规则叫**不变量（invariant）**。如果对象可以先进入非法状态，再希望“后面某层修好”，其他代码可能已经读到或保存了错误状态。

构造器、命名工厂和行为方法应阻止非法对象产生。

## 6. 聚合定义一次业务变更必须保持一致的边界

聚合（aggregate）是一组需要在同一次业务操作中保持规则一致的对象，外部通过聚合根访问。

```text
WorkOrder（聚合根）
  ├── Assignment
  ├── StatusHistory
  └── 当前 SLA 信息
```

并不是数据库所有关联表都属于同一聚合。聚合过大，会让每次操作加载太多数据并增加锁冲突；聚合过小，关键不变量要跨多个事务维护。

判断原则是：“哪些数据必须在同一个事务提交点共同满足规则”，而不是“哪些表有外键”。

## 7. 行为应放在拥有规则的对象上

贫血写法可能到处直接设置：

```java
workOrder.setStatus(CLOSED);
workOrder.setClosedAt(now);
```

更清楚的行为：

```java
workOrder.close(actor, now);
```

`close` 内部检查当前状态、操作者关系，设置关闭时间并产生状态变化事实。调用者不需要记住一组必须同时修改的字段。

不是每个 setter 都必须消失，但承载不变量的变化应通过有业务含义的方法进行。

## 8. Repository 表达“按身份取回和保存聚合”

Repository 是领域与持久化之间的接口概念：

```text
findById(tenantId, workOrderId)
save(workOrder)
```

它不应成为随意暴露所有表操作的万能工具。查询报表、搜索列表可以使用专门的读模型；修改业务状态则加载必要的聚合并执行规则。

接口放在哪一层取决于架构，但领域不应依赖 MyBatis 注解、HTTP DTO 或数据库行对象。

## 9. 应用服务负责编排一次用例

以分派工单为例：

```text
Application Service
  1. 从可信身份得到 tenant 和 actor
  2. 检查粗粒度权限
  3. Repository 加载工单
  4. 加载或验证技师可用性
  5. 调用 workOrder.assign(...)
  6. 保存聚合
  7. 记录/发布状态变化事实
```

应用服务处理事务和协作顺序；领域对象决定“此状态下是否允许分派”。不要把 HTTP `ResponseEntity` 塞进领域对象，也不要让 Controller 直接执行一串数据库更新。

## 10. 领域服务用于不自然属于单个对象的业务规则

例如“按多个技师技能、距离和班次计算最合适分派”可能涉及多个对象，不自然属于某一张工单。这时可以使用领域服务。

领域服务仍应表达业务能力，而不是把所有逻辑从实体搬到一个 `SomethingService` 大类。若规则只需要工单自己的状态，就优先放回工单行为。

## 11. 状态机把允许的变化列成有限规则

工单状态不是任意字符串。状态机（state machine）包含：

- 有限状态；
- 允许的转换；
- 触发动作；
- 转换条件（guard）；
- 转换后的动作或事件。

简化教学状态：

```text
CREATED → ASSIGNED → IN_PROGRESS → CLOSED
    └──────────────→ CANCELLED
```

这只是用来理解机制的投影。FactoryCare 真正项目的状态合同可能更多，必须以唯一项目合同为准，不能让教学图悄悄替换生产状态。

## 12. 转换表比散落的 if 更容易发现空白

| 当前状态 | 动作 | 条件 | 新状态 |
| --- | --- | --- | --- |
| CREATED | assign | 技师有效且同租户 | ASSIGNED |
| ASSIGNED | start | 当前用户是被分派技师 | IN_PROGRESS |
| IN_PROGRESS | close | 关闭信息完整 | CLOSED |
| CREATED / ASSIGNED | cancel | 有取消权限与原因 | CANCELLED |

表格可以明确：

- 哪些转换合法；
- 终态是否还能离开；
- 同一动作在不同状态含义是否相同；
- 缺少了哪些失败合同。

代码可以用 enum、映射或行为方法实现，形式不如规则完整重要。

## 13. Guard 是转换前必须满足的条件

“ASSIGNED 可以变 IN_PROGRESS”只是结构规则，还可能需要：

- 操作者就是被分派技师；
- 技师账号仍有效；
- 工单没有被租户冻结；
- 当前时间不早于允许开工时间。

这些条件叫 guard。失败时应返回稳定的业务错误，如 `INVALID_STATE_TRANSITION` 或 `NOT_ASSIGNED_TECHNICIAN`，不要只抛一个含糊的空指针异常。

## 14. 终态要明确是否真正终止

`CLOSED` 和 `CANCELLED` 通常是终态，但现实业务可能允许“重新打开”。这不是简单删除终态限制，而应定义一个新动作：

```text
reopen：
  谁能做？
  在关闭多久内？
  重新进入哪个状态？
  SLA 如何重算？
  是否保留原关闭记录？
  审计和事件怎样表示？
```

状态转换应表达业务事实，不能因为数据库字段可更新就允许任意跳转。

## 15. 状态历史和当前状态用途不同

当前状态用于快速判断现在是什么；状态历史用于回答如何走到这里。

```text
work_order.status = IN_PROGRESS

status_history:
  CREATED at t1
  ASSIGNED at t2 by dispatcher
  IN_PROGRESS at t3 by technician
```

历史记录应与状态提交保持一致，不能状态更新成功而历史丢失，或事务回滚后留下“已成功”的历史。它和安全审计有关联，但状态历史是领域事实，审计还包含访问拒绝、管理员操作等更广范围。

## 16. SLA 是一个可度量的服务承诺

SLA（Service Level Agreement）可能规定：

- 高优先级工单 30 分钟内响应；
- 4 小时内开始处理；
- 24 小时内解决；
- 暂停等待客户时是否停止计时。

必须先定义测量语义：起点、终点、时钟、暂停条件、工作日历、时区和违反后的动作。只有一个 `deadline` 字段，不能自动说明这些规则。

## 17. 时间点和持续时间不要混为一谈

Java 中常见选择：

- `Instant`：全球时间线上的一个时刻，适合存发生时间；
- `Duration`：两个时间点之间按秒/纳秒表示的持续长度；
- `LocalDate` / `LocalTime`：本地日历概念；
- `ZonedDateTime`：带时区规则的本地时间。

如果规则是“创建后 4 小时”，可以从 `Instant` 加 `Duration`。如果是“下一个工作日 17:00”，就需要业务日历和时区，不能简单加 24 小时。

数据库通常保存统一时刻，并在显示时按用户时区转换；本地日期规则则需保留其业务时区语义。

## 18. 用注入的 Clock 代替在规则中随处读取系统时间

直接调用 `Instant.now()` 会让测试依赖真实时间。可以让应用传入 `Clock` 或明确的 `now`：

```java
Instant now = clock.instant();
workOrder.start(actor, now);
```

测试可使用固定时钟，稳定验证截止前、刚好截止和截止后的边界。

这不是为了“测试技巧”，而是让时间成为用例的显式输入，避免一次操作的不同代码读取到略有差异的现在。

## 19. 超时检测有主动和被动两种方式

被动检查：用户查询或操作时，系统计算当前是否超时。

```text
优点：简单，不需要调度器
缺点：没人访问时不会主动触发通知
```

主动检查：定时任务或延迟消息在截止附近扫描并产生超时事件。

```text
优点：可主动告警和升级
缺点：任务可能重复、延迟或故障，需要幂等
```

常见做法是以数据库中的截止事实为准，查询时可即时计算，后台任务负责通知；不要把“定时器已经执行过”当作唯一真相。

## 20. HTTP 重试会让同一业务请求到达多次

用户双击、移动网络重试、代理超时或客户端自动恢复，都可能让创建/支付/分派请求重复到达。

**幂等**的含义是：同一个业务意图重复提交，不会产生多份副作用，并能得到一致或明确的结果。

```text
请求 1：Idempotency-Key = K，创建 WO-42
请求 2：同一个 K、同一 payload
结果：返回第一次的 WO-42，而不是再创建 WO-43
```

## 21. 幂等键要和主体、范围及请求内容绑定

只存一个全局字符串 key 不够。通常要考虑：

- 租户或调用方；
- 接口/操作类型；
- key；
- 请求内容摘要；
- 处理状态；
- 已生成的业务结果或响应；
- 过期时间。

同一个 key 配不同 payload 应拒绝为冲突，不能悄悄返回旧结果或执行新内容。幂等记录必须和业务副作用在可靠边界内协调，否则“业务成功、key 没记住”仍会重复执行。

## 22. 幂等和并发控制解决不同问题

```text
幂等：是不是同一个业务意图被重复提交？
并发控制：两个不同意图是否同时修改了同一版本数据？
```

两个调度员分别想把同一工单分给不同技师，使用不同幂等键。这不是重复请求，仍需要并发冲突检测。

相反，同一个请求因超时重试，可能没有并发发生，但需要幂等结果复用。

## 23. 乐观锁用版本号发现“我修改的是旧数据”

读取工单时得到：

```text
id=WO-42, status=CREATED, version=7
```

更新时：

```sql
UPDATE work_order
SET status = :newStatus,
    version = version + 1
WHERE tenant_id = :tenantId
  AND id = :id
  AND version = 7;
```

第一个更新成功后版本变 8。第二个仍带 7 的更新影响 0 行，系统就知道它基于旧快照，应该返回冲突而不是覆盖第一个人的结果。

## 24. update count 为 0 不能被忽略

乐观锁是否生效，关键不是表上有 `version` 字段，而是：

1. 查询读取版本；
2. 更新条件包含预期版本；
3. 成功时原子增加版本；
4. 检查受影响行数；
5. 0 行转成明确冲突处理。

如果代码无论影响几行都返回成功，用户会看到“操作成功”，数据库却没有变化，造成静默逻辑错误。

## 25. 冲突后的策略不是一律自动重试

对纯计数增加，可在重新读取后安全重试；对人工分派，自动重试可能把旧决定强加到新状态上。

可选策略：

- 返回 409 Conflict，让客户端显示最新状态并请用户重新决定；
- 在服务端重新加载并确认不变量后有限重试；
- 对可合并字段执行明确合并；
- 对高争用资源改用悲观锁或串行化入口。

策略取决于业务语义，不是数据库异常类别。

## 26. 悲观锁与乐观锁是争用取舍

悲观锁先锁住记录，假设冲突可能发生；乐观锁先允许并行，提交时检测版本。

| 维度 | 乐观锁 | 悲观锁 |
| --- | --- | --- |
| 冲突少 | 开销较低 | 可能无谓等待 |
| 冲突多 | 重试/失败多 | 可排队，但可能阻塞 |
| 持锁时间 | 通常短 | 依赖事务范围 |
| 风险 | 忽略版本、错误自动重试 | 死锁、超时、吞吐下降 |

不要在等待用户输入或外部网络时长期持有数据库锁。

## 27. 事件应描述已发生的领域事实

状态成功从 ASSIGNED 变为 IN_PROGRESS 后，可以产生：

```text
WorkOrderStarted
  eventId
  workOrderId
  tenantId
  technicianId
  occurredAt
  version
```

事件使用过去式，表示事实已经成立。它可驱动通知、SLA、审计或报表，但只有在业务事务真正提交后才应对外可见。可靠发布会在后面的 Outbox 讲义中展开。

## 28. 这篇的整体地图

```text
业务语言
  → 实体、值对象和不变量
  → 聚合决定事务一致边界
  → 应用服务编排，领域行为守规则
  → 状态机列出合法转换与 guard
  → SLA 明确时钟、日历和超时语义
  → 幂等识别重复意图
  → 乐观锁发现并发旧版本
  → 成功提交后产生领域事实
```

必须掌握：实体靠身份延续，值对象靠内容相等；不变量不能靠调用者记忆；状态不是任意字符串；SLA 必须定义时间语义；幂等与乐观锁不是同一个问题；更新 0 行必须显式处理。

复杂 DDD 战术模式、事件溯源和通用状态机框架属于“见过即可或需要时查询”。先让重要业务规则有清楚、唯一的落点。
