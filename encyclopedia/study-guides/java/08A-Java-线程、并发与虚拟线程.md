# Java：线程、并发与虚拟线程

## 1. 先分清程序、进程、线程和任务

一份 `.class` 或 JAR 文件是磁盘上的程序内容。执行 `java ...` 后，操作系统创建一次运行实例，这叫作**进程（process）**。一个进程有自己的内存空间、工作目录、打开的文件和其他运行资源。

进程中真正执行 Java 代码的是**线程（thread）**。每个 Java 程序启动时至少有主线程；程序还可以创建其他线程，让多个执行路径在时间上重叠。

**任务（task）**则是“要完成的一项工作”，例如：

- 查询一台设备；
- 读取一份附件；
- 发送一条通知；
- 计算一批工单优先级。

任务不是线程。任务是业务工作，线程是执行任务的资源或载体。同一个线程可以先后执行很多任务，一个任务也可以被提交给不同执行器。

### 1.1 并发和并行

- **并发（concurrency）**：多个任务在同一时间段内都有进展；
- **并行（parallelism）**：多个任务在同一时刻真正使用不同 CPU 核执行。

单核机器也可以并发：操作系统在多个线程之间切换。多核机器才可能真正并行。业务代码通常关心任务能否安全重叠，不能只凭“有多个线程”就声称获得并行加速。

### 1.2 CPU 密集和等待密集

- CPU 密集任务大部分时间在计算，例如图像处理、压缩、模型计算；
- 等待密集任务大部分时间在等网络、数据库、磁盘或外部服务。

增加线程对二者作用不同。CPU 核数量有限，给纯计算创建成千上万线程不会让 CPU 更快；等待密集任务则可能通过更多并发提高吞吐量。

这一节必须掌握：任务是工作，线程是执行路径，进程是一次运行容器；并发不等于并行，也不自动等于更快。

## 2. Thread：直接创建线程时要理解的生命周期

最小线程：

```java
Thread worker = new Thread(() -> {
    System.out.println("loading device");
});

worker.start();
```

`start()` 请求 JVM 启动一个新的执行线程，新线程随后调用任务的 `run()`。不要直接写：

```java
worker.run();
```

直接调用 `run()` 只是当前线程中的普通方法调用，不会创建并发执行路径。

### 2.1 join：等待另一个线程结束

```java
worker.start();
worker.join();
System.out.println("worker finished");
```

主线程会等待 `worker` 终止，再继续打印。`join` 不只是“停一下”；它还建立明确的完成顺序，使等待方在正常返回后能观察线程已完成的动作。

无限等待可能让程序永久卡住。真实边界可使用有时限等待，并在超时后决定取消、降级或记录故障。

### 2.2 Thread.State 是诊断快照

线程可能显示 `NEW`、`RUNNABLE`、`BLOCKED`、`WAITING`、`TIMED_WAITING` 或 `TERMINATED`。这些是 JVM 观察状态，不是业务状态机。

`RUNNABLE` 不保证此刻正在占用 CPU；`WAITING` 也不一定代表故障。诊断“程序卡住”还要结合堆栈、等待对象、锁和进展指标。

## 3. 中断：请求线程尽快停止当前工作

Java 没有一个安全的通用“强杀线程”按钮。`interrupt()` 发出协作请求：

```java
worker.interrupt();
```

任务需要在合适位置响应：

```java
while (!Thread.currentThread().isInterrupted()) {
    processNextItem();
}
```

某些阻塞方法在被中断时抛出 `InterruptedException`，并清除中断标记：

```java
try {
    queue.take();
} catch (InterruptedException error) {
    Thread.currentThread().interrupt();
    return;
}
```

如果当前层不能完成中断处理，通常应恢复中断标记或继续传播，让上层知道停止请求。下面的写法会吞掉取消信号：

```java
catch (InterruptedException ignored) {
    // 继续永久运行
}
```

响应中断还要清理当前任务拥有的资源，并决定部分工作能否提交。中断是协议，不保证任意第三方阻塞调用都会立即停止。

## 4. 并发真正困难的地方：共享可变状态

多个线程只读取不可变数据通常容易推理。多个线程同时读写同一对象时，会遇到三类问题：

1. **原子性**：一组操作会不会被其他线程插入；
2. **可见性**：一个线程写入的值，另一个线程何时保证看见；
3. **有序性**：编译器、JIT 和 CPU 优化后，哪些先后关系对其他线程有保证。

Java 内存模型（Java Memory Model，JMM）规定正确同步程序可以依赖哪些跨线程保证。不要用“它们共享同一块内存，所以马上看见”解释并发行为。

### 4.1 count++ 不是一个不可分割动作

```java
count++;
```

概念上包含：读取旧值、加一、写回。两个线程可能都读到 `10`，分别写回 `11`，于是丢掉一次更新。这叫作**竞态条件（race condition）**。

即使单次 `int` 读写具有某种原子性，完整的“读—改—写”业务操作仍然不是原子的。

### 4.2 check-then-act

```java
if (!assigned) {
    assigned = true;
    assignTechnician();
}
```

两个线程可能都在 `assigned` 仍为 `false` 时通过检查，然后执行两次派工。每一行单独看都简单，组合后却需要一个不可分割的临界区。

并发正确性必须围绕业务不变量设计，而不是给每个字段分别找一个“线程安全类型”就结束。

## 5. happens-before：跨线程可见性的可靠顺序

JMM 使用 **happens-before** 描述一个动作的结果保证对另一个动作可见，并且顺序受到约束。常见边包括：

- 同一线程中的程序顺序；
- 解锁 happens-before 后续对同一锁的加锁；
- 对 `volatile` 字段的写 happens-before 后续对同一字段的读；
- `Thread.start()` 之前的动作对新线程可见；
- 线程中的动作在另一个线程成功 `join()` 之后可见；
- 向执行器提交任务前的动作，经任务执行后，在 `Future.get()` 取得结果时形成相应可见性链。

这不是让你死记完整列表，而是提供一个判断方法：如果两个线程共享数据，就找出它们之间由哪条同步边建立可见性。找不到时，不能靠一次运行正常证明安全。

## 6. volatile：适合简单信号，不适合复合不变量

```java
private volatile boolean shutdownRequested;
```

一个线程写 `true`，其他线程后续读取同一 `volatile` 字段能获得相应可见性保证。它适合简单状态信号或独立配置快照。

`volatile` 不会把复合操作自动变成原子操作：

```java
private volatile int count;
count++; // 仍然会丢更新
```

它也不能守住多个字段之间的组合规则。例如 `balance` 和 `version` 必须一起更新，仅把两者分别声明 `volatile` 仍可能让观察者看到不一致组合。

选择 `volatile` 前要能完整说出：只有哪个字段、由谁写、由谁读、是否存在读改写、是否还有其他字段共同构成不变量。

## 7. synchronized：让同一监视器保护临界区

```java
class Counter {
    private int value;

    synchronized void increment() {
        value++;
    }

    synchronized int value() {
        return value;
    }
}
```

实例 `synchronized` 方法使用当前对象的**监视器（monitor）**。同一时刻只有一个线程能持有同一监视器执行相应临界区；释放锁与后续获取同一锁之间还建立 happens-before。

也可以锁一段代码：

```java
synchronized (lock) {
    checkAndUpdate();
}
```

### 7.1 锁对象身份决定是否真的互斥

```java
synchronized (new Object()) {
    // 每次都是新锁，线程之间并不互斥
}
```

若每次都创建不同锁对象，多个线程不会竞争同一监视器。分析同步代码时要画出“哪个状态由哪个稳定锁身份保护”。

### 7.2 所有访问路径要遵守同一规则

写方法加锁，读方法不加锁，仍可能读到没有同步保证的状态。对某项不变量的所有读写路径都要遵守同一锁或其他明确并发协议。

不要把 `public` 方法全加 `synchronized` 当作万能修复。锁范围过大会造成无关任务互相阻塞；锁范围过小又可能把一项业务操作拆开。临界区应该覆盖完整不变量，同时避免在持锁期间做长时间网络或磁盘等待。

## 8. ReentrantLock、原子类和并发集合各有用途

### 8.1 ReentrantLock 提供更灵活的锁操作

```java
lock.lock();
try {
    updateState();
} finally {
    lock.unlock();
}
```

它支持可中断获取、尝试加锁、超时、公平策略和多个 `Condition`。灵活性的代价是必须保证 `unlock()` 放在 `finally` 中。

普通互斥优先使用更简单、不易漏释放的 `synchronized`；真正需要高级能力时再用 `ReentrantLock`。选择依据是合同，不是“哪个性能一定更高”。

### 8.2 AtomicInteger 适合单个原子读改写

```java
AtomicInteger count = new AtomicInteger();
int next = count.incrementAndGet();
```

原子类可以完成单个变量的原子更新和比较交换。但多个原子变量之间仍可能有组合竞态。若业务要求“库存和版本一起变化”，不能只把两个 `int` 分别换成 `AtomicInteger`。

### 8.3 并发集合

`ConcurrentHashMap`、`BlockingQueue` 等类型提供特定并发合同：

- `ConcurrentHashMap` 支持并发查找和更新，但“先 get 再 put”的组合仍需使用 `compute`、`putIfAbsent` 等原子方法；
- `BlockingQueue` 可以在空或满时等待，适合生产者—消费者协作；
- `CopyOnWriteArrayList` 适合读多写极少的快照遍历，不适合高频写入。

“线程安全集合”只保证其 API 合同，不会自动保护元素内部对象，也不会替你完成跨多个集合的事务。

## 9. 减少共享通常比增加锁更简单

优先考虑：

- 不可变值；
- 每个任务自己的局部对象；
- 线程封闭状态；
- 通过消息或队列传递所有权；
- 构造完成后安全发布只读快照；
- 把复合状态封装在一个拥有锁和不变量的对象中。

如果没有共享写入，就不需要解决共享写入竞态。并发设计的第一问应该是“是否必须共享”，而不是“加哪一种锁”。

### 9.1 安全发布

一个对象创建完成后，要通过有同步保证的方式交给其他线程，例如：

- 放入正确使用的并发集合；
- 在启动线程前准备好并通过任务捕获；
- 通过 `volatile`/锁保护的引用发布；
- 使用正确构造的不可变对象和 final 字段语义。

把 `this` 在构造期间注册给其他线程，可能让外部看到半初始化对象。构造器章节中的“不泄漏 this”在并发环境里尤其重要。

## 10. 死锁、饥饿和活锁：线程没有前进的几种方式

### 10.1 死锁

线程 A 持有锁 1 等锁 2，线程 B 持有锁 2 等锁 1，两者永久等待：

```text
线程 A：持有 deviceLock → 等待 auditLock
线程 B：持有 auditLock  → 等待 deviceLock
```

常见预防方式：

- 全局规定锁获取顺序；
- 缩小同时持有多个锁的范围；
- 不在未知回调中持锁；
- 使用超时尝试锁并明确失败策略；
- 用更高层并发结构减少手工锁。

### 10.2 饥饿

某个线程长期得不到 CPU、锁或队列资源，其他任务却一直前进。公平锁可能缓解某些锁饥饿，但会有吞吐成本，也不能解决全部资源不公平。

### 10.3 活锁

多个线程都在不断响应对方、主动让步，却始终无法完成工作。它们不是阻塞不动，而是一直做无效动作。重试加入随机退避、上限和幂等规则，可以减少部分活锁风险。

### 10.4 诊断要看进展，而不仅看线程状态

线程 dump、锁拥有者、等待位置、队列长度和“最后成功时间”共同说明系统是否有进展。一次 `Thread.State` 快照不足以证明死锁或性能问题。

## 11. Executor：把任务提交和线程管理分开

直接为每个任务手动创建平台线程，调用方要负责命名、数量、排队和关闭。`Executor` 把“提交任务”与“怎样执行”分开：

```java
ExecutorService executor = Executors.newFixedThreadPool(4);
executor.execute(() -> process(order));
```

### 11.1 Runnable 和 Callable

```java
Runnable action = () -> sendNotification();
Callable<WorkOrder> query = () -> repository.findRequired(id);
```

- `Runnable.run()` 没有返回值，也不能在签名中抛任意受检异常；
- `Callable.call()` 返回结果，并允许抛异常。

`execute(Runnable)` 只提交任务；`submit(...)` 返回 `Future`，让调用方观察结果、失败或取消。

### 11.2 线程池不仅是“复用线程”

固定平台线程池还包含三个重要边界：

- 最大有多少工作线程；
- 任务来不及处理时怎样排队；
- 队列和线程都到上限时怎样拒绝。

便利工厂可能隐藏无界队列或动态增长策略。生产代码需要根据容量和失败政策审查 `ThreadPoolExecutor` 的核心线程数、最大线程数、队列、线程工厂和拒绝策略。

线程池把压力排进无限队列，并没有消除压力，只是把失败推迟成内存增长和高延迟。

## 12. Future：一次异步计算的结果协议

```java
Future<WorkOrder> future = executor.submit(query);
WorkOrder order = future.get();
```

`get()` 会等待任务结束。任务抛出的异常会被包装在 `ExecutionException` 中，真正原因在 `getCause()`。

一次任务至少有四种终局需要区分：

- 成功，得到结果；
- 失败，得到异常原因；
- 被取消；
- 等待结果的线程自己被中断。

### 12.1 超时只限制等待者

```java
future.get(2, TimeUnit.SECONDS);
```

超时会让等待方得到 `TimeoutException`，但不会自动保证后台任务已经停止。调用方要决定是否调用 `cancel(true)`、是否允许任务继续、是否需要关闭底层资源。

### 12.2 cancel 是协作请求

```java
boolean requested = future.cancel(true);
```

返回 `true` 表示取消请求被接受到相应状态，不等于外部数据库查询或网络请求已经瞬间停止。任务、驱动和资源 API 必须协作响应中断或取消。

### 12.3 不观察 Future 会让异常看似消失

通过 `submit` 提交的任务若失败，而代码从不调用 `get()`，异常可能只保存在 Future 中。系统表面没有堆栈，任务实际已经失败。每个异步任务都要有结果所有者：谁等待、谁记录失败、谁决定重试或降级。

## 13. ExecutorService 也有生命周期

执行器会持有工作线程和队列，不关闭可能让进程无法正常退出：

```java
try (ExecutorService executor = Executors.newFixedThreadPool(4)) {
    Future<String> future = executor.submit(() -> "done");
    System.out.println(future.get());
}
```

在支持 `AutoCloseable` 的当前 JDK 中，可以用 try-with-resources。显式生命周期通常包括：

1. 停止接收新任务；
2. 等待已提交任务在合理时间内完成；
3. 超时后请求中断；
4. 再次等待并记录仍未结束的任务。

不要在每次业务方法调用中创建一个线程池又不关闭，也不要关闭由外部容器拥有的共享执行器。资源所有权必须和文件流一样明确。

## 14. 虚拟线程：让大量等待型任务拥有自己的线程

平台线程通常对应一个操作系统线程，数量昂贵。虚拟线程由 JDK 调度，许多虚拟线程可以轮流运行在较少的平台载体线程上。当虚拟线程执行支持的阻塞 I/O 时，它可以卸载，让载体线程去执行别的虚拟线程。

```java
Thread thread = Thread.ofVirtual().start(() -> loadWorkOrder(id));
thread.join();
```

也可以每个任务启动一个虚拟线程：

```java
try (ExecutorService executor =
        Executors.newVirtualThreadPerTaskExecutor()) {
    Future<WorkOrder> future = executor.submit(() -> loadWorkOrder(id));
    WorkOrder order = future.get();
}
```

### 14.1 虚拟线程提升吞吐，不缩短单次计算

虚拟线程适合大量主要等待 I/O 的并发任务，例如每个请求要等待数据库或 HTTP。它们不会让一个 CPU 密集算法运行得更快，也不会创造更多 CPU 核。

官方的核心表述是：虚拟线程用于规模和吞吐，不是用于降低单个任务延迟。是否提升整体系统还要看数据库连接、远端限流、内存和其他资源瓶颈。

### 14.2 不要池化虚拟线程

虚拟线程本身很便宜，通常让每个并发任务对应一个虚拟线程，不用建一个固定大小的“虚拟线程池”。真正稀缺的是数据库连接、远端 API 配额或文件句柄，应直接用连接池、信号量或限流器约束这些资源。

```java
Semaphore permits = new Semaphore(20);
```

线程数量和资源并发上限是两个不同问题。

### 14.3 虚拟线程仍然是 Java 线程

它仍然遵守：

- JMM 和 happens-before；
- `synchronized`、锁和原子性规则；
- 中断与取消合同；
- `ThreadLocal` 语义；
- 异常、堆栈和调试规则。

把平台线程换成虚拟线程，不会修复共享可变状态竞态、死锁或错误超时。

### 14.4 JDK 25 的 pinning 边界

虚拟线程运行时会挂载到载体平台线程。若某些阻塞场景不能卸载，称为 **pinning**，会占住载体并降低伸缩性。

从 JDK 24 起，普通 `synchronized` 监视器阻塞已经不再造成过去那类常见 pinning。JDK 25 官方文档仍指出，虚拟线程运行原生方法或 Foreign Function 调用时可能被固定；JFR 的 `jdk.VirtualThreadPinned` 事件可用于观察剩余情况。

这部分是版本敏感知识。以后升级 JDK 时应查对应版本官方虚拟线程指南，不要继续照搬早期“见到 synchronized 就换 ReentrantLock”的旧建议。即使不会 pin，持锁做长 I/O 仍可能造成业务锁竞争，所以锁范围依然要小。

### 14.5 ThreadLocal 要考虑数量

虚拟线程可能达到很大数量。给每个线程缓存昂贵对象会放大内存占用；把数据库连接或大型缓冲永久放进 `ThreadLocal` 也可能绕过资源管理。线程上下文只保存真正必要、生命周期清楚的数据，并审查框架在虚拟线程下的使用方式。

这一节必须掌握：虚拟线程适合大量阻塞等待任务，目标是提高吞吐；不要池化虚拟线程，但要单独限制稀缺外部资源；它不改变共享状态和取消规则。

## 15. 结构化并发先理解目标，不急着依赖预览 API

一个请求可能并发查询设备、负责人和 SLA。三个子任务共同属于一个父操作：只要关键任务失败，其他任务应该取消；父操作结束前，子任务不应悄悄遗留。

**结构化并发（structured concurrency）**希望让这种父子生命周期在代码结构中清楚体现：

```text
父任务开始
├── 查询设备
├── 查询负责人
└── 查询 SLA
父任务统一等待、失败和取消
```

具体 JDK API 在部分版本中仍可能是预览特性，需要编译和运行开关，也可能继续演进。当前先掌握目标：相关任务应有共同作用域、统一错误传播和确定结束；真正采用时按项目锁定的 JDK 官方文档确认 API。

## 16. 并发测试为什么容易不可靠

写两个线程然后 `sleep(100)`，本机碰巧复现一次竞态，不能证明测试稳定。机器负载和调度变化后，测试可能忽红忽绿。

更可靠的做法是使用：

- `CountDownLatch` 控制多个线程到达同一阶段；
- `CyclicBarrier` 或 `Phaser` 协调交错；
- 有界超时，避免测试永久挂起；
- 固定任务数量和可验证后置条件；
- 重复运行用于放大概率，但不能替代确定性控制；
- 线程安全的结果收集器。

例如验证计数器时，不只看最后有没有异常，而要知道提交了多少次增量，等待所有任务完成，再断言最终值与预期一致。

### 16.1 超时不是越短越好

超时太短会在慢机器上误报，太长会让真正死锁拖慢整套测试。使用相对宽松的测试上限，同时用 latch 精确控制目标交错；性能结论则使用专门基准和观测，不靠单元测试墙钟时间。

## 17. 诊断并发故障的顺序

### 17.1 结果偶尔少一部分

检查共享计数、集合或 check-then-act；确认所有任务是否真的等待完成；查找未同步读写和被吞掉的 Future 异常。

### 17.2 进程不退出

检查执行器是否关闭、是否仍有非 daemon 平台线程、任务是否永久阻塞、关闭流程是否吞中断。

### 17.3 所有线程像是卡住

取得线程 dump，查看每个线程堆栈、锁拥有者和等待链；多次采样确认是否有进展。死锁通常能从循环锁等待看出。

### 17.4 超时后任务仍占资源

检查超时是否只结束了等待、是否调用取消、底层阻塞 API 是否响应中断、连接和流由谁关闭。

### 17.5 换虚拟线程后仍然慢

检查真正瓶颈：CPU、数据库连接池、远端限流、锁竞争、队列、磁盘或内存。虚拟线程只降低等待期间占用平台线程的成本，不消除外部容量上限。

诊断时优先保留：任务 ID、线程名、开始/结束时间、队列长度、Future 终局、异常 cause 和资源指标。不要在日志中记录令牌或完整用户数据。

## 18. 本章掌握边界

必须掌握：

- 线程、任务、并发与并行的区别；
- `start`、`join` 和中断的基本语义；
- 原子性、可见性、happens-before 和竞态；
- `volatile` 只适合简单可见信号；
- `synchronized` 由同一监视器保护完整不变量；
- Executor、`Runnable`、`Callable`、Future 的职责；
- 超时不自动停止任务，取消是协作协议；
- 执行器需要明确关闭；
- 虚拟线程适合大量 I/O 等待，不适合拿来加速 CPU 计算。

见过即可：

- `ReentrantLock` 的高级能力；
- 原子类与并发集合；
- 死锁、饥饿、活锁；
- 安全发布和结构化并发目标；
- JFR 的虚拟线程事件。

需要时查询：

- JMM 的完整同步规则；
- `ThreadPoolExecutor` 参数和拒绝策略；
- 各并发集合的复合原子操作；
- 当前 JDK 的虚拟线程 pinning 和结构化并发状态；
- 性能基准、锁分析和生产容量调优。

整章可以记成一句话：先把任务、执行资源和共享状态分开；用明确同步边维护不变量，用执行器管理任务生命周期，用中断与 Future 表达取消和失败；等待型高并发可用虚拟线程，但任何线程模型都不能替你解决共享状态与外部资源上限。
