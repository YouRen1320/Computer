# uni-app：设备能力、离线、测试与发布

## 1. 设备能力是可能失败、被拒绝和不一致的外部端口

扫码、相机、相册、定位和上传不只是一个函数调用。它们依赖：

- 当前平台是否支持；
- 系统硬件与开关；
- 应用/小程序权限声明；
- 用户是否同意；
- 宿主版本；
- 前后台和页面生命周期；
- 网络、临时文件与服务端。

因此结果不能只建模成“有数据/没数据”，要区分 unavailable、denied、cancelled、failed 和 success。

## 2. 条件编译在构建时选择代码

概念：

```text
源代码包含 MP-WEIXIN / APP / H5 分支
  → 构建某一目标
  → 不属于目标的分支从产物移除或替换
```

它适合平台 import、配置和确实不同的实现。宏写错可能让目标分支根本没进入产物。

条件编译不是运行时 if，也不能证明设备当前有相机或用户已授权。

## 3. 平台识别和能力检测解决不同问题

```text
平台识别：正在微信小程序运行
能力检测：当前基础库是否有某 API
权限状态：用户是否授予
设备状态：硬件/系统服务是否可用
```

即使同为微信小程序，不同基础库和设备也可能有差异。能力检测应靠近平台适配器，UI 消费统一结果。

不要用 User-Agent 或平台名称推断所有能力。

## 4. 平台适配器统一业务意图，不伪造完全相同能力

```ts
type ScanResult =
  | { status: 'success'; rawValue: string }
  | { status: 'cancelled' }
  | { status: 'denied'; canOpenSettings: boolean }
  | { status: 'unavailable'; reason: string }
  | { status: 'failed'; safeCode: string }
```

微信、App、H5 各自实现 `ScannerPort`。统一的是“请求扫描并返回可理解状态”，不是强迫 H5 提供它做不到的原生体验。

降级也是合同：手输设备码、从相册选择、跳系统设置或明确不可用。

## 5. 权限状态机不能无限弹窗

```text
unknown
  → request（由用户动作触发）
  ├── granted
  ├── denied-can-ask-again
  ├── denied-open-settings
  └── unavailable
```

进入页面就反复申请相机/定位会破坏体验并可能违反平台规则。先解释用途，在用户点击相应功能时请求。

拒绝后显示可继续的替代路径，不把拒绝当异常用户。

## 6. 业务同意和系统权限是两层

系统允许定位，不代表应用可把位置用于任意目的；隐私政策同意也不代表系统权限已授予。

```text
业务必要与透明说明
  + 用户针对目的的选择
  + 平台/系统权限
  + 服务端访问控制与保留策略
```

位置应可选时不要设成报修必填。精度只收集业务所需，不默认保存完整轨迹。

## 7. 扫码成功仍要验证内容

二维码可能是：

- FactoryCare 设备码；
- 普通网址；
- 恶意超长字符串；
- 其他租户设备；
- 已停用或伪造标签。

客户端只做长度/格式初筛，后端按签名、业务映射、租户和设备状态确认。不要直接把码中的 URL 交给后端抓取或客户端自动打开。

## 8. 临时图片文件不是永久附件

选择/拍摄后得到的路径可能只在临时目录或当前会话有效：

```text
选择图片
  → 本地临时文件
  → 预览/压缩/校验
  → 上传到受控对象存储
  → 得到 attachmentId
  → 创建工单时绑定 attachmentId
```

不要把本机临时路径保存到后端，其他设备无法访问。上传成功也不代表附件已与工单绑定。

## 9. 上传状态要按每个文件建模

```text
selected → validating → uploading → uploaded
                         ├── cancelled
                         └── failed-retryable / failed-final
```

每个文件记录本地 ID、进度、attachmentId、错误和重试次数。用户可删除、取消、重试；页面总体提交要说明允许部分成功还是必须全部完成。

## 10. uploadFile 的传输成功不等于业务成功

与 request 一样，要检查 HTTP 状态并解析响应字符串/JSON。还要验证：

- 服务端确认 MIME、大小和安全扫描；
- attachmentId 属于当前用户/租户；
- 预签名 URL 的范围和过期；
- 上传内容不可直接作为可执行 HTML；
- 文件名不用于构造任意路径。

日志不能记录临时路径中的隐私或上传凭据。

## 11. 上传完成但工单提交失败是正常可恢复状态

可选设计：

- 附件先进入未绑定状态，有短期保留并定时清理；
- 重试创建时复用已有 attachmentId；
- 客户端显示“照片已上传，工单未创建”；
- 提交使用幂等键，防止重复工单；
- 后端绑定时再次校验所有权。

不能看到提交失败就重新上传全部文件，既浪费流量也制造孤儿对象。

## 12. 定位结果必须包含坐标语义

经纬度需要说明：

- 坐标系；
- 精度；
- 获取时间；
- 是否用户确认；
- 来源/平台；
- 允许用途。

不同地图/平台坐标系直接混用会产生位置偏移。位置失败时工单核心流程若可继续，应允许手输厂区/设备或跳过。

## 13. 离线队列保存的是业务命令，不是任意 HTTP 请求

```json
{
  "commandId": "local-uuid",
  "type": "CreateRepairReport",
  "schemaVersion": 1,
  "tenantId": "tenant-A",
  "idempotencyKey": "stable-key",
  "createdAt": "...",
  "payload": {},
  "attempt": 0,
  "nextAttemptAt": "..."
}
```

命令说明用户意图，便于升级、显示和重放。不能把过期 Authorization header、任意 URL 和临时文件路径永久塞进队列。

## 14. 先持久化命令，再承诺“已保存待同步”

```text
用户提交
  → 验证本地草稿
  → 可靠写入队列
  → 写入成功后才显示“已保存待同步”
  → 调度器尝试发送
```

若先显示成功再写存储，进程被杀会丢命令。若网络请求和本地写入并行，也可能产生成功请求却留下一条待重放命令。

需要设计发送前状态和崩溃恢复，依赖服务端幂等吸收不确定重复。

## 15. 幂等键必须在命令创建时生成并稳定保存

同一离线命令每次重放使用同一个 key。若每次发送都生成新 key，服务端会把它当不同意图创建多张工单。

服务端将 key 与租户、操作、请求 hash 绑定并保存首次结果。客户端收到重复成功时复用原 resourceId，而不是认为“409 就失败”。

## 16. 调度器要有状态、锁和重试预算

```text
pending
  → sending
  ├── succeeded
  ├── retry-wait
  ├── blocked-auth
  ├── conflict-needs-user
  └── dead-letter
```

防止前后台、多个页面或多个实例同时重放同一命令。队头毒消息不应永远阻塞后续独立命令；有顺序依赖的同一工单操作则不能任意越过。

## 17. 失败分类决定能否自动重试

| 类别 | 动作 |
| --- | --- |
| 断网、超时、部分 5xx | 有限退避重试 |
| 401 | 暂停队列，统一恢复身份 |
| 403 | 不重试，提示无权限 |
| 400/字段校验 | 要用户修复 |
| 409/version 冲突 | 取最新事实，让用户决定 |
| 429 | 按 Retry-After 和预算 |
| schema 不支持 | dead-letter/升级处理 |

自动重试使用指数退避和抖动，有次数/总时长上限。手动重试也不能绕过上限制造请求风暴。

## 18. UI 不能只显示一个“正在同步”布尔值

用户需要看到：

- 本地待同步数量；
- 当前上传/创建进度；
- 哪条需要重新登录；
- 哪条发生冲突；
- 哪条永久失败以及如何编辑/删除；
- 成功后对应服务端工单 ID；
- 数据是否可能过期。

删除队列命令是用户数据操作，需要确认其影响和附件清理。

## 19. 缓存需要版本、身份和新鲜度

```text
cache key + schema version + user/tenant + savedAt + expiresAt + data
```

命中不代表可用。切租户/登出清理，发布升级迁移/丢弃旧 schema，存储配额不足要有降级。

离线显示缓存时明确“最后更新时间”，不能把旧工单状态呈现成实时事实。

## 20. 分包按用户旅程减少首包

```text
主包：启动、登录、首页、必要公共依赖
分包：报表、历史详情、管理功能等后续旅程
```

按功能旅程切，而不是按文件后缀。公共依赖可能被提升回主包；循环跨包依赖会破坏边界。

分包只是下载/加载组织，不保证代码执行快；还要看启动 CPU、渲染和网络。

## 21. 预加载和懒加载都要基于真实下一步

预加载过多会和首屏资源争抢；懒加载过碎会让用户点击后等待。

```text
测量用户常见路径
  → 找下一步高概率且有等待的分包
  → 在空闲/合适网络预加载
  → 观察首屏和下一页是否真的改善
```

不要因为 API 存在就预加载所有分包。

## 22. 资源预算包含包体、图片、字体和运行成本

- 图片按显示尺寸压缩，上传原图与缩略图分开；
- 图标避免整库引入；
- 中文字体体积很大，谨慎打包；
- 检查重复依赖和 source map；
- 控制主包/分包上限；
- 测量冷启动、可交互时间和页面进入。

骨架屏提前显示不代表按钮已可操作。性能完成定义要以用户任务为准。

## 23. 条件编译的每个活分支都要构建和运行

CI 可构建所有目标，发现语法和 import 问题；至少代表目标还需：

- 开发工具运行；
- 真机运行；
- 权限拒绝/取消；
- 网络和上传；
- 前后台切换；
- 不同系统/版本矩阵。

死分支几年没编译，不能因另一个目标通过就声称跨端可用。

## 24. 测试按纯逻辑、组件、宿主和真机分层

```text
纯函数：解析、reducer、重试分类
组件：状态呈现、事件、表单
平台适配器：按真实合同 Mock success/denied/cancelled
目标自动化：页面和平台集成
真机：权限、相机、扫码、定位、网络、后台恢复
```

Mock 不能只实现希望中的 success。宿主错误码、回调顺序和取消行为要来自官方合同/真机记录。

## 25. 真机与开发工具差异要保留最小证据包

记录：

- 平台、系统、设备型号；
- 宿主/基础库/开发工具/构建版本；
- 应用版本和 commit；
- 权限初始状态；
- 网络条件；
- 精确步骤、时间和第一条错误；
- 脱敏日志、截图/录屏；
- 是否可在另一个设备复现。

“我手机不行”不足以交给别人定位。

## 26. 网络调试要关联客户端、网关和后端

使用 requestId/traceId 对齐：

```text
页面动作
  → uni.request 开始/结束
  → 平台网络日志
  → 网关 access log
  → Spring trace
  → 数据库/Outbox 事实
```

客户端日志脱敏，不记录 Token、位置、图片 URL 凭据和工单正文。source map 必须与具体版本对应，否则产物行号会映错源码。

## 27. 隐私工程从数据清单开始

对每类数据记录：

- 收集字段和精度；
- 目的；
- 触发用户动作；
- 传给哪些服务/SDK；
- 本地和服务端保存位置；
- 保留/删除；
- 权限拒绝后的替代；
- 日志和监控是否采集。

平台隐私声明必须与代码和 SDK 实际行为一致，审核通过后也要持续防漂移。

## 28. 第三方 SDK 也是数据流的一部分

地图、崩溃监控、推送和统计 SDK 可能在启动时收集设备信息。引入前检查：

- 真正需要哪些能力；
- 初始化时机和同意边界；
- 收集字段、目的、地域和保留；
- 权限与平台声明；
- 可否关闭/延迟；
- 版本与安全更新；
- 删除/撤回路径。

“依赖库自己收集”不能免除应用责任。

## 29. 发布链应把 commit、环境、产物和平台版本关联起来

```text
确定 commit + lockfile + SDK/CLI 版本
  → 干净、可复现构建
  → 生成带版本标识的产物和 source map
  → 预览/体验版真机验证
  → 提交平台审核
  → 小范围/灰度发布
  → 监控错误、启动、关键旅程
  → 扩大或回退
```

预览成功、审核通过和用户已收到版本是不同事实。

## 30. 版本不只是用户看到的字符串

至少关联：

- 业务版本号；
- 平台构建号；
- commit；
- 构建时间/流水线；
- 环境；
- source map；
- 后端 API/schema 兼容范围；
- 隐私声明/审核提交版本。

错误监控没有这些关联，就无法知道哪个源码对应线上崩溃。

## 31. 灰度发布要有指标、停止条件和回退对象

灰度前定义：

- 谁进入样本；
- 关键成功率/崩溃率/启动时间；
- 最小观察时间；
- 何时扩大；
- 何时停止/回退；
- 数据/API 是否向后兼容；
- 回退的是客户端、配置还是后端。

移动/小程序客户端不能保证所有用户立即降级，所以服务端要支持一段版本兼容期。

## 32. 监控要能看到失败阶段而不泄露数据

事件可包含：

- app/build/平台版本；
- 页面和操作名；
- 安全错误码；
- requestId；
- 权限状态类别；
- 网络类型大类；
- 耗时和结果。

不含：完整二维码、位置、Token、Cookie、照片链接凭据、表单正文。没有错误报告也可能是监控未初始化或用户没进入功能，要结合覆盖和使用量解释。

## 33. FactoryCare 报修端的完整流程

```text
扫码/手输设备
  → 后端确认设备与租户
  → 编辑表单与可选位置
  → 选择/上传附件
  → 在线幂等提交或离线持久命令
  → 获得工单 ID
  → 查询/接收进度
  → 冲突、权限和失败都有可恢复 UI
  → 发布版本与服务端 trace 可关联
```

每个箭头都是边界，成功主线之外至少要设计拒绝、取消、断网、重复和版本漂移。

## 34. 这篇的整体地图

```text
平台适配器
  → 能力检测 + 权限状态机 + 正式降级
  → 扫码/上传/定位结果归一化
  → 离线业务命令稳定持久化
  → 幂等重放 + 分类重试 + 冲突人工处理
  → 分包/缓存/资源预算按真机基线优化
  → 纯逻辑、组件、宿主、真机分层验证
  → 隐私清单、可追溯构建、灰度和回退闭环
```

必须掌握：条件编译不等于能力检测；拒绝、取消和失败不同；临时文件不等于附件；离线命令必须稳定幂等；409 不能无限重试；模拟器通过不能代替真机；平台声明必须与实际数据流一致；客户端回退受分发限制。

具体平台宏、权限 API、包体上限和审核表单会变化，真正实施时查询当前 uni-app 与各目标平台官方文档。
