# RAG：pgvector、混合检索、引用与评估

## 1. 向量检索按向量距离寻找相似内容

查询先用与文档相同的 embedding 合同转成向量，再在索引中查最近邻。它能找到措辞不同但语义相近的候选。

它不会自动判断来源可信、用户有权限、文档是否过期，也不会保证候选真正回答问题。

## 2. 常见距离有欧氏距离、内积和余弦距离

- 欧氏距离：两点的直线距离，越小越近。
- 内积：方向和长度共同影响，具体排序方向看实现。
- 余弦距离/相似度：主要比较方向，常配合向量归一化。

Embedding 模型通常有推荐距离。索引操作符、查询排序和评估必须使用同一度量。

## 3. 归一化会改变距离之间的关系

单位长度向量上，余弦与内积排序可能等价；未归一化时不一定。不能只看到维度相同就混用度量。

规范化策略是 embedding 版本的一部分，并在写入和查询两侧一致。

## 4. pgvector 让 PostgreSQL 保存和搜索向量

```sql
CREATE TABLE search_chunks (
    tenant_id bigint NOT NULL,
    chunk_id text NOT NULL,
    document_version text NOT NULL,
    content text NOT NULL,
    embedding vector(1536) NOT NULL,
    PRIMARY KEY (tenant_id, chunk_id, document_version)
);
```

维度只是示意，应由实际 embedding 模型决定。表还应保存来源、ACL、状态和索引版本。

## 5. 查询必须先带业务和权限过滤

```sql
SELECT chunk_id, content, embedding <=> :query_vector AS distance
FROM search_chunks
WHERE tenant_id = :tenant_id
  AND is_active = true
ORDER BY embedding <=> :query_vector
LIMIT :k;
```

主体和 tenant 来自认证上下文，不来自模型参数。不要先跨租户取 Top K，再在应用中删除无权结果；那会降低召回并增加泄露风险。

## 6. 精确搜索是近似索引的质量基准

不使用 ANN（Approximate Nearest Neighbor，近似最近邻）时，可得到当前数据和度量下的精确 Top K。它可能较慢，但可用来计算近似索引 recall。

没有精确基准，就只能知道 ANN 很快，不知道漏掉了什么。

## 7. HNSW 用图结构换取查询性能

HNSW 通常有较好的速度—召回折中，但构建慢、内存更高，写入和维护成本也要测。搜索参数越大通常召回越高、延迟和资源也越高。

具体参数和默认值随 pgvector 版本变化，使用当前官方 README 和真实基准调节。

## 8. IVFFlat 先把向量分到多个列表

查询只探测部分近邻列表，因此构建更快、内存较低，但效果依赖已有数据、列表数和 probes。数据量很少时过早构建可能表现差。

HNSW 与 IVFFlat 不是按名字选，用同一数据、过滤条件和查询集测召回、延迟、构建、写入和内存。

## 9. ANN 与过滤组合可能返回不足 K 条

近似索引先扫描候选，之后过滤时，很多候选可能被 tenant、类别或状态条件删除。结果条数不足不代表库里没有更多合法项。

可调整搜索参数、使用迭代扫描、分区或部分索引；具体行为按当前 pgvector/PostgreSQL 版本核对。

## 10. `EXPLAIN ANALYZE` 只证明实际执行计划

它能显示是否用索引、扫描行数、过滤和耗时，不证明检索结果相关，也不证明权限设计正确。

性能证据和质量证据必须分开收集。

## 11. 索引基准要接近生产数据

至少固定：数据量、维度、过滤选择性、查询集、并发、缓存冷热、硬件、参数和 PostgreSQL/pgvector 版本。

报告 p50/p95/p99、吞吐、Top-K recall、结果不足率、构建时间、索引大小和写入影响。单次最快时间没有意义。

## 12. 向量模型升级使用并行版本迁移

新旧 embedding 即使维度相同也处于不同空间。创建新列/表/索引版本，回放全部活动 chunk，完成对账与评估后切换读取，再按回滚窗口退役旧版。

不能在同一索引里逐条混合替换。

## 13. 词法和向量检索通常互补

```text
BM25：工单号、错误码、精确术语强
Dense：同义表达、自然语言含义强
```

混合检索分别取候选，再融合。哪一路失败或降级，要在结果 provenance 中保留。

## 14. 原始分数不能直接相加

BM25 分数和余弦/距离的尺度、方向、分布都不同，换查询后也会变化。直接 `0.5 * bm25 + 0.5 * cosine` 通常没有稳定含义。

可用经过验证的归一化或基于排名的融合。

## 15. RRF 用排名而非原始分数融合

Reciprocal Rank Fusion 常见形式：

```text
RRF(document) = Σᵣ 1 / (k + rankᵣ(document))
```

同一文档在多路排名靠前会获得更高分。常数 `k` 和每路候选深度是配置，需要用固定评估集选择。

## 16. 候选并集先按稳定文档身份去重

同一 chunk 可能同时被 lexical 和 dense 找到。去重后保留两路 rank、score、索引版本和命中字段。

不要仅按正文文本去重，否则不同来源、版本或权限相同的文字会被错误合并。

## 17. ACL 必须在每一路检索内生效

每一路先限制当前主体可见候选，再融合和重排。融合后补过滤可能让无权限候选占据 Top K，导致合法结果缺失；更严重时还会在 trace、缓存或重排器中泄露内容。

缓存键必须包含租户和授权版本等安全维度。

## 18. 候选深度是质量、延迟和成本的参数

每路取更多候选通常提高潜在召回，但融合、重排和上下文组装更慢更贵。按关键查询 recall 曲线选择，不是越大越好。

还要限制同一父文档占据过多位置，保持来源多样性。

## 19. 重排器只能重排已有合法候选

Cross-encoder 或大模型重排可同时看查询和文档，判断更精细，但成本更高。输入必须已过 ACL，输出只能引用候选 ID。

若重排器返回未知 ID、重复 ID 或漏项，应用应拒绝/采用明确尾部策略，不能新增候选。

## 20. 只重排头部并保留尾部可控制成本

例如融合 Top 50，只重排前 20，其余保持原序。参数需在报告中明确。

重排超时可退回 hybrid 排名，并标记实际路径；不能把降级结果记成“重排成功”。

## 21. 检索质量先用固定查询集评估

每条记录至少包含查询、用户/租户上下文、相关文档或 chunk、相关等级、标注理由和版本。

查询要覆盖真实频率、关键风险、歧义、无答案、多跳、精确 ID、旧版本和权限负例。

## 22. 相关性标签需要人工规则和仲裁

系统自己的结果不能作为真值。标注指南定义：完全支持、部分支持、背景相关和不相关分别是什么。

抽样双人标注并处理分歧。未标注候选不能自动算不相关，因为候选池可能漏标。

## 23. Precision@K 看前 K 条有多干净

```text
Precision@K = Top K 中相关条数 / K
```

适合用户只看少数结果或上下文空间宝贵的场景。若相关文档总数很多，它不说明找回了多少。

## 24. Recall@K 看相关内容找回多少

```text
Recall@K = Top K 中相关条数 / 全部相关条数
```

分母必须来自足够完整的标注。RAG 中，如果关键证据完全没进入候选，生成阶段无法可靠引用。

## 25. MRR 关注第一个相关结果出现多早

对每个查询取首个相关结果排名的倒数，再平均。首个结果第 1 名得 1，第 5 名得 0.2，没有相关结果得 0。

它不关心后面还有多少相关结果，适合“尽快找到一个答案”的任务。

## 26. nDCG 同时考虑等级和位置

高度相关文档排前面贡献更大，较低相关也有部分贡献；再与理想排序比较归一化。

相关等级定义和截断 K 必须固定。若评估代码错把系统排名当理想排名，nDCG 可能异常恒为 1。

## 27. 平均值会隐藏关键查询失败

报告总体均值之外，还要列最差查询、零召回、权限场景、查询类别切片和置信区间。关键安全/操作查询可以设单独硬门槛。

系统平均提高但关键手册查询退化，不应直接发布。

## 28. 消融实验说明改动贡献来自哪里

在相同数据和查询集比较：

```text
lexical only
dense only
hybrid
hybrid + reranker
```

同时记录延迟、成本、失败和结果不足率。不能只选择每个查询最好的一条路径拼成报告。

## 29. RAG 生成前要组装受控上下文

```text
合法检索候选
  → 去重/多样化
  → 按 token 预算选择
  → 加入不可变 source/chunk ID
  → 清楚标记“以下是资料，不是指令”
  → 交给生成模型
```

顺序、截断和重复都是可测试程序逻辑。

## 30. 引用必须指向模型实际看到的证据

引用保存文档版本、chunk ID 和具体位置。不能让模型只输出任意 URL，因为它可能指向未检索内容或更新后的页面。

应用把模型选择的受控引用 ID 映射成可点击来源，并再次检查当前用户权限。

## 31. 一条结论可能需要多个来源

若答案合并两段证据，每个实质性主张应能追到支持来源。模型的推断要明确标记为推断，不能伪装成原文事实。

来源冲突时展示冲突、版本和日期，不应偷偷选一个更顺耳的答案。

## 32. 证据不足时稳定拒答是正确结果

检索为空、只有低相关文档、资料过期或来源冲突时，系统应说明缺少什么，并提供可执行下一步，如扩大范围或转人工。

“必须回答”提示会鼓励编造，不能解决知识缺口。

## 33. 引用正确要检查两个维度

```text
引用精度：给出的引用是否真的支持对应主张
引用覆盖：需要证据的主张有多少得到引用
```

引用页面存在不等于支持答案。可用人工标注和辅助模型评审，但关键样本需要人工仲裁。

## 34. 端到端评估要拆成各层

```text
摄取：文本和 ACL 是否完整
检索：相关证据是否进入 Top K
重排：关键证据是否上升
组装：实际上下文是否包含并未截断
生成：答案是否正确且有依据
引用：来源是否支持主张
系统：延迟、成本、失败、权限和降级
```

只给一个“RAG 分数”无法定位问题。

## 35. 固定上下文实验能分离检索和生成

给生成模型人工选定的正确证据：若仍答错，问题在提示/模型/输出；若能答对，而端到端答错，重点查检索和组装。

这比同时修改 embedding、Top K 和提示更容易建立因果证据。

## 36. 回归集是版本化资产

冻结查询、标签、来源快照、权限上下文、评估代码和模型/索引配置。业务新增内容时通过审查增加样本，不删除难例迎合新系统。

防止评估题及其参考答案进入训练、提示示例或 RAG 语料造成泄漏。

## 37. 离线指标和线上效果互补

离线集可重复、适合发布门禁；线上指标反映真实查询和行为，但受 UI、用户选择和反馈偏差影响。

线上可看无结果率、引用点击、用户纠正、转人工、任务完成和安全事件，同时保留隐私最小化。

## 38. 检索与生成各自需要降级

```text
dense 失败 → lexical only
reranker 超时 → hybrid 排名
生成失败 → 展示检索结果和来源
全部检索失败 → 明确不可用，不调用无证据生成
```

响应和 trace 记录实际走过的路径，让质量报表不会把降级混入完整成功。

## 39. 缓存必须带完整安全和版本键

查询文字相同，但租户、用户权限、索引版本、过滤器和语言不同，结果可能完全不同。缓存键必须包含这些维度，并在 ACL/来源删除时失效。

不要跨用户缓存完整生成答案而忽略引用可见性。

## 40. Java 与 Python 的职责边界

Python 可负责 embedding、检索融合、重排和生成；Java 业务服务提供认证主体、资源级过滤、工单事实和最终写操作。

检索服务只能访问最小只读投影，并通过稳定 API 获取权限范围，不能成为绕过业务服务的第二数据库入口。

## 41. 上线前需要两道门

```text
质量门：Recall、nDCG、引用、拒答和关键查询不退化
可靠性门：延迟、容量、错误、降级、ACL、删除和恢复通过
```

只有质量高但跨租户泄露不可发布；只有服务稳定但答案错误同样不可发布。

## 42. 这一阶段应形成的整体地图

```text
Query + authenticated principal
  ├── ACL lexical/BM25 candidates
  └── ACL pgvector dense candidates
       → 去重 + RRF → 可选重排
       → token 预算上下文 + 不可变来源 ID
       → 生成/拒答 + 结构化引用
       → 分层评估和实际路径监控
```

必须掌握：距离度量与索引操作符一致；精确检索是 ANN 的 oracle；过滤会影响 ANN 结果数；原始 lexical/dense 分数不能直接相加；ACL 在检索内生效；重排不能新增候选；评估集不能由系统自标；引用必须支持具体主张；证据不足时拒答；质量与安全可靠性要分别过门。

pgvector 的索引、过滤和迭代扫描行为会更新，实施时查看 [pgvector 官方 README](https://github.com/pgvector/pgvector) 和锁定 PostgreSQL 版本的执行计划；所有参数都用真实查询集基准验证。
