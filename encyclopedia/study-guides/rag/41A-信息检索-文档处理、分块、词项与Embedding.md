# 信息检索：文档处理、分块、词项与 Embedding

## 1. RAG 之前先把检索系统单独看清

Retrieval-Augmented Generation（检索增强生成）先找资料，再让模型基于资料回答。若检索根本没找到正确证据，再好的提示也无法稳定补救。

因此先独立评估文档摄取、分块、词法检索和向量检索，再接生成。

## 2. 文档摄取把外部来源变成规范记录

```text
来源文件/API
  → 获取不可变快照
  → 识别媒体类型
  → 解析正文和结构
  → 清洗但保留证据位置
  → 附加来源、版本、时间、ACL
  → 分块和索引
```

每一步都需要输入版本、输出数量、错误和可追溯标识。

## 3. 来源快照是之后所有证据的根

网页、共享文档和文件可能随时改变。摄取时保存内容哈希、来源 URI、获取时间、外部版本和解析器版本。

回答引用必须指向模型实际看到的那个版本，而非事后更新后的同名页面。

## 4. Loader 只负责可靠获取，不负责全部语义

Loader 读取 PDF、Markdown、HTML、CSV 或 API。它应明确媒体类型、编码、超时、最大大小、重试和权限。

用文件扩展名猜类型不够；不可信文件还涉及压缩炸弹、恶意 PDF、路径穿越和解析器漏洞，应在隔离和资源限制下处理。

## 5. 解析结果要保留来源位置

正文不仅是一个大字符串。可靠规范记录可包含：

```text
document_id / version
source_uri / title
section_path
page / line / character span
normalized_text
ACL / tenant
parser_version / content_hash
```

这些字段让引用、删除、重建和权限审计成为可能。

## 6. PDF 文本抽取不总等于视觉阅读顺序

PDF 保存的是页面绘制指令，双栏、表格、页眉和扫描图会让抽取顺序错乱。扫描件还需要 OCR，OCR 会产生字符和布局误差。

关键文档要保留页码和原页面快照，抽样人工核对。表格可同时保存结构化表示与可读文本。

## 7. 文本清洗要克制

可以统一换行、去除确定的重复页眉页脚、规范 Unicode，但不要删除标题、编号、单位和否定词。

过度清洗可能让文本更“漂亮”，却破坏引用位置和业务含义。每个不可逆步骤应有版本和差异检查。

## 8. Unicode 外观相同不代表底层相同

全角/半角、组合字符、不可见空格和不同连字符会影响哈希、词项和搜索。规范化策略必须固定，并保存原始快照。

安全标识、路径和账号字段不能随意用面向自然语言的规范化处理。

## 9. CSV 公式注入和类型推断要防范

以 `=、+、-、@` 开头的单元格导出到电子表格后可能被执行为公式。展示/导出时按目标格式转义。

ID 前导零、长数字和日期不能任由工具自动猜类型。正文列与权限元数据按稳定键连接并校验基数。

## 10. 内容哈希只对确定的输入合同有意义

要明确哈希的是原始字节、解码文本还是规范化文本。解析器升级后同一原文件可能产生不同规范文本。

哈希能发现内容一致，不自动证明来源、权限和业务版本相同。不同租户的相同正文仍必须是不同授权记录。

## 11. 摄取必须可幂等重跑

同一 `(source_id, version, parser_version)` 重跑不应产生重复活动文档和重复 chunk。可先写暂存区，完整验证后原子切换活动版本。

部分失败应隔离到错误队列，不能让整批显示成功却静默漏文档。

## 12. 删除和权限撤销要传播到所有派生物

删除来源后，规范文档、chunk、向量、词法索引、缓存和评估快照都要按保留政策处理。可先写墓碑立即阻止查询，再异步物理清理。

权限撤销延迟应有明确上限和监控；这是安全 SLO，不只是后台清理性能。

## 13. Chunk 是为了检索而创建的文本单元

整份手册太长，直接 embedding 会稀释局部主题并超出模型输入；切得太碎又会丢上下文。因此 chunk 是“能够独立支持一类问题的最小可检索证据单元”。

它不是随便每 500 字切一次。

## 14. 优先按语义结构切分

标题层级、段落、列表、表格、代码块和页面是自然边界。先保留这些结构，再在过长部分按句子或 token 预算继续拆。

代码与其解释、表头与表行、警告与适用条件不应轻易分开。

## 15. Chunk 长度使用模型实际预算单位

字符数容易实现，但上下文和 embedding 限制通常按 token。设计目标可包含最小、目标和最大 token，并把标题路径和元数据也算入。

分块器使用的 tokenizer/估算器版本要记录。

## 16. Overlap 只解决边界附近的上下文

相邻 chunk 重叠少量句子，可减少答案刚好跨边界时的损失。但 overlap 会增加存储、embedding 成本、重复检索和上下文浪费。

不要让 overlap 穿过文档、权限或明显章节边界。

## 17. 父子块让检索粒度和阅读粒度分开

可以用短子块做精确检索，命中后扩展到父章节或邻居块提供上下文。返回时仍要保留子块为什么命中、扩展了哪些范围。

扩展不能越过 ACL 或文档版本。

## 18. Chunk ID 和版本决定能否更新与引用

仅用顺序号 `doc-1-chunk-7` 易因前面插入段落导致后续全部变化；仅用内容哈希则同样文字在不同位置会碰撞。

常见做法组合文档身份、版本、结构路径、位置和内容哈希。分块器升级应产生新索引版本，而非原地混用。

## 19. ACL 必须随每个 Chunk 继承

每个 chunk 携带租户、可见角色/用户、来源权限版本和敏感等级。查询时由数据库/检索层使用认证主体过滤，不让模型判断谁能看。

正文与 ACL 分开异步写时需要对账，避免“内容已上线，权限还没到”。

## 20. 词法检索从 Tokenization 开始

检索 token 是索引规则产生的词项，不一定等于大模型 token。中文分词、英文大小写、标点、词干和同义词都会改变结果。

索引时和查询时必须使用同一规范化版本，否则同样文字也匹配不到。

## 21. 倒排索引从词项快速找到文档

```text
"pump" → D1:位置[3,9], D4:位置[2]
"alarm" → D2:位置[1], D4:位置[6]
```

它避免逐文档扫描，还能保存词频和位置，用于短语、邻近和相关性评分。

索引更新需要新增、修改、删除和版本切换协议，不只是修改一个字典。

## 22. TF、DF 和 IDF 不要混淆

- TF：某词在当前文档出现多少或多重要。
- DF：包含该词的文档有多少。
- IDF：根据 DF 降低常见词权重。

把总词频误当文档频率会改变整个排名。公式有多种变体，必须记录具体实现和参数。

## 23. TF-IDF 提高局部常见、全局少见词的权重

直觉上，一个词在当前文档常见但在整个语料少见，更能区分这篇文档。

它适合解释基础相关性，但不理解同义表达和深层语义。公式平滑、长度归一化和查询词重复政策都影响分数。

## 24. BM25 对词频做饱和并考虑文档长度

一个词从出现 0 次到 1 次很重要，从 50 次到 51 次通常没那么重要。BM25 通过词频饱和和长度归一化体现这个直觉。

参数与分词/字段设置一起版本化。分数只在同一索引和查询下相对比较，不是跨系统统一概率。

## 25. 停用词、词干和同义词都有副作用

移除常见词可省空间，但否定词和领域短词可能非常关键。词干能匹配变体，也可能把不同词混在一起。同义词提高召回，也可能扩大歧义。

每项变化都用固定查询集做消融比较，不把它们当免费升级。

## 26. 字段权重应保留字段来源

标题命中通常比正文命中更强，可分别评分后组合。必须保留每个字段的词项统计和贡献，否则无法解释为什么某文档上升。

业务过滤与相关性评分分层：先保证可见和合法，再在候选中排序。

## 27. 词法检索擅长精确术语和标识符

工单号、错误码、设备型号、函数名和罕见术语通常适合 BM25/倒排索引。它的弱点是用户用完全不同说法表达同一含义。

这正是语义向量检索的互补位置。

## 28. Embedding 把一段文本变成固定维向量

模型把语义和用法压进向量。查询和文档在同一 embedding 空间中比较距离，语义相近但用词不同的内容也可能互相靠近。

Embedding 本身不是答案，也不能证明文档相关或可信。

## 29. Embedding 空间由一组版本共同定义

```text
provider + model ID + model snapshot/版本
+ 输入规范 + 维度 + 归一化策略
```

相同维度的不同模型向量也不能混合比较。升级模型需要重算或双索引迁移，并分别评估。

## 30. Canonical input 保证同一 Chunk 稳定向量化

明确 embedding 输入是否包含标题、章节路径、正文和哪些元数据，以及分隔符与规范化规则。不要今天只嵌正文、明天悄悄加标题却写进同一索引版本。

权限标签通常用于过滤，不应随意拼进自然语言向量。

## 31. 空文本、超长文本和非有限向量要拒绝

空白 chunk 没有检索价值；超长输入需在分块阶段解决；返回向量需检查数量、维度、所有元素有限和范数符合预期。

一批返回顺序必须与输入稳定关联，最好使用明确 item ID，而不只依赖数组位置。

## 32. 批量 Embedding 提高吞吐但扩大失败范围

批次越大，请求开销占比越小，但延迟、内存、输入上限和重试成本更高。动态批次仍要保留输入 ID、顺序和幂等写。

单个坏项导致全批失败时，可二分或隔离，但必须限制尝试次数。

## 33. 摄取流水线需要检查点和状态机

```text
discovered → fetched → parsed → chunked
  → embedding_pending → embedded → indexed → active
  └── retry_wait / permanent_failed / deleted
```

每个阶段记录输入版本和产物哈希。进程崩溃后从已确认检查点继续，而不是全部重做或跳过不确定项。

## 34. 写入索引要幂等并可对账

使用稳定 `(index_version, chunk_id)` 唯一键 upsert。活动索引中规范 chunk 数、向量数、词法记录数和 ACL 数应能对账。

任务成功但数量不一致必须报警，不能只看队列没有错误。

## 35. 限流、退避和成本护栏属于摄取设计

Embedding API 有吞吐与输入限制。worker 共享速率预算，按可重试错误退避并加抖动；设置每日/每批 token 与费用上限。

达到护栏时暂停并显示待处理量，而不是无限重试或悄悄丢数据。

## 36. 分块策略用真实问题集选择

准备用户真实提问和相关证据位置，比较不同 chunk 大小、overlap、标题附加、父子扩展下的召回、重复、上下文 token 和延迟。

没有查询集时，凭感觉选“500 token + 50 overlap”只是起始假设。

## 37. 摄取质量要按来源分别验收

PDF、Markdown、CSV、扫描件的失败模式不同。分别报告成功率、空页、乱码、表格恢复、标题路径、ACL 完整、重复和处理延迟。

抽样人工查看原始页面与规范文本的差异。

## 38. 可观测性必须能追到某个 Chunk 的来历

通过 chunk ID 能找到来源版本、页面/段落、解析器、分块器、embedding 模型、索引版本和 ACL。反过来也能从来源列出全部派生 chunk。

这叫数据血缘，是引用、删除、回滚和事故调查的基础。

## 39. 这一阶段应形成的整体地图

```text
来源快照
  → 安全解析/克制清洗
  → 规范文档 + 版本 + ACL + 血缘
  → 语义分块 + 稳定 chunk ID
  ├── 分词/倒排/BM25
  └── canonical input/Embedding
  → 版本化检索索引
```

必须掌握：检索错误不能靠生成掩盖；引用要指向实际快照；PDF/OCR 有布局误差；分块优先按结构；overlap 有成本；ACL 随每个派生物传播；索引和查询规范化一致；BM25 擅长精确术语；embedding 空间必须版本一致；摄取要幂等、可对账、可删除。

解析器、embedding 模型和分词器都会更新，具体限制以所用工具当前官方文档为准；任何升级都创建新版本并用固定查询集比较。
