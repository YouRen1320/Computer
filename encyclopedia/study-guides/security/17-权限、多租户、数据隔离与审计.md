# 权限、多租户、数据隔离与审计

## 1. 登录成功只证明身份，不代表可以访问所有数据

用户通过登录后，系统知道“你是谁”。接下来每次操作仍要判断：

- 你想做什么；
- 对哪个资源做；
- 资源属于谁或哪个租户；
- 当前业务状态是否允许；
- 是否还有时间、地点或组织范围限制。

```text
认证：这是技师 user-17
授权：user-17 能否分派 tenant-A 的 work-order-42？
```

授权不是在登录时做一次就结束，而是在受保护能力真正执行前，根据当前资源和上下文判断。

## 2. 权限规则可以写成“主体对资源执行动作”

一个清楚的授权问题通常包含：

```text
主体（subject） + 动作（action） + 资源（resource） + 上下文（context）
```

例如：

```text
主体：技师 user-17
动作：关闭
资源：工单 WO-42
上下文：属于 tenant-A、已分派给该技师、当前状态 IN_PROGRESS
```

只问“是不是 TECHNICIAN”遗漏了资源归属和状态；只问“是不是创建者”又可能遗漏管理员等合法能力。

## 3. RBAC 用角色打包一组权限

RBAC 是 Role-Based Access Control，意思是**基于角色的访问控制**。

```text
用户 → 角色 → 权限

张三 → TECHNICIAN → WORK_ORDER_READ、WORK_ORDER_PROGRESS
李四 → DISPATCHER → WORK_ORDER_ASSIGN
王五 → TENANT_ADMIN → USER_MANAGE、DEVICE_MANAGE
```

角色适合表达组织中稳定的职责，比给每个用户单独配置几十个权限更容易管理。

但角色不要直接变成“万能 if”：

```java
if (user.role() == ADMIN) {
    return true;
}
```

不同管理员可能只管理自己的租户，审计员只读不能修改。角色应映射到明确能力，再结合资源范围判断。

## 4. Permission 比角色更接近真实动作

角色是权限的集合，权限是系统能执行的能力。常见命名：

```text
WORK_ORDER_READ
WORK_ORDER_ASSIGN
WORK_ORDER_CLOSE
USER_INVITE
AUDIT_READ
```

业务代码若直接依赖 `ADMIN`，组织角色一变化就要修改大量规则。依赖 `WORK_ORDER_ASSIGN` 更稳定：新建“值班主管”角色时，只需给它组合所需权限。

```text
角色回答：这个人在组织中是什么职责？
权限回答：系统允许他执行什么动作？
```

## 5. ABAC 根据属性和上下文判断

ABAC 是 Attribute-Based Access Control，意思是**基于属性的访问控制**。它会考虑：

- 用户属性：tenantId、departmentId、clearance；
- 资源属性：ownerId、tenantId、status、sensitivity；
- 环境属性：当前时间、来源网络、是否完成二次认证。

例如：

```text
允许关闭工单，当且仅当：
  用户拥有 WORK_ORDER_CLOSE
  且 用户 tenantId == 工单 tenantId
  且 工单 assignedTechnicianId == 当前用户 id
  且 工单状态 == IN_PROGRESS
```

实际系统常用 RBAC 表达粗粒度职责，再用 ABAC 做资源和业务边界，并非二选一。

## 6. 关系型授权关注“主体与资源是什么关系”

有些规则最自然的表达是关系：

- 用户是工单创建者；
- 技师是该工单被分派者；
- 经理管理该设备所属部门；
- 用户是某项目成员。

这类思路常称 ReBAC（Relationship-Based Access Control）。不必为了术语建立复杂平台，但要意识到“拥有角色”与“对具体资源有关系”是两层信息。

## 7. URL、方法和数据对象是三道不同边界

授权常分三层：

```text
URL 层：是否能进入这一类请求
  ↓
方法层：是否能调用这一项业务能力
  ↓
数据层：是否能访问这一条具体记录
```

例如：

- `/api/admin/**` 只让管理类权限进入；
- `assignWorkOrder()` 要求分派权限；
- 查询 SQL 必须限定当前租户，且规则检查工单所属范围。

只保护 URL 不够，因为方法可能被别的入口调用；只保护方法名也不够，因为错误查询可能已经把其他租户数据加载出来。

## 8. 默认拒绝让遗漏变成显式失败

规则应该是：

```text
命中明确允许条件 → 允许
否则 → 拒绝
```

而不是：

```text
命中几个禁止条件 → 拒绝
其他情况 → 默认允许
```

新增状态、角色或接口时，默认拒绝会暴露“规则尚未定义”；默认允许则可能悄悄扩大权限。

## 9. IDOR 是“只换一个 ID 就看到了别人的资源”

假设用户能访问：

```text
GET /api/work-orders/1001
```

他把 URL 改为 `1002`，如果后端只按主键查找、不检查租户和资源关系，就可能读到别人的工单。这类漏洞常称 IDOR，现今也常放在 Broken Object Level Authorization（对象级授权失效）下理解。

前端不显示别人的 ID 没有防护作用。ID 可以从日志、顺序、链接或猜测得到，真正边界必须在服务端。

## 10. 多租户意味着一套系统服务多个彼此隔离的客户

FactoryCare 可能同时服务工厂 A 和工厂 B。它们共享应用部署，但数据、用户和权限应隔离。

```text
同一应用
  ├── tenant-A：用户、设备、工单
  └── tenant-B：用户、设备、工单
```

常见数据部署模式：

| 模式 | 特点 |
| --- | --- |
| 每租户独立数据库 | 隔离强，运维和迁移成本高 |
| 每租户独立 schema | 中等隔离，连接和迁移更复杂 |
| 共享表 + `tenant_id` | 运维简单、成本低，每条查询都必须正确隔离 |

没有单一模式适合所有产品。当前讲义重点理解共享表模式，因为它最容易因遗漏条件产生跨租户泄露。

## 11. 租户上下文必须来自可信身份

请求体可能提交：

```json
{
  "tenantId": "tenant-B",
  "title": "维修设备"
}
```

如果当前用户属于 tenant-A，后端不能因为请求体写了 B 就切换过去。租户上下文应来自经过验证的来源，例如：

- 当前 Session 中的用户租户；
- 已验证 Access Token 中受信 issuer 签发的 claim；
- 管理员显式切换后由服务端建立的受审计上下文。

客户端传来的租户标识最多用于与可信上下文比对，不能成为权限事实本身。

## 12. 租户上下文要在请求入口建立并在结束时清理

概念流程：

```text
认证成功
  → 从可信主体取得 tenantId
  → 建立本次请求 TenantContext
  → Service / Repository 使用它
  → 请求结束清理
```

如果用 ThreadLocal 保存，必须考虑线程复用和异步传播；如果显式传参，则调用链更啰嗦但边界清楚。无论用哪种方式，都不能在找不到 tenant 时退回“查询全部租户”。缺少可信租户应默认失败。

## 13. 查询时把 tenant_id 作为数据边界

危险查询：

```sql
SELECT * FROM work_order WHERE id = :id;
```

共享表模式下更安全的查询形态：

```sql
SELECT *
FROM work_order
WHERE tenant_id = :currentTenantId
  AND id = :id;
```

这样不属于当前租户的数据在 Repository 边界就不会出现。随后 Service 仍可根据分派关系和状态做更细的对象级授权。

“先按 ID 查出来，再在 Controller 比 tenant”会让敏感对象进入过多层，也容易因某个新入口忘记比较而泄露。

## 14. 写操作也必须带租户条件

只保护读取不够。更新应同时限定租户和版本等条件：

```sql
UPDATE work_order
SET status = :newStatus,
    version = version + 1
WHERE tenant_id = :currentTenantId
  AND id = :id
  AND version = :expectedVersion;
```

受影响行数为 0 可能表示：不存在、不属于当前租户、版本冲突。对外是否区分这些情况要考虑信息泄露；内部必须保留足够诊断证据。

删除、批量导出、聚合统计和搜索同样要带租户边界，不能只修 `findById`。

## 15. 数据库约束也应包含租户维度

如果设备编码只要求在一个租户内唯一，约束应是：

```sql
UNIQUE (tenant_id, device_code)
```

只对 `device_code` 做全局唯一会让租户彼此抢占名称；完全不做约束则可能在并发请求中产生重复。

外键也要防止跨租户关联。例如工单不能指向另一个租户的设备，可以使用包含 tenant 维度的组合键/外键，或由数据库其他机制加强边界。仅在 Java 中比较一次不足以抵抗所有写入路径。

## 16. PostgreSQL RLS 可以成为额外隔离层

Row-Level Security（行级安全，RLS）让数据库根据策略限制哪些行可见或可修改。概念上：

```text
应用设置当前可信 tenant
  → 数据库策略只允许 tenant_id 相同的行
```

它可降低某条应用查询漏写 tenant 条件的风险，但不是一个自动开关：

- 连接池中上下文要正确设置和清理；
- 数据库角色可能绕过策略；
- 迁移、后台任务和管理员通道要单独设计；
- 策略本身要测试；
- 应用对象级权限仍然存在。

RLS 属于“需要时查询”的实现方案，先掌握可信租户来源和全链路隔离原则。

## 17. 缓存、搜索和消息也必须包含租户边界

跨租户漏洞不只在 SQL。

危险缓存键：

```text
work-order:1001
```

更清楚的键：

```text
tenant:tenant-A:work-order:1001
```

事件也应携带经过业务端生成的租户上下文，消费者处理时再次校验；搜索索引、对象存储路径、导出文件和监控标签都要避免混淆租户。

租户 ID 进入每个边界不代表都可以公开记录，仍要按隐私和高基数风险选择表示方式。

## 18. 后台任务不能丢失租户语义

HTTP 请求结束后，异步任务不再天然拥有请求上下文。错误做法是：上下文缺失时使用默认租户或查询全部数据。

事件或任务应显式包含：

- 经过服务端确认的 tenant ID；
- 业务资源 ID；
- 触发者或系统身份；
- 事件 ID 和发生时间；
- schema 版本。

消费者要把这些字段当作需要验证的合同，而不是因为来自消息队列就全部可信。

## 19. 跨租户测试要把两个租户放进同一场景

只用 tenant-A 的正常数据测试，无法证明隔离。有效场景是：

```text
准备 tenant-A 和 tenant-B
两边各有用户、设备和工单
用 A 的身份尝试：
  - 按 B 的 ID 查询
  - 更新 B 的状态
  - 在列表、搜索和聚合中看到 B
  - 命中 B 的缓存
  - 下载 B 的附件
期望全部不可访问且无旁路泄露
```

还应覆盖相同局部 ID、批量接口、导出和异步消费者。隔离测试的重点是负路径，不是让每个 Repository 都机械复制同一测试。

## 20. 审计记录回答“谁在什么时候对什么做了什么”

普通调试日志用于排查程序运行；审计事件用于追溯重要业务与安全操作。

一条审计事件常包含：

```text
eventId       唯一事件标识
occurredAt    发生时间
actor         谁发起
action        做了什么
target        针对哪个资源
tenantId      位于哪个租户边界
result        成功、拒绝或失败
reason        可安全记录的原因代码
requestId     与请求/trace 关联
source        来源应用、IP 或客户端（按必要性）
```

例子：管理员给用户增加角色、技师关闭工单、登录连续失败、跨租户访问被拒绝。

## 21. 审计事件应记录业务事实，不是复制整份对象

一个状态变更事件可以记录：

```text
workOrderId=WO-42
from=IN_PROGRESS
to=CLOSED
actor=user-17
tenant=tenant-A
result=SUCCESS
```

不必把整张工单、备注、联系方式和 Token 全部序列化进去。最小化能减少隐私泄露、存储成本和未来数据删除冲突。

“越详细越安全”是误解。审计内容应该足够追责，同时只保留有明确用途的字段。

## 22. 审计成功必须和业务事务事实一致

如果先写“关闭成功”的审计，再更新工单失败回滚，审计会声称一件没有发生的事。可以：

- 与业务变更放在同一事务中记录已提交事实；
- 记录 `ATTEMPTED` / `DENIED` / `FAILED` 等准确结果；
- 对提交后发送使用 Outbox 等可靠机制。

安全拒绝不一定进入业务事务，但仍可记录一条明确的拒绝事件。关键是事件语义要说明它记录的是尝试还是已完成事实。

## 23. 审计数据要防篡改，但“绝对不可变”也要谨慎解释

常见目标是 append-only：应用只能追加，不能随意覆盖旧记录。还可通过：

- 独立写入权限；
- 数据库约束或专用存储；
- 哈希链、签名或外部归档；
- 访问和导出本身再审计；
- 保留期与删除流程；
- 时间同步和完整性监控。

但法律隐私请求、错误数据修正和存储生命周期可能要求受控处理。合理目标是“修改可受控、可检测、可追溯”，不是一句 `final` 就解决治理。

## 24. 敏感信息不能因为叫审计就随便保存

通常禁止记录：

- 原始密码和密码重置秘密；
- Session ID、完整 Access/Refresh Token；
- 支付或身份材料的完整值；
- 无业务必要的工单正文和个人信息；
- 加密密钥、数据库凭据。

可以记录稳定的内部主体 ID、Token 指纹的一小部分或不可逆摘要，但也要确认是否真的用于调查。审计查看权限应比普通业务日志更严格。

## 25. 授权失败对外和对内可以有不同信息量

对外直接回答“工单存在，但属于 tenant-B”会泄露资源存在性。系统有时统一返回 404 或普通 403，避免暴露细节。

内部审计则可以在受控条件下记录：

```text
actor=user-A
requestedTarget=WO-B
decision=DENY
reason=TENANT_MISMATCH
```

对外最小信息和对内可追责并不冲突，但内部数据必须受限、脱敏并有保留策略。

## 26. 权限变化需要考虑已有 Session 和 Token

管理员撤销用户角色后：

- 若每次从数据库读取权限，变化生效快但增加查询或缓存复杂度；
- 若权限保存在 Session，需要更新或使 Session 失效；
- 若权限写入自包含 JWT，可能要等 Token 到期或使用撤销机制；
- 缓存中的授权决策也要失效。

授权模型不仅是 `if` 条件，还包含“策略何时更新到各执行点”的一致性问题。

## 27. 设计权限时先写矩阵，再写代码

例如：

| 动作 | 报修人 | 被分派技师 | 调度员 | 租户管理员 |
| --- | --- | --- | --- | --- |
| 查看自己的工单 | 允许 | 允许 | 允许 | 允许 |
| 分派工单 | 拒绝 | 拒绝 | 允许 | 允许 |
| 开始处理 | 拒绝 | 仅分派给自己 | 拒绝 | 按业务决定 |
| 管理用户 | 拒绝 | 拒绝 | 拒绝 | 允许 |

然后补充共同约束：必须同租户、状态转换合法、账号有效、资源未删除。矩阵让冲突和遗漏在写注解前暴露出来。

## 28. 这篇的整体地图

```text
可信身份
  → 角色映射权限（RBAC）
  → 结合主体/资源/环境属性（ABAC / 关系）
  → URL + 方法 + 数据层共同执行
  → tenant_id 贯穿查询、写入、缓存、消息
  → 默认拒绝和跨租户负面测试
  → 审计重要尝试与已提交事实
```

必须掌握：角色不是万能通行证；前端按钮不是授权；租户来自可信身份而不是请求体；共享表查询和写入都要带 tenant 条件；审计不是调试日志，也不能保存凭据。

数据库 RLS、外部策略引擎和复杂关系图属于“需要时查询”。先把边界和事实模型做好，再决定工具。
