# Web 安全：威胁模型、Cookie、CORS 与 CSRF

## 1. 安全不是加一个登录页

一个系统可以功能正确，但仍然不安全。正常用户按正常顺序提交工单能成功，不能回答：

- 攻击者能否冒充他人；
- 一个租户能否读到另一个租户的数据；
- 用户访问恶意网站时，浏览器会不会替他向 FactoryCare 发请求；
- 一个工单描述能否在其他人页面上执行脚本；
- 后端能否被骗去请求内网管理地址；
- 访问日志和错误信息是否泄露密码、Token 和个人数据。

安全的核心是：在假设输入、调用顺序和部分边界会被故意滥用的情况下，系统仍保护关键资产。

## 2. 先说清要保护什么

安全设计应先列出资产（asset），例如：

- 用户密码和恢复凭据；
- Session ID、Access Token、Refresh Token；
- 设备和工单数据；
- 租户边界与权限配置；
- 维修人员的联系方式和定位信息；
- 审计记录的完整性；
- 服务可用性，不能被廉价请求拖垮；
- 签名密钥、数据库凭据和管理端点。

“数据”不只需要保密。常用安全目标：

- **机密性（confidentiality）**：未授权主体看不到；
- **完整性（integrity）**：数据不能被未授权修改，历史不能被悄悄改写；
- **可用性（availability）**：合法用户在需要时可以使用；
- **可追责性（accountability）**：关键操作能追溯到真实主体与时间。

一个错误的批量删除权限主要威胁完整性和可用性，即使它没有泄露任何数据。

## 3. 信任边界是数据跨越不同信任级别的地方

```text
互联网用户浏览器
      │  不可信网络与输入
      ▼
Nginx / 公开 API
      │  反向代理到应用边界
      ▼
FactoryCare 应用
      │  数据库凭据与内部网络
      ▼
PostgreSQL / Redis / RabbitMQ
      │
      └──▶ 第三方邮件或 AI 服务
```

信任边界（trust boundary）不只是防火墙。一个普通用户向管理员功能发请求，同样在跨越权限边界；已认证租户 A 的数据访问租户 B，是跨租户信任边界。

每个边界都要回答：

- 谁能穿过；
- 用什么身份和凭据；
- 哪些数据允许进出；
- 输入如何验证；
- 失败时默认允许还是拒绝；
- 哪些证据用于追溯，又如何避免证据本身泄密。

## 4. 威胁建模是对设计做有结构的攻击思考

一个通用流程是：

1. 我们正在构建什么；
2. 可能出什么问题；
3. 准备如何应对；
4. 怎样确认做得足够好。

不需要先选一套复杂方法论才能开始。对一个功能画数据流、标记资产和信任边界，再提出滥用场景，就能比“上线前扫一遍”更早发现架构问题。

常见威胁角度可以用 STRIDE 帮助记忆，但先理解含义：

| 问题 | 通俗说法 | FactoryCare 示例 |
| --- | --- | --- |
| Spoofing | 冒充别人 | 窃取 Session 后冒充技师 |
| Tampering | 悄悄改数据 | 修改工单租户 ID |
| Repudiation | 抵赖操作 | 管理员删工单但无审计记录 |
| Information disclosure | 泄露信息 | 错误页返回 SQL 和 Token |
| Denial of service | 拖垮服务 | 无限大查询占满连接池 |
| Elevation of privilege | 获得过高权限 | 普通用户调用租户管理 API |

威胁模型不是一次性文档。增加了文件上传、外部 URL 抓取或新身份提供方后，数据流和边界改了，威胁也要重新评审。

## 5. 安全与 IP、DNS、TCP、TLS 处在不同层

访问：

```text
https://factorycare.example:443/api/work-orders
```

大致经历：

```text
DNS：factorycare.example → IP 地址
TCP：建立客户端到服务器 443 端口的可靠字节流
TLS：验证服务器身份，建立加密与完整性保护
HTTP：传送 method、path、header 和 body
Application：认证用户、授权和执行业务
```

TLS 保护传输中的机密性和完整性，不会自动证明当前用户可以看这张工单。HTTPS 也不防止服务端把密码原样写入日志。

DNS 只负责名称到地址的解析，不代表目标一定可信。服务端主动访问用户提供 URL 时，DNS 结果和重定向都必须纳入 SSRF 防护。

## 6. 密码必须用专用密码哈希保存

系统不应保存可恢复的明文密码，也不应用普通快速哈希（如单独 SHA-256）保存。密码哈希算法故意设计得较慢，并为每个密码使用随机 salt，提高离线猜测成本。

```text
注册：原始密码 → 密码哈希算法 + salt + 当前成本参数 → 保存结果
登录：候选密码 + 已保存参数 → 重算并比较
```

常见选择包括 Argon2、bcrypt、scrypt 和 PBKDF2，应使用成熟实现并根据当前安全指南配置成本，不自己设计算法。

凭据生命周期还包括：注册、登录限速、改密码、忘记密码、多因子、凭据泄露后失效、Session/Token 撤销和审计。弱的密码重置链接可以绕过强哈希算法。

## 7. Cookie 是浏览器根据规则自动携带的字段

服务端可在响应中设置：

```http
Set-Cookie: SESSION=opaque-value; Path=/; Secure; HttpOnly; SameSite=Lax
```

后续满足 domain、path、secure 和 SameSite 规则的请求，浏览器会自动携带 Cookie。这个“自动”既方便 Session 登录，也是 CSRF 风险的根源。

常用属性：

- `Secure`：只在 HTTPS 请求中发送；
- `HttpOnly`：不允许普通页面 JavaScript 直接读取，降低 XSS 直接窃取 Session ID 的能力；
- `SameSite`：控制跨站场景中是否携带；
- `Path`：限制路径范围；
- `Domain`：限制主机范围；
- `Max-Age` / `Expires`：持久时间。

`HttpOnly` 不会阻止 XSS 借用当前页面直接发已登录请求，它只限制直接读 Cookie。`Secure` 也不会阻止服务端接受被盗用的有效 Cookie。

## 8. Session 将认证状态主要保存在服务端

常见模型：

```text
浏览器 Cookie：SESSION=abc123
                         │
                         ▼
服务端 Session 存储：abc123 → 用户、权限、过期时间
```

Cookie 里通常只放一个高熅、不可猜测的 Session ID，真正认证状态在服务端。服务端可直接使 Session 失效，但多实例部署需要共享存储、粘性会话或其他一致方案。

不要把敏感权限完全依赖可被客户端直接修改的普通 Cookie 值，如 `role=ADMIN`。加密或签名 Cookie 可以改变信任模型，但需要完整的密钥、过期、重放和撤销设计，不是在字符串后加一个哈希。

## 9. Session fixation 是攻击者让用户登录到已知 Session ID

攻击流程：

```text
1. 攻击者先获得一个未认证 Session ID = X
2. 设法让受害者使用 X 打开登录页
3. 受害者登录成功，系统仍保留 X
4. 攻击者用已知 X 访问已认证 Session
```

防护核心是在认证成功、权限提升等信任级别变化时，更换 Session ID 或创建新 Session，不让攻击者预先选定的标识继续代表已认证身份。

退出时应使服务端 Session 失效并清理相关 Cookie，不只是前端跳回登录页。

## 10. Origin 由协议、主机和端口组成

```text
https://app.example.com:443
└─协议─┘ └──主机──┘ └端口┘
```

三项任何一项不同，origin 就不同。

```text
https://app.example.com       与 http://app.example.com       不同源
https://app.example.com       与 https://api.example.com       不同源
https://app.example.com:443   与 https://app.example.com:8443  不同源
```

同源策略主要限制一个 origin 中的脚本读取另一 origin 的敏感内容。它不是网络防火墙：浏览器可能仍然发出某些跨源请求，只是不允许页面脚本读响应。

## 11. CORS 是服务端告诉浏览器哪些跨源读取可以被允许

当前端在 `https://app.example.com`，API 在 `https://api.example.com`，浏览器会带 `Origin`：

```http
Origin: https://app.example.com
```

如果 API 允许这个来源读响应，可返回：

```http
Access-Control-Allow-Origin: https://app.example.com
```

对某些非简单方法、header 或媒体类型，浏览器会先发送 `OPTIONS` 预检（preflight），询问方法和 header 是否允许。预检通过后才发真正请求。

重要边界：

- CORS 是浏览器实施的读取策略，`curl` 和服务器对服务器调用不受它保护；
- 允许 origin 不等于该 origin 中的每个用户都有业务权限，认证和授权仍要执行；
- 带 Cookie 的跨源请求需要显式 credentials 策略，不能把通配 origin 与 credentials 随意组合；
- 反射任意 `Origin` 到允许响应，相当于没有白名单。

CORS 错误通常表示“浏览器不让页面读”，不代表 API 一定没收到请求。调试时要分别看预检、真实请求和响应 CORS header。

## 12. CSRF 利用浏览器自动携带认证凭据

用户已在 FactoryCare 登录，浏览器保存 Session Cookie。他同时访问恶意页面，该页面诱导浏览器向 FactoryCare 发一个修改请求：

```text
恶意页面发请求
        ↓
浏览器根据 Cookie 规则自动加上 FactoryCare Session
        ↓
FactoryCare 如果只检查 Session，会把请求当作用户本人发出
```

这叫 **Cross-Site Request Forgery（跨站请求伪造，CSRF）**。攻击者不一定能读响应，只要能借用用户凭据产生有效副作用就可以造成损害。

## 13. CSRF Token 证明请求来自拿到页面秘密的合法客户端

服务端为用户会话生成攻击站点无法读到的随机 token，对改变状态的请求要求同时提交：

```text
Session Cookie：浏览器自动携带
CSRF Token：合法页面从已授权响应取得并显式放入请求
```

恶意站点可以诱导浏览器携带 Cookie，却受同源策略限制，无法读取合法页面中的 CSRF Token。服务端同时验证两者，便能拒绝伪造请求。

不要用 GET 执行修改。搜索引擎、预加载、链接预览和各类代理都可以自动访问 GET URL。

## 14. SameSite 是一层 CSRF 降低风险机制

Cookie 的 SameSite 常见值：

- `Strict`：跨站请求中最严格限制，但可能影响从外部链接进入站点的登录体验；
- `Lax`：对部分顶层安全导航允许 Cookie，同时阻止许多跨站子请求和非安全方法；
- `None`：允许跨站携带，现代浏览器通常要求同时使用 `Secure`。

SameSite 很有价值，但不要在所有架构中将它当作唯一 CSRF 防护。子域信任、旧客户端、特殊跳转流程和站点概念都会影响边界。使用 Cookie 认证且有状态修改的应用，应以框架的 CSRF 保护作为默认，只在理解威胁模型后精确调整。

## 15. CORS 与 CSRF 不是同一个问题

```text
CORS：恶意页面的 JavaScript 能不能读另一 origin 的响应？
CSRF：恶意页面能不能让用户的浏览器借凭据发生副作用？
```

将 CORS 限制为自己的前端 origin 是好做法，但不代替 CSRF Token。因为某些跨站请求可以在不需要读响应的情况下发出，而 CORS 主要管理浏览器是否将响应暴露给调用脚本。

同样，开放 CORS 不是让后端放弃授权。允许前端代码发请求，不等于当前登录人对所有工单都有权限。

## 16. XSS 让不可信数据变成页面中的可执行代码

用户在工单描述中提交：

```html
<script>/* 恶意操作 */</script>
```

如果页面将它当 HTML 插入 DOM，脚本就在 FactoryCare origin 下执行，可以读页面数据、以当前用户身份发请求，或诱导输入凭据。这是 **Cross-Site Scripting（XSS）**。

主要防护原则：

- 在输出到 HTML 文本位置时做 HTML 上下文编码；
- 使用前端框架默认的文本插值，避免不必要的 `innerHTML` / `v-html`；
- 如果业务真的允许富文本，使用专用且当前维护的 HTML sanitizer 白名单化；
- 不要使用自制正则“删掉 script 标签”，HTML 解析上下文比这复杂得多；
- 使用 Content Security Policy 作为减少影响的第二层，不取代正确输出处理。

输出编码必须与上下文匹配。HTML 文本、HTML 属性、URL、CSS 和 JavaScript 字符串的安全编码规则不完全相同。

## 17. 输入校验不能取代输出编码

“设备名不允许 `<`”可以是业务格式规则，但不应是整个 XSS 防护。合法数据可能包含引号、括号和国际字符，它们在不同输出上下文中需要不同处理。

可将边界分为：

```text
输入时：格式、范围、长度、业务规则
保存时：保存真实数据，不预先猜测所有未来输出上下文
输出时：根据 HTML/URL/SQL/命令等上下文做正确编码或参数化
```

对 SQL 使用 PreparedStatement 参数绑定，对操作系统命令避免通过 shell 拼接，对 HTML 使用上下文编码。它们共同的核心是不让数据逃出它应在的值边界并变成指令结构。

## 18. SSRF 利用服务器的网络位置代攻击者发请求

如果 FactoryCare 提供“输入图片 URL，后端下载并作为设备图片”，攻击者可能输入：

```text
http://127.0.0.1:...
http://169.254.169.254/...
http://internal-admin/...
```

后端可以访问用户无法直接访问的本机、云元数据或内网服务。这叫 **Server-Side Request Forgery（SSRF）**。

防护需要组合：

- 最好不接受任意 URL，使用固定服务或允许列表；
- 只允许所需协议，通常是 HTTPS；
- 解析并规范化 URL，不用字符串前缀作为唯一检查；
- 阻止本机、私有地址、链路本地、保留网段和内部 DNS 目标；
- 对每次重定向后的新目标重新检查；
- 考虑 DNS rebinding，连接前基于真正解析地址执行策略；
- 设置连接/读超时、大小上限、媒体类型和下载速率边界；
- 用网络出站策略限制应用可访问的目标。

只禁止字符串 `localhost` 不够，因为同一地址有多种 IP 表达和 DNS 别名。

## 19. 默认拒绝和最小权限减少遗漏边界

当新增一个 API 但忘记写安全规则时，有两种默认：

```text
默认允许：没命中规则 → 任何人可访问
默认拒绝：没命中规则 → 拒绝，必须显式开放
```

安全边界应优先默认拒绝（deny by default）。同时给服务账号、数据库用户、管理员和微服务尽量小的必需权限，这叫**最小权限**。

最小权限不只是角色名称更多。它要求把访问范围、资源、操作和时间都限制到真正需要的程度。

## 20. 防御要分层，不要寄希望于一个开关

以 XSS 为例：

```text
输入长度/格式约束
  + 前端默认文本绑定
  + 输出上下文编码
  + 富文本白名单消毒
  + Content Security Policy
  + HttpOnly Cookie
  + 敏感操作再认证/审计
```

任何一层都可能有边界和配置错误。多层防御（defense in depth）让一个控制失败后，攻击者仍需要跨过其他边界。

但分层不是无限堆产品。每一层都应对应具体威胁、有负责人、配置检查和失效证据。

## 21. 安全失败时不应泄露更多信息

登录时对外统一返回“凭据无效”，可以减少账号是否存在的举枚信息。但服务端内部仍需要记录可诊断类别，例如账号禁用、密码不匹配、MFA 失败和限速。

对外错误不应包含：

- 密码哈希；
- Session ID 或 Token；
- 数据库连接串、SQL 和签名密钥路径；
- 内网主机、堆栈和类路径；
- 可用于区分“账号存在”的细节。

安全日志同样需要脱敏。把 Token 写进只有内部人能看的日志，仍然扩大了凭据副本、访问者和保留时间。

## 22. 这篇的整体地图

```text
资产 + 安全目标
  → 数据流和信任边界
  → 威胁与滥用路径
  → 分层控制、默认拒绝、最小权限
  → 负面测试、日志和监控验证

浏览器边界：
Cookie 自动携带 → Session 方便，也带来 CSRF 威胁
Origin 与同源策略 → CORS 控制跨源读取
不可信文本 → 上下文错用会造成 XSS
不可信 URL → 后端主动请求会造成 SSRF
```

必须掌握的区分：HTTPS 不是业务授权；CORS 不是 CSRF 防护；HttpOnly 不是 XSS 免疫；输入校验不能取代输出上下文编码；攻击面包括服务器主动发出的请求，不只是进入 Controller 的参数。
