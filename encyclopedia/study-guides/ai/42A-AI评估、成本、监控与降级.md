# AI：评估、成本、监控与降级

## 1. AI 功能不能靠“看几个回答不错”验收

大模型输出具有概率性，同一提示在不同输入、模型和时间下表现不同。可靠上线需要固定任务定义、数据集、评分规则、失败样本和发布门槛。

演示展示可能性，评估衡量在目标分布上的稳定表现。

## 2. 先把产品任务写成可判断的结果

```text
输入：当前租户的一张工单及允许引用的知识片段
输出：优先级建议、简短理由、引用
允许：信息不足时拒绝建议
禁止：修改工单、猜测未提供事实、引用无权文档
```

任务越模糊，评分越容易变成主观喜好。

## 3. 一次评估样本需要完整上下文

至少包含输入、身份/权限、期望行为或评分标签、重要性、数据来源、标注版本和禁止条件。

仅保存用户问题而不保存当时检索资料、工具状态和版本，之后无法复现结果。

## 4. 评估集应覆盖真实频率和高风险长尾

随机抽样覆盖常见流量，人工策划覆盖罕见但危险情况：跨租户请求、证据冲突、无答案、超长输入、提示注入、工具重复、模型拒绝和降级。

高风险样本可以在发布门中拥有单独硬要求，不能被大量简单样本平均掉。

## 5. 训练/开发集与最终评估集要分开

开发者不断查看并针对某组失败改提示，这组数据已成为验证集。保留独立、受控的最终回归集，减少对已知题目的过拟合。

评估内容也应防止被放进提示示例、RAG 语料或微调数据。

## 6. 确定性检查应优先自动化

程序能可靠检查的内容不要全部交给另一个模型：

- JSON/Schema 是否有效；
- 必填字段和枚举；
- 引用 ID 是否来自实际上下文；
- 是否出现无权资源；
- 工具是否在白名单；
- token、延迟和成本预算；
- 是否达到协议完成状态。

这些是强 oracle（判定依据）。

## 7. 语义评分需要清晰量表

例如理由质量可分：

```text
0：与资料冲突或编造
1：结论大致相关但缺关键依据
2：结论正确，主要依据充分
3：正确、完整、说明不确定性且引用准确
```

每一级附正反例，让不同标注者尽量一致。

## 8. 人工标注需要培训和仲裁

双人独立标注一部分样本，统计一致性，分歧由领域负责人仲裁。持续发现歧义时先修量表，而不是强迫标注者猜。

标注者也必须遵守租户和隐私权限，只看到完成任务所需的最小数据。

## 9. 模型评审器只能作为有误差的测量工具

LLM-as-a-judge 可扩大量级和解释失败，但可能偏好冗长、受提示注入、与被评模型共享偏差。应在人工标注集上校准，并监控一致率。

关键安全门不能只由同类模型自评。

## 10. 成对比较常比绝对打分稳定

给同一输入的 A/B 输出，按明确标准选择更好、相当或都不合格，通常比凭空打 1–10 分更容易。

隐藏系统身份并随机交换顺序，减少位置和品牌偏差。

## 11. 指标分母必须明确

“准确率 95%”要说明：哪些样本被排除、拒答算成功还是失败、Schema 失败如何计、无答案问题的正确行为是什么。

同时保存原始逐样本结果，使任何汇总都能重算。

## 12. 平均分不能代表全部质量

报告总体、关键切片、最差样本、失败类别和不确定区间。按语言、租户类型、文档来源、输入长度、工具路径和风险等级切片。

样本很少的切片必须显示数量，避免把噪声当趋势。

## 13. 回归门既看改善也限制退化

新版本可要求主指标达到目标，并且任何关键安全/业务切片不低于最低门槛。还可设置非劣界：总体提升不能以某关键类别明显退化为代价。

门槛在看结果前确定，避免每次为想发布的版本改标准。

## 14. Prompt、模型、Schema 和检索配置应分别版本化

一次只改一个主要变量更容易归因。实际发布包至少记录：

```text
model ID/config
prompt template hash
output schema version
retrieval/index/reranker version
tool registry version
policy version
```

“AI v2”无法说明到底变了什么。

## 15. 离线评估、影子流量和线上实验层层递进

```text
离线固定集：快速可重复门禁
影子流量：不影响用户，观察真实输入
小流量灰度：真实效果与可靠性
受控 A/B：比较产品结果
全面发布：持续监控
```

高风险写操作在影子模式中必须禁用或使用无副作用模拟。

## 16. 在线反馈容易有选择偏差

愿意点赞/纠正的用户不是随机样本；“没有投诉”也可能是用户放弃。结合任务完成、转人工、编辑量、引用点击和抽样复核，而非只看点赞率。

反馈不得直接未经审查进入训练或长期日志。

## 17. Token 使用要按请求类型记录

区分输入、缓存输入、输出、检索上下文和工具结果。每条请求关联模型、提示和功能版本。

字符数不能精确替代 token。使用供应商响应 usage 作为实际证据，估算只用于请求前护栏。

## 18. 成本是多部分之和

```text
模型输入/输出
+ embedding 摄取与查询
+ 重排/评审模型
+ 向量与文档存储
+ 数据库/网络/计算
+ 监控和人工审核
```

只算一次生成价格会低估整个产品成本。

## 19. 价格必须作为带日期的外部配置

供应商价格、模型和计费类别会变化。估算服务读取经过审查的价目快照并记录生效日期；不要在长期讲义中写死价格常量。

预算报警与财务账单定期对账，说明差异来源。

## 20. 成本护栏分请求、用户和系统层

- 请求：最大输入/输出 token、最大工具轮数。
- 用户/租户：分钟、日和月配额。
- 系统：总预算、异常增长报警、紧急开关。

达到护栏时给出明确降级或拒绝，不能继续消费后只隐藏结果。

## 21. 延迟需要分阶段和分位数

记录请求排队、检索、首 token、生成、工具、校验和持久化。报告 p50/p95/p99，不只平均值。

流式可改善感知延迟，但不会自动降低完整完成时间和成本。

## 22. SLO 把可靠性目标和用户体验连接起来

例如在一个滚动窗口内：成功完成率、首事件延迟、完整响应延迟、Schema 成功、检索可用和安全过滤延迟达到目标。

SLO 应有错误预算和负责人。目标不是所有指标永远 100%，而是明确何时停止发布、优先修可靠性。

## 23. 错误分类比错误总数更有用

```text
客户端输入/权限
供应商认证/限流/5xx
超时/取消/断流
Schema/解析/领域校验
检索空或低相关
工具冲突/审批拒绝
预算耗尽/降级
```

每类有不同重试、用户提示和负责人。

## 24. 质量监控与服务监控是两套互补信号

服务可能 99.9% 成功返回，但答案质量下降；质量可能稳定，但延迟和成本不可接受。分别监控后再关联。

代理指标如输出长度和检索分数不能替代真实标注质量。

## 25. 输入漂移可能让离线评估失效

监控语言、长度、主题、来源、缺失字段、工具选择和风险类别的分布变化。变化只是调查信号，不自动证明质量下降。

从新流量按隐私规则抽样，补充标注和回归集。

## 26. 模型/供应商行为变化要可识别

即使应用代码没变，模型别名、平台策略或依赖版本也可能变化。生产记录实际模型标识、请求 ID 和可用的系统指纹/版本证据。

关键流程优先使用固定并经过评估的模型版本策略。

## 27. Prompt 变更也需要可观测发布

部署日志记录提示版本和变更说明，允许按版本比较错误、成本和用户结果。回滚提示不应依赖重新部署整个系统。

但远程配置本身需权限、审计、审批和安全默认。

## 28. 降级必须保留语义透明度

如果从“基于内部资料的引用回答”降级为“通用模型回答”，风险完全不同，通常不应静默发生。

更安全的降级往往是展示搜索结果、规则模板、缓存的明确旧版本或转人工，并告诉用户限制。

## 29. 降级层级在事故前定义

```text
L0：完整 RAG + 主模型 + 工具
L1：无重排的检索生成
L2：只展示检索与引用
L3：确定性规则/表单
L4：转人工或功能暂不可用
```

每级写明触发、质量门、允许动作、用户文案和恢复条件。

## 30. 缓存是性能工具，也可能制造陈旧和越权

缓存键包括主体/权限、模型、提示、Schema、索引、工具和输入版本。文档删除、ACL 变化和政策更新应能失效。

只缓存经过批准的低风险结果；不要跨租户共享完整回答。

## 31. 重试预算也计入成本和延迟

监控逻辑请求与实际供应商尝试数。一次用户请求在 SDK、代理和应用三层重试，可能造成成本突增。

每次尝试关联同一逻辑 request ID，另外保留 attempt ID。

## 32. 监控不应默认保存完整提示和回答

使用哈希、长度、分类、版本和脱敏摘要满足大多数运维需要。需要完整内容做质量抽样时，进入独立受控数据集，有权限、保留期限、删除和访问审计。

日志系统不是训练数据仓库。

## 33. 告警必须连接行动

每个告警写清门槛、持续时间、影响、负责人、检查面板和第一步缓解。例如成本突增可先降低并发/输出上限，质量退化可切回旧版本。

没有响应流程的告警只会产生噪声。

## 34. 事故时间线需要跨系统关联 ID

从用户请求追到 API 网关、检索、模型调用、工具、业务写入和最终响应。记录阶段起止、版本、状态和安全摘要。

关联 ID 不应包含邮箱、姓名或工单正文等 PII。

## 35. 回滚单元应包含整套相互依赖配置

模型、提示、Schema、解析器、工具和检索配置往往共同演化。只回滚模型可能与新 Schema 不兼容。

定义可发布 bundle 和兼容矩阵，保留最近已验证 bundle 的快速切换能力。

## 36. 供应商切换不是普通异常重试

不同供应商模型在消息、工具、Schema、内容政策、数据保留和错误语义上不同。适配器可统一基础合同，但切换前仍要独立评估和安全审查。

不要在请求失败后把敏感输入自动发送给未经批准的第二供应商。

## 37. 评估代码本身也要测试

用小型手算样本验证指标、分母、拒答处理、切片和报告。锁定数据顺序、随机性和依赖版本。

评估器 bug 可能让所有候选看似提升，因此报告要保留逐样本结果供复算。

## 38. 一次可信发布报告应包含什么

```text
变更范围和假设
评估数据版本与覆盖
总体/切片/安全结果
与当前生产版的成对差异
延迟、token、成本和失败
人工复核与已知限制
灰度、监控、停止和回滚方案
```

明确哪些结果来自离线验证，哪些尚未在真实流量确认。

## 39. 这一阶段应形成的整体地图

```text
任务合同
  → 版本化评估集 + 确定性检查 + 人工/模型评分
  → 回归门与切片
  → 影子/灰度发布
  → 质量 + 延迟 + 错误 + token/成本监控
  → 分级降级、熔断和 bundle 回滚
  → 新失败回流评估集
```

必须掌握：演示不是评估；确定性规则优先由代码检查；模型评审器也有偏差；平均分会隐藏关键失败；价格要带日期；成本包括整个系统；服务成功不等于答案正确；降级不能偷偷改变承诺；监控数据要最小化；回滚应覆盖相互依赖的配置 bundle。

模型 API、价格、usage 字段和评估工具会变化，生产决策必须按当前供应商官方文档和实际账单/响应复核，讲义不固定具体价格或模型别名。
