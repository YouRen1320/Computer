# 大模型：Transformer、模型 API、提示与结构化输出

## 1. 大模型的核心任务是根据上下文预测后续 Token

输入文本先被 tokenizer 切成 token，token 转成 ID 和向量，Transformer 结合上下文计算下一个 token 的概率，再反复选择后续 token。

它生成的是统计上合适的延续，不是从一张“事实数据库”逐条复制答案。因此语言流畅和事实正确是两件事。

## 2. Token 不等于字、词或字符

同一个中文词、英文单词、代码片段和空格组合可能拆成不同数量 token。模型的上下文上限、输入计费和输出长度通常都以 token 衡量。

容量设计应读取真实 API usage 或使用对应 tokenizer 估算，不要用字符数直接替代。

## 3. Embedding 把离散 Token 映射成向量

向量让模型能进行连续数值计算。向量空间中的接近表示模型认为两者在训练和任务表示上相似，不等于两个对象事实相同。

用于检索的 embedding 和生成模型内部 token embedding 也不应混为一个 API 概念。

## 4. 注意力让每个位置汇总相关上下文

Query、Key、Value 计算相关权重，再把其他位置的信息加权汇入当前位置。位置机制告诉模型 token 的顺序。

注意力权重不是可靠因果解释；不能因为某段权重高就断言它决定了回答。

## 5. 自回归生成会把已生成内容继续放回上下文

```text
输入上下文
  → 预测一个 token
  → 把它接到上下文后
  → 再预测下一个
  → 直到停止条件
```

早期错误可能影响后续内容。停止原因、最大输出和结构是否完整都属于调用结果的一部分。

## 6. 温度改变采样分布，不会创造知识

温度较低通常使输出更集中，较高会增加变化。top-p 等参数也影响采样候选。

事实任务不能只靠降低温度获得可靠性；仍需权威数据、引用、Schema、评估和业务校验。相同参数也不应承诺逐字完全一致。

## 7. 上下文窗口是有限的工作区

系统/开发者指令、用户内容、历史消息、检索片段、工具结果和输出预算都会占空间。超限可能失败或按明确策略截断。

长上下文不等于永久记忆，也不保证模型同等注意每个位置。应只放当前任务真正需要的内容。

## 8. 训练、微调、上下文学习和 RAG 不同

```text
预训练：从大规模数据学习通用参数
微调：用特定样本改变模型行为参数
上下文学习：本次请求中根据指令和示例完成任务
RAG：运行时检索外部资料并放进上下文
```

一次对话通常不会把内容自动训练进模型参数。需要最新或私有事实时，RAG/工具比期待模型记忆更可控。

## 9. 一次模型 API 调用经过多个边界

```text
业务请求
  → 输入清理与授权
  → 提示和上下文组装
  → 模型 API
  → 响应封套/状态
  → 输出解析与运行时校验
  → 业务规则与存储/展示
```

任何一层都可能失败。不能把“HTTP 200”直接等同于业务成功。

## 10. API 密钥是访问能力

密钥只放服务端 secret 管理或受控环境变量，不写源码、前端包、日志或讲义示例。应按环境和服务拆分权限，支持轮换和撤销。

浏览器或移动端若直接携带长期密钥，用户可以提取它；需要由自己的后端代理并执行授权和限流。

## 11. 模型 ID 是发布配置

不同模型和快照在能力、延迟、价格、上下文、工具和结构化输出支持上可能不同。生产请求显式指定经过评估的模型，不依赖模糊默认。

升级模型应像升级依赖：固定候选、跑回归集、比较质量/延迟/成本/安全，再灰度和回滚。

## 12. 提示也是可版本化的发布物

提示变化可能改变输出、成本和安全行为。保存提示模板 ID/版本、模型配置、Schema 版本和评估结果。

不要把大型提示散落在业务代码字符串中；集中管理，但也不要引入不必要的复杂平台。

## 13. 指令与用户数据必须分层

```text
开发者定义：任务、边界、输出合同、安全规则
用户输入：需要处理的数据或问题
检索内容：不可信的外部证据
工具结果：不可信的外部返回
```

用户文档里出现“忽略前面规则”仍然只是文档内容。来源标签有帮助，但真正控制要靠程序授权和工具边界。

## 14. 好提示先写清任务和完成条件

比起堆很多形容词，更重要的是：

- 输入是什么；
- 需要产生什么；
- 依据哪些资料；
- 不足时怎样处理；
- 禁止做什么；
- 输出 Schema；
- 一个或少量有代表性的示例。

提示应短到能审查，也完整到能稳定评估。

## 15. 示例帮助说明边界，但不会证明正确

Few-shot 示例可展示字段、风格和特殊情况。示例过多会占上下文，还可能让模型机械模仿错误细节。

示例来自真实数据时必须脱敏，并纳入版本和评估管理。

## 16. 消息不是简单拼接的一个字符串

现代模型 API 通常把指令、用户消息、图片、文件、工具调用和工具结果表示成有类型的输入/输出项目。应用应保留这些结构，而不是全部压成难以审计的文本。

使用 OpenAI 新项目时，当前官方文档推荐 Responses API；具体字段和支持能力要按当前 SDK 与官方指南核对。

## 17. Responses API 的输出包含有类型的 Item

普通文本可以使用 SDK 的便捷字段读取；涉及 reasoning、工具或多模态时，应遍历输出并按 Item 类型处理。

不要假设每个输出项都是文本消息，也不要把工具调用参数直接显示成最终回答。

## 18. 对话状态有三种常见管理方式

- 应用自己保存并裁剪先前输入/输出项目；
- 通过前一响应 ID 串联；
- 使用供应商提供的持久会话对象。

选择取决于隐私保留、可审计、分支、成本和可移植性。即使引用前一响应，历史上下文仍可能计入用量。

## 19. 稳定指令要在每次需要时明确提供

某些状态串联方式不会自动继承上一请求的顶层 instructions。应用不能假设“第一次说过就永远有效”。

同时避免把旧的用户输入误升格为开发者规则。

## 20. 使用量和成本来自实际响应证据

成本估算需要模型价目快照、输入/缓存/输出 token 和请求数量。估算与最终账单不是同一个事实。

```text
估算成本 = 各类 token 用量 × 对应单价
```

价格会变化，不应把未经更新的数字写死在业务代码或长期讲义。财务对账以供应商账单为准。

## 21. 延迟要拆成阶段

```text
排队与连接
  + 首事件时间
  + 生成时间
  + 工具/检索时间
  + 输出校验与持久化
```

只测总秒数无法定位慢点。流式 UI 关注首个可展示内容和完整完成时间，批处理则更关注吞吐。

## 22. 自由文本适合人读，不适合稳定程序接口

让模型输出“优先级：5，原因：……”后用正则拆字段，很容易受换行、措辞和语言变化影响。

程序要可靠消费结果时，应定义结构化 Schema，并把拒绝、截断和失败作为独立状态。

## 23. JSON、JSON Mode 和 Structured Outputs 保证不同

```text
普通文本：不保证 JSON
JSON Mode：保证语法上是 JSON，不保证符合你的字段合同
Structured Outputs：在支持范围内约束结果符合给定 JSON Schema
```

即使 Schema 合法，也仍可能在业务含义上错误，所以还需要领域校验和评估。

## 24. Schema 是外部接口的一部分

```json
{
  "type": "object",
  "properties": {
    "priority": {"type": "integer", "minimum": 1, "maximum": 5},
    "reason": {"type": "string"}
  },
  "required": ["priority", "reason"],
  "additionalProperties": false
}
```

字段名、类型、必填、枚举和额外字段策略都需要版本化。Schema 描述结构，不替代权限和领域规则。

## 25. `additionalProperties: false` 能发现未知字段

若允许任意额外字段，模型或上游拼错名称时可能静默进入系统。严格对象常拒绝未知字段，让漂移立即可见。

但兼容性要求不同的读取接口可能需要保留扩展。应按合同选择，不要依赖默认值。

## 26. 字段描述帮助模型理解业务含义

`priority` 仅写 integer 不够，可说明 1 最低、5 最高、依据是什么。枚举适合有限标签，数值范围适合明确上下界。

描述能提升行为，却不是安全控制；服务器仍需验证并重新授权。

## 27. 结构化输出和工具调用用途不同

```text
需要模型给应用一个结构化回答 → Structured Output
需要模型建议调用应用能力 → Function/Tool Calling
```

两者都可使用 Schema，但工具调用后还要由应用决定是否执行。结构化回答不会自动产生业务副作用。

## 28. 先检查响应封套，再解析业务对象

可能状态包括成功完成、拒绝、内容不完整、传输失败和解析失败。不要在任何情况下都直接访问某个 JSON 字段。

```text
响应状态有效？
  → 有期望输出类型？
  → 完整完成？
  → Schema 解析成功？
  → 领域校验通过？
```

每层失败要保留不同错误类别。

## 29. Refusal 不是 Schema 解析错误

模型因安全原因拒绝时，供应商可能用独立 refusal 表示，而不是勉强填满业务 Schema。UI 和编排层应把拒绝作为明确结果显示或降级。

不要把拒绝文本送进自动“JSON 修复器”，这会绕过安全语义。

## 30. 不完整输出不应被当成完整对象

达到输出上限、断流或其他原因可能只生成部分结构。即使前半段看起来像有效字段，也不能保存为最终业务结果。

对可恢复情况可在严格预算内重试或缩短输入；高风险任务应转人工。

## 31. Pydantic 可以做本地运行时校验

```python
from pydantic import BaseModel, ConfigDict, Field

class PrioritySuggestion(BaseModel):
    model_config = ConfigDict(extra="forbid")

    priority: int = Field(ge=1, le=5)
    reason: str
```

SDK 的结构化解析辅助可以直接映射模型，但仍要固定 SDK/Pydantic 版本，并处理拒绝和 API 错误。

## 32. Schema 模型与领域模型不应完全共用

模型输出 `PrioritySuggestion` 是建议；真正工单优先级由 Java 领域服务根据当前规则、权限和状态决定。

```text
模型 Schema → 解析成功的建议 → 领域命令校验 → 可选人工确认 → 写入
```

这样模型字段变化不会直接改变核心实体合同。

## 33. 自动修复输出要非常克制

删逗号、补字段或再次让模型“修一下 JSON”，可能把明显失败伪装成成功，并增加请求和成本。

若采用修复，应只用于低风险、可观察场景，保留原始失败、限制次数并再次完整校验。安全拒绝和领域冲突不能自动修复。

## 34. 错误分类决定能否安全重试

```text
认证/权限：修复配置，不自动重试
输入过大/Schema 不支持：修改请求
限流/临时服务错误：按服务建议退避重试
拒绝：按产品策略处理
解析/领域失败：记录并评估，不盲重试
```

把所有异常统一成“AI 失败”会让恢复和监控都失真。

## 35. 日志记录标识和摘要，不记录秘密正文

建议字段：业务 request ID、供应商 request ID、模型/提示/Schema 版本、状态、token usage、阶段延迟、错误类别和重试次数。

用户正文、附件、检索片段和完整模型输出只在合法、最小且受控的评估存储中保留，不能默认进入普通日志。

## 36. 测试分成确定性和真实模型两层

确定性层用 Fake 响应覆盖：成功、拒绝、不完整、Schema 错、超时和限流。它验证自己的解析、错误映射和降级。

真实模型层用固定评估集验证语义质量、提示和模型版本。不要用逐字快照要求生成文本完全一致。

## 37. 结构正确不等于内容正确

一个完全符合 Schema 的对象仍可能引用错误工单、编造理由或违反业务规则。评估要分别看：

- Schema 成功率；
- 字段语义准确；
- 引用是否支持结论；
- 拒绝是否恰当；
- 业务校验失败率；
- 人工接受和纠正情况。

## 38. 模型供应商通过端口隔离

应用层可依赖自己的接口：

```text
class PrioritySuggester:
    suggest(context) -> SuggestionResult
```

适配器负责供应商 SDK、请求格式、响应项目和错误转换。不要为了“可替换”抹平所有能力；共同核心与供应商特性可以分层暴露。

## 39. 一次模型升级需要完整回归

比较相同评估集下的：正确性、引用、拒绝、Schema 成功、延迟、token、成本、安全负例和工具行为。通过后先影子或小流量灰度，保留快速回退到旧模型/提示/Schema 的能力。

模型别名和可用能力会变化，升级时查看当前模型目录与迁移说明。

## 40. 这一阶段应形成的整体地图

```text
token + Transformer → 概率生成
  → API 请求（模型/提示/上下文版本）
  → 有类型响应状态
  → Structured Output Schema
  → Pydantic 运行时校验
  → 领域校验、授权与人工边界
```

必须掌握：Token 不是字符；上下文有限；低温度不保证事实；密钥不能进客户端；模型和提示都是发布物；Structured Outputs 约束结构不保证语义；refusal/incomplete 不是普通解析错误；模型建议不能越过领域规则；升级必须跑评估并可回退。

当前 OpenAI 官方文档建议新项目使用 Responses API；具体模型、字段、存储默认、Schema 子集和 SDK 辅助 API 会更新，实施前查看 [Responses 迁移指南](https://developers.openai.com/api/docs/guides/migrate-to-responses) 与 [Structured Outputs 指南](https://developers.openai.com/api/docs/guides/structured-outputs)。
