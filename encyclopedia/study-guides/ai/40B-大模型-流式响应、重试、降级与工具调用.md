# 大模型：流式响应、重试、降级与工具调用

## 1. 流式响应是事件协议，不是不断收到完整答案

模型生成较长内容时，服务端可以通过流逐步发送事件。客户端更早显示内容，但必须处理创建、增量、完成、错误和不同输出类型。

网络分片与语义事件不是一回事；不能假设一次网络读取正好是一段完整文本或 JSON。

## 2. SSE 是常见的 HTTP 流式传输方式

Server-Sent Events 让服务器在一个 HTTP 响应上持续发送有类型事件。OpenAI Responses 流使用语义化事件，常见文本生命周期包括：

```text
response.created
response.output_text.delta（多次）
response.completed
error
```

事件集合和字段以当前官方 API 参考为准。

## 3. Delta 只是增量，不是最终承诺

前几个 delta 拼起来看似一句完整话，后面可能继续补充、拒绝或失败。应用需要把“屏幕上的临时草稿”和“可以持久化的最终结果”分开。

只有收到明确完成终态并通过输出校验，才能把结果当业务完成。

## 4. EOF 不等于成功完成

连接结束可能因为正常完成、代理断开、客户端取消或网络故障。若没有看到协议的 completed 终态，应把它视为不完整或未知，而不是成功。

这与下载文件只收到一半却没有校验类似。

## 5. 客户端需要显式状态机

```text
idle → connecting → streaming
  ├── completed
  ├── failed
  ├── cancelled
  └── incomplete
```

每个终态定义 UI、日志、是否保留草稿和是否允许重试。不要用一个 `loading: boolean` 承担所有情况。

## 6. 文本拼接要按事件类型和顺序

不同输出项可能并行存在，工具调用参数也可能以独立 delta 流入。至少按 response ID、output index/item ID 和事件类型关联。

不能把所有 delta 无差别追加到一个字符串，也不能在参数尚未完成时执行工具。

## 7. 结构化输出流要等到完整后校验

半个 JSON 通常无法解析。UI 可以展示进度或逐字段临时视图，但最终对象必须在 done/completed 后按 Schema 验证。

不要靠每个 delta 都补大括号来伪造“实时合法 JSON”。

## 8. 流式内容更难做完整输出审核

如果系统必须在展示前完成整体安全检查，直接把未完成 delta 展示给用户会打破这个门槛。可选方案是缓冲后审核、分段审核、只流内部进度，或对高风险场景禁用流式展示。

产品体验不能绕过安全要求。

## 9. 背压处理生产者快于消费者

模型事件可能比浏览器渲染、WebSocket 转发或数据库记录更快。无限队列会持续占内存。

可合并短时间内的 UI 文本更新，但不能丢失语义事件。队列需有上限、取消和过载策略。

## 10. 超时应拆成多个预算

```text
连接/首字节超时
首个语义事件超时
事件间空闲超时
工具调用超时
总请求截止时间
```

一个总 30 秒无法说明到底卡在哪里。所有子操作应共享父 deadline，避免每层重新获得完整超时时间。

## 11. 客户端取消要向下传播

用户离开页面后：前端通知服务端、服务端取消流读取和内部 Task、关闭连接并停止后续工具循环。

取消不保证远端计算瞬间停止，也不撤回已经执行的业务工具。应用仍要记录最终已知状态。

## 12. 隐藏 UI 不等于取消任务

只把 loading 动画关掉，后台请求可能继续耗费 token、占连接并更新旧页面状态。请求所有者应持有取消句柄和 generation ID。

旧结果回来时还要检查是否仍属于当前页面/会话。

## 13. 重试前先判断失败是否短暂

可能适合有限重试：连接重置、临时 5xx、明确的限流或服务不可用。通常不应原样重试：认证失败、权限不足、非法 Schema、输入过大和业务拒绝。

以供应商错误类别、HTTP 状态和建议等待时间为证据，不按字符串模糊匹配全部异常。

## 14. 指数退避加抖动减少重试风暴

```text
等待时间约为 base × 2^attempt + 随机抖动
```

设置最大次数、最大单次等待和总 deadline。抖动让大量客户端不要在同一时刻再次请求。

重试不是无限循环；耗尽后必须进入明确失败或降级。

## 15. SDK 重试和应用重试可能叠加

若 SDK 内部已重试 3 次，应用外层又重试 3 次，最坏可能产生远多于 3 次调用。需要记录每层策略，并尽量由一层拥有重试决定。

端到端 deadline 必须覆盖所有实际尝试。

## 16. 读请求和生成请求的重复代价不同

纯生成重试可能多花 token 并产生不同文本；带工具/业务写入的循环还可能重复副作用。

在不知道前一次是否已完成时，应优先按请求 ID 查询状态或使用幂等机制，而非盲目再执行。

## 17. 降级是预先定义的较低能力路径

例如：

```text
主要模型不可用 → 经过评估的备用模型
RAG 不可用 → 显示搜索结果而不生成总结
生成超时 → 规则模板或人工处理
工具写入不可用 → 只读建议
```

降级必须明确告诉调用者能力变化，不能用旧缓存或空字符串假装完整成功。

## 18. 备用模型不是自动兼容

不同模型可能不支持同一 Schema、工具、上下文或参数，质量也可能不同。备用路径必须独立跑评估，并在日志和响应中记录实际模型。

若不满足安全/质量门槛，可靠失败比不受控降级更好。

## 19. 熔断器保护持续失败的下游

当短窗口失败率达到门槛，暂时停止新调用并快速降级；过一段时间允许少量探测，成功后恢复。

熔断器不是错误隐藏器。状态、打开原因、探测结果和人工开关都要可观察。

## 20. 工具调用的本质是模型提出结构化意图

```text
应用把工具名称和参数 Schema 提供给模型
  → 模型返回 function/tool call
  → 应用解析并校验参数
  → 应用重新检查身份、权限和状态
  → 应用决定执行、拒绝或要求人工确认
  → 把最小工具结果返回模型
  → 模型继续或结束
```

模型本身不拥有执行权。

## 21. Tool Schema 只约束参数形状

```json
{
  "name": "assign_work_order",
  "parameters": {
    "type": "object",
    "properties": {
      "orderId": {"type": "string"},
      "technicianId": {"type": "integer"}
    },
    "required": ["orderId", "technicianId"],
    "additionalProperties": false
  }
}
```

Schema 不能证明工单存在、技师有资格、当前用户有权限或状态允许分派。

## 22. 工具列表必须是服务端白名单

模型只能从当前用户、当前流程真正允许的最小工具集选择。不要让提示中的工具名通过反射直接调用任意类或函数。

一个明确的 registry 把公开工具名映射到受控 handler，并拒绝未知名称。

## 23. 工具描述要说明何时用和何时不用

相似工具如果名称和描述含糊，模型容易选错。描述包含用途、前提、关键参数和禁止场景，但不能依靠描述执行安全控制。

工具越多，上下文和选择复杂度通常越高。按任务阶段提供小集合。

## 24. 参数需要两层校验

```text
Schema 校验：字段、类型、枚举、长度
领域校验：资源存在、当前版本、状态转换、业务范围
```

参数中的 URL、路径、查询和自由文本还要做安全限制。不要把模型提供的 SQL、Shell 或代码直接执行。

## 25. 每次执行都重新授权

授权基于经过认证的当前主体和服务端资源，不能相信模型参数里的 `userId`、`tenantId` 或 `isAdmin`。

资源级查询应天然带租户/所有者范围。即使模型几秒前已检查权限，执行前仍要再次判断，避免 TOCTOU 状态变化。

## 26. 人工确认不是模型输出一个布尔值

高风险写入应创建待审批记录，展示具体动作、参数、影响和依据，由已认证的人明确批准。审批有 ID、身份、时效和一次性使用规则。

模型说“用户已经同意”不是证据。聊天中的普通“好”也不能自动批准内容已变化的动作。

## 27. 幂等键防止重复业务副作用

```text
同一业务意图 + 同一幂等键
  → 首次执行并保存结果
  → 重复请求返回同一结果或明确冲突
```

call ID 用于关联模型工具循环，不一定就是长期业务幂等键。跨重试和恢复应使用服务端定义的稳定键。

## 28. 幂等不等于无需事务

写入业务表和记录幂等结果要在可靠一致性边界内，否则可能出现业务已执行但幂等记录没写，重试又执行一次。

需要数据库事务、唯一约束或状态机，而不是只在内存集合记一次。

## 29. 工具结果应最小、结构化并可区分状态

```json
{
  "status": "conflict",
  "code": "ORDER_VERSION_CHANGED",
  "retryable": false,
  "safeMessage": "工单状态已变化，请重新确认"
}
```

不要把完整数据库实体、内部堆栈或其他租户数据返回模型。工具错误是数据，编排器仍需按状态控制流程。

## 30. 工具结果也是不可信上下文

外部网页、文档和第三方 API 返回中可能含提示注入文字。模型应把它们当证据数据，不能让内容改变系统规则或授权。

程序层限制工具、参数和下一步动作，提示只提供补充行为指导。

## 31. 多个工具调用要处理依赖关系

两个只读查询可并行；“创建工单后上传附件”有先后依赖；两个修改同一资源可能冲突。

并行前分析资源、事务和顺序，不要因为模型一次返回多个调用就全部并行执行。

## 32. 并行工具也需要有界并发

限制并发数、每轮工具数、总工具数和总 deadline。批量授权按每个资源检查，不能一个允许就放行整个数组。

部分成功要有明确结果和补偿策略。

## 33. Agent 循环必须有多维预算

```text
最大模型轮数
最大工具调用数
最大 token/成本
总时间 deadline
连续无进展次数
失败重试次数
```

只设置最大循环次数不够，因为一次工具可能昂贵或有副作用。达到预算后进入稳定终态并保留轨迹摘要。

## 34. 无进展检测防止反复做同一件事

可比较工具名、规范化参数、结果摘要和状态。如果连续几轮没有新增信息或状态变化，停止并说明需要人工处理。

不要让模型通过轻微改写参数绕过预算。

## 35. Kill switch 要真正停止新工作

关闭开关后，入口不再创建新循环，队列消费者停止领取，现有任务收到取消或安全排空策略，工具层也拒绝新写入。

只隐藏按钮并不能关闭后台 Agent。开关状态和残余任务数需要可验证。

## 36. Java 与 Python 可以按事实边界分工

```text
Java：身份、权限、事务、工单状态机、审计、幂等写
Python：模型调用、检索、提示、评估和编排建议
```

Python Agent 通过受控 API 请求 Java 执行业务命令，不能绕过领域服务直接写业务数据库。

## 37. 流式工具调用要等参数完成

函数参数 delta 可以逐步到达。只有收到相应 done 事件并完成 JSON/Schema/领域校验后才能执行。

把半截参数当完整值可能执行错误资源；同一流中多个调用要按 output index 和 call ID 分别累积。

## 38. 工具循环的测试不需要每次调用真实模型

用脚本化 Fake 依次返回：合法调用、未知工具、Schema 错、无权限、冲突、重复调用、并行调用和最终回答。验证编排器是否执行正确 handler、限制预算并保留错误类别。

真实模型集成测试再检查工具选择质量和提示行为，不能替代确定性安全测试。

## 39. 故障注入要覆盖不确定窗口

重点场景：工具完成后响应丢失、持久化前进程崩溃、用户在审批后资源变化、客户端取消但工具已提交、流断开后自动重连。

系统应通过幂等、状态查询、版本检查和审计恢复，而不是猜“前一次大概没执行”。

## 40. 这一阶段应形成的整体地图

```text
流式：typed event → delta 暂存 → completed → 最终校验
韧性：deadline → 分类重试 → 退避/熔断 → 明确降级
工具：模型提议 → Schema → 授权/领域校验 → 审批/幂等执行
Agent：有界循环 → 无进展检测 → kill switch → 可审计终态
```

必须掌握：delta 不是最终回答；EOF 不等于完成；取消不撤回副作用；SDK 和应用重试不能无意叠加；降级要经过独立评估；Schema 不是授权；模型没有执行权；人工审批必须有真实身份；call ID 不自动等于幂等键；Agent 必须有预算和停止开关。

OpenAI Responses 当前使用有类型的流事件，具体事件与工具字段会变化，实施前查看 [流式响应指南](https://developers.openai.com/api/docs/guides/streaming-responses) 和 [Function Calling 指南](https://developers.openai.com/api/docs/guides/function-calling)。
