# Web：测试、错误恢复、SSE 与性能

## 1. Web 工程的目标是让用户在真实条件下完成任务

“组件能显示”只是起点。真实页面还会遇到：

- 慢网络、离线和请求乱序；
- 登录过期与权限变化；
- 服务端字段错误和并发冲突；
- 浏览器前进后退与刷新；
- 键盘、屏幕阅读器和缩放；
- 大列表、慢设备和资源加载；
- 新版本发布后旧页面仍在运行。

测试、错误恢复、实时更新和性能优化都应围绕用户可见合同，而不是为了工具覆盖率数字。

## 2. 先写清“什么结果算正确”

测试预言（test oracle）是判断结果正确的依据。例如：

```text
输入：当前用户无 WORK_ORDER_ASSIGN 权限
动作：访问分派页或直接触发分派
预期：UI 不提供可执行入口，API 返回 403，工单不变化
```

若只断言“按钮 class 是 disabled”，实现稍改测试就坏，也没证明 API 安全。预言应尽量靠用户可观察结果和稳定合同。

## 3. 不同测试层解决不同风险

| 层级 | 适合验证 | 不擅长 |
| --- | --- | --- |
| 纯函数单元 | 格式化、映射、业务规则 | 浏览器集成 |
| Composable/Store | 响应状态和副作用编排 | 完整页面导航 |
| 组件测试 | Props、事件、表单、异步 UI、可访问查询 | 后端真实合同 |
| API/契约测试 | 请求响应 schema、错误码 | 视觉交互 |
| E2E | 登录、导航、关键业务跨层流程 | 大量边界穷举 |
| 视觉/无障碍检查 | 布局回归、焦点、语义 | 后端数据一致性 |

测试金字塔不是固定比例；按故障影响和定位成本选择最轻能否证声明的层。

## 4. Vitest 运行 JavaScript/TypeScript 测试

基本结构：

```ts
describe('formatPriority', () => {
  it('formats critical priority', () => {
    expect(formatPriority(5)).toBe('严重')
  })
})
```

Arrange–Act–Assert：准备、执行、断言。名字说明场景和行为，不重复函数名。

单元测试不需要启动完整 Vue 应用或真实浏览器。若代码依赖 DOM，可使用模拟 DOM 环境，但它不能完全等同 Chrome 布局、导航和无障碍树。

## 5. 组件测试按用户能看到和操作的方式查询

优先：

- 可访问角色和名称；
- label 对应的表单控件；
- 可见文字和稳定状态；
- 组件对外 emit/导航/API 调用。

谨慎：

- CSS class；
- `data-testid`；
- 内部 ref/方法；
- 子组件私有实现。

如果无法通过角色/label 找到“提交工单”按钮，可能本身就是语义问题。测试选择器可推动更可访问的结构。

## 6. 测试异步 UI 要等待结果，不等待猜测时间

```text
触发提交
  → 断言 loading 可见
  → 解决 API Promise
  → 等待“创建成功”出现
```

不要使用固定 500 ms sleep。CI 速度不同会导致偶发失败。Vue 更新、Promise、计时器各有明确等待机制；使用 fake timer 时也要理解 microtask 与 DOM 更新。

失败超时应显示当前 DOM 和未完成请求，方便定位。

## 7. Mock 只替换当前测试不想验证的外部边界

例如组件测试替换 WorkOrderApi：

```ts
const api = {
  create: vi.fn().mockResolvedValue({ id: 'WO-42' }),
}
```

Mock 应遵守真实接口类型，并有成功、校验失败、403、409、网络失败等代表场景。

不要 Mock Vue 响应式、Router 所有内部方法或待测函数本身。越接近内部实现，测试越可能“验证了自己的假实现”。

## 8. 合同测试防止前后端各自想象一种 API

共同合同应明确：

- method/path/query；
- request/response schema；
- null/缺失/默认语义；
- 状态码和稳定错误 code；
- 分页、排序和时间格式；
- 认证和幂等 header；
- version/ETag 等并发字段。

OpenAPI 可生成/校验部分类型，但业务语义和权限仍需场景测试。TypeScript interface 不能验证服务器真实响应。

## 9. 端到端测试只保留关键旅程

代表旅程：

```text
登录
  → 打开工单列表
  → 创建工单
  → 进入详情
  → 分派并观察状态
  → 刷新后仍正确
```

再覆盖高风险反路径：跨租户访问、权限拒绝、Session 过期、409 冲突。大量输入组合留给更低层测试，避免 E2E 套件慢且难诊断。

E2E 数据应独立、可清理、避免多个并行用例争同一用户/工单。

## 10. 视觉测试发现截图差异，但不知道业务对错

视觉回归适合：

- 核心布局；
- 主题；
- 响应式断点；
- 长文本、空状态、错误状态；
- 组件库。

要固定字体、时区、动画、数据和视口，减少噪声。截图相同不能证明键盘、无障碍名称或请求正确；截图不同也可能是合法改版，需要人工审查。

## 11. 无障碍测试需要自动与人工组合

自动规则可发现：缺 label、部分对比、错误 ARIA、重复 ID。人工至少检查：

- 仅键盘完成流程；
- 焦点顺序/可见性；
- 模态框焦点恢复；
- 页面导航和动态状态提示；
- 屏幕阅读器的名称、角色、状态；
- 200% 放大和窄屏；
- 减少动效。

自动工具通过不等于 WCAG 或真实可用性全部通过。

## 12. 错误边界应按能否局部恢复设计

```text
一个卡片加载失败 → 卡片内重试，不毁掉整页
详情核心资源不存在 → 页面级 404
认证失效 → 保存安全回跳并登录
整个应用 chunk 损坏 → 全局恢复/刷新
```

Vue 的 `onErrorCaptured`、全局 error handler、组件 error boundary 模式各有范围。不要捕获后渲染空白，也不要让一个非关键图表异常摧毁整个工单页面。

## 13. 错误 UI 要告诉用户发生了什么和下一步

有效信息：

- 简洁问题说明；
- 数据是否可能已保存；
- 可执行的重试、返回或刷新；
- request ID 供支持定位；
- 是否需重新登录或联系管理员。

不展示堆栈、SQL、内部主机和 Token。`console.error` 可辅助开发，但生产要发脱敏遥测，并防止同一错误无限上报。

## 14. 写请求超时后的结果可能“不确定”

```text
浏览器发创建请求
服务器已提交
响应在网络中丢失
浏览器看到 timeout
```

前端不能直接说“创建失败”并无条件重试。可使用 Idempotency-Key、查询最终状态、显示“结果待确认”，或让用户在列表中核对。

错误恢复文案应区分“服务器明确拒绝”和“客户端没有得到结果”。

## 15. 409 冲突要求重新获取事实再决定

用户编辑 version 7，别人先提交 version 8。服务端返回 409 后：

1. 保留用户草稿；
2. 获取/使用服务端最新 version；
3. 展示冲突字段或变化；
4. 允许重新应用、合并或放弃；
5. 新提交带最新版本。

自动覆盖或无限重试会丢他人修改。前端必须把冲突当业务状态，不是普通网络错误。

## 16. 离线不只是 navigator.onLine 的真假

浏览器“在线”只代表有网络接口，不保证 API 可达；请求失败也可能是 CORS、DNS、TLS 或服务端故障。

离线体验按产品需求分级：

- 明确提示当前无法同步；
- 保留未提交草稿；
- 读取最后缓存并标记可能过期；
- 将安全可重放操作入队；
- 恢复后由用户确认或按幂等合同同步。

高风险状态转换不能仅靠本地队列盲目重放。

## 17. 新版本资源加载失败要有恢复通道

部署后，旧 HTML/运行中页面可能请求已删除的旧 chunk。表现为动态 import 失败或空白页面。

可：

- 静态资源文件名带 hash 且长期保留一段时间；
- HTML 不长期缓存旧入口；
- 捕获 chunk load error，提示一次安全刷新；
- 防止自动刷新死循环；
- Service Worker 更新有明确版本策略。

原子发布和回滚比前端无限 reload 更根本。

## 18. SSE 用一条 HTTP 响应持续接收服务端事件

Server-Sent Events（SSE）适合服务器向浏览器单向推送：

```text
浏览器发 GET /api/events
  → 服务器保持 text/event-stream 响应
  → 不断发送 event/data/id
  → 浏览器按事件更新 UI
```

适合工单状态、通知和后台任务进度。浏览器发命令仍使用普通 HTTP；若需要高频双向实时通信，WebSocket 可能更适合。

## 19. SSE 消息有事件类型、ID 和数据

概念格式：

```text
id: 1842
event: work-order-updated
data: {"workOrderId":"WO-42","version":8}

```

空行结束一条事件。data 是文本，应用可约定 JSON 并运行时验证。event ID 可帮助断线后恢复位置。

不要直接把数据库内部实体或敏感字段广播给所有连接。

## 20. EventSource 有自动重连，但业务仍要补一致性

```js
const source = new EventSource('/api/events')

source.addEventListener('work-order-updated', event => {
  const raw = JSON.parse(event.data)
  // schema 验证，再失效对应 query
})
```

连接断开会尝试重连，并可通过 Last-Event-ID 恢复。服务器是否保留足够事件、负载均衡是否支持、ID 是否可重放，需要自行设计。

若事件有缺口，客户端应重新获取事实快照，不应把本地状态当完整事件日志。

## 21. SSE 事件最好触发“失效或增量合并”

两种策略：

- 事件只带 ID/version，客户端使 query 失效并重新获取；简单可靠，网络更多；
- 事件带完整最小变更，客户端按 version 合并；延迟低，逻辑复杂。

无论哪种，都要：

- 按租户/用户授权连接；
- 验证事件 schema；
- 忽略旧版本；
- 防重复；
- 处理列表筛选变化；
- 断线后快照恢复。

## 22. SSE 的认证、CSRF 和代理边界

原生 EventSource 发送自定义 Authorization header 能力有限，常见 BFF/同源 Session Cookie 模式更自然。Cookie 连接仍需认证授权，并限制 origin、CORS 与凭据策略。

SSE GET 本身应只订阅，不用来执行修改，降低 CSRF 副作用。服务端按当前用户过滤事件，不能让客户端传 tenantId 就订阅任意租户。

反向代理需要关闭不合适的响应缓冲并设置长连接/心跳超时，具体配置按部署环境验证。

## 23. SSE 连接需要心跳、容量和清理

中间代理可能关闭长时间无数据连接。服务器可发送注释心跳；浏览器离开页面/组件卸载时 `source.close()`。

要监控：

- 当前连接数；
- 每用户/租户连接上限；
- 事件发送延迟；
- 断线重连率；
- 客户端落后程度；
- 代理和服务器文件描述符/内存。

无限连接不是“HTTP 很轻”就自动可扩展。

## 24. 性能先以用户体验指标定义

Web Vitals 常关注：

- LCP：主要内容何时显示；
- INP：用户交互到下一次视觉反馈的延迟；
- CLS：页面意外布局位移。

还要看业务指标：登录到可用、工单列表加载、提交确认、SSE 更新延迟。

具体阈值会随标准更新，实施时看当前官方 Web Vitals 文档；不要把实验室单次分数当全部用户体验。

## 25. 实验室数据和真实用户数据互补

Lab：固定设备/网络，可重复，适合开发定位。RUM（真实用户监控）：反映真实设备、地区、网络和页面，但噪声大且有隐私约束。

```text
Lab 发现可能原因
RUM 确认影响范围和分位数
发布前预算防回归
发布后监控验证真实改善
```

指标应按页面/设备/版本等低基数维度分析，不记录用户敏感输入。

## 26. 性能预算把“不能无限变慢”写成合同

可定义：

- 初始 JavaScript 压缩大小；
- 单路由懒加载块上限；
- 图片和字体预算；
- 关键页面 LCP/INP/CLS 目标；
- API 延迟分位数；
- 长任务数量；
- 第三方脚本成本。

预算超出应在 CI 或评审显式可见。不要仅按总 bundle 判断：关键路径、缓存和执行成本同样重要。

## 27. JavaScript 成本包括下载、解析和执行

低端设备可能下载不慢，但解析/执行大包很慢。优化顺序：

- 删除不需要依赖和重复 polyfill；
- 路由/功能级代码分割；
- 避免把整个库只为一个小函数引入；
- 延迟非关键第三方脚本；
- 检查 source map/bundle analyzer；
- 减少水合范围或使用更适合的渲染策略。

过细代码分割会增加请求和加载瀑布，按真实导航验证。

## 28. 图片通常是最大的页面资源

- 输出接近显示尺寸；
- 使用现代格式并保留兼容策略；
- `srcset/sizes` 让浏览器选择；
- 非首屏 lazy load；
- 首屏主图不要错误 lazy；
- 写 width/height 防 CLS；
- CDN/缓存；
- 私有图片仍做授权。

压缩不能以故障细节看不清为代价。设备维修图片可能需要原图查看，但列表缩略图不应下载原图。

## 29. 字体加载会影响文本显示和布局

减少字重/字符集、合理预加载关键字体、选择相近 fallback、设置 font-display，并检查中文字体体积。

不要预加载所有字体和页面资源，预加载会争夺关键带宽。系统字体可能是企业后台最稳妥选择。

字体切换后度量差异会引发 CLS，可通过 fallback metrics 和布局设计减少。

## 30. 大列表要控制 DOM 和渲染工作

一千行表格即使数据已在内存，也可能产生大量组件、监听和布局。可：

- 服务端分页；
- 虚拟滚动只渲染视口附近；
- 分块/增量显示；
- 减少每行响应式依赖；
- 避免每次筛选重复昂贵排序；
- 保持稳定 key。

虚拟列表增加键盘、屏幕阅读和动态高度复杂度，先确认真实数据规模与性能瓶颈。

## 31. 监听器、Observer 和连接都要随页面清理

离开页面时取消：

- Fetch/搜索请求；
- SSE/EventSource；
- setInterval/setTimeout；
- window/document listener；
- Resize/Intersection/MutationObserver；
- WebSocket；
- 第三方图表实例。

KeepAlive 页面还要处理 activated/deactivated，而不仅是 unmounted。

资源泄漏会表现为重复请求、重复 Toast、内存增长和后台 CPU。

## 32. Performance 面板从主线程时间线找因果

一次慢交互可看：

```text
Input
  → JavaScript Long Task
  → Style / Layout
  → Paint / Composite
  → 下一帧显示
```

再用 Vue DevTools 找组件重渲染，Network 看瀑布，Memory 查保留对象。先建立复现和基线，再改一项并复测。

不要看到函数耗时就立即 memoize，可能真正瓶颈是网络、图片或布局。

## 33. 错误和性能遥测要保护隐私

避免采集：

- 工单正文和表单值；
- URL 中的敏感 query；
- Token、Cookie、完整 header；
- DOM 全量快照；
- 不必要的用户标识。

采样、脱敏、保留期和访问权限要明确。Session replay 尤其要遮挡输入和敏感页面，并满足用户同意与法规要求。

## 34. 发布验证要覆盖成功与恢复路径

```text
构建与类型检查
  → 关键组件/合同测试
  → E2E 关键旅程和权限负路径
  → 生产样式构建下性能/无障碍
  → 分阶段发布
  → 监控错误、Web Vitals、API 与 SSE
  → 必要时回滚
```

绿色测试只能证明执行过的范围。未测试的浏览器、网络和恢复路径应明确记录，不说“全面无问题”。

## 35. 这篇的整体地图

```text
用户合同
  → 最轻适合的测试层提供证据
  → 错误按局部/页面/全局边界恢复
  → 写请求不确定与 409 有专门状态
  → SSE 传递服务端事件，断线后用快照恢复
  → Web Vitals + 业务指标定义性能
  → 资源、JS、DOM、主线程按证据优化
  → 发布后真实监控验证
```

必须掌握：测试按用户结果而非实现细节；异步测试不靠 sleep；写请求超时不等于未执行；SSE 是单向推送且会断线/重复；性能包括加载与交互；自动无障碍检查不能替代键盘和屏幕阅读器；遥测不能泄露用户数据。

具体 E2E 框架、Web Vitals 阈值、Service Worker 缓存策略和浏览器性能 API 属于“需要时查询”。
