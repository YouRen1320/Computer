# 制品、部署、迁移与回滚

## 1. 发布的核心是把已验证的同一份内容送到生产

源码不是运行制品。Java JAR、前端静态包、Python 镜像和配置经过构建、检查后，形成可部署的 artifact（制品）。

可靠发布要求制品不可变、来源可追溯、逐环境晋级，并在失败时有清楚的恢复路径。

## 2. 构建与部署是两个阶段

```text
构建：源码 + 固定依赖 + 工具链 → 制品
部署：制品 + 环境配置 → 运行实例
```

部署阶段不应再次修改或重新编译制品，否则测试环境验证的内容与生产实际内容可能不同。

## 3. 制品使用不可变标识

人类可读版本和标签便于沟通，但可能被覆盖。镜像 digest 是内容标识，更适合证明运行内容。

生产记录版本、标签和 digest；发布工具最终按不可变标识部署。

## 4. 发布元数据把证据连起来

一份发布清单可包含：

- 源码提交和仓库；
- 流水线运行编号；
- 各制品 digest；
- SBOM 与扫描结果；
- 自动检查报告；
- 数据库迁移版本；
- 配置版本与功能开关；
- 审批、部署和回滚入口。

它回答“这次发布到底包含什么”。

## 5. 来源证明说明制品怎样产生

Provenance（来源证明）记录受控构建者、源码输入和构建过程。配合签名，部署端可以验证制品来自允许的流水线且内容未被替换。

它提高供应链可信度，但仍不能证明应用逻辑没有缺陷。

## 6. 同一制品逐环境晋级

推荐先在集成或预发布环境运行同一 digest，验证后再提升到生产。环境差异只来自受控配置和基础设施，不来自重新构建。

晋级记录应能显示制品经过哪些门禁以及目前在哪些环境运行。

## 7. 环境一致不等于完全相同

生产容量、域名、秘密和外部依赖与测试环境不同，但运行模型、配置键、迁移方式和代理链路应尽量一致。

重点是差异明确且可验证，而不是强行让所有环境拥有同样数据和规模。

## 8. 发布前先定义完成和停止条件

完成条件包括健康、核心业务流程、指标和版本核对；停止条件包括迁移失败、错误率超阈值、跨租户风险或关键依赖异常。

如果没有条件，团队在异常时很容易边争论边扩大影响。

## 9. 变更窗口按风险决定

低风险、可自动回滚的应用更新可以频繁发布；高风险数据迁移或身份变更可能需要人员、备份和业务低峰窗口。

窗口不是可靠性的替代品，即使凌晨发布也要有监控和恢复能力。

## 10. 滚动部署逐步替换实例

一部分旧实例继续服务，新实例通过就绪检查后再接流量，然后逐步替换其余实例。它减少整体停机，但要求新旧版本在一段时间内兼容共享数据和请求。

若新旧版本不能并存，滚动策略会直接暴露问题。

## 11. Blue-Green 使用两套环境切换

Blue 运行当前版本，Green 部署新版本并验证，然后切换流量。回切应用较快，但两套环境成本更高，数据库仍是共同难点。

如果 Green 已写入旧版本无法理解的数据，简单切回 Blue 也可能失败。

## 12. Canary 先让少量流量使用新版本

金丝雀发布按实例、用户、租户或流量比例逐步扩大。每一阶段观察成功率、延迟、业务指标和资源，再决定继续或停止。

流量必须能稳定分组，指标也要能区分版本，否则无法判断新版本影响。

## 13. Feature Flag 可控制功能暴露

代码部署和功能启用分开后，可以只对内部账号或少量租户打开新能力。出现问题时关闭开关通常比重新部署快。

但数据库变化和启动错误不能靠功能开关自动解决；开关也要有生命周期和安全默认值。

## 14. 数据库迁移是最难回滚的部分

应用实例可以替换，已修改的数据却不能总是恢复原状。删列、改类型、重写大量数据和改变含义都可能阻止旧版本工作。

因此数据库演进通常优先兼容，而不是依赖逆向脚本。

## 15. Expand-Contract 把破坏性变化拆开

以字段改名为例：

```text
Expand：新增字段，旧字段仍保留
Migrate：新旧应用兼容，逐步回填并切换读写
Contract：确认没有旧消费者后删除旧字段
```

三个阶段通常跨多个发布，不能在同一次部署中急于完成。

## 16. 先扩展 Schema 再部署新代码

新增可空列、表或索引通常可以先执行，让旧应用仍然工作。随后部署能识别新结构的代码。

具体 DDL 是否锁表、耗时多久取决于 PostgreSQL 版本、表规模和操作方式，必须在代表性数据上验证。

## 17. 双读双写是临时迁移手段

迁移期间应用可能同时写新旧字段，读取时优先新字段并兼容旧字段。它减少切换风险，却增加逻辑和不一致可能。

要记录迁移阶段、监控差异，并明确何时删除临时代码。

## 18. Backfill 将历史数据补到新结构

回填应分批、可暂停、可重入，并限制数据库压力。记录游标、处理量、错误和剩余量，不在一个巨大事务中锁住全表。

回填过程中仍有新写入，所以要设计并发和最终一致性策略。

## 19. 数据校验决定是否可以切读

对新旧字段比较数量、空值、抽样内容和关键业务不变量。只有差异达到明确条件，才让读取流量切换到新结构。

“脚本执行完成”不等于迁移正确。

## 20. Contract 阶段最后执行

删除旧列、旧事件字段或旧 API 前，确认所有实例、后台任务、报表、移动端和外部消费者均已迁移，并监控旧访问降为零。

过早 contract 会让尚未更新的消费者立即失败。

## 21. 向后兼容与向前兼容要分别考虑

```text
新应用 + 旧 Schema 是否能启动？
旧应用 + 新 Schema 是否能继续运行？
新旧应用是否能理解彼此写入的数据？
```

滚动发布和回滚分别依赖不同方向的兼容，不能只做一次编译检查。

## 22. 事件和消息也需要演进策略

消费者可能比生产者晚升级。新增可选字段通常较容易兼容；改名、删除或改变含义会破坏旧消费者。

事件是已经发生的事实，不应悄悄重新解释同一个字段。

## 23. API 迁移考虑长期离线客户端

Web 前端通常可随刷新更新，移动端可能数周不升级。删除旧 API 或枚举值前，要根据真实客户端版本分布规划兼容期。

服务端记录版本调用量，不能只根据发布时间猜测迁移完成。

## 24. 迁移执行需要锁和所有者

同一数据库不能让多个部署任务同时执行相同迁移。使用框架迁移历史和数据库锁，并规定由哪个部署阶段负责执行。

应用启动时自动迁移很方便，但大规模生产变化可能需要独立受控任务。

## 25. 长迁移与发布解耦

创建大型索引、回填历史数据或重算向量可能超过应用部署时间。把它们作为可观测、可暂停的运维任务，先完成安全阶段，再发布依赖结果的代码。

不要让健康检查一直等待数小时迁移。

## 26. 备份不能替代迁移设计

发布前备份提供最后保护，但从完整备份恢复可能超过 RTO，也可能覆盖发布后合法新数据。

优先使用兼容演进和前向修复，备份作为灾难恢复层。

## 27. 应用回滚是重新部署已知旧制品

回滚需要明确旧 digest、配置版本、兼容条件和流量切换方式。不要在事故中临时重新构建所谓“上一版”。

回滚后仍要验证真实用户路径和数据状态。

## 28. 数据库通常采用前向修复

已执行的迁移若涉及数据写入或删除，逆向操作可能进一步丢数据。更安全的办法常是保留兼容 Schema，发布修复代码或新增修复迁移。

这叫 roll forward（前向修复），并不等于永远禁止数据库回滚；选择取决于实际可逆性和证据。

## 29. 回滚条件应自动与人工结合

明显的健康失败、错误率突增和启动失败可自动停止或回滚；数据语义、用户投诉和安全风险可能需要人工判断。

自动化阈值要防止短暂噪声造成来回切换。

## 30. 发布观察窗口不能太短

某些问题只在缓存过期、定时任务、峰值流量或长事务出现。金丝雀每阶段要覆盖足够请求和关键场景，而不只是等待固定一分钟。

观察时间与风险和业务周期相关。

## 31. 发布指标要按版本分组

对新旧版本分别查看请求量、错误率、延迟、资源和业务结果。若所有实例混成一条曲线，少量金丝雀异常可能被整体平均掩盖。

版本标签应低基数且与真实制品对应。

## 32. 冒烟检查验证最小关键能力

部署后通过真实入口检查 TLS、Nginx、登录、核心读取和一次安全写入。冒烟检查要快速且可清理，不能污染生产业务数据。

只调用 `/health` 无法证明用户链路正常。

## 33. 合成检查持续模拟用户路径

定时从外部访问登录、查询等受控流程，可以发现 DNS、证书、代理和应用的整体问题。账号和数据专门隔离，失败时链接到 trace。

合成检查不替代真实用户指标，但能在无人使用时主动发现问题。

## 34. 发布日志记录每个关键决定

记录谁批准、部署哪个 digest、何时开始、迁移结果、每阶段指标、暂停原因、回滚或完成时间。它既用于事故时间线，也用于改进流程。

不要在日志中记录秘密本身。

## 35. 配置必须与制品一起核对

同一镜像因错误环境变量、证书或功能开关仍会表现不同。发布清单引用配置版本，并在运行时报告非敏感配置摘要。

配置回滚也要考虑新代码是否仍需要新增键。

## 36. 多组件发布安排兼容顺序

Java、Vue、Flutter、Python 和 MCP 不一定同时升级。先部署能够兼容新旧协议的提供方，再逐步升级消费者，最后删除旧契约。

每个阶段都应保持可运行，而不是依赖“一秒内全部完成”。

## 37. AI 和检索制品也要版本化

提示模板、模型选择、Embedding 模型、分块策略和索引版本都会改变结果。发布记录这些版本，并允许新旧索引并行验证和切换。

不要在生产中无记录地替换模型别名后仍沿用旧评估结论。

## 38. 失败注入验证回滚路径

在安全环境模拟新实例健康失败、迁移中断、错误率升高和外部依赖不可用，确认流水线能停止、保留证据并执行预定恢复。

没有演练过的回滚说明，只是一项假设。

## 39. 权限把构建、审批和部署分开

构建任务不必拥有生产部署权；部署身份只允许指定环境和制品来源；高风险生产发布可以要求环境审批。

职责分离降低单个账号或流水线被滥用的影响。

## 40. 发布速度来自小批量和自动证据

更小、兼容的变更更容易理解、验证和回滚。自动化构建、检查、制品追踪与监控减少重复人工操作。

速度不是跳过门禁，而是让门禁快速、可信、可重复。

## 41. 发布完成后清理临时兼容层

迁移结束后，安排删除双写、旧字段、旧开关和旧 API，但只能在使用证据确认安全后执行。清理本身是独立变更并有回滚考虑。

临时方案没有到期机制就会变成永久复杂度。

## 42. 需要时查询当前平台细节

容器注册表签名、CI 环境、编排器发布策略和 PostgreSQL DDL 行为都会演进。真正发布前按当前官方文档和实际版本验证。

长期稳定的是构建一次、不可变制品、兼容迁移、分阶段流量、证据门禁和预演恢复。

## 43. 这一章形成的整体地图

```text
源码与固定输入
  → 可追溯制品、digest、SBOM、来源证明
  → 同一制品逐环境晋级
  → 滚动 / Blue-Green / Canary
  → Expand → Backfill → 切读写 → Contract
  → 版本指标和真实冒烟
  → 应用回滚或数据库前向修复
  → 清理临时兼容层
```
