# Linux、Docker 与 Compose

## 1. 这一章把“在我电脑上能跑”变成“在统一环境里能跑”

应用进入服务器后，会遇到用户权限、文件路径、进程生命周期、网络端口、环境变量和持久化数据等问题。Linux 提供运行基础，Docker 固定应用环境，Compose 描述多个容器怎样组成一个系统。

它们解决的是交付和运行一致性，不会自动修复代码缺陷或架构问题。

## 2. Linux 把很多系统能力表示成文件和进程

配置、日志、设备和程序通常都能通过文件系统或进程工具观察。理解目录、权限、进程、端口和标准输入输出，就能处理大部分基础部署问题。

先学会查看事实，再学习修改命令；生产故障中，证据比熟记大量命令更重要。

## 3. 绝对路径与相对路径

绝对路径从根目录 `/` 开始；相对路径从当前工作目录开始。

```text
/opt/factorycare/app.jar    绝对路径
./config/application.yml   相对路径
```

服务启动时的工作目录可能与交互终端不同，所以关键文件最好使用明确配置，不依赖“碰巧在这个目录”。

## 4. Linux 目录各有常见用途

常见约定包括：

- `/etc`：系统和服务配置；
- `/var/log`：传统日志文件；
- `/var/lib`：服务持久状态；
- `/opt`：可选的应用软件；
- `/tmp`：临时文件，不能当长期存储；
- `/proc`：内核提供的进程和系统信息。

这些是惯例，不是要求所有应用必须照搬。

## 5. 用户和用户组决定身份

Linux 每个进程都以某个用户和组运行。权限判断的核心问题是：这个进程是谁，它要访问的文件属于谁，权限位允许什么。

生产服务不应长期以 `root` 身份运行。被攻破后，低权限账号能缩小影响范围。

## 6. 文件权限分为读、写和执行

权限分别作用于所有者、用户组和其他人：

```text
r：读取
w：写入
x：执行文件，或进入目录
```

目录的执行权限表示能否穿过目录，不等同于执行其中每个文件。排查权限问题要检查路径上每一级目录。

## 7. 最小权限比“全部 chmod 777”可靠

遇到权限错误就开放所有权限，会让任何本机用户或进程都能修改文件。应先确认运行身份和真正需要的操作，再只授予必要权限。

密钥、环境文件和备份尤其不应对所有用户可读。

## 8. 进程是正在运行的程序实例

同一个可执行文件可以启动多个进程。每个进程有 PID、父进程、用户、环境、打开文件和资源使用情况。

查看进程时，不只看“有没有”，还要看它用什么参数、由谁启动、是否反复重启、占用多少 CPU 和内存。

## 9. 前台进程与后台服务

开发时程序通常挂在终端前台；终端关闭后它也会结束。服务器服务需要由进程管理器负责启动、停止、重启、日志和开机自启。

在常见 Linux 系统中，这个角色通常由 systemd 承担。

## 10. systemd 用 unit 描述服务

一个 service unit 会说明启动命令、运行用户、工作目录、环境、依赖和重启策略。常见操作是查看状态、启动、停止和读取日志。

不要把无限重启当作恢复策略。程序配置永久错误时，快速重启只会制造日志风暴。

## 11. 退出码是进程对外报告的结果

退出码 `0` 通常表示成功，非零表示某类失败。部署脚本和服务管理器根据退出码决定下一步。

应用遇到缺少必需配置时应清楚报错并非零退出，而不是表面启动后在首次请求中失败。

## 12. stdout 与 stderr 适合容器日志

正常运行事件写 stdout，诊断和错误写 stderr。容器平台收集这两条流，再交给日志系统。

生产应用通常不应自己管理复杂的容器内日志轮转；否则日志可能随容器删除，或填满容器可写层。

## 13. 信号用于通知进程

服务停止时通常先收到 `SIGTERM`，应用应停止接收新请求、完成有限时间内的在途工作并释放资源。超时后才可能被强制终止。

优雅停机不是无限等待，必须有明确上限。

## 14. 端口属于监听进程

服务监听某个地址和端口，例如 `0.0.0.0:8080`。排查“无法访问”时依次确认：

```text
进程是否存在
→ 是否监听预期地址和端口
→ 本机能否访问
→ 容器/主机网络是否放行
→ DNS 和代理是否指向正确位置
```

只看到进程存在不能证明端口已正常服务。

## 15. DNS 把名称解析成地址

应用通常依赖服务名而不是固定 IP。DNS 解析成功后，仍要建立 TCP 连接、完成 TLS（如有）并发送应用协议请求。

“域名能解析”和“服务可用”是不同阶段。

## 16. 常见网络排查要分层

- `dig` 或 `nslookup` 看 DNS；
- `curl -v` 看 HTTP/TLS 交换；
- `ss` 看本机监听和连接；
- `ping` 只能说明特定 ICMP 路径，不代表 HTTP 可用；
- 应用日志和 trace 看请求是否到达。

不要用单一命令推断整条链路。

## 17. 环境变量用于注入运行配置

镜像保持相同，部署环境通过环境变量或挂载配置改变数据库地址、日志级别等。配置名、类型、是否必需和默认值应明确记录。

环境变量会被子进程继承，也可能被诊断工具看见，因此不能认为它天然安全。

## 18. Docker 镜像是只读的应用模板

镜像由多层文件系统和元数据组成，包含运行应用所需的文件、入口和默认配置。镜像应可重复构建并有不可变标识。

标签如 `latest` 可以被重新指向；生产证据应记录明确版本，重要场景可固定 digest。

## 19. 容器是镜像的运行实例

容器不是轻量虚拟机的完整替代品。它通常与主机共享内核，但拥有隔离的进程、网络和文件系统视图，并受资源和权限限制。

删除容器不会删除镜像，但容器可写层中的未挂载数据会一起消失。

## 20. Dockerfile 是构建配方

Dockerfile 逐步定义基础镜像、复制文件、安装依赖、构建产物、运行用户和入口。构建上下文只应包含需要的文件，使用 `.dockerignore` 排除源码外的秘密、缓存和大型目录。

不要把密码写入 `ARG`、`ENV` 或构建层；即使后面删除，也可能留在历史层中。

## 21. 镜像层会被缓存

Docker 根据指令和输入复用构建层。把变化少的依赖描述放前面、频繁变化的源码放后面，可以减少重复下载和构建。

缓存提高速度，不是正确性来源。依赖版本仍要锁定，构建结果仍要验证。

## 22. 多阶段构建把编译环境与运行环境分开

```text
builder 阶段：JDK、Maven、源码 → app.jar
runtime 阶段：较小运行时 + app.jar
```

最终镜像不必包含 Maven、编译缓存和全部源码，体积与攻击面更小。Python 或前端构建也可采用同样思路。

## 23. 基础镜像需要明确选择和维护

选择受维护、来源可信且满足运行需要的基础镜像。较小镜像不一定总是更安全：过度精简会增加诊断和兼容成本。

基础镜像即使标签不变也会更新，因此要安排重建、漏洞扫描和升级，而不是一次构建后永久不动。

## 24. 容器内使用非 root 用户

Dockerfile 在复制应用、准备目录后切换到专用用户。运行目录、临时目录和挂载卷要预先拥有正确权限。

容器内 root 仍然是高权限身份；容器隔离不应成为放弃最小权限的理由。

## 25. PID 1 有特殊责任

容器入口进程通常是 PID 1，它需要正确接收信号并回收子进程。Shell 包装脚本如果没有使用 `exec` 交出进程位置，停止信号可能到不了 Java 或 Python 应用。

入口尽量直接、明确，复杂初始化应谨慎设计。

## 26. 容器最好保持无状态

应用实例的可替换性越强，滚动发布和故障恢复越简单。上传文件、数据库和队列数据应放到明确的持久化服务或卷中。

“无状态”不代表业务没有状态，而是单个应用容器不拥有不可替代的唯一状态。

## 27. Volume 保存需要跨容器存在的数据

命名卷由 Docker 管理，绑定挂载把指定主机路径映射进容器。开发时绑定源码很方便；生产时要考虑路径、权限、备份和主机迁移。

创建了卷不等于完成备份。卷损坏或误删仍会丢失数据。

## 28. 端口发布连接主机与容器

容器服务监听内部端口；`ports` 可把主机端口映射过去。只有需要从宿主机或外部访问的服务才发布端口。

数据库若只供同一 Compose 网络内应用使用，通常不需要公开到所有主机网卡。

## 29. 容器网络使用服务名发现彼此

Compose 默认网络中，服务可以用服务名访问，例如应用连接 `postgres:5432`，而不是 `localhost:5432`。

容器里的 `localhost` 指当前容器自身，这是初学部署时最常见的误区之一。

## 30. Compose 描述一组相关服务

`compose.yaml` 可以声明应用、数据库、Redis、消息队列、网络、卷、环境和健康检查。它适合本地集成环境、小规模部署和可重复演示。

Compose 不是完整集群调度器，但对于 FactoryCare 的单机环境非常实用。

## 31. 服务依赖不等于服务已经可用

数据库进程先启动，不代表它已经能接受连接。只写启动顺序时，应用仍可能在数据库初始化期间失败。

应给依赖配置真实健康检查，并让下游按健康条件等待，应用本身也要有有限重试和清楚错误。

## 32. 健康检查必须验证真实能力

一个有效检查应快速、稳定，并验证服务完成核心准备。例如数据库能接受简单连接，API readiness 能访问必要依赖。

只检查“进程还在”或固定返回 200，会掩盖线程池耗尽、迁移失败和依赖不可用。

## 33. 存活与就绪是两个问题

```text
liveness：进程是否陷入无法自行恢复的状态
readiness：当前是否应该接收流量
```

数据库短暂故障时，应用可能仍存活但不应接收需要数据库的请求。错误地让存活检查依赖所有下游，会引发无意义重启。

## 34. Compose 配置要区分默认值和秘密

普通本地默认配置可以进入版本库；密码、Token 和证书私钥不能。敏感值通过受控秘密管理或部署环境注入。

`.env` 文件便于本地使用，但它仍是明文文件，必须避免提交并限制权限。

## 35. Compose 网络按信任边界拆分

可以让 Nginx 同时加入外部网络和应用网络，让应用加入应用与数据网络，而数据库只加入数据网络。

网络隔离不是认证和授权的替代品，但能减少不必要的可达路径。

## 36. Profiles 与多文件组合用于环境差异

开发环境可能需要数据库管理界面和源码热更新，生产环境不需要。可以用 profiles 或明确的覆盖文件表达差异。

配置合并容易产生意外结果，发布前应查看最终展开后的 Compose 配置，而不是只读某一个文件。

## 37. 资源限制防止单个容器拖垮主机

为 CPU、内存、进程数和日志大小制定边界。Java 堆大小还要与容器总内存协调，给原生内存、线程栈和系统组件留空间。

资源限制设置过小会频繁 OOM，完全不设又可能影响整台机器；应根据测量逐步调整。

## 38. 只读文件系统降低意外写入

如果应用只需写临时目录，可把根文件系统设为只读，只为明确目录提供临时或持久挂载。这能暴露隐藏写入依赖并减小被篡改范围。

启用前先梳理 JVM/Python 临时文件、证书、缓存和上传路径。

## 39. 不把开发工具留在生产容器

编译器、包管理器、Shell 和调试工具会增加体积与攻击面。但完全移除所有工具也会影响现场诊断。

常见取舍是生产镜像保持精简，另准备受控的诊断容器或临时工具环境。

## 40. 容器启动失败按层定位

```text
镜像是否存在且架构正确
→ 入口和参数是否正确
→ 配置与秘密是否齐全
→ 文件权限是否允许
→ 依赖 DNS、端口和健康是否正常
→ 应用日志和退出码是什么
```

不要在失败容器里不断手工修改；定位后回到 Dockerfile、Compose 或配置源修复，才能保证下次可重复。

## 41. 可重复构建需要固定输入

源码提交、依赖锁定、构建工具版本、基础镜像和构建参数共同决定产物。构建记录这些输入，才能回答“线上运行的到底是哪一版”。

同一版本号不应对应多个不同镜像。

## 42. 本地 Compose 是生产链路的近似，不是证明

它能提前发现服务名、端口、配置、迁移和启动顺序问题，但无法完全模拟生产证书、资源压力、备份、外部负载均衡和真实权限。

因此本地通过后，还需要部署环境的冒烟检查和可观测性证据。

## 43. 需要时再查询具体命令和字段

Dockerfile、Compose 规范、systemd 选项和各镜像使用方式都会演进。真正配置时查当前官方文档和所用镜像说明，不靠背诵某一版字段。

长期要掌握的是进程、权限、网络、文件系统、不可变镜像、健康和持久化这些模型。

## 44. 这一章形成的整体地图

```text
Linux 用户 / 文件 / 进程 / 信号 / 端口
  → Docker 镜像与容器
  → 多阶段构建、非 root、不可变运行
  → 网络、端口、卷与配置
  → Compose 服务编排
  → 健康、就绪、依赖与资源限制
  → 可重复构建和分层排障
```
