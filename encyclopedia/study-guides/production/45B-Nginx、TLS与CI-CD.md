# Nginx、TLS 与 CI/CD

## 1. 这一章连接“用户请求”与“可靠交付”

Nginx 位于用户和应用之间，负责接入、转发和静态资源；TLS 保护传输；CI/CD 把代码变更稳定地变成可部署制品。

三者共同回答两个问题：请求怎样安全到达正确服务，以及正确版本怎样安全到达服务器。

## 2. 反向代理替后端接收外部请求

```text
浏览器 → Nginx → Java API
               → Nuxt / 静态前端
               → Python AI 服务（通常经内部 API）
```

客户端只看到 Nginx 的公开地址。Nginx 根据主机名和路径选择内部服务，并隐藏内部端口布局。

## 3. 反向代理与正向代理方向不同

正向代理代表客户端访问外部服务；反向代理代表服务端集群接收客户端请求。Nginx 在 FactoryCare 中通常是反向代理。

理解“代理代表谁”比记名称更重要。

## 4. Nginx 配置有层级和匹配规则

常见层级包括全局、`events`、`http`、`server` 和 `location`。一个请求先选择 `server`，再根据 URI 选择 `location`。

匹配规则有精确、前缀和正则等形式。配置复杂时要用真实 URI 验证，不凭肉眼猜最终命中位置。

## 5. server_name 和监听端口决定入口

一个站点通常按域名和端口区分：

```text
factorycare.example.com:443
api.factorycare.example.com:443
```

DNS 把域名指向服务器，Nginx 再根据请求中的主机名选择虚拟主机。DNS 正确不代表 Nginx 一定配置正确。

## 6. proxy_pass 决定转发目标和 URI 处理

`proxy_pass` 末尾是否带路径，会影响转发后的 URI。这个细节很容易让 `/api/orders` 变成意外地址。

配置时写出几个输入 URI 和期望上游 URI，用真实请求确认。不要仅靠记忆斜杠规则。

## 7. 转发头保留原始请求信息

后端常需要知道原始主机、协议和客户端地址。代理应设置受控的转发头，例如 Host 和标准 Forwarded/X-Forwarded 信息。

后端只能信任来自已知代理的这些头；若直接相信任意客户端提交的 `X-Forwarded-For`，审计和安全判断会被伪造。

## 8. 客户端 IP 是一条信任链

请求可能经过 CDN、负载均衡和 Nginx。每一层需要知道哪些上游代理可信，才能提取真实客户端地址。

记录完整链路并在可信边界解析，不要简单取用户可控列表中的第一个值。

## 9. 超时要对应实际阶段

代理连接上游、发送请求、等待上游数据和发送给客户端是不同阶段。某些 Nginx timeout 表示两次读写之间允许的间隔，并不一定是整个请求总时长。

具体字段和默认值应按当前官方文档确认；设计层面先建立端到端时间预算。

## 10. 请求体大小需要限制

上传接口要明确允许的最大正文。Nginx、Java、Python 和对象存储若限制不一致，用户会在不同层得到不同错误。

大文件通常应流式处理或直传对象存储，不要让每一层都把完整文件读入内存。

## 11. 缓冲影响流式接口

普通响应使用代理缓冲可以提高吞吐；SSE、逐步输出或模型流式响应需要及时向客户端转发，过度缓冲会让用户最后一次性看到全部内容。

只对确实需要的路由调整缓冲，并同时考虑压缩、超时和中间 CDN。

## 12. WebSocket 和长连接需要显式支持

协议升级、连接头和超时与普通短 HTTP 请求不同。若 FactoryCare 使用 WebSocket，要在对应路径配置升级并验证断线、重连和负载均衡行为。

SSE 仍是 HTTP 响应流，不等同于 WebSocket。

## 13. 静态文件可以由 Nginx 直接提供

构建后的 JS、CSS、字体和图片适合由 Nginx 或 CDN 分发。带内容哈希的资源可长期缓存；入口 HTML 通常要更谨慎缓存，以便引用最新资源。

缓存策略应与构建文件名策略配套。

## 14. SPA 路由需要回退到入口文件

Vue 单页应用在浏览器直接打开 `/work-orders/123` 时，服务器文件系统没有同名文件。Nginx 可在找不到静态资源时回退到 `index.html`，让前端路由接管。

API 路径不能也被回退为 HTML，否则客户端会把错误页面当 JSON 解析。

## 15. Nuxt 的部署方式取决于渲染模式

纯静态输出可以像普通静态站点分发；需要服务端渲染时，Nginx 代理到 Nuxt 进程。两种模式对缓存、健康检查、进程管理和资源需求不同。

部署前先确认产物类型，不把所有 Nuxt 项目都当静态文件。

## 16. TLS 保护传输中的机密性和完整性

HTTPS 通过 TLS 让客户端验证服务器身份，并加密双方传输，降低窃听和篡改风险。

TLS 不会验证业务数据本身是否正确，也不会替代登录、授权或输入校验。

## 17. 证书把域名与公钥联系起来

证书由受信任的证书机构签发，包含域名、公钥、有效期等信息。服务器还持有对应私钥。

私钥绝不能进入源码仓库或镜像公开层；泄露后需要更换密钥和证书，而不只是删除文件。

## 18. TLS 握手建立安全连接

客户端验证证书链、域名和有效期，双方协商协议与算法，并建立会话密钥。握手成功后才传输受保护的 HTTP 数据。

服务器时间严重错误、证书链缺失或域名不匹配都会造成连接失败。

## 19. HTTP 应重定向到 HTTPS

公开站点通常在 80 端口只做跳转，在 443 提供服务。稳定后可使用 HSTS 告诉浏览器一段时间内只用 HTTPS。

HSTS 配置错误会长期阻止 HTTP 回退，启用前要确认全部相关子域都已正确支持 TLS。

## 20. 现代 TLS 配置应跟随维护中的基线

安全协议、算法和浏览器支持会变化，不应从旧文章复制一串永久不变的 cipher。使用当前 Nginx、操作系统或可信安全基线的推荐配置，并持续更新。

讲义需要记住的是及时禁用过时协议、保护私钥、自动续期和验证实际配置。

## 21. 证书续期是运行流程

自动签发工具可以续期，但仍要监控到期时间、续期作业和 Nginx 重新加载是否成功。只有“配置了自动续期”而没有告警，仍可能在某天突然过期。

续期演练要覆盖失败通知和恢复步骤。

## 22. 安全响应头是额外保护层

内容安全策略、禁止 MIME 猜测、Referrer 策略等响应头可以降低部分浏览器攻击风险。它们需要根据前端真实资源逐步收紧。

不要复制一组头后就宣布安全完成；错误 CSP 可能破坏应用，过宽 CSP 又没有保护价值。

## 23. 限流和连接限制保护入口

Nginx 可以按可信客户端标识限制请求速率和并发连接，用于削峰和基础滥用防护。

限流维度要考虑登录用户、IP、租户和接口成本。NAT 后大量真实用户可能共享 IP，单纯按 IP 会误伤。

## 24. 配置修改先检查语法

加载前用 Nginx 自带配置检查确认语法和引用文件，再进行平滑 reload。reload 让新工作进程使用新配置，旧连接在合理范围内完成。

语法通过只证明能解析，仍需用真实域名、TLS 和路由做冒烟检查。

## 25. CI 是每次变更的自动质量入口

Continuous Integration（持续集成）在推送或合并请求时自动获取代码、安装固定工具、构建并运行检查。它让同一套规则不依赖某个人的电脑状态。

CI 成功表示定义的检查通过，不表示所有未定义风险都不存在。

## 26. 工作流由触发条件、任务和步骤组成

常见触发包括推送、合并请求、版本标签和手动启动。任务可以并行或通过依赖关系排序，每个步骤执行一个清晰动作。

把失败定位到具体任务，比一个超长脚本更容易维护。

## 27. CI 环境应从干净状态构建

流水线不能依赖开发者本地已有的 `target`、`node_modules` 或秘密文件。每次从源码与明确依赖开始，才能发现缺失声明和不可重复构建。

本地生成物应被忽略，而不是意外提交来“帮助”CI。

## 28. 工具链版本需要固定

JDK、Maven、Node、Python、Docker action 和操作系统镜像的版本变化都可能影响结果。应明确版本并定期升级，而不是永远使用会漂移的模糊标签。

版本更新单独审查，失败时更容易回滚和定位。

## 29. 依赖缓存不是构建制品

缓存用于加速可重新下载或生成的依赖，例如 Maven 和包管理器缓存；artifact（制品）是某次任务要交给后续任务或留作证据的输出。

缓存可能缺失或被污染，流水线必须在无缓存时仍然正确。来自不可信分支的缓存也要按不可信输入对待。

## 30. 构建一次，逐环境提升同一制品

推荐链路：

```text
源码提交
→ 构建并检查
→ 生成带唯一标识的镜像
→ 部署测试环境
→ 验证
→ 将同一镜像提升到生产
```

如果每个环境重新构建，就无法证明生产使用的是已经验证过的那份内容。

## 31. 制品需要可追溯

镜像或包至少关联源码提交、构建编号、依赖信息和创建时间。生产运行记录镜像 digest，而不只记录可移动标签。

这样故障时能从运行实例追溯到代码、流水线和变更审查。

## 32. CI 中的秘密只给必要步骤

普通合并请求通常不需要生产凭据。秘密应按环境和权限隔离，避免输出到日志，也避免传给不可信第三方 action 或 fork 代码。

优先使用短期身份和工作负载联合认证，减少长期静态密钥。

## 33. 第三方 action 和构建依赖属于供应链

工作流运行的 action 本身就是代码。应选择可信来源、固定不可变版本或提交，并限制它得到的令牌权限。

自动化越强，流水线凭据越有价值，供应链审查越重要。

## 34. 必需检查保护主分支

格式、编译、单元与集成检查、安全扫描和镜像构建可按项目风险设置为合并前必需。快速检查先运行，昂贵检查在必要时继续。

保护规则必须与团队实际流程一致，不能允许任意跳过后仍宣称主分支可发布。

## 35. 失败时保留有用证据

CI 失败应保留结构化报告、必要日志和环境信息。日志不得包含秘密或完整敏感请求。

证据有保留期限；容量和隐私也要纳入设计。

## 36. 并发控制避免旧部署覆盖新部署

同一环境的多个部署同时运行时，较旧流水线可能晚于新流水线完成并覆盖它。为环境设置并发组、队列或取消策略，可以保证部署顺序可解释。

数据库迁移等不可随意取消的步骤，需要更谨慎的锁和恢复策略。

## 37. CD 不等于每次自动上生产

Continuous Delivery（持续交付）表示软件始终处于可发布状态，生产发布可以有人工批准；Continuous Deployment（持续部署）则让通过策略的变更自动进入生产。

选择取决于风险、团队成熟度和监管要求，不是自动化越多越先进。

## 38. 环境审批展示具体部署内容

审批者应看到制品版本、变更摘要、检查结果、迁移计划、风险和回滚方式。只显示一个“Deploy”按钮无法形成有意义的批准。

批准的是确定制品和确定环境，不是一张空白授权。

## 39. 部署完成后仍需验证

至少检查：

- 进程和容器是否健康；
- Nginx 是否能通过真实 HTTPS 域名访问；
- 核心 API 和身份流程是否正常；
- 新旧实例是否运行预期版本；
- 错误率、延迟和资源是否异常。

流水线命令退出 0 只是部署步骤成功，不代表用户路径已经可用。

## 40. 发布流程必须包含失败路径

在执行前明确：迁移失败怎么办、健康检查失败怎么办、部分实例已更新怎么办、是否能回滚旧镜像、数据是否向后兼容。

回滚不能只写成一句“重新部署上一版”，它需要可执行步骤和事前验证。

## 41. Nginx 与应用日志使用同一关联信息

入口生成或传递 request/trace ID，Nginx 访问日志记录它，后端继续传播。出现 502、504 或用户错误时，能沿同一个标识查完整链路。

日志中要区分客户端断开、代理超时、上游拒绝和应用主动返回。

## 42. 502 与 504 指向不同方向

`502 Bad Gateway` 常表示代理无法获得有效上游响应；`504 Gateway Timeout` 表示等待上游超时。它们是入口观察到的现象，不直接等同于根因。

继续检查上游是否启动、DNS/网络、TLS、连接池、应用日志和资源压力。

## 43. 配置和流水线也要进入版本审查

Nginx、Compose、CI 工作流和部署脚本都是生产代码。它们需要代码审查、变更历史、静态检查和受控发布。

不要在服务器上手改后忘记回写；那会产生无法重现的隐藏状态。

## 44. 需要时查询当前规范

Nginx 指令语义与默认值、TLS 推荐基线、CI 平台字段和第三方 action 都可能变化。实施时查当前官方文档并固定实际版本。

长期不变的是代理信任边界、端到端时间预算、不可变制品、最小权限和证据化发布。

## 45. 这一章形成的整体地图

```text
DNS / HTTPS 请求
  → TLS 身份与加密
  → Nginx 路由、头、超时、缓存和限流
  → 应用服务

代码变更
  → CI 干净构建与质量门
  → 可追溯不可变制品
  → 环境审批与部署
  → 冒烟、监控、失败处理和回滚
```
