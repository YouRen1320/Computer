# 日志、指标、链路、SLO 与性能

## 1. 可观测性帮助我们从外部证据理解系统内部状态

生产系统的问题很少能靠单条报错解释。一个请求可能经过 Nginx、Java、Python、数据库和模型服务。可观测性就是提前留下足够证据，让团队能回答“发生了什么、影响多大、原因在哪里”。

Observability（可观测性）不是购买一个监控平台，也不是打印更多文字。

## 2. 监控与可观测性侧重点不同

传统监控常回答已知问题，例如 CPU 是否超过阈值；可观测性还希望支持尚未预料的问题，例如“只有某租户在新版本上出现哪条调用链变慢”。

两者并不冲突：可靠系统既需要固定告警，也需要可探索的证据。

## 3. 常见信号包括日志、指标和链路

```text
日志 logs：某个时刻发生的一条事件
指标 metrics：一段时间内可聚合的数值
链路 traces：一次请求跨组件经过的步骤
```

OpenTelemetry 还把 baggage 等上下文传播机制单独描述。各种信号互补，没有一种能替代全部其他信号。

## 4. 日志记录离散事件

适合记录启动、配置装载结果、请求完成、状态变化、外部依赖失败和安全审计事件。每条日志应有明确用途。

“进入方法”“变量值是……”这类无目标日志在生产量大且噪声高，调试价值通常有限。

## 5. 结构化日志比拼接句子更易查询

```json
{
  "event": "work_order_closed",
  "workOrderId": "WO-123",
  "tenantId": "T-8",
  "traceId": "...",
  "durationMs": 42
}
```

字段有稳定名称和类型，日志平台才能可靠筛选和聚合。自然语言 `message` 可以保留，但不应承担全部结构。

## 6. 日志级别表达处置意义

- `DEBUG`：开发或临时诊断细节；
- `INFO`：正常生命周期和重要业务事件；
- `WARN`：出现异常状况但当前请求可能仍可完成；
- `ERROR`：当前操作失败或系统需要处理。

级别不是情绪强度。可预期的用户输入错误通常不该每次都记成 ERROR。

## 7. 异常只在能处理或补充上下文的位置记录

同一个异常若在每层都打印堆栈，会产生多条重复 ERROR。一般由边界层记录一次完整异常，并附上业务动作、资源标识和关联 ID。

中间层若只是继续抛出，不必重复记录；若转换异常，要保留原始 cause。

## 8. 日志中不得出现秘密和不必要的个人数据

密码、Token、Cookie、私钥、完整请求头、银行卡信息等不能写日志。姓名、电话、工单描述也应按用途最小化和脱敏。

日志通常被复制到多个系统并长期保留，一次泄露会扩大影响范围。

## 9. 审计日志与诊断日志目的不同

诊断日志帮助工程师排障；审计记录回答谁在什么时间对什么资源做了什么、结果怎样。

审计数据需要更强的完整性、访问控制和保留策略，不能因为应用日志轮转就丢失。

## 10. 关联 ID 把分散日志串成一次请求

入口生成或接受受控格式的 trace/request ID，后续调用通过标准上下文传播。每个组件把它写入日志。

关联 ID 不是秘密、身份或幂等键。它只帮助定位同一条技术调用链。

## 11. 指标是带维度的时间序列

例如请求计数、错误计数、延迟分布、队列长度、数据库连接使用量和 JVM 堆占用。指标适合聚合趋势和触发告警。

指标通常不能说明某一个具体请求的完整细节，这时要跳转到 trace 或日志。

## 12. Counter 表示只增不减的累计量

请求总数、失败总数、处理工单数适合使用 Counter。查询时通常看单位时间增长率，而不是从进程启动开始的绝对值。

进程重启会让本地累计值重置，监控系统需要正确处理。

## 13. Gauge 表示当前瞬时状态

当前队列长度、在线任务数、内存使用量可以用 Gauge。它可以上升也可以下降。

不要用 Gauge 表示累计事件，否则抓取之间发生的变化可能丢失。

## 14. Histogram 描述数值分布

只看平均延迟会掩盖少量极慢请求。Histogram（直方图）把请求时长放入区间，进而估算 P50、P95、P99 等分位数。

桶边界应覆盖业务关心的范围；改变桶定义会影响历史比较。

## 15. 百分位回答“多数用户有多慢”

P95 为 800ms 表示约 95% 的观测不超过 800ms，剩余约 5% 更慢。它不是“最慢请求”，也不能仅凭两个百分位还原完整分布。

选择 P95 还是 P99 取决于流量、业务风险和尾部体验。

## 16. 指标标签必须控制基数

`method`、规范化 `route`、状态类别适合作为标签；用户 ID、工单 ID、完整 URL 和 trace ID 会产生海量唯一组合。

高基数会显著增加内存、存储和查询成本。具体实例细节放到日志或 trace，指标保留可聚合维度。

## 17. HTTP 服务先看四个黄金信号

一个实用起点是：

- 流量：每秒请求数；
- 错误：失败率及错误类别；
- 延迟：成功与失败请求的分布；
- 饱和度：线程、连接、CPU、内存或队列是否接近上限。

它们覆盖用户体验和资源压力，但仍需结合业务指标。

## 18. 业务指标说明系统是否创造正确结果

例如工单创建成功率、超时工单数量、AI 建议采纳率、任务积压年龄。CPU 很健康但所有工单都无法提交，系统仍然不可用。

业务指标定义要与产品含义一致，不能为了好看而排除真实失败。

## 19. Trace 表示一次请求的因果路径

一条 trace 由多个 span 组成，每个 span 表示一个操作，有开始时间、持续时间、状态、属性和父子关系。

```text
HTTP POST /work-orders
  ├─ Java validation
  ├─ PostgreSQL INSERT
  └─ Python classify
       └─ model request
```

它能看出时间花在哪一层，以及错误从哪里开始。

## 20. Span 属性保持低基数且有语义

使用标准语义约定记录 HTTP 方法、规范化路由、服务名、数据库系统等。工单 ID 若业务确实需要，可谨慎放在受控日志或受保护 span 属性中。

属性也可能包含敏感数据，不能因为 trace 只给工程师看就忽略隐私。

## 21. 上下文传播是链路连续的前提

HTTP、消息队列和异步任务都要传递 trace context。若某个服务重新生成完全无关的 ID，链路会在边界断开。

对外部不可信请求头要解析和限制；内部传播也不能把认证信息混进 trace baggage。

## 22. 采样控制成本

全量保存每条 trace 在高流量下成本很高。可以按比例采样、优先保留错误/慢请求，或在收集端根据完整结果决定。

采样策略会影响可见性。错误数量依赖指标，不应只按采样 trace 估算真实失败率。

## 23. OpenTelemetry 提供统一采集方式

OpenTelemetry 定义 API、SDK、语义约定和 Collector，帮助应用产生并导出日志、指标和 trace。它不是最终存储或展示产品。

代码埋点和零代码自动埋点可以配合：自动埋点覆盖框架调用，手工埋点补充业务语义。

## 24. Collector 解耦应用与后端平台

应用把遥测数据发给 Collector，Collector 可以批量、过滤、脱敏、采样并导出到一个或多个后端。

Collector 也是生产组件，需要资源限制、健康检查、队列、重试和自身监控。

## 25. 健康接口服务于自动化判断

通常区分：

```text
/live：进程是否还具备继续运行的基本能力
/ready：此刻是否适合接收新流量
```

健康响应不应暴露完整配置、依赖地址、堆栈或凭据。

## 26. 就绪检查只包含必要依赖

如果创建工单必须访问 PostgreSQL，那么数据库不可用时相关实例不应接流量。一个非关键统计服务失败，未必需要让全部 API 下线。

依赖关系要按功能和降级方案判断，不能把所有下游机械塞进一个总开关。

## 27. SLI 是实际测量值

Service Level Indicator（服务水平指标）是可测量结果，例如成功请求比例或请求在 500ms 内完成的比例。

SLI 应从用户能观察的边界定义，而不是只看内部进程是否存活。

## 28. SLO 是一段时间内的可靠性目标

例如“滚动 30 天内，99.9% 的有效 API 请求成功”。目标包含指标、阈值、统计窗口和排除规则。

SLO 是团队内部工程目标；SLA 是对外承诺，通常还包含合同后果，两者不要混用。

## 29. 100% SLO 通常代价极高

允许一个很小的失败预算，团队才能在可靠性与迭代速度之间做明确取舍。若系统已经消耗过多预算，应减少高风险变更，优先恢复可靠性。

错误预算不是允许团队故意制造错误，而是承认复杂系统不可能永远完美。

## 30. 可用性计算要定义有效请求

用户输入非法、没有权限的请求一般不应算服务故障；服务内部异常、超时和错误拒绝则可能算。限流是否计入取决于服务承诺。

排除规则越多，指标越容易失真，因此必须少而透明。

## 31. 延迟 SLO 通常只针对成功请求但要单独看失败

失败请求往往很快，若混进延迟分布，系统大量快速报错时平均延迟反而变好。延迟和成功率应分开衡量，再共同判断用户体验。

还可按关键路由分 SLO，不让大量简单健康请求掩盖核心流程。

## 32. 告警应指向需要行动的问题

一个好告警说明影响、严重度、相关仪表盘和初步处置入口。没有人需要响应的波动不应叫醒值班人员。

阈值过敏会造成告警疲劳，最后真正事故也被忽略。

## 33. 基于错误预算消耗速度告警

Burn rate（燃烧率）表示错误预算消耗有多快。短窗口发现快速严重故障，长窗口发现缓慢持续退化。

相比单一瞬时错误率，它更贴近 SLO 是否面临风险。

## 34. 仪表盘围绕问题组织

首页先展示用户结果和 SLO，再下钻到 API、依赖、数据库、JVM/Python 和基础设施。每张图都应回答一个问题。

堆满几十条颜色曲线但没有单位、阈值和用途，不等于有可用监控。

## 35. 性能是满足目标所需资源的能力

性能不只是“越快越好”。需要同时看延迟、吞吐、错误率、资源消耗和成本，并明确负载条件。

一次本机调用 10ms，不能证明 500 并发用户下也能达到目标。

## 36. 先测量再优化

优化流程是：

```text
定义目标和代表性负载
→ 建立基线
→ 找最大瓶颈
→ 只改变一个主要因素
→ 重新测量
→ 检查功能和资源副作用
```

凭直觉改代码容易优化不重要路径，甚至让系统更复杂。

## 37. 延迟由排队和服务时间组成

即使每个请求实际计算只需 50ms，资源饱和后等待线程、连接或 CPU 的排队时间也可能占大头。

接近容量上限时，延迟往往非线性恶化，所以要保留余量。

## 38. 吞吐与并发不是同一概念

吞吐是单位时间完成多少工作；并发是同时在处理或等待多少工作。提高并发不一定提高吞吐，可能只增加排队和内存。

线程、连接池和队列大小应与下游真实容量协调。

## 39. 容量规划从需求和单实例测量开始

估计峰值请求、增长、任务大小和容灾余量，再用负载实验测出单实例在 SLO 内的安全吞吐。容量按安全区间规划，而不是压到极限点。

还要考虑发布期间少一部分实例、依赖变慢和突发流量。

## 40. 负载实验要像真实流量

代表性场景应包含不同路由、认证、数据规模、缓存命中率、读写比例和思考时间。只重复一个最简单 GET 会得到过度乐观结果。

实验环境、数据和版本都要记录，结果才可比较。

## 41. 压力、容量和耐久实验目的不同

- 负载实验：目标流量下是否满足 SLO；
- 压力实验：超过目标后怎样失效和恢复；
- 耐久实验：长时间运行是否泄漏、积压或退化；
- 突发实验：短时流量跳升怎样响应。

不同实验不能用一个“性能通过”概括。

## 42. 数据库常是关键瓶颈

观察慢查询、执行计划、锁等待、连接池、缓存命中和数据规模。增加应用线程无法修复缺索引或锁冲突，反而会给数据库更大压力。

优化查询前先确认慢在数据库，而不是网络或应用排队。

## 43. 缓存改善延迟但增加一致性风险

性能数据要同时记录命中率、回源成本、失效行为和热点键。只测全命中会掩盖缓存冷启动和大规模失效时的真实容量。

缓存不可用时要明确是降级回源、限制流量还是拒绝部分功能。

## 44. AI 路径要单独衡量成本和延迟

模型调用的首 token 时间、总时长、输入输出量、失败率、重试和降级比例都影响用户体验与费用。不要让 AI 慢调用占满普通 API 的线程或连接资源。

模型和供应商字段会变化，具体计量按当前官方接口实现。

## 45. 性能改动也需要正确性保护

批处理、缓存、并行化和异步化可能改变顺序、一致性和错误处理。每次优化都要验证业务结果、幂等、权限和审计没有被破坏。

快但错误的工单系统没有价值。

## 46. 观测系统自身也可能失败

日志代理堵塞、Collector 队列满、指标后端不可用时，不能无限阻塞业务请求或填满磁盘。遥测路径要有缓冲边界、丢弃策略和自身告警。

安全审计等关键证据与普通 DEBUG 日志可能采用不同可靠性策略。

## 47. 需要时查询当前工具细节

OpenTelemetry 语义属性、SDK、导出器和监控平台查询语言会演进。使用时按当前官方文档和所选后端确认。

长期稳定的是三类信号分工、上下文传播、基数控制、用户视角 SLI/SLO 和测量驱动优化。

## 48. 这一章形成的整体地图

```text
用户请求与业务结果
  → 结构化日志 + 指标 + Trace
  → 统一上下文与安全采集
  → SLI / SLO / 错误预算
  → 可行动告警与下钻仪表盘
  → 基线、负载、瓶颈与容量规划
  → 用测量验证每次性能改动
```
