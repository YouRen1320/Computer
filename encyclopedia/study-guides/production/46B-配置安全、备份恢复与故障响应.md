# 配置安全、备份恢复与故障响应

## 1. 可靠运行要为错误和意外提前设计

生产事故可能来自错误配置、密钥泄露、依赖故障、误操作、硬件损坏或软件缺陷。可靠性不是保证永不出错，而是限制影响、快速发现、正确恢复并避免重复发生。

这一章把安全配置、供应链、备份、恢复和故障响应放进同一个闭环。

## 2. 配置是随环境变化的运行输入

数据库地址、功能开关、日志级别、超时和资源限制属于配置。源码和镜像保持不变，同一制品通过受控配置运行在不同环境。

配置也需要类型、校验、版本和所有者，不是任意字符串集合。

## 3. 启动时尽早校验必需配置

应用应在接收流量前检查必需字段、格式、范围和相互关系。缺少数据库地址或出现非法超时，应清楚报错并非零退出。

Fail Fast（快速失败）比带着错误配置进入半可用状态更容易定位。

## 4. 默认值只用于安全且明确的情况

开发日志级别可以有合理默认值；生产数据库、租户模式或认证签发者不应悄悄使用开发默认值。

高风险配置宁可要求显式填写，也不要“为了能启动”自动选择危险行为。

## 5. 配置优先级必须可解释

应用可能从默认文件、环境文件、环境变量和命令行读取配置。要明确后者是否覆盖前者，并在启动日志中显示生效来源，但敏感值只能显示已设置或掩码。

同名配置在多层出现时，排障首先确认最终有效值。

## 6. Secret 是需要受保护的敏感配置

密码、API Token、私钥、签名密钥和数据库凭据属于 secret（秘密）。它们与普通配置的区别在于泄露会直接扩大权限。

秘密不能进入 Git、公开镜像、普通日志、截图或聊天记录。

## 7. 秘密管理包含完整生命周期

```text
生成 → 存储 → 分发 → 使用 → 轮换 → 撤销 → 审计
```

把秘密放进一个环境变量只是分发方式之一，不代表生命周期已经安全。

## 8. 使用短期和最小权限凭据

能用短期工作负载身份时，优先于长期静态 Token。每个服务只获得访问必要资源的权限，开发、测试和生产凭据完全分开。

共享一个超级管理员密码会让审计、轮换和隔离都失去意义。

## 9. 秘密轮换不能依赖停机手工替换

可采用一段时间内同时接受新旧凭据：先让消费者支持新值，再切换提供方，确认无旧调用后撤销旧值。

轮换过程要有所有者、时间限制、监控和回滚办法。

## 10. 泄露后的首要动作是撤销

从 Git 删除秘密并不能让历史副本失效。发现泄露后先评估范围、撤销或轮换凭据、检查异常使用，再清理传播副本和改进流程。

不要为了隐藏证据而先破坏审计记录。

## 11. 配置变更也应走审查和发布流程

超时、限流、权限开关和连接池的变更都可能造成事故。非敏感配置可以版本化；敏感值的元数据和引用可以审查，但明文本身放在秘密系统中。

紧急修改后仍要补齐记录，避免服务器状态与版本库长期漂移。

## 12. Feature Flag 把发布与启用分开

功能代码可以先部署但默认关闭，再按租户或比例逐步启用。它能降低发布风险，却也增加分支和配置复杂度。

开关需要所有者、过期日期、默认行为和故障时的安全值。长期不清理会形成隐藏系统。

## 13. 外部输入一律不可信

HTTP 参数、上传文件、消息、AI 输出、MCP 内容和第三方 API 数据都要在边界校验。类型正确也不代表内容安全或业务允许。

校验包括长度、范围、格式、资源权限、租户和当前状态。

## 14. XSS 来自不可信内容被当成可执行页面

Cross-Site Scripting（跨站脚本）通常发生在用户内容未经正确上下文转义就写入 HTML、属性或脚本。前端框架的普通文本绑定会帮助转义，但直接插入原始 HTML 仍然危险。

处理方式包括默认输出编码、严格限制富文本、内容安全策略和避免动态执行字符串。

## 15. SSRF 来自服务端替用户访问任意地址

Server-Side Request Forgery（服务端请求伪造）可能让攻击者借应用访问内部管理接口、云元数据或本机服务。

对用户提供的 URL 采用允许的协议和目标清单、解析后校验地址、限制重定向、阻止私有/保留网段，并在网络层进一步限制出口。

## 16. 上传文件要同时检查内容和处理路径

文件名、扩展名和客户端 Content-Type 都可伪造。服务端限制大小、检测实际类型、生成自己的存储名、隔离存储，并在需要时扫描。

不要把上传目录直接当可执行或可信静态内容目录。

## 17. 依赖也是进入系统的代码

Java、Node、Python、Docker 基础镜像和 CI action 都属于软件供应链。需要明确来源、锁定版本、审查变更并持续扫描已知风险。

扫描报告是风险线索，不是自动修复器；团队仍要判断可利用性、替代版本和升级影响。

## 18. SBOM 是制品的软件成分清单

Software Bill of Materials（软件物料清单）记录制品包含的组件和版本。出现新漏洞时，可以快速回答哪些发布版本受影响。

SBOM 要和具体制品 digest 绑定；一份与实际镜像无关的清单价值很低。

## 19. 制品签名和来源证明增强信任

构建系统可以为制品生成签名和 provenance（来源证明），记录由哪条受控流水线、基于哪个源码提交产生。

部署端验证身份、制品摘要和策略，避免仅凭一个可移动标签拉取未知内容。

## 20. 构建环境需要最小权限和隔离

不可信合并请求不应接触生产秘密。构建任务只拿完成当前步骤所需权限，第三方脚本不能默认获得仓库写权限或云管理员身份。

构建输出也视为不可信，经过检查后才能提升为可发布制品。

## 21. 备份是独立于在线数据的可恢复副本

数据库副本、只读节点或同一磁盘快照不一定是充分备份，因为误删除、错误迁移和账号被攻破可能同步影响它们。

备份需要隔离故障域、限制访问并有保留策略。

## 22. RPO 表示最多可接受丢失多少数据

Recovery Point Objective（恢复点目标）回答“恢复后最多回到多久以前”。RPO 为 15 分钟意味着事故时可能丢失最近约 15 分钟变化。

更小 RPO 往往需要更频繁备份、日志归档或同步复制，成本也更高。

## 23. RTO 表示最多可接受中断多久

Recovery Time Objective（恢复时间目标）回答“从事故发生到恢复服务允许多久”。它包含发现、决策、准备环境、恢复数据和验证的全部时间。

一份恢复需六小时的备份无法满足一小时 RTO。

## 24. 先按业务重要性确定恢复目标

核心工单数据、审计数据、可重新生成的搜索索引和临时缓存不必使用同一备份方案。根据业务后果确定 RPO、RTO、保留期和恢复顺序。

全部数据追求最高级别会非常昂贵，也可能拖慢恢复。

## 25. PostgreSQL 备份有逻辑和物理路线

逻辑备份按数据库对象导出，便于选择性恢复和跨部分版本迁移；物理备份保存数据库文件与日志，适合大规模和时间点恢复。

具体工具、兼容范围和步骤应按当前 PostgreSQL 官方文档设计并验证。

## 26. 时间点恢复依靠基础备份和持续日志

Point-in-Time Recovery（PITR，时间点恢复）可以把数据库恢复到误操作前的某一时刻。它需要完整基础备份、连续归档的写前日志和可靠时间信息。

缺少中间一段日志会让恢复链断裂。

## 27. 备份必须加密并限制访问

备份往往包含比在线查询更完整的数据。它应在传输和静态存储时加密，使用独立权限，并记录读取和删除行为。

加密密钥本身也需要备份和恢复方案，否则加密后的副本可能永远无法使用。

## 28. 保留策略平衡恢复、法规和成本

可以组合每日、每周、每月备份，并按业务和法规保留。过早删除无法满足追溯；无限保留则增加成本和隐私风险。

删除策略同样需要审计和防误操作保护。

## 29. 只有成功恢复过的备份才可信

备份任务显示成功，只证明文件可能写完，不证明内容完整、密钥可用、步骤正确或时间达标。

定期在隔离环境恢复，检查数据一致性、应用启动、权限和实际耗时。

## 30. 恢复演练需要明确验收条件

演练前写清目标恢复点、目标环境、负责人、预期 RTO 和验证数据。恢复后不仅查数据库能连接，还要通过核心业务读取和写入链路验证。

演练结果用于改进脚本、容量和操作手册。

## 31. 灾难恢复考虑整个系统依赖

数据库恢复后，仍可能缺少对象存储、消息、密钥、DNS、镜像、配置或身份服务。Disaster Recovery（灾难恢复）计划要列出依赖顺序和替代方案。

恢复基础设施但无法取得部署制品，也不算系统恢复。

## 32. 故障响应先保护用户和控制影响

事故发生时，优先级通常是：

```text
确认影响
→ 阻止继续扩大
→ 恢复最关键服务
→ 持续沟通
→ 保存证据
→ 后续查根因并改进
```

不要在高压中同时做无关重构。

## 33. Incident 有明确角色更高效

常见分工包括：

- 事件负责人：协调决策和优先级；
- 操作人员：执行诊断与恢复；
- 沟通人员：向用户和利益相关者更新；
- 记录人员：维护时间线、假设和动作。

小团队可以一人兼任，但职责仍应清楚。

## 34. 严重度按影响而不是技术名称判断

数据库 CPU 很高但用户无影响，未必是最高级事故；核心工单无法创建，即使只是一条配置错误，也可能非常严重。

严重度标准应考虑用户数量、关键功能、数据风险、持续时间和可替代方案。

## 35. 事件时间线只记录事实和明确推断

记录告警时间、影响开始、观察证据、做过的动作和结果。把“已确认”和“怀疑”分开，避免一个早期猜测变成所有人的默认结论。

命令、仪表盘和变更版本都应可追溯，但秘密要脱敏。

## 36. 缓解与根治不是同一步

回滚、关闭功能开关、限制流量或切换依赖可以先恢复服务；真正原因可能稍后才能找到并修复。

不要为了追求当场完美根治而延长用户中断，也不要恢复后就忘记长期修复。

## 37. 回滚前检查数据兼容性

旧代码可能读不懂新数据，数据库迁移也可能无法逆转。回滚应用镜像前确认 Schema、消息格式、缓存和外部副作用仍兼容。

有时前滚修复比回滚更安全，选择要基于证据。

## 38. 沟通要说明影响和下一次更新时间

对外信息使用用户能理解的语言，说明受影响功能、已知范围、可用替代方法和下一次更新时间。未知就明确说未知，不编造精确恢复时间。

内部沟通保留更多技术细节，但避免多人在不同频道发出矛盾指令。

## 39. 事后复盘寻找系统改进

复盘应重建时间线、影响、促成因素、有效和无效响应，以及可验证的改进行动。目标是让系统和流程更强，不是寻找一个人背锅。

“操作失误”只是起点，还要问为什么单次操作能造成这么大影响、为何未提前发现、为何恢复困难。

## 40. 五个为什么只是辅助方法

连续追问可以深入机制，但事故通常有多个共同因素，不一定是一条单线根因。配置审查缺失、权限过大、无演练和告警迟缓可能同时存在。

复盘应保留这种多因素事实，而不是强迫得到一句口号。

## 41. 改进行动要有所有者和完成证据

“加强监控”“以后注意”不可验证。更好的行动是：明确修改什么、谁负责、何时完成、怎样确认有效。

行动按风险和成本排序，避免事故后列出几十项却没有一项落地。

## 42. Runbook 把常见处理变成可执行步骤

操作手册应包含适用症状、权限前提、诊断顺序、安全命令、成功判断、升级路径和回滚。每次事故或演练后更新。

手册不能只在事故负责人个人电脑上，也不能嵌入明文秘密。

## 43. Chaos 验证故障假设但要控制范围

故障实验可以主动终止实例、增加延迟或断开依赖，验证健康检查、降级和恢复是否有效。先在安全环境做，从小范围开始，并设停止条件。

没有可观测性和回滚能力时，不应贸然在生产注入故障。

## 44. 容量故障也需要保护机制

队列上限、连接池、超时、限流、熔断和负载削减用于防止过载扩散。拒绝一部分低优先级工作，有时比让全部请求一起超时更可靠。

保护参数必须通过负载测量调整，不能复制别人的数字。

## 45. AI 功能要有安全降级

模型不可用、超时或输出不可信时，FactoryCare 的核心工单流程仍应可运行。可以暂时取消建议、使用规则结果或进入人工处理，而不是让核心事务阻塞。

降级结果要明确标记，不能把替代输出冒充模型成功。

## 46. 安全事件与普通故障有额外要求

可能的数据泄露、账号滥用或供应链攻击需要限制证据访问、保护取证完整性、评估通知义务，并谨慎轮换凭据。

不要在未保存必要证据前随意清除所有系统，也不要在公共频道暴露敏感细节。

## 47. 需要时查询具体机制

秘密平台、SBOM 格式、签名工具、PostgreSQL 恢复命令和法规要求都会变化。实施时使用当前官方文档并在隔离环境验证。

长期稳定的是最小权限、独立副本、RPO/RTO、恢复演练、证据化响应和无责改进。

## 48. 这一章形成的整体地图

```text
受控配置与秘密生命周期
  → 输入安全与供应链信任
  → 可追溯制品和 SBOM
  → 按 RPO / RTO 设计备份
  → 定期恢复与灾难演练
  → 发现、控制、恢复、沟通
  → 复盘和可验证改进
```
