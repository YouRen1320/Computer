# MCP、Agent 边界与人工审批

## 1. MCP 解决模型应用与外部能力的连接协议

Model Context Protocol（模型上下文协议）定义主机怎样发现并调用服务器提供的工具、资源和提示，以及双方怎样初始化、协商能力和交换消息。

它标准化连接方式，不决定模型怎样思考，也不自动提供业务授权和安全。

## 2. Host、Client 和 Server 各有职责

```text
Host：用户直接使用的 AI 应用，协调模型、权限和多个连接
Client：Host 内与某一个 MCP Server 维持协议会话的组件
Server：暴露聚焦的上下文和能力
```

一个 Host 通常为每个 Server 建立独立 Client，隔离连接和能力。

## 3. MCP 的数据层基于 JSON-RPC

请求有方法、参数和 ID，响应与 ID 关联；通知不要求响应。协议错误与工具执行错误应分开处理。

SDK 会封装格式，但调试时仍要理解请求—响应、通知和错误对象。

## 4. 传输层负责消息怎样到达

常见传输包括本地进程间的 stdio 和远程服务的 Streamable HTTP。传输选择影响进程权限、认证、网络暴露、取消和部署。

同一 MCP 数据协议不代表两种传输拥有同样安全边界。

## 5. Stdio Server 作为本地子进程运行

Host 通过标准输入输出交换协议消息。stdout 必须保留给协议，诊断写 stderr，否则会破坏消息帧。

本地 server 可能继承用户的文件和网络权限，应限制工作目录、环境变量、可执行文件和沙箱能力。

## 6. Streamable HTTP 适合远程和多客户端连接

它使用 HTTP 请求，并可结合流式机制。必须使用 HTTPS、认证、限流、来源/会话保护和安全部署。

远程 server 不是因为使用 MCP 就自动受信任，它是一个标准外部服务边界。

## 7. 初始化阶段协商协议版本和能力

Client 与 Server 先声明支持的协议版本、工具/资源/提示和其他能力，再开始正常调用。双方只能使用实际协商成功的能力。

不要根据 server 名称猜功能，也不要在能力缺失时静默走不安全替代路径。

## 8. 协议版本应作为运行证据

MCP 规范使用日期版本并持续演进。日志和兼容测试记录协商版本、SDK 和 server build。

实现时查当前规范与 changelog，不把某一旧版本字段当永久事实。

## 9. Tool 是可执行能力

Server 通过工具列表提供名称、说明和输入 Schema，Host/模型可以提出调用。工具可能只读，也可能写文件、调用 API 或改变业务状态。

Tool description 和 annotations 只是提示信息，Host 仍按自己的政策判断风险和确认。

## 10. Resource 是可读取的上下文

资源用 URI 标识文件、Schema、记录或其他内容。它适合读取和订阅，不应为了任何数据获取都滥用写工具。

Resource URI 不是公开 URL；读取时仍需认证、授权、大小限制和内容类型检查。

## 11. Prompt 是可复用的交互模板

Server 可提供带参数的提示模板，帮助 Host 构造任务。Prompt 不拥有更高权限，也不能覆盖 Host 的安全政策。

从第三方 server 获取的 Prompt 本身也是不可信内容，需要用户可见和版本审查。

## 12. Tool Schema 不是权限

Schema 只能说明参数形状，例如需要 `orderId` 字符串。它不能说明当前用户是否能读取或关闭该工单。

Server 在每次调用中从认证上下文重新授权，并验证领域状态。

## 13. Tool 名称映射使用静态注册表

```text
"get_work_order" → GetWorkOrderHandler
"propose_assignment" → ProposeAssignmentHandler
```

拒绝未知工具名。不要通过字符串反射、Shell 拼接或动态 import 调用任意本地函数。

## 14. 工具输入先 Schema，再领域校验

Schema 检查字段和类型；领域层检查资源、租户、状态、版本、范围和业务规则。自由文本、路径、URL 和查询还有专门安全策略。

模型输出永远不能跳过这两层。

## 15. 工具输出最小化

返回模型完成下一步所需的字段，不返回完整数据库行、内部配置、Token 和堆栈。大结果用有权限的 Resource 引用或分页，而非塞进一条工具结果。

结构化结果区分 succeeded、not_found、forbidden、conflict、retryable_failure 等状态。

## 16. 协议错误与执行错误不同

```text
协议错误：JSON-RPC 无效、方法不存在、参数形状错误
执行错误：下游超时、资源不存在、业务冲突、权限拒绝
```

Client 用前者判断连接/实现问题，用后者决定业务流程。不要把协议错误伪装成模型可读的普通成功文本。

## 17. 错误信息不能泄露内部结构

对 Host 返回稳定代码、安全说明和关联 ID。内部日志保留受控堆栈和 cause，但不输出文件系统全路径、SQL、其他用户数据或凭据。

## 18. 每个 HTTP 请求都需要认证和授权

会话 ID 不应被当作认证身份。Server 验证 access token 的签发者、受众、过期和 scope，并根据实际请求参数做资源级授权。

协议会话状态不能替代身份验证。

## 19. Token Passthrough 是禁止的反模式

Server 不能接收一个原本发给别的服务的 Token，既不验证受众又原样转给下游。这会造成 confused deputy（混淆代理）、绕过控制和审计失真。

Server 调用下游时使用单独、面向下游受众的最小权限凭据。

## 20. OAuth 授权要最小 scope 和明确同意

远程 MCP 按当前规范使用资源绑定、PKCE、精确 redirect URI、安全存储和短期 Token 等机制。只在需要某项能力时请求对应 scope。

具体流程变化快，应直接按当前 MCP Authorization 与 OAuth 安全规范实现，不凭讲义复制旧字段。

## 21. MCP Server 不应绕过业务服务直连核心库

理想边界：

```text
MCP Tool
  → 认证与参数校验
  → FactoryCare Java API / application service
  → 领域规则、事务、审计、数据库
```

若 server 自己直接修改表，会复制规则、绕过事件和租户隔离。

## 22. 只读 Server 也使用受控投影

为检索/查询建立最小字段视图或业务 API，限制租户、行数、时间窗和敏感字段。不要给 Server 数据库超级用户后依赖提示词“只查自己的”。

## 23. Host 才负责最终的用户体验和同意

Server 可以声明工具风险或请求 elicitation，Host 决定如何向用户显示、是否需要确认、哪些数据可发送给 Server。

第三方 Server 不能自己声称“用户已经批准”后获得额外能力。

## 24. 能力发现可能动态变化

Server 可通知工具、资源或提示列表变化。Host 刷新后仍需应用本地白名单和政策；新工具不能在活跃会话中自动获得高风险权限。

变更记录 server version 和 Schema hash，并重新评估。

## 25. 取消和长任务需要明确语义

Client 取消请求后，Server 应尽力停止可取消工作并返回/记录状态。但外部副作用可能已提交。

长任务使用有状态 task/operation ID、查询状态和幂等键；实验性协议能力尤其要按协商结果使用。

## 26. MCP 生命周期要有所有者

Host 负责启动/连接、初始化、健康检查、刷新能力、取消、断线重连和关闭。Server 负责释放数据库连接、子进程和临时文件。

重连不能自动重复未知状态的工具写入。

## 27. Agent 是在不确定步骤中选择下一动作的系统

模型根据目标和当前状态选择工具、观察结果并继续。它适合开放探索和信息收集，不适合所有流程。

Agent 不等于“调用一次模型”，也不等于拥有无限自主权。

## 28. 确定性工作流适合规则明确的业务

创建工单、审批、扣费、状态转换和合规检查有固定步骤与事务，应该由普通代码/状态机掌控。模型可以分类、摘要和提出建议，但不改变权威规则。

越高风险，越倾向确定性控制。

## 29. Agent 适合路径确实无法提前完全列出的任务

例如在多个只读来源中研究、逐步缩小排障线索、选择不同检索工具。即使如此，工具集、预算、数据范围和结束条件仍由程序限定。

## 30. 常见 Agent 反模式

- 用 Agent 代替普通 `if`/工作流；
- 给几十个相似且过宽工具；
- 让模型自行提高预算或权限；
- 用自然语言保存唯一业务状态；
- 无终止条件地反思重试；
- 把完整数据库和 Shell 暴露为万能工具；
- 失败后静默切换到更高权限。

## 31. Agent 循环要有状态和预算

```text
目标 + 当前证据 + 已用工具 + 剩余预算
  → 选择下一步
  → 校验/授权/执行
  → 记录结果和进展
  → 完成、拒绝、等待人工或停止
```

限制模型轮数、工具数、token、成本、总时间、并发和无进展次数。

## 32. 无进展检测防止循环空转

规范化比较最近调用和结果：若反复调用同一工具、参数基本相同、没有新证据或错误不可修复，就停止。

停止结果说明缺少什么，不再让模型换措辞继续消耗。

## 33. Kill switch 是运行时强制开关

可关闭整个 Agent、某 MCP Server、某工具或所有写工具。开关在入口、队列和执行层生效，已有任务按安全取消/排空策略处理。

开关只能由受权人员修改，并有审计、TTL、安全默认和恢复确认。

## 34. 人工审批是一个持久状态机

```text
proposed → awaiting_approval
  ├── approved → executing → succeeded/failed/conflict
  ├── rejected
  └── expired/cancelled
```

它不是 `approved=true` 临时变量。每个状态有身份、时间、动作哈希和资源版本。

## 35. 审批界面展示用户真正批准的内容

包括工具名称、业务动作、目标资源、重要参数、影响、来源、可逆性和风险。秘密字段应隐藏但可说明来源。

模糊的“允许助手继续吗”不足以授权不可逆写入。

## 36. 执行时重新检查全部前提

批准之后重新验证操作者权限、资源版本、当前状态和幂等键。发生变化时返回 conflict 并创建新的提议，而不是沿用旧批准。

这解决审批等待期间的 TOCTOU。

## 37. 写工具必须幂等且有事务边界

模型、网络和恢复都可能重复调用。Java 业务服务用唯一幂等键和数据库事务保证同一动作不会重复产生效果。

MCP request ID、模型 call ID 和业务幂等键用途不同，分别记录并关联。

## 38. Java 与 Python/MCP 的职责边界

```text
Java：认证主体、ACL、工单领域规则、状态机、事务、审计、幂等
Python/Agent：提示、模型、RAG、评估、步骤建议与编排
MCP：受控地暴露前述系统的最小工具/资源/提示
```

任何语言都能实现这些职责，但边界应保持一致。

## 39. MCP Server 测试分协议、工具和安全层

- 协议：初始化、能力协商、list/call、错误、取消、关闭。
- Schema：合法/非法参数与结果。
- 领域：成功、不存在、冲突、重复和幂等。
- 安全：无 Token、错 audience、跨租户、scope 不足、提示注入。
- 故障：下游超时、断线、崩溃窗口和重连。

## 40. Host 集成测试要验证用户同意

检查高风险工具不会静默执行，审批内容与最终动作完全一致，拒绝后停止，权限变化后冲突，工具列表变化不自动放权。

模型可用脚本化 Fake 控制每条路径。

## 41. 可观测性贯穿模型、MCP 和业务服务

使用 trace/request ID 关联模型 call、MCP JSON-RPC ID、tool call ID、approval ID、idempotency key 和领域事件。记录版本、耗时、状态与安全摘要。

不要记录 Token、完整 PII、系统提示和不必要的工具正文。

## 42. 部署本地 Server 要最小系统权限

明确允许目录、网络域、环境变量和子进程；使用签名/可信安装来源；锁定依赖；更新前审查；显示 Server 当前权限。

本地运行不等于安全，反而可能拥有用户桌面权限。

## 43. 部署远程 Server 要像普通生产 API

TLS、OAuth、速率限制、WAF/输入限制、隔离、日志、SLO、备份、密钥轮换和事故响应都需要。MCP 只定义协议，不替代这些工程。

## 44. 这一阶段应形成的整体地图

```text
Host（模型、用户体验、安全政策）
  → 每个 Server 一个 Client
  → 初始化/能力协商 + JSON-RPC
  → Tools / Resources / Prompts
  → MCP Server 适配器
  → Java/Python 受控业务或检索 API

Agent：最小工具 + 授权 + 预算 + 无进展检测
高风险动作：持久审批 + 版本检查 + 幂等事务
```

必须掌握：MCP 是连接协议不是安全模型；Host/Client/Server 不同；能力必须协商；Tool Schema 不是权限；stdio stdout 不能混诊断；远程请求每次认证；禁止 Token passthrough；MCP Server 不绕过业务服务；确定性工作流优先；Agent 有界运行；人工审批绑定具体动作；恢复和重试都依赖业务幂等。

MCP 规范仍在演进，开发时从 [MCP Architecture](https://modelcontextprotocol.io/docs/learn/architecture)、[最新规范入口](https://modelcontextprotocol.io/specification/) 和 [Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices) 核对当前协议版本、传输与授权要求。
