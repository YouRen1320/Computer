# FactoryCare 验收、发布与下一阶段

## 1. 最终验收判断的是系统能力，不是文件数量

学习路线完成后，真正要确认的是 FactoryCare 能否在明确环境中部署、由不同角色正确使用、在故障下安全退化并恢复。

写过多少类、通过多少零散检查都只是局部证据，不能替代完整业务链路。

## 2. 验收前先固定范围

列出本次候选版本必须支持的角色、业务流程、客户端、外部依赖和质量目标，同时写明非目标。

范围不固定，验收过程中不断加入新功能，就永远无法形成清晰结论。

## 3. 验收环境从空白状态建立

用发布清单指定的镜像、配置、迁移和基础设施，在干净环境部署。不要依赖开发机残留数据库、手工文件或 IDE 自动运行配置。

空白部署能验证文档、制品和自动化是否真的完整。

## 4. 候选版本必须身份明确

记录源码提交、Java/Vue/Python 等制品 digest、数据库迁移版本、AI 配置、功能开关和构建流水线。

验收期间若重新构建或改代码，就形成新的候选版本，需要重新确认受影响证据。

## 5. 验收矩阵连接需求与证据

```text
需求 / 风险
→ 验收场景
→ 期望结果
→ 自动或人工证据
→ 当前结论
→ 缺陷与处置
```

矩阵防止只验证容易展示的成功页面，遗漏安全、故障和恢复。

## 6. 验收环境与生产差异要列出来

数据规模、外部身份、模型供应商、证书、域名、资源和网络可能不同。每项差异说明对结论的影响，以及上线后怎样继续验证。

未模拟生产峰值时，只能说功能链路通过，不能声称生产容量已确认。

## 7. 先做部署完整性检查

确认所有容器和服务运行预期 digest，健康与就绪正常，迁移历史一致，Nginx 使用正确证书，日志、指标和 trace 能进入观测系统。

进程存在不是完整性证明，还要核对版本和实际入口。

## 8. 通过真实 HTTPS 入口验收

浏览器和客户端应走生产相同方向的 DNS、TLS、Nginx 和认证链路，而不是绕过代理直连后端端口。

否则无法验证证书、转发头、缓存、限流、CORS 和超时配置。

## 9. 角色矩阵验证每类用户

例如管理员、调度员、技术员和只读审计人员分别有哪些允许与拒绝动作。每个关键权限同时检查正向和负向路径。

“管理员能操作”不能证明普通用户受到正确限制。

## 10. 双租户场景是隔离的最低证据

准备租户 A 和 B 的用户、工单、附件、缓存和知识文档，确认任何列表、详情、搜索、RAG、导出和实时事件都不会交叉出现。

只在 UI 隐藏数据不够，必须从服务端响应与存储访问证明隔离。

## 11. 核心工单生命周期要完整走通

从创建、分配、开始处理、记录费用到关闭，检查状态转换、必填条件、时间、金额、版本和审计历史。

每一步都验证业务结果，而不只是 HTTP 返回 200。

## 12. 非法状态转换必须被拒绝

例如未完成必要检查就关闭、已关闭后再次修改、普通技术员分配他人工单。拒绝应有稳定错误代码且不产生部分写入。

失败后查看数据库和事件，确认没有隐藏副作用。

## 13. 并发更新验证冲突保护

两个客户端读取同一版本并同时提交不同修改，只有符合策略的一个成功，另一个获得清楚冲突并能刷新处理。

最后一次无提示覆盖会让用户劳动丢失，属于业务缺陷。

## 14. 重复提交验证幂等

在响应超时或客户端重试情境下，用相同幂等键重复创建或执行关键命令。系统只产生一份业务结果，并能返回第一次处理状态。

换一个请求正文却复用同一键，应被识别为冲突。

## 15. 金额与时间检查边界值

费用使用整数最小单位和精确运算，覆盖零值、较大值和溢出保护。时间检查时区、跨日、排序和 SLA 计算。

界面显示格式可以本地化，但服务端事实保持统一语义。

## 16. Web 客户端验证完整浏览器链路

覆盖登录恢复、路由权限、表单校验、错误显示、刷新、并发冲突、弱网重试和退出登录。浏览器控制台不应有未处理异常或敏感信息。

客户端不能自行绕过服务端合同，也不能把错误 HTML 当 JSON。

## 17. 移动端验证真实设备能力

Flutter 或 uni-app 客户端检查网络切换、离线队列、重复同步、拍照/文件权限、前后台切换和不同屏幕布局。

模拟器通过不能完全代表真机权限、性能和系统生命周期。

## 18. 多客户端必须共享同一业务事实

Web 创建的工单能在移动端正确读取，移动端更新后 Web 刷新能看到一致状态。不同客户端不能各自发明状态或字段含义。

冲突和离线同步最终由后端版本与领域规则裁决。

## 19. API 契约与实际响应保持一致

导出当前 OpenAPI，确认主要客户端生成类型或运行时 Schema 与服务一致。检查错误模型、分页、枚举、空值和版本兼容。

文档页面能打开不代表契约没有漂移。

## 20. 数据库验收关注约束和迁移

从空库执行全部迁移，再从受支持的旧版本执行升级。确认唯一约束、外键、索引、租户条件和迁移历史。

开发环境中手工修过的表结构不能成为发布前提。

## 21. 消息与异步任务要检查重复和积压

模拟消费者暂时停止、消息重复投递和处理失败。恢复后任务最终完成，不产生重复通知或重复业务写入，死信和积压能被观察。

队列清空不等于每条业务结果正确。

## 22. 缓存验收重点是隔离与失效

检查键是否包含必要租户和版本信息，更新后旧值何时失效，权限改变后是否仍可读取缓存内容，Redis 不可用时系统如何降级。

缓存命中率高不能掩盖错误数据。

## 23. AI 输出只能处在约定边界内

分类、摘要和建议标明来源与不确定性；业务状态、权限和金额仍由确定性代码控制。模型输出必须经过结构校验和领域校验。

AI 给出看似合理文本不能成为越权或写入的理由。

## 24. RAG 同时验收相关性、引用和权限

为一组稳定问题保存预期可接受文档范围，检查检索结果、最终回答引用与原文一致，并验证无权用户无法通过查询、缓存或引用看到受限内容。

只看回答流畅度会漏掉最危险的错误。

## 25. 提示注入场景验证系统边界

在知识文档和用户输入中放入要求泄露秘密、忽略权限或调用高风险工具的文字。系统把它们当不可信内容，不能改变授权和工具政策。

防线必须在代码、数据访问和审批层，而不只是一句系统提示。

## 26. 工具调用与 MCP 验收权限和审批

只读能力仅返回用户可见的最小字段；写能力展示明确参数并在需要时获得人工批准。批准后执行前重新检查身份、资源版本和幂等。

取消、超时和重连不能重复未知状态的副作用。

## 27. AI 不可用时核心工单仍然可用

断开模型或 Python 服务，创建、分配和关闭工单仍按设计运行。AI 功能清楚显示暂时不可用、进入规则回退或人工处理。

这证明 AI 是增强能力，而不是核心事务的单点故障。

## 28. 安全检查围绕真实威胁

覆盖认证绕过、资源级越权、跨租户、CSRF/CORS、XSS、SSRF、上传、限流、秘密泄露和依赖风险。每项检查连接到威胁和预期防线。

扫描工具无发现不等于系统安全，只表示其规则没有发现已知模式。

## 29. 隐私检查数据最小化和保留

查看 API、日志、trace、AI 请求、向量索引、备份和导出是否只包含必要个人数据。确认访问、保留和删除策略一致。

脱敏后的开发数据也要评估能否重新识别。

## 30. 性能验收使用代表性负载

根据预期租户、并发、数据规模和读写比例运行负载，检查关键路由的成功率、P95/P99、吞吐和资源余量。

结果必须附环境、版本、数据和负载模型，不能只保留一个“每秒请求数”。

## 31. 容量验收包含降级和恢复

逐步增加流量观察瓶颈、排队、限流和错误形态，再回到正常流量确认系统能恢复。过载时应保护关键功能，不让全部请求无限等待。

压力实验要有停止条件，避免破坏共享环境。

## 32. 可观测性验收从一个请求下钻

从用户请求找到 Nginx 记录、Java span、数据库调用、Python/模型 span 和对应结构化日志；再从错误率告警下钻到具体 trace。

指标、链路和日志之间不能互相跳转时，真实事故定位会很慢。

## 33. 告警验收确认有人能够行动

触发受控故障，确认告警包含影响、严重度、仪表盘、关联版本和操作手册，并到达正确人员。恢复后告警自动结束或明确关闭。

仅证明监控系统收到数据，不等于告警闭环有效。

## 34. 日志验收关注信息量和泄露

关键成功与失败事件有稳定字段、trace ID 和版本；同一异常没有多层重复堆栈；Token、Cookie、密码和敏感正文没有出现。

同时检查日志量不会在普通流量下迅速填满存储。

## 35. 容器和主机验收最小权限

服务以专用非 root 用户运行，根文件系统和挂载只有必要写权限，不公开内部数据库端口，资源限制和优雅停机生效。

镜像中不含源码秘密、构建缓存或多余管理工具。

## 36. Nginx 与 TLS 验收真实外部行为

确认域名、证书链、续期监控、HTTP 到 HTTPS、代理头、正文限制、静态缓存、SPA 回退和流式路由。使用外部入口而不是只在服务器本机检查。

TLS 当前协议和配置基线按发布时官方建议核验。

## 37. 备份验收必须执行恢复

从受控备份在隔离环境恢复 PostgreSQL 和必要对象数据，核对目标时间点、业务一致性、权限和实际耗时。

将结果与 RPO/RTO 比较；未达到就不能把备份状态标为已满足目标。

## 38. 故障响应演练检验人与系统协作

模拟数据库不可用叠加错误发布，确认严重度、负责人、时间线、沟通、缓解、恢复和证据保存。过程以用户影响为中心。

演练后形成具体、有所有者和验收标准的改进行动。

## 39. Canary 验收真实发布控制

让少量受控流量进入候选版本，按版本比较错误、延迟、资源和业务结果。达到门禁后逐步扩大，任何停止条件触发就暂停或回退。

不要让整体平均值掩盖少量新版本实例的问题。

## 40. 回滚演练必须包含数据兼容

部署候选版本并产生受控新数据，再切回旧应用，确认旧版本仍能安全读取或明确由前向修复恢复。数据库迁移、事件和缓存都纳入检查。

只替换镜像成功不等于业务已经回滚。

## 41. 发布决策分为通过、有条件通过和不通过

```text
通过：全部必须项有可信证据
有条件通过：低风险缺口有明确临时控制、所有者和期限
不通过：核心功能、安全、数据、恢复或回滚存在不可接受风险
```

不能为了赶日期把未知风险自动写成通过。

## 42. 已知问题要写影响而不只是编号

每项说明触发条件、受影响用户、临时方案、严重度、负责人和计划版本。读者才能判断是否阻止发布。

隐藏问题只会把决定推迟到生产事故时。

## 43. 正式发布沿用已经验证的同一制品

生产部署使用候选环境验收过的 digest 与受控配置，不重新编译。发布清单、审批和流水线构成证据链。

若生产前改动任何制品内容，原验收结论不能直接继承。

## 44. 发布当天先确认人员和回退条件

明确发布负责人、观察人员、业务联系人和必要权限，确认备份、监控、操作手册、旧制品与停止条件可用。

这些准备应在变更前完成，而不是故障发生后寻找。

## 45. 发布后观察业务与技术指标

同时看工单成功率、错误代码、延迟、资源、队列、AI 降级和用户反馈。观察窗口覆盖足够的真实流量和定时任务。

没有立即报错不表示发布已经安全结束。

## 46. 发布完成后保存可复现记录

记录运行版本、迁移、配置、开始与结束时间、门禁结果、异常、回滚情况和批准人。以后可以从生产实例追到这一份记录。

记录中只引用秘密位置，不保存秘密内容。

## 47. 最终复盘不等于给自己打一个总分

分别看概念理解、阅读代码、修改代码、从零构建、诊断故障、解释取舍和使用 AI 验证这些能力。某一项强不能自动代替其他项。

复盘目的是选择下一阶段，而不是制造一个好看的百分数。

## 48. 区分“看懂”“会改”和“能负责”

```text
看懂：能说明代码和概念在做什么
会改：面对新需求能修改并验证
能负责：能定义边界、处理失败、发布和维护
```

AI 可以显著加快前两层，但第三层仍需要你判断风险和承担验证责任。

## 49. 下一阶段采用项目驱动而不是重新背全书

选择一个真实增量，例如备件库存、排班、客户门户或现场离线同步。先写需求和验收，再让 AI 提供候选实现，你负责阅读、取舍、修改和证据。

遇到知识缺口时回看对应主题讲义和权威文档，不必从第一章重新开始。

## 50. AI 适合承担生成和检索

AI 可以生成骨架、重复代码、迁移草案、测试候选、文档和排障假设，也能快速定位官方资料。

你要保留需求澄清、边界选择、敏感权限、关键审查、真实运行验证和最终发布决定。

## 51. 阅读 AI 代码采用固定顺序

```text
先看输入和输出
→ 再看业务规则和状态变化
→ 再看失败、权限、并发与数据边界
→ 最后看语法和风格
```

这样能避免代码看起来整洁，却在核心业务上犯错。

## 52. 修改需求比重复默写更接近真实工作

在已有 FactoryCare 上增加字段、改变规则、替换依赖或支持新客户端，会迫使你理解现有结构和影响范围。

完全脱离参考从零重写仍可偶尔用于确认基础，但不必成为每章固定仪式。

## 53. 故障诊断继续使用证据链

从用户现象开始，依次查看边界请求、状态码、日志、trace、指标、依赖和数据最终状态。提出可证伪假设，每次用最小动作验证。

不要让 AI 根据一段截断日志直接大范围改代码。

## 54. 讲义是地图，不是永久规范

这些主题文件帮助建立长期概念和导航。框架版本、API 字段、安全基线和部署平台会变化，真正实现时回到当前官方文档。

每次遇到有价值的新理解，可以用自己的话补充讲义，但不把临时命令混成永恒规则。

## 55. 学习节奏以完整概念组为单位

先连续阅读一章，标记真正不懂的地方；集中提问后进入一个完整项目切片；最后用运行证据和自己的解释收束。

不需要每读一个小标题就停下来等待下一条指令。

## 56. 时间记录用于调整节奏

记录实际学习时间和主要活动，例如阅读、项目修改、排障和复盘。时间不是成绩，但能帮助发现讲义过密、项目过大或重复劳动。

没有计时时如实写未计时，不估造数字。

## 57. 能力证据保留最小充分集合

每个重要能力保留一份最能说明问题的代码或文档、一条可重复命令和一段结果说明。过多重复输出会淹没真正证据。

失败记录有价值，只要它说明怎样定位和修复。

## 58. 技术路线根据真实目标继续分叉

若走 Java 后端，可深入性能、分布式数据和云平台；走全栈可深入产品交互、前端工程和跨端；走 AI 应用可深入检索评估、Agent 安全和模型服务。

选择一条主线，其他内容按项目需要补充，避免再次同时铺开所有方向。

## 59. 每个新阶段重新定义边界

写清这阶段要交付什么、哪些不做、怎样验收、哪些信息需要查当前文档、AI 可以做什么、你必须亲自判断什么。

这能让学习保持项目感，而不是回到无限知识点清单。

## 60. FactoryCare 路线最终形成的整体地图

```text
计算机与语言基础
  → Java / Spring / SQL / 安全 / 架构
  → Web / Vue / Nuxt / 跨端
  → Python / 机器学习 / RAG / Agent
  → Linux / 容器 / 交付 / 可观测性 / 恢复
  → FactoryCare 端到端验收与发布
  → 用真实增量继续深化主线能力
```

到这里，“学完”不是再也不查资料，而是你已经有一张可复用地图，能借助 AI 和官方文档把新需求安全地落到系统中。
