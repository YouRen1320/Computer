# 作品集、系统设计与项目表达

## 1. 作品集的作用是让能力可以被验证

简历上的“熟悉 Java、Vue、AI”只是声明。作品集要把声明连接到真实问题、设计选择、代码、运行结果和复盘证据。

它不是把所有源码堆给别人看，而是帮助读者在有限时间内判断你做过什么、为什么这样做、结果如何。

## 2. 一个完整项目比许多零散示例更有说服力

FactoryCare 可以贯穿后端、前端、移动端、数据、AI、安全和部署。它展示的是组合能力，而不只是多个“Hello World”。

小示例仍适合学习单个概念，但作品集首页应聚焦一个能够讲清楚的系统。

## 3. 先明确目标岗位和读者

后端岗位更关心领域模型、事务、数据和可靠性；全栈岗位还关心界面、状态与跨端；AI 应用岗位会关注检索、评估、安全和降级。

同一个真实项目可以准备不同入口，但不能为了匹配职位虚构没有做过的经验。

## 4. 岗位描述是需求来源，不是关键词复制表

把职位要求拆成能力：

```text
“Spring Boot” → 能否设计并解释可靠 API
“PostgreSQL”  → 能否建模、索引和处理事务冲突
“Docker”      → 能否构建可追溯制品并诊断运行问题
“AI/RAG”      → 能否评估质量、控制数据权限并安全降级
```

作品集用证据对应能力，而不是在 README 重复几十个技术名词。

## 5. 项目首页先回答五个问题

读者应快速看懂：

1. FactoryCare 为谁解决什么问题；
2. 你具体负责什么；
3. 系统由哪些主要部分组成；
4. 最值得看的三项工程决策是什么；
5. 怎样运行、查看演示或检查证据。

其余细节通过链接逐层展开。

## 6. 项目描述从业务场景开始

比起“使用 Spring Boot + Vue + PostgreSQL”，更清楚的表达是：现场技术员创建工单，调度员分配任务，管理者跟踪 SLA，AI 只提供分类和知识建议，关键状态仍由业务服务控制。

技术选择随后解释它怎样支持这个场景。

## 7. 明确个人贡献边界

如果 AI 生成过代码，应说明你怎样提出约束、审查补丁、发现问题和验证结果。如果项目参考了课程或模板，也要区分已有骨架与你完成的设计。

诚实边界不会削弱作品，反而能展示真实协作和判断力。

## 8. 证据要能从声明一路追到工件

```text
能力声明
→ 项目中的具体场景
→ 设计记录或代码位置
→ 自动检查 / 运行日志 / 截图
→ 已知限制与复盘
```

截图只能证明某一刻显示了某个画面，不能单独证明安全、性能或可恢复性。

## 9. 证据索引降低阅读成本

为关键能力建立短表：领域状态机、租户隔离、幂等、可观测性、RAG 引用、故障降级和部署回滚分别链接到相关文档、代码和验证结果。

不要把阅读者丢进几万行仓库让其自行寻找亮点。

## 10. README 与架构文档分工

README 提供项目入口、快速运行和核心概览；架构文档解释边界、数据流、质量目标与取舍；操作手册解释部署和故障处理。

一份无限长 README 会让不同读者都难以定位信息。

## 11. 架构图只画有解释价值的关系

上下文图显示用户、FactoryCare 和外部系统；容器图显示 Web、Java、Python、数据库和消息系统；关键流程图显示一条业务链路。

图中每条箭头应有方向、协议和主要含义。彩色方框多不等于架构清楚。

## 12. 系统设计从需求开始而不是从技术名开始

推荐顺序：

```text
用户与业务目标
→ 功能范围与非目标
→ 质量目标
→ 数据和规模假设
→ 边界与关键流程
→ 故障路径
→ 技术选择和取舍
```

先决定“必须微服务”再寻找理由，是典型的倒置。

## 13. 功能需求说明系统要做什么

例如创建工单、分配技术员、记录维修过程、上传附件、跟踪 SLA、搜索知识和生成 AI 建议。

系统设计不需要把每个页面按钮都列出，但要覆盖决定架构的关键流程。

## 14. 非功能需求说明系统要做到什么程度

包括预期流量、延迟、可用性、数据一致性、安全、隐私、恢复目标和成本边界。

“高并发、高可用、高性能”没有数字和场景，无法指导设计。

## 15. 非目标阻止设计无限膨胀

例如第一阶段不支持全球多区域主动写入、不训练自有基础模型、不提供复杂计费。明确非目标让方案聚焦，也便于解释为什么没有引入某些技术。

非目标未来可以改变，但当前必须写清。

## 16. 假设要显式写出来

系统设计一定包含不完整信息。记录租户数、活跃用户、每日工单、附件大小、峰值比例和增长预期，并标明是估算还是已有测量。

数字错了可以修正，隐藏假设则无法讨论。

## 17. 容量估算先统一单位

例如：

```text
每日请求数 ÷ 86400 ≈ 平均每秒请求数
平均值 × 峰值系数 ≈ 峰值请求数
每日新增记录 × 单条大小 × 保留天数 ≈ 基础存储量
```

估算用于发现数量级和瓶颈，不追求虚假精确。要把字节、KB、MB 以及秒、天统一。

## 18. 数据模型围绕不变量

工单、用户、租户、分配、状态历史和附件各有身份与生命周期。设计时说明唯一性、引用关系、删除方式和哪些变化必须在同一事务中完成。

表数量不是重点，业务事实能否保持一致才是重点。

## 19. 一致性根据业务后果选择

关闭工单与写入关闭审计可能要求同一事务；搜索索引和统计报表可以稍后更新；AI 摘要失败不应撤销工单创建。

“强一致”和“最终一致”都有成本，必须指出用户会观察到什么。

## 20. 关键流程同时画成功与失败路径

创建工单的成功路径之外，还要说明重复提交、数据库冲突、消息发送失败、AI 超时和客户端断开时会发生什么。

只画成功箭头无法展示可靠性设计。

## 21. 信任边界决定安全检查位置

浏览器、移动端、MCP、Python 和第三方服务都在不同信任边界。每次跨边界都考虑认证、授权、输入校验、数据最小化、超时和审计。

内部网络可达不等于调用方可信。

## 22. 单体与微服务是取舍而不是等级

模块化单体部署简单、事务直接，适合团队和业务尚在成长时；微服务能独立部署和扩展边界，但增加网络、数据一致性、观测和运维成本。

FactoryCare 可以先用清晰模块边界，等出现真实独立扩展或团队自治需求再拆分。

## 23. 数据库选择要连接到访问模式

PostgreSQL 适合核心关系数据、约束和事务；Redis 适合有明确失效策略的缓存、短期状态或限流；向量索引用于语义候选检索。

每引入一个存储，都要说明权威数据在哪、失败时怎样恢复和一致性要求。

## 24. 同步与异步按用户等待和耦合选择

用户必须立即知道结果的核心校验适合同步；通知、索引和部分 AI 处理可以异步。异步会引入消息重复、顺序、积压和最终一致性问题。

消息队列不是让慢接口自动变快的魔法。

## 25. 缓存设计要说明失效和降级

缓存什么、键怎样包含租户、允许旧多久、写入后怎样失效、缓存不可用时怎么办，这些比“使用 Redis”更重要。

尤其要防止跨租户共享错误键造成数据泄露。

## 26. 可靠性从故障模式反推

至少考虑数据库不可用、单实例退出、下游超时、队列积压、磁盘满、错误发布和凭据过期。对每种情况说明发现方式、用户影响、保护措施和恢复路径。

高可用不是把每个组件都复制三份，而是关键用户路径在可接受范围内恢复。

## 27. SLO 把“可靠”变成可衡量目标

为关键 API 定义成功率和延迟目标，为异步任务定义完成时限，为恢复定义 RPO/RTO。随后才能解释容量、冗余和告警为什么这样设计。

没有目标就无法判断额外复杂度是否值得。

## 28. 安全设计说明威胁和控制

不要只写“使用 JWT”“使用 HTTPS”。应说明身份怎样建立、资源怎样授权、租户怎样隔离、Token 怎样保护、上传与 URL 怎样限制、审计怎样保留。

还要说明残余风险和不在当前范围内的威胁。

## 29. AI 设计要把不确定性放在边界内

模型输出是建议，不是权威事实；RAG 检索按用户 ACL 过滤；引用能回到原文；高风险写操作需要普通代码校验和人工批准；模型不可用时核心业务能降级。

只展示一段好看的回答，无法证明 AI 功能可靠。

## 30. 设计决策用 ADR 保留背景

Architecture Decision Record（架构决策记录）可以很短，包含问题背景、选项、选择、理由、后果和重新评估条件。

它保留“当时为什么合理”，避免几个月后只看到结果却误以为是随意选择。

## 31. 取舍表达必须同时说收益和代价

例如选择模块化单体：收益是部署和事务简单；代价是模块不能独立扩容；适用前提是当前团队小、核心负载接近；触发拆分的条件是某模块出现独立容量或发布需求。

只说优点不是取舍。

## 32. 分阶段演进比一步到位更可信

```text
阶段 1：单实例 + PostgreSQL + 明确备份
阶段 2：多实例 + 外部缓存 + 观测完善
阶段 3：按真实瓶颈拆独立服务或异步链路
```

每一步由测量或组织需求触发，避免提前承担未来复杂度。

## 33. 技术表达采用“结论—证据—取舍”

先说你选择了什么，再给场景和数据证据，最后说明代价、替代方案及何时改变。这个顺序比从技术历史讲起更容易理解。

面试中答案长度有限，先让对方知道核心判断。

## 34. 项目故事采用“背景—行动—结果—反思”

背景说明问题和约束；行动说明你亲自做了什么以及怎样验证；结果用可核查现象或数据；反思说明限制和下一次改进。

它与常见 STAR 表达相近，但不要机械背模板。

## 35. 故障故事比完美故事更能展示工程能力

可以讲一次整数溢出、跨租户缓存风险、数据库锁冲突、错误部署或 AI 超时。重点是如何收集证据、缩小范围、恢复服务和补充防线。

不要捏造严重事故，也不要把团队成果全部描述为个人完成。

## 36. AI 协作要展示审查能力

可说明 AI 生成了候选方案，你如何检查业务边界、发现隐藏网络调用或缺少负向验证，并用原有 oracle 验证修复。

会使用 AI 的价值不在复制速度，而在能把不可信候选变成可验证结果。

## 37. 不把无法解释的代码放进核心展示

如果某段代码完全由工具生成且你不知道输入、输出、失败路径和取舍，它不应作为能力证明。先把它读懂、验证、简化并记录来源。

面试者沿着一段关键代码追问时，真实理解很容易看出来。

## 38. 演示选择稳定的黄金路径和可控故障

准备一个短流程展示核心业务，再准备一个可解释的失败与恢复，例如重复提交被幂等保护，或 AI 不可用时回退到人工流程。

演示前固定数据和版本，避免依赖随机外部状态。

## 39. 本地运行说明要从干净环境可复现

列出必要工具、启动顺序、配置示例、数据库初始化、演示账号和关闭清理方式。秘密使用占位符，绝不提交真实凭据。

如果某部分需要付费外部服务，应提供安全的关闭或替代模式。

## 40. 文件和编码问题会破坏作品的第一印象

仓库使用统一 UTF-8、清楚目录名、可移植路径和合理换行。不要提交 IDE 缓存、构建产物、绝对本机路径或含用户名的日志。

在另一台干净机器或 CI 中验证，是发现隐藏依赖的有效方法。

## 41. Git 历史展示工作的演进

提交聚焦一个意图，信息说明为什么改变。分支、合并请求和审查记录可以体现协作，但不要为“好看”伪造历史。

若秘密误入历史，立即轮换，并按风险决定历史清理与通知。

## 42. 仓库导航应让陌生读者不迷路

顶层目录说明各模块职责；生成目录与源码明确区分；关键文档从 README 可达；代码链接指向权威文件而不是 `target`、`dist` 等产物。

IDE 搜索时先确认打开了正确工作区和源码根目录。

## 43. 双语材料按真实需求准备

如果目标岗位需要英文，可准备一页英文项目摘要和关键术语；不必把所有内部文档逐字翻译。中英文都保持相同事实和边界。

翻译不是夸大项目规模的机会。

## 44. 简历项目条目优先写影响和证据

一条内容通常包含场景、行动、关键约束和可验证结果。例如说明实现了租户隔离与负向检查，而不是只罗列“Spring Security、JWT”。

没有真实测量时，不写虚假的百分比提升。

## 45. 模拟面试用于发现表达断点

录音或录屏后检查：是否先给结论、是否把假设当事实、是否能解释取舍、是否知道失败路径、是否说清个人贡献。

它是反馈工具，不是背诵固定答案。每次只改善一两个最明显问题。

## 46. 遇到不知道的问题可以展示推理方法

先明确需求和假设，再从边界、数据、规模、故障与安全逐步分析，并说出需要补充哪些证据。诚实区分已确认内容和推断，比随口给一个确定答案更专业。

## 47. 反馈要回到材料和能力缺口

如果别人看不懂架构图，就改善图和说明；如果无法解释事务边界，就回到概念和代码验证；如果演示不稳定，就修复环境可重复性。

不要只练更流利地讲一个仍然错误的设计。

## 48. 作品集要有版本和维护边界

标明当前可运行版本、最近验证日期、已知限制和归档内容。依赖和外部 API 会变化，旧截图不能永久证明当前版本可用。

项目可以阶段性冻结，但要诚实说明状态。

## 49. 不需要展示所有学习过程

笔记和小示例保留在学习区；作品集挑选能够支持核心声明的内容。删去重复、过时或无法解释的展示，比不断增加页面更有价值。

深度和清晰度通常比数量更重要。

## 50. 这一章形成的整体地图

```text
目标岗位与真实业务问题
  → 能力声明和证据索引
  → 需求、规模、边界、数据与故障设计
  → ADR 和分阶段取舍
  → 可复现仓库、演示与运行证据
  → 结论—证据—取舍的项目表达
  → 反馈、复盘与持续更新
```
