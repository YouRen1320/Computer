# 隔离解析：AI 协作、隐私、补丁审查与可证伪验证

完成公开练习并保存预测后再阅读。

## A

Goal 应写成 `minutes=0` 返回 0；Context 只给计价规则、相关文件和合成用例；Constraints 限定可改路径、禁止改 oracle / 联网 / 新依赖 / 秘密；Done when 要求旧回归和新 oracle 都通过、diff 已审、可回滚。上下文不足会诱发猜测，整仓库上传则扩大隐私、商业秘密、提示注入和许可证暴露面。

## B

读取指定源和运行已知本地只读检查通常可在最小权限内进行；修改允许文件与运行会产生文件的测试应受工作区边界约束；安装依赖、联网、推送、删目录要逐项审查；生产写入在本任务禁止。真实批准策略取决于风险和组织政策，不能把某产品的默认模式当成授权。

## C

“不训练”只回答一种二次用途，不回答是否传输、保存多久、谁能访问、反馈是否上传、第三方 MCP / 连接器如何处理、客户端是否明文缓存，也不替代业务授权。应先分类和最小化，用合成 / 脱敏数据，核对具体产品、计划、端点与日期。真实秘密一旦暴露，应停止继续传播、撤销 / 轮换、检查日志和使用记录、按组织流程报告；删除聊天不能替代轮换。

## D

API 主张用当日官方文档和最小可执行样例验证；日志主张用本机可复跑命令、退出码与原始输出验证；引用主张打开原文核对作者、日期和上下文。反例包括 API 已删除、日志为手写、链接不存在。自信是表达风格，不是独立证据。

## E

逐 hunk 记录“为何需要、改了什么、允许吗、如何推翻”。至少核对未请求路径、边界 / 错误语义、网络 / shell / 文件 / 外部写入、敏感数据、依赖来源和许可证、是否删弱测试、生成物来源、回滚点。只看最终文件会漏掉删除、移动、权限变化和夹带范围。

## F

运行前确认受保护 oracle 摘要和负测存在；运行中确认正确测试集合真实执行且非零会中止；运行后核对测试数量、跳过项、diff 和原始日志。删掉失败测试可以制造“全绿”，因此绿色必须绑定测试集合与版本。

## G

自动化可以检查来源字段是否存在、SPDX 表达式语法、许可证文件 / NOTICE 是否缺失以及策略门禁；不能仅凭模型描述判断权利、兼容性或义务。SPDX 提供标准化识别，OSI 说明某许可证经其开源定义审查；具体项目仍要确认真实代码来源、实际许可证文本、组合 / 链接 / 分发方式与组织政策。高风险场景交给合格人员或法务，本练习不是法律意见。

## H

公开 `verify.rb` 就是一个答案：候选是静态数据，先审作用域、受保护文件、禁用 token、schema、上下文分类和依赖门禁；只有结构审查通过才应用到隔离副本；再由独立 oracle 判定。拒绝时返回原副本摘要，接受后用原始基线副本回滚，两次报告用规范 JSON 摘要比较。

## I

两种工具可共用任务简报、数据分类、最小权限、逐 hunk diff、主张—证据矩阵、项目测试、安全扫描、回滚和证据保存。供应商的数据训练选择、保留时长、反馈上传、客户端缓存、权限和沙箱细节属于版本表面；必须核对具体账号类型、部署方式、第三方服务、组织配置与当日官方文档，不能跨产品类推。

## J

合格证据应包含补丁前预测、逐项决定、公开命令、退出码、报告摘要和未验证边界。拒绝隐藏网络、删除负测、伪造日志与未知许可证依赖；接受零分钟最小修复；回滚后摘要恢复、旧回归绿、新需求 oracle 红。若只能复述答案而不能在无 AI 条件下重做，不算掌握。
