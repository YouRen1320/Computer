# 南昌岗位后续复采手册

## 目标

每次复采都应回答一个具体问题，例如：

- 本周有哪些可投的1—3年Java/Vue岗位？
- R1简历的Vue/前端相邻岗位是否足够？
- RAG/大模型应用岗位要求的是应用工程还是算法研究？
- 面试反馈中的某个缺口是否在多个完整JD中重复出现？

不要以“抓得越多越好”为目标。

## 推荐节奏

- 每周两次增量扫描：周一、周四；
- 每月一次结构化复盘；
- 每20—30次高匹配投递复盘简历，而不是每天改技术路线；
- 岗位下线后保留历史状态，但不要继续计为可投岗位。

## 来源顺序

1. 公司招聘官网/官方公众号：最接近一手信息；
2. 智联、BOSS、前程无忧、猎聘等官方详情页；
3. 官方结构化搜索职位卡；
4. 搜索引擎摘要，只用于发现链接；
5. 聚合薪资/转载站只作线索，不作为当前岗位记录。

至少每月加入两个不同平台，避免单平台偏差。跨平台出现的同公司同岗位应合并为一条，并保留多个来源链接。

## 单条岗位采集流程

1. 打开具体岗位详情页，不把搜索聚合页当成岗位链接；
2. 记录标题、公司、城市、发布日期和URL；
3. 原样记录薪资、经验、学历、行业和明确技能；
4. 标记证据等级；
5. 记录是否外包/驻场、工作区域、职责、必须项和加分项；
6. 选择R1—R4，并写一条“为什么匹配”；
7. 记录一个最大缺口和是否仍值得投；
8. 投递前重新确认岗位仍有效。

来源没有显示的字段留空，不根据公司规模、标题或经验猜测。

## 证据等级

| 等级 | 允许写入 | 禁止做法 |
| --- | --- | --- |
| 完整JD已打开 | 页面明确字段和职责 | 把模糊描述改写成确定要求 |
| 官方结构化职位卡 | 卡片明确字段与技能标签 | 声称已核验全部JD |
| 搜索摘要 | 摘要逐字明确的信息 | 补公司、薪资、日期或完整技能 |
| 转载/聚合 | 仅保存线索链接 | 与官方岗位混为同等证据 |

## 去重规则

优先级从高到低：

1. 同平台官方岗位编号；
2. 规范化详情链接；
3. 公司标准名 + 标准化标题 + 城市/区县 + 发布时间；
4. 跨平台疑似同岗人工确认。

标题标准化只能用于发现重复，不应覆盖原始标题。公司同名、同标题但不同岗位编号可能是重新发布，保留并标记关系。

## 薪资解析

- 月薪区间可转换为千元/月；
- `13薪/14薪` 保留在单独周期标记，不能简单加到月薪；
- 日薪、时薪、周薪和年薪不要混进月薪中位数，除非另建清晰折算字段；
- “面议”保持空值；
- 不用招聘上限代表可获得薪资。

## 时效窗口

- 主分析优先近30天；
- 样本不足时扩到近90天；
- 无日期记录不得伪装成近期岗位；
- 下线、重复发布和长期常驻招聘分别标记；
- 比较两期数据时使用相同平台、查询、页数和过滤规则。

## 正确统计

可以统计：

- 当前快照的样本数、来源分布和证据等级；
- 可解析月薪样本的分位数；
- 明确技能标签或完整JD词频；
- 经验、学历和行业在样本中的分布；
- 投递后的沟通率、面试率和失败阶段。

不能统计为市场结论：

- 不同主动查询结果数的直接占比；
- 搜索引擎宣称的“约X条结果”；
- 重复岗位未去重前的数量；
- 把职位卡没展示的技能计为“不要求”；
- 用一次快照预测长期趋势。

## 脚本复采

在工作区根目录：

```bash
python3 job-market/scripts/collect.py
python3 job-market/scripts/analyze.py
python3 job-market/scripts/validate.py
```

运行前应先复制当前快照到按日期命名的外部归档（如果想比较历史）；当前脚本会覆盖 `raw/job-postings.csv`。采集器仅用于低频个人研究：

- 不登录、不自动投递；
- 不采集招聘者个人资料；
- 不绕过验证码、风控或访问控制；
- 接口返回结构异常时停止并人工检查；
- 平台规则变化时优先改为人工采样。

脚本不会自动改写解释性Markdown。新快照通过验证后，还要人工更新 `source-log.md`、`analysis.md` 和 `resume-mapping.md`，并重新检查所有结论的分母和时间窗口。
