# AI协作与Vibe Coding学习规范

## 1. 核心原则

本计划允许大量使用Codex、Claude等工具写代码，但目标不是“AI能完成项目”，而是“你能让AI在受控范围内完成工作，并对结果负责”。

AI 的参与强度随当前概念熟悉度变化。新概念先用完整示例建立模型，再逐步拿掉帮助；熟悉项目则让 AI 高效实现。统一闭环是：

> 判断熟悉度 → 建立整体模型/业务契约 → 示例渐隐或 AI 实现 → 产生一个新变化 → 比例化验证 → 复盘与间隔回忆

如果代码能运行但你不能解释关键数据流、权限、事务和错误路径，它仍属于未掌握状态。

默认允许在概念学习、实验、项目和普通周收束中使用 AI。对新概念，AI 可以先提供完整可运行示例，随后只保留脚手架，让学习者补全、比较或迁移承载概念的部分；对熟悉项目，AI 可以生成主要实现与测试。学习者不靠重复输入样板代码证明能力，但只阅读成品代码也不足以证明迁移。

### 教学问题必须有完整上下文

学习中的预测题或排错题必须先给出完成判断所需的信息：完整方法签名、相关实现、输入约束、预期业务规则和已学前置。不能只给一个孤立调用，让学习者猜测未展示的实现；也不能把尚未进入的Spring、数据库或AI框架当成默认基础。

推荐顺序是：先看整体目标与完整可运行代码，再解释本次真正需要的语法，随后用少量自我解释、关键补全和相似变化逐步减少帮助。预测只在结果能够暴露重要心智模型时使用，不考短期记忆或冷门命令。

## 2. 推理强度怎么选

不要长期固定使用最高推理强度。任务越开放、跨模块、风险越高，越需要更强推理；机械任务使用高强度只会增加等待和消耗。

| 强度 | 适用任务 | 学习中的例子 |
| --- | --- | --- |
| 轻度 | 机械、局部、结果容易验证 | 解释一个语法错误、格式化、生成少量测试数据、命令提醒 |
| 中 | 单模块概念、练习、常规审查 | Java集合比较、Vue组件拆分、为一个Service补边界测试 |
| 高 | 多约束、调试、数据/权限/事务 | 慢SQL、事务失效、RBAC设计、离线同步、RAG失败定位 |
| 极高 | 重大架构、安全、迁移和最终审计 | Java/Python边界、认证方案、数据模型重构、发布前威胁建模 |

推荐默认使用“中”；真正需要比较方案或定位复杂故障时使用“高”；“极高”只用于少数重大决策。无论强度多高，都不能跳过测试和人工判断。

## 3. 七种协作模式

### 模式A：老师

用途：第一次学习概念。

```text
背景：我有Vue/TypeScript经验，正在学习Java的______。
请按“它解决的问题 → 核心机制 → 与我已知概念的类比 → 类比失效处 → 最小例子 → 常见错误 → 自测题”讲解。
先不要生成完整项目代码。
```

要求：看完后用自己的话概括关键责任与边界，并用一个明确例子校验理解；不要求为了形式关闭 AI 或重写示例。

### 模式B：苏格拉底教练

用途：避免直接抄答案。

```text
我要实现______。
我的理解和伪代码是：______。
请一次只问我一个关键问题，引导我发现遗漏；不要直接给最终实现。
当我的方案已经满足验收标准时，再给审查清单。
```

### 模式C：结对实现

用途：项目小切片。

```text
目标：______
范围：只修改______
明确不做：______
现有约束：______
接口/数据契约：______
验收标准：______
请先列2—3种实现方案，比较成本、风险、回滚和维护；等我选择后再修改。
每次只实现一个可测试切片，并说明验证命令。
```

### 模式D：严格代码审查

用途：检查AI或自己写的代码。

```text
请审查当前diff，不要重写整个模块。
按严重度检查：需求偏差、权限、事务、并发、空值、异常、SQL、缓存、资源释放、日志敏感信息、测试遗漏、升级兼容。
每个问题给出证据、触发条件、影响和最小修复建议；没有证据的判断标为推测。
```

### 模式E：对抗性测试

用途：补错误路径。

```text
针对______列出可执行的失败场景，至少覆盖：重复、越权、并发、超时、取消、部分失败、脏数据、依赖不可用和重试。
先输出风险矩阵和测试优先级，不直接生成全部测试代码。
```

### 模式F：面试官

用途：口述与追问。

```text
你是南昌一家企业软件公司的面试官。
围绕我项目中的______进行20分钟追问。
一次只问一题；根据我的回答继续追问，不要提前给答案。
最后从准确性、深度、表达、诚实边界和项目证据评分，并给出三项补强任务。
```

### 模式G：故障演练教练

用途：培养接管能力。

```text
为FactoryCare设计一个______故障。
只告诉我用户现象、初始日志和可用工具，不直接告诉根因。
根据我提出的排查动作逐步返回结果；结束后复盘我的假设、证据链、无效动作和预防措施。
```

## 4. 学习任务的固定流程

### 第一次接触

1. 用老师模式给出概念地图、明确非目标和一个完整可运行示例；
2. 只追问 2—3 个能揭示机制或边界的问题；
3. 保留样板，拿掉或改变少量承载概念的步骤，让学习者补全；
4. 用一个相似但不相同的小任务确认迁移，AI 可以提示和排错；
5. 选择能证伪关键声明的最轻验证，不为每个语法点新建测试；
6. 下次课用 3—5 分钟回忆或变化一次，不在同一天反复考试。

### 已经会的内容复健

1. 先用一道迁移题、代码审查或行为预测确认真实缺口，默认允许 AI；
2. 根据真实错误决定复习范围；
3. 用AI生成有针对性的反例，不从头看完整课程；
4. 将知识进入FactoryCare真实切片；
5. 能迁移则直接进入工程模式，不用重复初学者练习。

### 项目实现

1. 先写`templates/project-task.md`；
2. 对重大选择执行方案比较；
3. AI只改明确文件和模块；
4. 检查每个diff，不接受一次性生成整个系统；
5. 自动运行format/lint/typecheck/test/build；
6. 手工验证主要成功与失败路径；
7. 更新文档和ADR；
8. 由学习者确认验收结果后小步提交，提交信息描述业务行为。

## 4.1 三种学习通道的 AI 边界

| 通道 | AI 默认行为 | 学习者产生的新内容 |
| --- | --- | --- |
| 习得 | 先展示完整示例，再逐步减少关键帮助 | 自我解释、补全、比较或小迁移 |
| 复健 | 提供一道诊断变化，只补暴露出的缺口 | 修正错误并换表面重试 |
| 工程 | 在明确契约内生成主要代码和测试 | 需求、范围、diff 决策、风险验证和回滚判断 |

“从零重建”只用于一个连贯模块的最小代表切片，不用于每一章，也不等同于关闭 AI。阶段门或面试需要时，才做 5—15 分钟独立抽查。

## 5. 不能交给AI决定的事项

- 用户需求的最终含义；
- 数据模型、数据迁移和删除范围；
- 事务边界和一致性承诺；
- 认证、授权、租户和密钥策略；
- 工具调用是否可以产生真实写操作；
- 生产数据、隐私和合规判断；
- 测试是否足以证明验收；
- 部署、回滚和故障处置决策；
- 简历上“掌握”和“商业经验”的真实性。

AI可以给方案和风险清单，人必须做最终选择并留下理由。

## 6. AI生成代码检查表

### 通用

- [ ] 修改是否严格在任务范围内？
- [ ] 是否发明了不存在的API、字段、依赖或配置？
- [ ] 是否使用项目锁定版本的当前API？
- [ ] 命名、模块边界和已有约定是否一致？
- [ ] 是否出现重复逻辑、过度抽象或无用兼容层？
- [ ] 错误、空值、取消和资源释放是否处理？
- [ ] 日志是否泄漏token、密码、文档或个人信息？
- [ ] 测试是否真正触发了要证明的行为？

### Java/Spring

- [ ] 事务是否通过代理生效，边界是否过大？
- [ ] 权限是否在服务端，tenantId是否来自可信上下文？
- [ ] 并发是否只靠先查后写，是否需要约束或版本？
- [ ] DTO、领域对象和持久化对象是否被错误混用？
- [ ] 重试是否可能重复写，是否幂等？
- [ ] 异步任务是否丢失安全/trace上下文？

### SQL/Redis

- [ ] SQL是否参数化，过滤/排序字段是否白名单？
- [ ] 是否N+1、全表扫描或索引顺序错误？
- [ ] 唯一性是否只靠应用检查？
- [ ] 缓存失效、穿透、雪崩和旧数据是否考虑？
- [ ] Redis失效后业务是否仍正确？

### Vue/Nuxt/多端

- [ ] 是否把服务端状态重复复制进多个store？
- [ ] 组件卸载时请求、订阅和SSE是否取消？
- [ ] 是否只有成功状态，没有loading/empty/error/partial？
- [ ] Nuxt代码是否在服务端访问`window`等客户端API？
- [ ] Token是否不安全地长期存储？
- [ ] 离线同步是否可能重复提交或覆盖新版本？

### Python/AI

- [ ] async函数内部是否调用阻塞IO？
- [ ] 工具参数是否schema验证，权限是否最小？
- [ ] 是否有最大步数、超时、并发和预算？
- [ ] 检索是否在查询阶段执行tenant/ACL过滤？
- [ ] 引用是否真的支持答案？
- [ ] AI建议是否被当成业务事实直接写入？
- [ ] Prompt/model/index版本和评估是否可追踪？

## 7. 独立抽查边界

普通学习周不设“每周关闭 AI 若干小时”的配额，也不要求每章从空文件手写项目。AI 默认可以参与讲解、实现、测试、审查和验收；是否通过取决于学习者能否控制需求与证据，而不是键盘输入占比。

只有以下场景可以安排短暂独立抽查：

- G1—G8 阶段门，用 5—15 分钟抽查当前项目中的代码导航、规则解释、小范围修改或日志诊断；
- 模拟面试或真实面试准备，按目标岗位的现场要求练习；
- 现有证据无法区分“理解”与“照读”时，对具体缺口做一次定向复测。

独立抽查期间可以查官方文档和项目源码，但不使用 AI 代答当次题目。抽查失败只形成一个明确补强项，不抹掉已经通过真实测试和审查得到的其他证据；普通周不得把它扩展成 1—2 小时的固定仪式。

## 8. AI会话记录

对架构、数据、权限、迁移和重要故障，记录：

- 问题与上下文；
- 你最初的判断；
- AI给出的方案；
- 你选择或拒绝了什么；
- 验证结果；
- AI哪里出错；
- 最终结论和可复用规则。

模板可使用[AI会话记录](./templates/ai-session.md)。这份材料既帮助复盘，也能在面试时真实说明你如何使用AI提高质量，而不是只说“我会vibe coding”。

## 9. 停止条件

出现以下情况时，暂停生成并回到问题定义：

- AI连续两次误解需求；
- diff跨越多个未授权模块；
- 数据模型、API或权限契约开始变化；
- 需要删除、迁移或覆盖数据；
- 测试失败但AI开始不断打补丁；
- 同一问题出现第三次却没有证据链；
- 你无法解释生成代码中关键部分；
- 依赖版本或官方API不确定。

这时应缩小任务、读官方文档、构造最小复现或请求方案评审，而不是继续提高提示词长度。

## 10. 工作中的目标状态

理想的AI协作不是“AI写100%，人点运行”，而是：

- 人负责目标、领域、边界、验收和风险；
- AI负责检索、样板、小切片实现、测试建议和审查辅助；
- 编译器、类型、测试、日志和评估负责提供客观反馈；
- 人根据反馈决定接受、修改、回滚或重新设计。

达到这种状态后，Vibe Coding才是工程效率，而不是把未知风险延迟到线上。
