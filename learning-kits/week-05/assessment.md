## 场景：未关闭工单索引

输入是一组可能包含重复工单 id 的 WorkOrder，要求生成“按设备 id 分组的未关闭工单索引”。

非 `CREATED` 状态仅是查询夹具中的已有样本，不考状态转换。可以使用项目已有的安全 test fixture；若没有，则使用不可变 `WorkOrderSnapshot` 投影完成本题，不得为领域实体增加 public `setStatus`。

### 明确契约

1. `null` 输入拒绝；
2. 输入元素、id、equipmentId、status 不得为 null；
3. 先按 `WorkOrderId` 去重，保留首次出现；
4. 未关闭指 status 不是 `CLOSED` 且不是 `CANCELLED`；
5. 组的顺序为首次出现设备的顺序；
6. 每组内保持工单首次出现顺序；
7. 返回外层 Map 和内层 List 都不可修改，且不与方法内部临时容器共享；
8. 不要求深拷贝 WorkOrder 实体；
9. 空输入返回空的不可修改结果。

## A. 集合设计（10 分，10 分钟）

在编码前写：

- 去重、分组、顺序分别需要什么语义；
- 选择哪些接口和实现；
- 每步平均时间复杂度；
- 为什么不用 TreeMap、HashMap随机顺序或嵌套List扫描；
- 结构快照与实体深拷贝的边界。

## B. 实现（25 分，35 分钟）

实现一个方法，返回 `Map<EquipmentId, List<WorkOrder>>`。要求：

- 无 raw type 和无理由强转；
- 不暴露内部可变集合；
- 不用 `ordinal()` 判断关闭；
- 不出现项目词表之外的状态；
- 方法可读，重复/过滤/冻结阶段可辨认。

## C. 测试与故障（20 分，25 分钟）

测试至少覆盖：空、单项、重复id、多个设备、`CLOSED`、`CANCELLED`、`VERIFIED`仍保留、顺序、外层修改失败、内层修改失败、null元素。

主动制造以下一个故障并恢复：只冻结外层；使用 HashMap 导致顺序无契约；先分组再错误去重；把 `VERIFIED` 当关闭。

记录失败测试与根因。

## D. equals/hashCode 口袋实验（15 分，10 分钟）

构造一个可变 key：保存到 HashMap 后修改参与 hash 的字段。演示查询问题，并写出 FactoryCare Entity 的正确相等字段选择。故障类型不得进入正式模型。

## E. 双指针（10 分，15 分钟）

实现已排序 `int[]` 的原地去重，返回唯一前缀长度。写 5 个边界测试、不变量、时间/空间复杂度，并声明会修改输入。

## F. 口述（15 分，20 分钟）

1. List、Set、Map、Deque 的选择依据；
2. ArrayList 与 LinkedList 的取舍；
3. HashMap 查询的高层步骤；
4. equals/hashCode 契约与碰撞；
5. 泛型为什么不协变；
6. PECS 的直觉；
7. 类型擦除的两个限制；
8. `unmodifiableList`、`List.copyOf`、深拷贝的区别；
9. Comparable 与 Comparator；
10. 为什么不创建万能 BaseRepository。
